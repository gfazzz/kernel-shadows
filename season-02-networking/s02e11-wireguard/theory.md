# Теория — s02e11

## 1. VPN, который «иногда отваливался»

> *Мы подняли VPN до офиса, и он работал. Почти. Раз в час-полтора кто-нибудь писал: «отвалилось». Проверяешь — работает. Пингуешь — идёт. Через минуту снова письмо.*
>
> *Я потратил неделю. Смотрел логи, менял MTU, подозревал провайдера. Однажды заметил закономерность: жаловались только те, кто работал из дома, и только после обеда.*
>
> *Палыч выслушал и спросил одно:*
>
> — Кто инициирует соединение — они или сервер?
> — Они, конечно.
> — А после того, как они полчаса ничего не отправляли, кто до кого достучится?
>
> *И тут я понял. NAT провайдера держит запись минуту-другую. Пока человек работает, запись обновляется. Пошёл на обед — запись протухла, и сервер до него дозвониться уже не может. Человек вернулся, нажал что-нибудь — соединение «починилось».*
>
> *Одна строка: `PersistentKeepalive = 25`.*
>
> — Заметь, что ты искал, — сказал он потом. — Ты искал поломку. А поломки не было: система вела себя ровно так, как устроена. Это другой класс задач, и он труднее — потому что нечего чинить, надо понять.
>
> — Как такое вообще искать?
> — Спрашивать «при каких условиях наблюдаемое было бы нормальным». Ты бы вышел на NAT за час, а не за неделю.

## 2. Чем WireGuard отличается

| | OpenVPN / IPsec | WireGuard |
|---|---|---|
| Размер реализации | сотни тысяч строк | несколько тысяч |
| Согласование шифров | есть, настраивается | нет: набор зафиксирован |
| Аутентификация | сертификаты, PSK, логины | пара ключей Curve25519 |
| Состояние соединения | сессия, реконнекты | **нет**: только ключи и адреса |
| Смена сети клиентом | разрыв и переподключение | ничего не происходит |
| Работает в | userspace | **ядре** |
| Конфигурация | десятки директив | одна секция и по секции на пира |

Отсутствие согласования шифров — не упрощение ради простоты. Договорённость о параметрах — исторически главный источник уязвимостей в TLS и IPsec: сторону можно уговорить на слабый вариант. Здесь уговаривать не о чем.

**Отсутствие состояния** объясняет главное практическое свойство: WireGuard не «подключён» и не «отключён». Есть интерфейс, есть таблица пиров; пакет либо подходит под чей-то ключ, либо отбрасывается.

## 3. Ключи

```bash
wg genkey > private.key
chmod 600 private.key
wg pubkey < private.key > public.key
wg genpsk > preshared.key        # опционально: общий секрет поверх пары ключей
```

Приватный ключ не покидает узел. Публичный раздают — знание публичного ключа не даёт ничего, кроме возможности зашифровать для его владельца.

`PresharedKey` добавляет симметричный секрет к обмену: это защита от расшифровки записанного трафика будущим квантовым компьютером. На сегодня — предосторожность, не необходимость.

**Ключ в конфиге лежит открытым текстом.** Отсюда права `0600` на `/etc/wireguard/wg0.conf` и `PostUp`-приём с чтением ключа из отдельного файла, если конфиг куда-то копируется.

## 4. `AllowedIPs` — cryptokey routing

Одна строка отвечает на два вопроса:

```
[Peer]
PublicKey  = Vkxt97L+…
AllowedIPs = 10.50.0.0/16, 10.77.0.1/32
```

- **исходящий пакет:** адрес назначения ищется среди `AllowedIPs` всех пиров; найденный пир получает пакет, зашифрованный его ключом;
- **входящий пакет:** после расшифровки проверяется адрес источника; если его нет в `AllowedIPs` этого пира — пакет отбрасывается молча.

Второе делает `AllowedIPs` ещё и списком доступа: пир не может выдать себя за чужой адрес, даже подписав пакет верно.

**Пересечение `AllowedIPs` — самая частая ошибка.** Ошибки не возникает; трафик просто уходит первому подошедшему пиру. `wg show` при этом покажет второго пира нормальным, с нулевым счётчиком.

Типовые схемы:

| Задача | `AllowedIPs` у пира |
|---|---|
| доступ к сети офиса | `10.50.0.0/16` |
| полный туннель (весь трафик) | `0.0.0.0/0, ::/0` — и тогда пир **один** |
| прямой канал до одного узла | `10.77.0.5/32` |
| узел-концентратор для всей VPN | `10.77.0.0/24` — и тогда прямых пиров нет |

## 5. Интерфейс и маршруты

```
[Interface]
Address = 10.77.0.4/32
PrivateKey = …
DNS = 10.50.0.53
MTU = 1420
Table = auto
PostUp = ip rule add ...
```

**`Address` с `/32`.** В WireGuard сеть описывается списками пиров, а не маской интерфейса. `/24` создаст маршрут на всю подсеть VPN через `wg0`, который вступит в спор с `AllowedIPs` каждого пира. `/32` означает «здесь живёт ровно мой адрес», и маршруты берутся из `AllowedIPs`.

**`MTU`.** Заголовки WireGuard съедают 60–80 байт. По умолчанию `wg-quick` ставит 1420, и обычно этого достаточно; симптом неверного MTU узнаваем — ssh соединяется, а большие ответы «зависают».

**`Table = off`** отключает автоматическое создание маршрутов, если ты хочешь управлять ими сами. Нужен редко, но объясняет, откуда маршруты вообще берутся: их создаёт `wg-quick`, а не сам WireGuard.

**`DNS`** заставляет `wg-quick` подменить резолвер на время работы интерфейса. Без него внутренние имена не разрешатся, хотя адреса будут доступны. При полном туннеле без `DNS` получается утечка: трафик идёт через VPN, а запросы имён — мимо.

## 6. Работа и отладка

```bash
wg-quick up wg0 / down wg0
systemctl enable --now wg-quick@wg0
wg show                       # рукопожатия, счётчики, endpoint
wg show wg0 latest-handshakes
ip route show dev wg0         # что создалось из AllowedIPs
ip -s link show wg0           # счётчики интерфейса
```

Порядок отладки, который отвечает почти всегда:

1. **`wg show`** — есть ли рукопожатие. Нет ни одного — пакеты не доходят: UDP-порт закрыт, `Endpoint` неверен, ключи не соответствуют.
2. Рукопожатие есть, счётчики нулевые — трафик не маршрутизируется: смотреть `AllowedIPs` и `ip route`.
3. Байты идут, а приложение не работает — MTU или DNS.

`wg show` — единственное место, где видна правда. «Интерфейс поднят» не означает ровно ничего: WireGuard поднимет его и без единого достижимого пира.

## 7. Серверная сторона и фаервол

Узлу, к которому приходят, нужны:

```
[Interface]
ListenPort = 51820        # фиксированный порт
```

и открытый **UDP**-порт в фаерволе:

```bash
ufw allow 51820/udp
```

Частая ошибка после [`s02e06`](../s02e06-firewall-ufw/) — открыть TCP: WireGuard работает только по UDP. Правило `ufw allow 51820` без указания протокола откроет оба, что тоже не идеально.

Для маршрутизации трафика дальше, во внутреннюю сеть, шлюзу нужен `net.ipv4.ip_forward=1` и правило NAT — это уже про сам шлюз, и разбирается в Season 7.

**Скрытность:** WireGuard не отвечает на пакеты без корректной подписи вовсе. Со стороны сканера порт выглядит закрытым — свойство, которого нет ни у OpenVPN, ни у IPsec.

## 8. Метанавык: различать поломку и устройство

История из начала — про класс задач, где искать нечего: система ведёт себя ровно так, как устроена, а ожидание было неверным. Симптомы у него узнаваемые:

- «работает, но иногда» — почти всегда таймаут, срок жизни записи или кеш;
- «работает у одних и не работает у других» — разное окружение, а не разный софт;
- «починилось само» — значит, что-то обновилось по времени, а не было исправлено.

Вопрос, который экономит дни: **«при каких условиях наблюдаемое было бы нормальным поведением?»** Он переводит поиск из «что сломалось» в «чего я не знаю про устройство», и второе почти всегда ближе к правде.

Обратная сторона — привычка читать документацию не тогда, когда сломалось, а когда что-то ведёт себя непонятно, но работает. Именно в этот момент ты ещё способны спокойно сопоставить прочитанное с наблюдаемым.
