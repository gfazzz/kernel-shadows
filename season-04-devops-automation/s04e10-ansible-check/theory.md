# Теория — s04e10

## 1. Отчёт, в котором всё было хорошо

> *У нас был ночной скрипт сверки конфигураций. Каждое утро приходило письмо: «расхождений не найдено». Полгода подряд.*
>
> *Потом выяснилось, что месяц назад на одной машине поменяли каталог, скрипт перестал находить файлы и честно не находил расхождений: сравнивать было нечего.*
>
> — Письмо приходило? — спросил Палыч.
> — Каждое утро.
> — И ты его читал?
> — Ну... я видел, что оно пришло.
>
> *Он поправил:*
>
> — Значит, ты проверял не конфигурации. Ты проверял, что скрипт запускается. Это тоже полезно, но это другое.
>
> *С тех пор такие отчёты у нас пишут иначе: не «расхождений нет», а «сверено 143 файла на 27 машинах, расхождений нет». Второе можно опровергнуть, глядя на число.*

## 2. Идемпотентность

Свойство, ради которого всё устроено именно так: **повторный запуск не меняет ничего**.

```
первый запуск:  changed=8   ok=6
второй запуск:  changed=0   ok=14
```

Второй запуск — не формальность, а проверка: если он снова показывает `changed`, задача написана неверно. Классические причины:

| Задача | Почему всегда changed |
|---|---|
| `command: systemctl restart X` | команда выполняется всегда |
| `lineinfile` без якоря | строка добавляется заново |
| `copy` шаблона с датой внутри | содержимое каждый раз новое |
| `file: state=touch` | время изменения обновляется |

Лечится либо переходом на декларативный модуль, либо явным `changed_when`:

```yaml
- name: собрать индекс
  ansible.builtin.command: /usr/local/bin/reindex
  register: r
  changed_when: "'updated' in r.stdout"
```

`changed_when: false` — «эта задача только смотрит». Так помечают проверки, чтобы они не создавали шум в счётчике.

## 3. Режим проверки

```bash
ansible-playbook site.yml --check           # ничего не менять, рассказать
ansible-playbook site.yml --check --diff    # и показать построчно
ansible-playbook site.yml --diff            # применить и показать, что изменилось
```

Модуль в режиме проверки не выполняет действие, а сравнивает описанное с существующим. Модули различаются тем, насколько хорошо они это умеют:

| Модуль | В режиме проверки |
|---|---|
| `copy`, `template`, `file`, `lineinfile` | точное сравнение, есть diff |
| `apt`, `package` | предсказывает по базе пакетов |
| `service`, `systemd` | сравнивает состояние |
| `command`, `shell` | **пропускается целиком** |
| `uri`, `git` | частично: зависит от параметров |

Отдельно стоит помнить о **зависимых задачах**: если первая задача в режиме проверки не создала каталог, вторая, которая туда пишет, может отчитаться об ошибке, которой в жизни не будет. Ложная тревога в `--check` — нормальное явление, и она не повод его не запускать.

```yaml
- name: посмотреть версию (безопасно даже в check)
  ansible.builtin.command: /usr/bin/app --version
  check_mode: false
  changed_when: false
```

## 4. Как читать diff

```
--- before: /etc/ssh/sshd_config     ← состояние машины
+++ after:  /etc/ssh/sshd_config     ← состояние из описания
```

Направление постоянно путают, и ошибка дорогая: строка со знаком минус — это **то, что есть сейчас**, а не то, что кто-то удалил. В режиме проверки ни одна из сторон ещё не применена.

Для `template` diff показывает результат подстановки переменных, а не сам шаблон, — это удобный способ проверить, какие значения на самом деле подставились (та же роль, что у `ansible-inventory --host`).

Для файлов с секретами вывод глушат:

```yaml
- name: приватный ключ
  ansible.builtin.copy: { … }
  no_log: true
```

## 5. Ограничение области

```bash
--limit production            # только группа
--limit prod-web27*           # только машина
--limit '!prod-db*'           # все, кроме
--tags certs                  # только помеченные задачи
--skip-tags slow
--start-at-task "имя задачи"
```

Разумный порядок в незнакомой системе: `--check --diff --limit одна_машина`, потом `--limit группа`, потом всё. Разница с «просто запустить» — не в осторожности, а в том, что каждый шаг даёт данные для следующего.

## 6. Дрейф: описание или машина

Каждая строка `changed` в режиме проверки — место, где описанное разошлось с существующим. Вопрос всегда один: **что из двух сдвинулось**.

| Картина | Что произошло | Что делать |
|---|---|---|
| меняется почти везде | описание ушло вперёд | применить |
| меняется у группы целиком | группа настроена иначе | проверить, намеренно ли |
| меняется у одной машины | машина ушла в сторону | **выяснить, кто и когда** |
| меняется каждый раз, сколько ни запускай | задача не идемпотентна | чинить задачу |

Третья строка — единственная, где сначала выясняют, а потом применяют. Ansible с удовольствием приведёт машину к описанию и заодно сотрёт следы: чужой ключ исчезнет, `PermitRootLogin` вернётся, и вопрос «кто это сделал» останется без ответа навсегда.

## 7. Что режим проверки не покажет никогда

| Не покажет | Почему |
|---|---|
| файлы, о которых нет задач | описания нет — сравнивать не с чем |
| результат `command`/`shell` | не выполняется |
| состояние недоступных машин | задачи на них не шли |
| последствия применения | порядок, перезапуски, зависимости |
| что было изменено и возвращено обратно | сравнивается текущее состояние, а не история |

Последняя строка — причина, по которой рядом с конфигурацией держат журнал: `auditd`, `last`, история команд. Состояние отвечает на вопрос «как сейчас», журнал — «как стало так».

## 8. Метанавык: расхождение — это данные

Разница между описанным и существующим почти всегда воспринимается как помеха: «надо привести в порядок». Полезнее обратное отношение — **расхождение и есть результат измерения**, а его распределение говорит больше, чем сам факт.

| Где встречается | Что значит массовое расхождение | Что значит единичное |
|---|---|---|
| `--check` по паркy машин | описание обновили | машину трогали руками |
| сверка копии с оригиналом | сменился формат | повреждение |
| тесты после обновления библиотеки | поменялось поведение | ваш код зависел от частности |
| документация против кода | документацию забыли | кто-то поправил код мимо ревью |

Практический приём: прежде чем устранять расхождение, посмотреть на **форму** его распределения. Устранение стирает данные, и второй раз посмотреть будет уже не на что.
