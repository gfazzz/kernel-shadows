## II. Теория: из чего состоит откат

### Откат — не «назад», а ещё один выкат

Время не идёт назад. «Откатиться» означает **выкатить ещё одну версию**, просто более старую: с тем же риском, той же проверкой и той же записью в журнал. Отсюда всё остальное.

| Что откатывается | Что не откатывается |
|---|---|
| образ приложения | схема базы после миграции |
| конфигурация из репозитория | данные, уже записанные новой версией |
| версия в журнале выкатов | ответы, которые клиенты успели получить |
| | сообщения, ушедшие в очередь |

Это та же граница, что в [`s04e03`](../s04e03-gitignore-secrets/): удалить секрет из репозитория можно, сделать его неутёкшим — нельзя.

### Чтобы откатиться, у версии должно быть имя

```bash
docker pull registry.shadow.io/ops/collector:3f8ba110   # можно
docker pull registry.shadow.io/ops/collector:latest     # «то, что сейчас», то есть сломанное
```

Откат возможен только потому, что конвейер из [`s04e07`](../s04e07-ci-pipeline/) метит каждую сборку хешем коммита. С тегом `latest` предыдущей версии просто не существует как адресуемой вещи.

### Журнал выкатов

Помнить, какая версия была рабочей, — не человеческая задача, особенно в 15:47.

```
время                 версия    состояние миграция комментарий
2025-10-29T09:14:02Z  3f8ba110  healthy   no
2025-10-29T11:31:57Z  b0c4d5e6  failed    no       готовность не подтвердилась
2025-10-29T15:46:58Z  a1b2c3d4  healthy   no       «minor fix»
```

Читается он так же, как юнит systemd из [`s03e05`](../../season-03-system-administration/s03e05-systemd-service/): **последняя запись о версии побеждает**. Одна и та же версия бывает здоровой утром и снятой с боя вечером — значение имеет последняя.

Отсюда правило выбора цели: не «строка перед текущей», а **последняя версия, чьё последнее состояние `healthy`**.

### Миграция как точка невозврата

Миграция схемы — односторонняя дверь. Старый код, увидев новую схему, обычно падает; иногда — что хуже — не падает и портит данные.

Поэтому скрипт отката **отказывается** идти через миграцию и требует явного решения человека. Важна деталь: значение имеют только миграции, применённые **после цели**. Миграция, случившаяся раньше, уже была в бою, когда цель работала, и откату не мешает.

Про сине-зелёный выкат, канареечный выкат и совместимость версий базы — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Проверка готовности прошла, а приложение отдаёт пятисотую. Проверка сломана?»*

<details>
<summary>Подумай 30 секунд</summary>

Нет. Она отвечает ровно на свой вопрос — «процесс поднялся и слушает порт» — и отвечает верно.

Получается лестница из трёх ступеней, и в этом сезоне пройдена каждая:

1. **Контейнер запущен** — `Up` в [`s04e06`](../s04e06-compose/).
2. **Служба отвечает** — `Up (healthy)` там же и `curl /healthz` в конвейере.
3. **Служба отвечает правильно** — этого не проверяет никто, кроме настоящих запросов.

Практический вывод не «сделать идеальную проверку», а знать, на какой ступени ты находишься. `/healthz`, который ходит в базу и делает один настоящий запрос, поднимает тебя на полступени вверх — и стоит десяти минут работы.
</details>

**LILITH:** *«Откатились. Через час выкатили исправление. Оно снова сломалось, и ты откатываешься опять. Куда попадёшь?»*

<details>
<summary>Ответ</summary>

Туда, куда записано в журнале. Если откат не пометил снятую версию как `failed`, второй откат честно вернёт в бой её же — ту самую, из-за которой всё началось.

Это и есть причина, по которой откат обязан **писать** в журнал, а не только читать. Скрипт, который меняет состояние мира и не оставляет следа, при повторном запуске работает против себя.
</details>

## IV. Задание: `rollback.sh`

Артефакт — `artifacts/rollback.sh`.

```bash
cp starter/rollback.sh artifacts/
bash tests/test.sh
```

```
rollback.sh --journal FILE --host HOST --image IMAGE
            [--to ВЕРСИЯ] [--force] [--dry-run] [--health URL]
```

| Требование | Почему |
|---|---|
| цель — последняя версия с последним состоянием `healthy` | строка перед текущей может быть неудачным выкатом |
| отказ (код 3), если после цели была миграция | откат кода не отменяет изменения схемы |
| `--force` снимает отказ | решение принимает человек, но явно |
| выкат точным тегом, по `ssh` на `--host` | `latest` — это «сломанное, что сейчас» |
| проверка готовности после выката | «команда выполнена» ≠ «служба отвечает» |
| не ответила — код возврата 1 | молчаливый успех хуже отказа |
| журнал дописывается: снятая → `failed`, восстановленная → `healthy` | иначе следующий откат вернёт сломанное |
| `--dry-run` печатает план и не меняет ничего | в 15:47 полезно сначала увидеть, что произойдёт |
| ни одного зашитого значения | тест подставит другой журнал, хост и образ |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Последнее состояние версии: `awk -v v="$1" '$2==v {s=$3} END{print s}'`.

Версии в порядке последнего упоминания: собрать `last[$2]=NR`, затем `sort -rn`.

Миграции после цели: запомнить номер последней строки цели и смотреть только `NR > n`.

Эталон — в `solution/`, там прокомментирован каждый шаг.
</details>

### Три ошибки, которые здесь делают

**Взять предпоследнюю строку журнала.** Работает ровно до первого неудачного выката — то есть до того дня, когда откат действительно понадобится.

**Проверить, есть ли в журнале миграции вообще.** Тогда скрипт откажется откатываться навсегда: миграции есть в любом журнале старше месяца. Значение имеют только те, что после цели.

**Считать откат успешным по коду возврата `ssh`.** `ssh` вернёт ноль, если команда на той стороне выполнилась. Она и выполнилась — контейнер поднялся. Отвечает ли служба, знает только сама служба.

Ханс выводит на экран `git diff` между двумя версиями. Одна строка.

```python
-DB_HOST = os.environ["DB_HOST"]
+DB_HOST = "localhost"
```

> — На стенде база действительно на localhost. В бою она в отдельной сети. Тесты прошли, потому что тесты запускались на стенде. Проверка готовности прошла, потому что она не ходит в базу.

> — Кто виноват? — спрашивает Дмитрий, и по лицу видно, что ответ он уже придумал сам.

> — Неверный вопрос. — Ханс закрывает ноутбук. — Правильный: почему система позволила одному человеку в пятницу днём отправить в бой изменение, которое не проверялось нигде в тех условиях, где оно ломается. Ты был последним, кто её коснулся. Это не то же самое, что причина.

Он перечисляет, что меняется завтра: стенд получает конфигурацию боевого контура, `/healthz` начинает делать один настоящий запрос к базе, а откат перестаёт быть тем, что человек делает руками по памяти.
