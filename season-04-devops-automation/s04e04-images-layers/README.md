## II. Теория: из чего состоит образ

### Слои и кеш

Каждая инструкция `Dockerfile`, меняющая файловую систему (`RUN`, `COPY`, `ADD`), создаёт **слой** — разницу относительно предыдущего состояния. `ENV`, `CMD`, `WORKDIR`, `USER` меняют только метаданные и весят ноль.

```bash
docker history образ            # слои сверху вниз, от последнего к первому
docker inspect образ            # метаданные: User, Env, Cmd, размер
docker image ls                 # что лежит на машине
docker save образ | tar -tv     # содержимое слоёв как есть
```

Слои **кешируются**: при пересборке docker берёт готовый слой, если инструкция и её вход не изменились. Отсюда правило порядка — **редко меняющееся выше, часто меняющееся ниже**:

```dockerfile
COPY requirements.txt .          # меняется редко
RUN pip install -r requirements.txt
COPY . /app                      # меняется каждый раз
```

Наоборот — и `pip install` будет выполняться при каждой правке кода.

### Удаление не уменьшает образ

```dockerfile
COPY deploy_key /tmp/deploy_key
RUN rm -rf /tmp/deploy_key       # слой: 0B, а ключ остался в предыдущем
```

Слой удаления только **помечает** файл отсутствующим для верхнего уровня. Данные лежат ниже и извлекаются из архива образа. Правильно — не создавать слой вовсе:

```dockerfile
RUN --mount=type=secret,id=key … # секрет доступен только во время сборки
```

или собирать в **несколько ступеней**, где в итоговый образ переносится только результат.

### `ENV` — не место для секретов

```bash
docker inspect образ | grep -A5 Env
```

Переменные окружения из `ENV` видны любому, у кого есть образ, — их печатает `inspect`, они попадают в `docker history`, они уезжают в реестр. Секреты передают при **запуске** (`--env-file`, secrets оркестратора), а не при сборке.

### Пустое поле `User` означает root

В `inspect` пустая строка `"User": ""` — не «никто», а умолчание. Контейнер стартует от root, и процесс внутри получает root в своём пространстве имён. Лечится одной инструкцией `USER` — и об этом следующая серия.

### Тег `latest` ничего не гарантирует

`latest` — обычный тег, а не «самая свежая версия». Он указывает туда, куда его поставили в последний раз, и завтра может указывать на другое. Для воспроизводимой сборки берут точную версию, а лучше — дайджест `image@sha256:…`.

Про многоступенчатую сборку, `.dockerignore`, размеры баз и сканеры — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«В Dockerfile: `COPY secret .` , потом `RUN использовать && rm secret`. Секрет в образе?»*

<details>
<summary>Подумай 30 секунд</summary>

Да. `COPY` создал слой с файлом; `RUN … && rm` создал следующий слой, где файла нет. Оба слоя в образе, и первый достаётся распаковкой.

Работает другое: `RUN --mount=type=secret` (файл существует только во время выполнения инструкции и в слой не попадает) или многоступенчатая сборка, где секрет остаётся в промежуточной ступени, не попадающей в итоговый образ.

Проверить себя: `docker history` покажет слой `COPY` ненулевого размера — это и есть ответ.
</details>

**LILITH:** *«`docker images` показывает семь строк. Сколько образов на машине?»*

<details>
<summary>Ответ</summary>

Меньше семи, если у какого-то образа несколько тегов. Один образ с тегами `1.4.0` и `latest` занимает две строки и один `IMAGE ID`.

```bash
docker images --format '{{.ID}}' | sort -u | wc -l
```

Отсюда же практический вывод про место: удаление тега `latest` не освобождает ничего, пока на тот же идентификатор указывает другой тег.
</details>

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
D=../data/docker_ops_snapshot.txt
sec() { awk -v s="$1" '$0=="=== "s" ===" {f=1; next} /^=== /{f=0} f' "$D"; }

sec 'docker images' | awk 'NR>1{print $3}' | sort -u | wc -l
sec 'docker history ops/collector:1.4.0'
sec 'docker inspect ops/collector:1.4.0' | grep -A6 '"Env"'
```

Строки базового образа в истории помечены `#(nop)` — их писали не вы, и в вопросе про «крупнейший слой сборки» они не участвуют.

Эталон — в `solution/`, там же команда над каждым значением.
</details>

### Три ошибки, которые здесь делают

**Считать образы по строкам `docker images`.** Один образ с двумя тегами даёт две строки. Считать надо по `IMAGE ID`.

**Считать крупнейшим слоем базовый.** Он действительно самый большой — 149 МБ, — но его писали не вы. Вопрос про то, что добавила **сборка**, а это 260 МБ поверх.

**Прочитать `"User": ""` как «пользователь не задан, наверное, обычный».** Пустое поле означает root. Это умолчание, и оно ровно то, чего не хочется в контейнере, который ходит в сеть.

Ты сдаёшь отчёт. Софи читает и молча разворачивает ноутбук к тебе.

```
$ docker save ops/collector:1.4.0 -o /tmp/img.tar
$ tar -xf /tmp/img.tar -C /tmp/img
$ find /tmp/img -name '*.tar' -exec tar -tf {} \; | grep deploy_key
tmp/deploy_key
```

> — Вот он. Из образа, где его «удалили».

> — Кто его туда положил?

> — Хороший вопрос. Дмитрий говорит, что не он. — Она пожимает плечами. — Возможно, правда не он: `deploy_key` мог приехать вместе с `COPY . /app`, если он лежал в рабочем каталоге. Это и есть настоящая причина, по которой существует `.dockerignore` — тот же `.gitignore`, только для сборки.

Она закрывает ноутбук.
