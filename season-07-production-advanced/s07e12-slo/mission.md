## Обстановка

Заказчик хочет стопроцентную доступность. Бьёрн предлагает 99.5 % и
счётчик, по которому видно, сколько от обещания осталось.

Соглашение уже написано и лежит в `data/slo.conf`: два показателя,
порог предупреждения, два окна скорости расхода. Наблюдения за три окна
сняты сегодня в 08:00 и лежат в `data/measurements.txt`.

Нет только программы, которая превратит эти два файла в решение —
выкатываем сегодня или чиним.

## Приказ

Написать `artifacts/slo.py`: посчитать бюджет ошибок за длинное окно,
скорость его расхода за короткие и вынести приговор.

```bash
cp starter/slo.py artifacts/
python3 artifacts/slo.py data/slo.conf data/measurements.txt
bash tests/test.sh
```

## Дано

| Файл в `data/` | Что в нём |
|---|---|
| `slo.conf` | окно, порог предупреждения, показатели с целями, окна скорости |
| `measurements.txt` | счётчики по трём окнам: всего и «хороших», отдельно по запросам и по задержке |

Всё в целых числах и в миллионных долях: `995000 ppm` — это 99.5 %.
Никаких процентов с плавающей точкой: они расходятся между машинами и
локалями, а обещание заказчику расходиться не должно.

## Что считать

| Величина | Как |
|---|---|
| бюджет ошибок | `total × (1e6 − target_ppm) / 1e6` |
| израсходовано | `total − good` |
| доля расхода, % | `spent × 100 / allowed`, целочисленно |
| фактический уровень | `good × 1e6 / total` |
| приговор показателя | `spent > allowed` → `violated`; `pct ≥ warn` → `burning`; иначе `met` |
| скорость расхода | `spent × 1e6 × 100 / (total × (1e6 − target_ppm))` |
| итог | `violated` ▸ `at-risk` ▸ `ok` |

Бюджет считается по длинному окну (`window_days` → `30d`), скорость — по
коротким (`1h`, `6h`). Это два разных вопроса: первый про месяц, второй
про «что происходит прямо сейчас».

## Формат вывода

```
SLO <имя> target_ppm=<n> actual_ppm=<n> budget_allowed=<n> budget_spent=<n> budget_pct=<n> verdict=<met|burning|violated>
BURN <имя> window=<окно> rate_x100=<n> threshold_x100=<n> alert=<yes|no>
VERDICT <ok|at-risk|violated>
```

Порядок строк фиксирован: сначала все `SLO` в порядке соглашения, потом
все `BURN`, потом `VERDICT`. Код возврата: `0` — уложились, `1` — SLO
нарушено, `2` — вход не разобран.

## Критерии приёмки

- [ ] Все величины считаются целочисленно, без `float`.
- [ ] Цели, порог и окна берутся из `slo.conf`, а не зашиты в код.
- [ ] Бюджет — по длинному окну, скорость расхода — по коротким.
- [ ] `violated` перевешивает `at-risk`, `at-risk` перевешивает `ok`.
- [ ] Неверный вызов и неразобранный вход дают код `2`, а не трассировку.
- [ ] Идеальное окно даёт `ok` и код `0`, полный отказ — `violated` и код `1`.
- [ ] `stdout` — только строки отчёта; диагностика идёт в `stderr`.
- [ ] Два прогона подряд дают побайтово одинаковый вывод.
- [ ] `bash tests/test.sh` → 40 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| Python | 3.8+ |
| Сеть | не нужна |
| Prometheus | **не нужен** — наблюдения сняты в `data/` |
| Внешние пакеты | нет |
| Изоляция теста | свои файлы в `mktemp -d`, данные только читаются |

Тест не сверяет вывод с константами: он пересчитывает каждую величину сам
из `slo.conf` и `measurements.txt`. Поменяется соглашение — поменяются и
ожидания. Отдельно проверяется, что данные не выродились: показателей не
меньше двух, окон скорости не меньше двух, ровно один показатель нарушен
и хотя бы одно окно горит быстрее порога.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `budget_pct` на единицу меньше ожидаемого | деление с плавающей точкой и округление | целочисленное `//` на всех шагах |
| `actual_ppm` в процентах | цель в ppm, факт в процентах | одна единица на обе величины |
| скорость совпала с долей расхода | взято длинное окно | скорость считается по `1h` и `6h` |
| `VERDICT ok` при нарушенном показателе | приговор собран по последнему показателю | флаги накапливаются по всем |
| код `0` при `violated` | код возврата не связан с приговором | `1` при любом нарушенном SLO |
| трассировка вместо кода `2` | вход не проверен | ошибки чтения и разбора ловятся |
| тест ругается на `stderr` | отладочная печать ушла в `stdout` | диагностика — в `stderr` |
| ужесточение цели ничего не меняет | цель зашита в код | читать `target_ppm` из файла |

## После выполнения

Зелёный тест означает, что построенное за сезон получило число: не «нам
кажется, что стало лучше», а «бюджет по задержке превышен на 38 %,
выкаты остановлены».

Главное, что стоит унести: **бюджет ошибок работает в обе стороны.**
Исчерпан — останавливаемся и чиним. Не израсходован — едем слишком
медленно и платим за перестраховку скоростью. Обе стороны следуют из
одного вычитания, и именно это отличает обещание от лозунга.

И второе: **порог SLO ставят там, где стоит граница корзины.** Иначе
показатель приходится интерполировать, и обещание оказывается основано
на догадке — ровно на том, от чего оно должно было избавить.

## Кумулятивность

Показатель доступности считается по счётчику из
[`s07e05`](../s07e05-metrics-exporter/), показатель задержки — по корзине
гистограммы из [`s07e09`](../s07e09-latency-percentiles/): значение
`le="0.3"` даёт точное число быстрых запросов без интерполяции.

Пара окон скорости расхода — то же решение, что в
[`s07e06`](../s07e06-alert-rules/): короткое окно реагирует быстро и
шумит, длинное молчит и опаздывает. Кому именно достаётся сработавшее
оповещение, решает маршрутизация из [`s07e07`](../s07e07-alert-routing/).

Нарушенный здесь показатель задержки — тот самый пул соединений, найденный
в [`s07e08`](../s07e08-bottleneck/) и не починенный в
[`s07e10`](../s07e10-tuning/). Серия закрывает сезон тем, что превращает
эту находку в решение: выкаты остановлены, пока число не вернётся.

Целочисленная арифметика вместо процентов с плавающей точкой — то же
правило, что в [`s07e09`](../s07e09-latency-percentiles/) и в §4.3
[плана курса](../../V2.0_UPGRADE_PLAN.md): сравнивают свойство, а не
величину, зависящую от порядка машинных операций.
