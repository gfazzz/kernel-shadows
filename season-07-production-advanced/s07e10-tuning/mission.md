## Обстановка

Дмитрий принёс файл из блога: девять параметров, «проверенный конфиг для
высоконагруженных серверов». Первого из них нет в ядре с версии 4.12.
Четвёртый выключает защиту от `SYN flood`. Пятый настраивает подкачку на
машине, где подкачки нет.

Реальных измерений три: очередь принятия переполняется сто восемьдесят
четыре раза в минуту, таблица отслеживания соединений заполнена на девяносто
процентов, файловых дескрипторов на пике четырнадцать тысяч восемьсот при
пределе шестнадцать триста восемьдесят четыре.

## Приказ

Написать `artifacts/tuning.conf` — только то, что закрывает измерения, и с
обоснованием у каждой строки.

```bash
cp starter/tuning.conf artifacts/
bash tests/test.sh
```

| Файл в `data/` | Что в нём |
|---|---|
| `measurements.txt` | что измерено и что из этого требует изменения |
| `requirements.txt` | какие параметры обязаны быть и каким свойством |
| `allowed.txt` | какие параметры вообще есть в этом ядре |
| `harmful.txt` | что кочует из статьи в статью и почему не надо |
| `current_sysctl.txt` | что действует сейчас |
| `cargo_cult.conf` | файл из блога — не образец |

## Чем добывать

| Что нужно | Как |
|---|---|
| значение параметра | правило из `requirements.txt` и число из `measurements.txt` |
| правило `>=2*M4` | «не меньше двух измеренных значений `M4`» |
| существует ли параметр | `grep -x` по `allowed.txt` |
| не пустая ли строка | сравнить с `current_sysctl.txt` |
| обоснование | комментарии над строкой, с идентификатором измерения |

## Критерии приёмки

- [ ] Все параметры из `requirements.txt` заданы, и каждый удовлетворяет своему правилу.
- [ ] У каждой строки есть обоснование со ссылкой на измерение (`M1`, `M4`, …).
- [ ] Все параметры существуют в ядре по `allowed.txt`.
- [ ] Ни одного параметра из `harmful.txt`.
- [ ] Ни один параметр не выставлен в уже действующее значение.
- [ ] В файле нет параметров, не закрывающих ни одного требования.
- [ ] `bash tests/test.sh` → 18 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep |
| Сеть | не нужна |
| **применение sysctl** | **не требуется** — проверяется текст настройки |
| Внешние пакеты | нет |
| Изоляция теста | разбор пишется в `mktemp -d`, система не трогается |

Тест берёт правила из `requirements.txt` и числа из `measurements.txt`, а
список существующих параметров — из `allowed.txt`. Отдельно проверяется,
что данные не выродились: что измерений, требующих действия, не меньше
трёх, что в файле из блога действительно есть вредные параметры и что
среди них есть несуществующий в ядре.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «в ядре нет: …» | параметр взят из статьи | сверить с `allowed.txt` |
| «без ссылки на измерение» | обоснования нет или в нём нет `Mn` | комментарий над строкой |
| «выставлены в то же, что уже есть» | значение совпало с действующим | строка есть, эффекта нет |
| «из M3 следует не меньше …» | значение занижено | правило из `requirements.txt` |
| «не задан, хотя M1 требует» | закрыта одна очередь из двух | их две: полуоткрытые и принятые |
| «параметров без требования» | добавлено «на всякий случай» | каждый лишний придётся объяснять |

## После выполнения

Зелёный тест означает, что из девяти строк осталось четыре, у каждой есть
измерение, из которого получено значение, и внизу файла записано, чего в
нём нет и почему.

Главное, что стоит унести: **настройка, которую нельзя объяснить,
неотличима от настройки, которую нельзя убрать.** Параметр без измерения
не просто бесполезен — он делает файл неприкасаемым, и это переживёт и
задачу, и того, кто её написал.

И второе: **проверяется состояние, а не факт действия.** `sysctl --system`
применит файл частично и не сообщит об этом; узнать можно, только прочитав
`journalctl -u systemd-sysctl` или сами значения. Тот же принцип, что с
`kubectl apply` в [`s07e04`](../s07e04-rollout-stuck/) и с созданием службы
в [`s07e03`](../s07e03-service-config/).

## Кумулятивность

Список измерений — прямое продолжение
[`s07e08`](../s07e08-bottleneck/): `TcpExtListenOverflows` и переполнение
таблицы соединений найдены там методом USE, здесь они превращаются в
параметры.

Требование «сравнить до и после в одинаковых условиях» опирается на
[`s07e09`](../s07e09-latency-percentiles/): без понимания разрешения
измерения любое сравнение покажет улучшение.

Конфигурация, у которой каждая строка обоснована, — та же дисциплина, что
в [`s05e11`](../../season-05-security-pentesting/s05e11-hardening/) и
[`s02e09`](../../season-02-networking/s02e09-ssh-hardening/): там правила
укрепления тоже выводились, а не копировались.

Разбор «что применилось на самом деле» продолжает
[`s04e11`](../../season-04-devops-automation/s04e11-iac-audit/): описанное
состояние и фактическое — разные вещи, и сверять надо второе.
