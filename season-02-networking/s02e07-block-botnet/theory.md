# Теория — s02e07

## 1. Скрипт, который заблокировал офис

> *Мы держали список адресов, с которых шёл перебор паролей, и я написал скрипт: читает список, применяет `iptables -A INPUT -s ... -j DROP` на каждый. Запускается по cron раз в час. Красиво.*
>
> *Через неделю утром никто не смог зайти на сервер из офиса.*
>
> *Разбираемся. В списке появился наш собственный внешний адрес. Попал он туда честно: кто-то из разработчиков в цикле дёргал API с неверным токеном, детектор посчитал это перебором и добавил адрес. Скрипт послушно применил.*
>
> *Палыч разбирал со мной не логику детектора, а устройство самого скрипта.*
>
> — Между тем, что список пополнился, и тем, что офис отрезан, что было?
> — Ничего. Cron запустился и применил.
> — Вот это и есть ошибка. Не в детекторе — детекторы всегда ошибаются, это их природа. Ошибка в том, что между решением и действием у тебя не было ни одного места, куда можно посмотреть.
>
> *Он предложил переделать так: скрипт **генерирует** файл правил, кладёт рядом с прошлым, и первым делом показывает `diff`.*
>
> — Смотришь, что изменилось со вчера. Три новых адреса — применяешь. Тридцать новых адресов или ваша подсеть в списке — идёшь разбираться. Причём разбираться до того, как всё сломалось, а не после.
>
> *Позже я понял, что это общий приём, а не частный. Всё, что меняет систему массово и необратимо, стоит разделять на две фазы: подготовить артефакт и применить артефакт. `terraform plan` и `apply`, `--dry-run` в kubectl, `-C` в Ansible — везде одна и та же мысль, придуманная до нас.*

## 2. Способы заблокировать

```bash
sudo ufw deny from 185.220.101.47                     # один адрес
sudo ufw deny from 185.220.101.0/24                   # подсеть
sudo ufw insert 1 deny from 185.220.101.47            # в начало: до разрешающих правил
sudo iptables -A INPUT -s 185.220.101.47 -j DROP      # уровнем ниже
sudo iptables -A INPUT -s 185.220.101.47 -j REJECT    # с уведомлением отправителю
```

**`DROP` или `REJECT`.** `DROP` молча отбрасывает пакет, `REJECT` отправляет ICMP-сообщение «недоступно». Для внешнего мира обычно берут `DROP`: он не тратит ресурсы на ответ и не подтверждает атакующему, что хост существует. Внутри сети предпочтительнее `REJECT` — иначе свои же клиенты будут ждать таймаута вместо мгновенной ошибки.

**Порядок важен.** Правило `deny`, добавленное после `allow` для того же трафика, никогда не сработает: побеждает первое совпавшее. В `ufw` для этого есть `insert N`.

**Блокировать адрес или подсеть.** Если атакующие адреса группируются в один блок, правило на подсеть заменяет сотни отдельных. Но `/16` — это 65 тысяч адресов, среди которых может оказаться нужный; ширину блокировки выбирают по данным, а не по удобству.

## 3. Масштаб: `ipset` и nftables sets

Цепочка `iptables` проверяется линейно: каждый пакет сравнивается с правилами по порядку до первого совпадения. Тысяча правил — тысяча сравнений на пакет.

```bash
sudo ipset create botnet hash:ip timeout 3600     # набор с автоистечением через час
sudo ipset add botnet 185.220.101.47
sudo iptables -I INPUT -m set --match-set botnet src -j DROP
sudo ipset save botnet > /etc/ipset.conf          # сохранить набор
```

Одно правило вместо тысячи; проверка — обращение к хеш-таблице. Плюс `timeout`: адреса выпадают из набора автоматически, и список не растёт вечно.

В nftables то же самое встроено в язык:

```
table inet filter {
  set botnet { type ipv4_addr; flags timeout; }
  chain input { ip saddr @botnet drop }
}
```

## 4. Границы блокировки по адресам

Блокировка помогает против известного и конечного списка. Против остального — нет:

**Адреса меняются.** Ботнет из тысяч заражённых машин выдаёт новые адреса быстрее, чем их вносят. Список устаревает за часы.

**Объёмная атака заканчивается до фаервола.** Если канал до сервера — гигабит, а атака даёт полтора, пакеты теряются у провайдера независимо от того, что написано в правилах. Такие атаки гасят выше по потоку: у оператора, в CDN, через сервисы очистки трафика.

**Адрес может быть общим.** За одним адресом NAT сидит офис, университет или мобильный оператор. Блокировка отрезает вместе с атакующим сотни непричастных.

Что применяют дополнительно:

```bash
sudo ufw limit 22/tcp                                # частота новых подключений
sudo sysctl -w net.ipv4.tcp_syncookies=1             # против SYN-флуда
sudo iptables -A INPUT -p tcp --syn -m limit --limit 25/s -j ACCEPT
```

SYN cookies заслуживают пояснения: при переполнении очереди полуоткрытых соединений ядро перестаёт хранить состояние и кодирует его в номере последовательности ответа. Настоящий клиент вернёт корректный ответ, поддельный источник — нет. Это делает классический SYN-флуд неэффективным ценой отказа от некоторых опций TCP.

## 5. `fail2ban` — автоматизация того же самого

`fail2ban` читает логи (`auth.log`, логи веб-сервера), по регулярным выражениям находит признаки перебора и временно банит источник через фаервол:

```bash
sudo fail2ban-client status sshd        # что сейчас забанено
sudo fail2ban-client set sshd unbanip 10.50.1.5
```

Ключевое слово — **временно**: бан с истечением решает проблему разрастающегося списка и ошибочных срабатываний. Именно этого не хватало скрипту из воспоминания.

Управляется он через systemd, поэтому полноценно разбирается в Season 5. Здесь достаточно знать, что ручная блокировка — это первый шаг, а не конечная форма.

## 6. Почему две фазы лучше одной

| Одна фаза (применить сразу) | Две фазы (сгенерировать → применить) |
|---|---|
| ошибка в данных = мгновенное последствие | ошибка видна до применения |
| нельзя показать коллеге | артефакт можно ревьюить |
| нет истории изменений | файл версионируется, `diff` показывает разницу |
| откат надо придумывать | файл отмены генерируется из того же списка |
| «что именно сделал скрипт?» — по логам | ответ в самом артефакте |

Стоит это одной лишней команды. Отказываются от этого обычно в спешке — то есть ровно тогда, когда вероятность ошибки максимальна.

## 7. Метанавык: доверие к входным данным

Скрипт из воспоминания был написан правильно. Неправильным было предположение, что список адресов всегда содержит только чужие адреса.

Любые входные данные, пришедшие извне — из чужого файла, из детектора, из API, от пользователя, — заслуживают одного вопроса: **что будет, если здесь окажется не то, что я ожидаю**. Не «может ли», а «что будет».

Ответ обычно подсказывает и защиту: проверить формат, отсеять невалидное, исключить заведомо свои значения, ограничить масштаб изменения, разделить подготовку и применение. Ни одна из этих мер не стоит дорого — дорого стоит их отсутствие в тот единственный раз, когда данные оказались другими.
