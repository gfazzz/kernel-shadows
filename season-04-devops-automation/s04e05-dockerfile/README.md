## II. Теория: за что платит каждая строка

### `FROM` — выбор поверхности

```dockerfile
FROM python:3.11          # ~1 ГБ, 61 уязвимость: полный Debian с компиляторами
FROM python:3.11.6-slim   # ~130 МБ, 9 уязвимостей
FROM python:3.11-alpine   # ~50 МБ, но musl вместо glibc
FROM gcr.io/distroless/…  # только рантайм, даже без оболочки
```

Дело не в мегабайтах, а в **поверхности**: каждая программа внутри может содержать уязвимость, и сканер честно посчитает их все.

Версию задают точно. `python:3.11` завтра означает другой образ; `latest` — обычный тег, а не «самое свежее».

### Порядок = кеш

Слой берётся из кеша, если инструкция и её вход не изменились. Первое расхождение обесценивает **всё, что ниже**. Отсюда порядок, обратный частоте изменений:

```dockerfile
RUN apt-get …             # раз в полгода
COPY requirements.txt .   # раз в неделю
RUN pip install -r …
COPY . /app               # каждый раз
```

Поменяйте две последние пары местами — и `pip install` будет выполняться при каждой правке одной строки кода.

### Что удаляется, а что нет

```dockerfile
RUN apt-get update && apt-get install -y … && rm -rf /var/lib/apt/lists/*
```

`rm` работает, только если он **в той же инструкции**. Отдельным `RUN` кеш apt останется в предыдущем слое — ровно то, что разбирали вчера.

То же с ключами: `COPY` + `RUN rm` не убирает файл. Не создавать слой вовсе — `RUN --mount=type=secret` или многоступенчатая сборка.

### `USER`

```dockerfile
RUN useradd --system --create-home --uid 10001 collector
COPY --chown=collector:collector . /app
USER collector
```

`USER` ставят **после** установки (она требует root) и **до** `CMD`. Числовой UID задают явно: оркестраторы умеют требовать «не root» и проверяют номер, а не имя.

`COPY --chown` избавляет от отдельного `RUN chown` — то есть от лишнего слоя размером со всё приложение.

### `CMD` строкой и массивом

```dockerfile
CMD python /app/collector.py           # → /bin/sh -c "python …"
CMD ["python", "/app/collector.py"]    # процесс становится PID 1
```

В первом случае PID 1 достаётся оболочке, а приложение получает PID 2. Оболочка не пересылает сигналы — и `docker stop` вместо остановки ждёт десять секунд и убивает контейнер. Тот же вопрос, что `TERM` против `KILL` в [`s03e04`](../../season-03-system-administration/s03e04-processes/).

Про многоступенчатую сборку и `.dockerignore` — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«`docker stop` не останавливает контейнер, ждёт десять секунд и убивает. Приложение обрабатывает SIGTERM. Почему?»*

<details>
<summary>Подумай 30 секунд</summary>

`CMD` записан строкой. Контейнер запускает `/bin/sh -c "…"`, оболочка становится PID 1, приложение — её потомком.

`docker stop` посылает `SIGTERM` **первому процессу**. `sh` его получает, но не пересылает детям и сам не завершается. Через таймаут прилетает `SIGKILL`, и приложение умирает, не успев прибраться.

Лечится exec-формой: `CMD ["python", "app.py"]` — приложение само становится PID 1 и получает сигнал.
</details>

**LILITH:** *«`RUN apt-get install` и отдельной строкой `RUN rm -rf /var/lib/apt/lists/*`. Сколько места сэкономлено?»*

<details>
<summary>Ответ</summary>

Нисколько. Слой установки уже записан вместе с кешем; следующий слой только помечает файлы удалёнными, а данные остаются ниже.

Работает единственный вариант — всё в одной инструкции:

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

Проверить себя: `docker history` покажет размер каждого слоя, и слой «удаления» будет `0B`.
</details>

## IV. Задание: переписать образ

Артефакты — два файла в `artifacts/`: `Dockerfile` и `dockerignore` (в репозитории — `.dockerignore`).

```bash
cp starter/Dockerfile starter/dockerignore artifacts/
bash tests/test.sh
```

| Требование | Почему |
|---|---|
| облегчённая база с точной версией | 9 уязвимостей вместо 61, воспроизводимость |
| зависимости отдельным слоем, код последним | кеш не сбрасывается на правке кода |
| `apt-get` с `--no-install-recommends` и очисткой в той же строке | иначе кеш остаётся в слое |
| ни одного `ENV` с секретом и ни одного `COPY` ключа | их видит каждый, у кого есть образ |
| непривилегированный пользователь, `USER` до `CMD` | контейнеру сборщика root не нужен |
| запуск в exec-форме | иначе `docker stop` не работает |
| заполненный `.dockerignore` | `COPY .` иначе затянет `.git` и ключи |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Пользователя надо не только указать в `USER`, но и **создать** — `RUN useradd`. Иначе контейнер не стартует.

`COPY --chown=имя:имя . /app` ставит владельца сразу, без отдельного `RUN chown`.

Эталон — в `solution/`, там же комментарий к каждому решению.
</details>

### Три ошибки, которые здесь делают

**Указать `USER`, не создав пользователя.** Файл выглядит правильно, тест на «не root» проходит, контейнер не запускается: такого пользователя в образе нет.

**Поставить `USER` до установки пакетов.** `apt-get` и `pip` в системные каталоги требуют root. Порядок жёсткий: root ставит, `USER` переключает, `CMD` запускает.

**Оставить `CMD` строкой.** Ничего не сломается до первого `docker stop` — и тогда окажется, что контейнер не останавливается, а убивается.
