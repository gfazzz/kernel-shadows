## I. Датчик, которого не существует

Ли Вэй выкладывает на стол плату размером с ноготь.

> — Промышленный датчик вибрации. Отдаёт двести измерений в секунду по своей шине. Драйвера для Linux нет и не будет: контора, которая его делала, закрылась.

> — Читать из пользовательского пространства?

> — Двести раз в секунду через переключения контекста? Половину пропустишь. Это работа для ядра: оно ловит прерывания, складывает измерения в буфер, а пользовательская программа забирает их пачками, когда ей удобно.

Он открывает пустой файл.

> — И сразу договоримся, чего мы делать не будем. Мы не будем отлаживать это перезагрузками.

> — А как ещё?

> — Смотри. Что здесь может сломаться? Кольцевой буфер: индекс уехал за границу, переполнение посчитано неверно, самое старое не то, что думаешь. Разбор параметра: пришло сто тысяч вместо восьми. Печать температуры: минус четыре и восемьсот семьдесят пять тысячных вдруг стали «минус четыре точка минус восемьсот семьдесят пять».

Он проводит черту по экрану.

> — Ни одна из этих ошибок не имеет отношения к ядру. Это обычная арифметика на C. Вынеси её в отдельный файл, который не подключает ни одного заголовка ядра, — и проверяй обычным `gcc` за миллисекунды. В ядро уедет проверенный код, а там останется двадцать строк обвязки, где ломаться почти нечему.

> — А если ошибка всё-таки в обвязке?

> — Тогда её увидишь сразу: она либо не соберётся, либо не загрузится. Ошибка в арифметике — другое дело: модуль загрузится, поработает три часа и уронит машину, когда индекс наконец уедет.

> **LILITH:** *«Цена ошибки в ядре — не в том, что она сложнее. В том, что цикл „поправил — проверил" стоит перезагрузку вместо миллисекунды. Поэтому главное архитектурное решение принимается до первой строки: что именно обязано жить в ядре, а что может быть проверено снаружи.»*

## II. Теория: модуль и его границы

### Что такое модуль

Модуль — кусок кода, который загружается в работающее ядро и становится его частью. Не процесс: у него нет своей памяти, своего адресного пространства и никакой изоляции. Ошибка в модуле — ошибка в ядре.

```bash
insmod shadow.ko depth=8      # загрузить с параметром
lsmod | grep shadow           # посмотреть
modinfo shadow.ko             # метаданные
dmesg | tail                  # что он сказал
rmmod shadow                  # выгрузить
```

### Скелет

```c
static int __init shadow_mod_init(void)   { … return 0; }   /* 0 — успех */
static void __exit shadow_mod_exit(void)  { … }

module_init(shadow_mod_init);
module_exit(shadow_mod_exit);

MODULE_LICENSE("GPL");
```

| Элемент | Зачем |
|---|---|
| `__init` | память под функцию освобождается после загрузки |
| `__exit` | код выгрузки не включается, если модуль вкомпилирован в ядро |
| `MODULE_LICENSE("GPL")` | без совместимой лицензии ядро метит себя `tainted` и закрывает часть символов |
| `MODULE_PARM_DESC` | описание параметра видно в `modinfo` |

Возврат из `init` — не `void`: `0` означает успех, отрицательное значение — код ошибки (`-ENOMEM`, `-EINVAL`). Ненулевой возврат отменяет загрузку, и **всё, что модуль успел выделить, обязан освободить он сам**.

### Чего в ядре нет

| Нет | Вместо этого |
|---|---|
| стандартной библиотеки C | `pr_info` вместо `printf`, `kmalloc` вместо `malloc` |
| **плавающей точки** | целочисленная арифметика |
| сборщика мусора | что выделил — освободи, иначе течёт до перезагрузки |
| защиты памяти | выход за границу массива портит чужие данные |
| возможности «выйти» | из ядра некуда выходить |

Отсутствие плавающей точки — не каприз: регистры FPU не сохраняются при переключении контекста в ядре, и `float` там молча испортит вычисления пользовательского процесса. Отсюда приём, который встречается по всему ядру: величины хранят в тысячных, а печатают целую и дробную части раздельно.

```c
*whole = sign * (milli / 1000);
*frac  = milli % 1000;          /* всегда неотрицательна */
```

Ловушка в знаке: `-4875 / 1000` даёт `-4`, а `-4875 % 1000` — `-875`, и печать «`%d.%d`» превращается в `-4.-875`. Разделять знак и дробную часть надо явно.

### Параметр приходит извне

```c
static int depth = 16;
module_param(depth, int, 0444);
MODULE_PARM_DESC(depth, "глубина кольцевого буфера (4..64)");
```

Права `0444` создают файл `/sys/module/shadow/parameters/depth`, доступный на чтение. Значение задаёт тот, кто загружает модуль, — то есть **это внешний ввод**, и доверять ему нельзя ровно так же, как аргументу командной строки или полю запроса:

```
insmod shadow.ko depth=100000
```

Без проверки это запись за пределы массива в адресном пространстве ядра. Отсюда `shadow_param_clamp` перед любым использованием.

### Ресурсы освобождает тот, кто их взял

```c
ring = kzalloc(sizeof(*ring), GFP_KERNEL);
if (!ring)
        return -ENOMEM;        /* ничего не выделено — ничего не освобождаем */
…
static void __exit shadow_mod_exit(void)
{
        kfree(ring);           /* всё, что взяли при загрузке */
}
```

Когда шагов инициализации несколько, каждый следующий обязан уметь откатить все предыдущие. В ядре это оформляют лестницей меток:

```c
        a = alloc_a();  if (!a) return -ENOMEM;
        b = alloc_b();  if (!b) { err = -ENOMEM; goto err_a; }
        c = alloc_c();  if (!c) { err = -ENOMEM; goto err_b; }
        return 0;
err_b:  free_b(b);
err_a:  free_a(a);
        return err;
```

Это один из немногих случаев, где `goto` — не дурной тон, а принятый в ядре способ не забыть освобождение.

### Граница: что проверяется без ядра

```
shadow_ring.c   ── ни одного linux/-заголовка ──▶ gcc + юнит-тесты, миллисекунды
shadow_mod.c    ── module_init, kzalloc, pr_info ──▶ сборка .ko, insmod, dmesg
```

Правило простое: **всё, что не обязано быть в ядре, из ядра выносится.** Не ради красоты — ради цены цикла проверки.

Про `printk` и уровни, `dmesg`, символы и `EXPORT_SYMBOL`, `kbuild`, блокировки и `KASAN` — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Логика вынесена в файл без заголовков ядра. Разве это не искусственное усложнение ради тестов?»*

<details>
<summary>Подумай 30 секунд</summary>

Тесты — приятное следствие, а не причина. Причина в цене цикла «поправил — проверил».

В пользовательском пространстве он занимает секунду: собрал, запустил, посмотрел. В ядре — сборку модуля, `insmod`, чтение `dmesg`, `rmmod`, а при неудачной ошибке ещё и перезагрузку машины. Разница в три порядка, и она умножается на число итераций отладки индексов кольцевого буфера.

Вторая причина видна на длинной дистанции: у кода без зависимостей от ядра **другой набор возможных ошибок**. Он не может испортить чужую память, не может забыть блокировку, не может уронить машину. Сузив ядерную часть до двадцати строк обвязки, ты сужаешь и множество мест, где может случиться катастрофа.

Это общий приём, а не свойство ядра. Так же поступают с кодом, зависящим от базы, от сети, от файловой системы: ядро логики отделяют от границы с миром — и получают возможность проверять первое как арифметику.
</details>

**LILITH:** *«`depth` — просто число, которое задаёт администратор при загрузке. Зачем его проверять?»*

<details>
<summary>Ответ</summary>

Затем, что «просто число, которое задаёт администратор» — это ровно определение внешнего ввода. Модуль не знает, кто и как его загрузил: это может быть скрипт с опечаткой, конфигурация из системы развёртывания или строка в `/etc/modprobe.d/`, куда полгода назад кто-то вписал `depth=100000`.

В пользовательском пространстве такая ошибка даёт `Segmentation fault`: процесс умирает, остальные работают. В ядре защиты нет — запись по индексу 100000 в массив на 64 элемента портит **чужую память ядра**, и упадёт не обязательно твой модуль и не обязательно сразу. Такие ошибки диагностируются днями.

Отсюда правило, которое в ядре звучит жёстче, чем где-либо: **всё, что пришло снаружи, проверяется на границе.** Параметр модуля, данные из `copy_from_user`, содержимое буфера от устройства, значение из дерева устройств. Граница — это то место, где заканчивается твой контроль, и в ядре она проходит гораздо ближе, чем кажется.
</details>

## IV. Задание: `shadow_ring.c` + `shadow_mod.c`

Артефакты — `artifacts/shadow_ring.c` (логика) и `artifacts/shadow_mod.c` (обвязка).

```bash
cp starter/* artifacts/
bash tests/test.sh
```

| Файл | Требование |
|---|---|
| `shadow_ring.c` | ни одного заголовка ядра; собирается `-Wall -Wextra -Werror` |
| | кольцо не растёт, вытеснения считаются, `pop` отдаёт старейшее, `peek(0)` — свежайшее |
| | `shadow_param_clamp` выдерживает и перепутанные границы |
| | `shadow_scale_milli` — целочисленно, дробная часть неотрицательна |
| | указатели проверяются: `NULL` не роняет |
| `shadow_mod.c` | `module_init`/`module_exit`, `__init`/`__exit`, метаданные, `MODULE_LICENSE("GPL")` |
| | `module_param` с восьмеричными правами и `MODULE_PARM_DESC` |
| | параметр загоняется в границы **до** использования |
| | `kzalloc` с обработкой неудачи и парным `kfree` |
| | ни `float`, ни `printf`, ни `malloc`, ни `stdio.h` |
| | арифметика кольца не продублирована здесь |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Интерфейс задан в `shadow_ring.h` — менять не надо.

Самое старое лежит на `count` позиций назад от `head` по модулю `capacity`; самое свежее — на шаг назад от `head`.

`peek` не меняет состояние: только читает.

Знак в `shadow_scale_milli`: запомнить, взять модуль, поделить, вернуть знак в целую часть; при нулевой целой части сообщить о минусе возвратом `1`.

Требования к обвязке перечислены в `data/module_rules.txt`, запреты — в `data/forbidden.txt`; тест читает те же файлы.

Эталон — в `solution/`, там у каждого решения написано, что оно предотвращает.
</details>

### Три ошибки, которые здесь делают

**Оставить арифметику в модуле.** Отладка индексов начинает стоить перезагрузку за итерацию.

**Взять `depth` как есть.** Параметр приходит снаружи; `depth=100000` — это запись за границу массива в памяти ядра.

**Напечатать дробь через плавающую точку.** В ядре её нет, и код либо не соберётся, либо испортит регистры чужого процесса.

## V. Двадцать строк в ядре

Макс сдаёт два файла. Ли Вэй смотрит на строку сборки.

```
  Логика: 35 passed, 0 failed
```

> — Тридцать пять проверок за двенадцать миллисекунд. Столько же в ядре — это полтора часа с перезагрузками.

Он собирает модуль, загружает, читает `dmesg`, выгружает.

> — Работает. Но пока это вещь в себе: буфер есть, а забрать из него данные никто не может. Модуль ядра, к которому нельзя обратиться из пользовательской программы, — это половина устройства.

Он рисует на доске `/dev/shadow0`.

> — Завтра доделаем вторую половину. Файл, который можно открыть, прочитать и закрыть — обычными `open`, `read`, `close`. И тогда твой сборщик заберёт измерения у ядра напрямую, без всякого MQTT. На этом Шэньчжэнь для тебя закончится.
