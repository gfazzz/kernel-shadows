## Обстановка

Восемь закреплений найдены и сняты в хранилище инцидента. Узлов пятьдесят,
какие из них грязные — неизвестно; часть уже чистили руками, и кто именно
что чистил, тоже неизвестно.

Отчёт вечером. В нём должно быть число, а не «мы всё убрали».

## Приказ

Написать `artifacts/cleanup.sh`: привести узел к состоянию из плана и уметь
подтверждать это состояние, ничего не меняя.

```bash
cp starter/cleanup.sh artifacts/
cp -r data/node_snapshot /tmp/узел
bash artifacts/cleanup.sh --verify /tmp/узел data/cleanup_plan.txt
bash artifacts/cleanup.sh /tmp/узел data/cleanup_plan.txt
bash tests/test.sh
```

## Договор

```
cleanup.sh [--verify] <корень> <план>

ITEM <состояние> <действие> <объект>       FIXED | ALREADY | FAILED
SUMMARY fixed=<n> already=<n> failed=<n>

код возврата: 0 — состояние достигнуто, 1 — нет, 2 — вход не разобран
```

## Формат плана

```
remove-file  <путь>                 файла быть не должно
remove-line  <путь> <подстрока>     строки с этой подстрокой быть не должно
remove-user  <путь> <имя>           учётной записи в файле быть не должно
```

Каждая строка описывает **состояние**, а не команду. Отсюда всё остальное.

## Что здесь легко пропустить

**Проверка после действия — отдельный шаг.** Код возврата команды говорит о
команде: `rm -f` на отсутствующий файл возвращает ноль, ничего не сделав.
Состояние узнаётся только повторной проверкой.

**Второй прогон обязан сказать `ALREADY`.** Не `FIXED`. Разница между ними —
это разница между «сколько было работы» и «чисто ли», и в отчёте нужны оба
числа.

**`--verify` не меняет ничего.** Тест сравнивает дерево до и после целиком.

**Файлы правятся точечно.** В `authorized_keys` есть чужой ключ и свой; в
`rc.local` — добавленная строка и рабочее содержимое; в `passwd` — восемь
законных записей и одна лишняя. Удаление файла целиком отрезает узел от
управления.

## Критерии приёмки

- [ ] Договор вызова соблюдён, коды 0/1/2 различаются по смыслу.
- [ ] `--verify` на грязном узле возвращает 1 и ничего не меняет.
- [ ] Все восемь пунктов достигнуты, состояние проверено после действия.
- [ ] Законное содержимое не задето: свой ключ, `rc.local`, `root` и прочие записи.
- [ ] Второй прогон возвращает 0 и помечает всё как `ALREADY`.
- [ ] Третий прогон не меняет содержимое дерева.
- [ ] `--verify` после очистки возвращает 0 и подтверждает все пункты.
- [ ] На одинаковых деревьях — одинаковый вывод и одинаковый результат.
- [ ] `bash tests/test.sh` → 38 passed, 0 failed.

## Требования среды

| Требование | Значение |

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «свой ключ удалён вместе с чужим» | файл почищен целиком | удалять строку по подстроке |
| «из passwd удалён root» | совпадение по `uid`, а не по имени | якорь `^имя:` |
| второй прогон печатает `FIXED` | состояние спутано с действием | проверять до применения |
| «--verify изменил дерево» | общая ветка кода с очисткой | ветвление до записи |
| `failed` при достигнутом состоянии | проверка сделана до применения и не повторена | проверить снова после |
| «rc.local опустошён» | удалена не та строка | подстрока из плана, а не весь файл |
| «деревья после очистки различаются» | зависимость от порядка обхода | идти строго по плану |
| код 0 при `failed>0` | код не связан с итогом | 1, если хоть один пункт не достигнут |

## После выполнения

Зелёный тест означает, что скрипт можно запустить на всех пятидесяти узлах,
не выясняя заранее, какие из них уже чистили, — и что его вывод годится в
отчёт.

Главное, что стоит унести: **«я удалил» и «файла нет» — разные утверждения.**
Первое про прошлое и непроверяемо, второе про настоящее и перепроверяется
кем угодно в любой момент. В отчёт идёт второе.

И второе: **идемпотентность — это не про элегантность, а про право
запустить.** Скрипт, который безопасно запускать повторно, применяется ко
всему парку одной командой. Скрипт, который может навредить при повторе,
требует, чтобы кто-то помнил, где он уже был, — а помнить будет некому.

## Кумулятивность

Идемпотентность вводилась в
[`s04e10`](../../season-04-devops-automation/s04e10-ansible-check/) и
[`s04e12`](../../season-04-devops-automation/s04e12-ansible-playbook/) — там
на развёртывании, здесь на очистке; цена ошибки выше, потому что очистка
уничтожает улики.

План очистки собран из находок [`s08e05`](../s08e05-persistence/): каждый
пункт — одна строка того отчёта. Инструмент нашёл, план описал, скрипт привёл
— и это тот самый порядок, ради которого находки печатались машинно.

Точность правки вместо ширины — то же, что в
[`s08e04`](../s08e04-zeroday/) и [`s02e06`](../../season-02-networking/s02e06-firewall-ufw/):
мера, задевающая лишнее, ломает работу и в разгар инцидента стоит дороже
самой находки.

Проверка состояния вместо доверия к коду возврата — продолжение
[`s07e04`](../../season-07-production-advanced/s07e04-rollout-stuck/), где
выкат «шёл» и не ехал.
