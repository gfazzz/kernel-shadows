## 1. Жизненный цикл: `inactive` → `pending` → `firing`

```
каждые evaluation_interval:
    условие ложно  ──▶ inactive
    условие истинно ─▶ pending  ──держится for──▶ firing ──▶ Alertmanager
                          │
                          └─ условие перестало выполняться → сброс в inactive
```

Три следствия, которые видны только зная механику:

**Счётчик `for` сбрасывается целиком.** Не «накапливается за час», а именно сбрасывается: девять минут выполнения при `for: 10m` и одна ложная проверка — начинаем сначала. Для дребезжащего условия это означает, что оповещение не сработает **никогда**, хотя суммарно проблема длится часами.

**Состояние живёт в памяти Prometheus.** Перезапуск сбрасывает все `pending`. Отсюда практика не перезапускать Prometheus во время происшествия и держать два экземпляра, считающих одни и те же правила.

**Оповещение «гаснет» само.** Как только условие перестало выполняться, Prometheus сообщает Alertmanager `resolved`. Разослать уведомление о разрешении — задача Alertmanager, и по умолчанию он это делает.

Посмотреть состояние можно в самом Prometheus:

```promql
ALERTS{alertname="AuroraHighErrorRate"}          # ряд с меткой alertstate
ALERTS_FOR_STATE                                 # когда началось pending
```

## 2. Правила записи: когда выражение считают заранее

```yaml
- record: aurora:requests:rate5m
  expr: sum by (code) (rate(aurora_requests_total[5m]))
```

Правило записи вычисляет выражение по расписанию и складывает результат в новый ряд. Зачем:

| Причина | Пример |
|---|---|
| выражение дорогое | агрегат по тысяче рядов на панели, которую открывают постоянно |
| выражение повторяется | одна и та же доля ошибок в четырёх правилах и трёх панелях |
| нужно длинное окно | `rate` за 30 дней считается по предвычисленному, а не по сырому |

Соглашение об именах: `уровень:метрика:операция` — двоеточия в именах разрешены **только** правилам записи, и это способ отличить вычисленное от собранного с одного взгляда.

Ловушка, о которой стоит знать заранее: правила внутри одной группы считаются **последовательно**, а разные группы — параллельно. Правило, опирающееся на результат другого, обязано лежать в той же группе и ниже него.

## 3. `histogram_quantile` и его честная цена

```promql
histogram_quantile(0.95, sum by (le) (rate(aurora_request_duration_seconds_bucket[5m])))
```

Что здесь происходит по шагам: `rate` превращает счётчики корзин в скорость попаданий, `sum by (le)` складывает одноимённые корзины всех реплик, `histogram_quantile` **интерполирует** внутри той корзины, в которую попал искомый перцентиль.

Слово «интерполирует» и есть цена. Функция не знает, как распределены наблюдения внутри корзины, и считает их равномерными. Если корзины `0.25` и `1` соседние, а 95-й перцентиль попал между ними, ответ будет линейной догадкой в интервале длиной в семьсот пятьдесят миллисекунд.

Практические следствия:

- **Точность ответа задаётся границами корзин**, и выбирать их надо там, где нужна точность, — обычно вокруг порога SLO.
- Значение выше верхней конечной корзины оценить нельзя: всё, что попало в `+Inf`, интерполируется в её нижнюю границу. Поэтому «p99 = 1 с» при верхней корзине в 1 с означает «p99 где-то за пределами измеримого».
- `sum by (le)` обязателен: без него перцентиль посчитается для каждой реплики отдельно, а такие числа не складываются (см. [`s07e05/theory.md`](../s07e05-metrics-exporter/theory.md)).

## 4. Правила, которые обязаны быть в любом кластере

| Правило | Зачем |
|---|---|
| `Watchdog` | срабатывает **всегда**; внешняя система поднимает тревогу, если перестала его получать |
| `up == 0` по всем заданиям | цель недоступна для сбора |
| `absent()` по ключевым рядам | цель отвечает, но нужного ряда нет |
| расхождение `generation` и `observedGeneration` | контроллер отстал (см. [`s07e04`](../s07e04-rollout-stuck/)) |
| место на диске Prometheus | хранилище кончается тихо и целиком |

`Watchdog` — единственный способ обнаружить, что мониторинга больше нет. Prometheus не может оповестить о собственном отказе: некому вычислить правило. Поэтому конструкция выворачивается наизнанку — «молчание есть авария», а решение о тревоге принимает кто-то снаружи.

Та же логика, что с `HEARTBEAT` дрона в [`s06e05`](../../season-06-embedded-iot/s06e05-mavlink-telemetry/): сигнал существования нужен не тому, кто его шлёт.

## 5. Почему готовый набор правил не работает

Наборы правил для Kubernetes существуют, их можно поставить одной командой, и результат почти всегда тот, с которого начинается эта серия: десятки срабатываний и пропущенные аварии. Причины конкретные:

**Пороги чужие.** «Память узла выше 90 %» — это авария там, где узел на 8 ГБ, и норма там, где на 256.

**Оповещения по причинам, а не по симптомам.** Готовые наборы состоят из них по необходимости: автор не знает, что для тебя является симптомом, и оповещает про всё, что умеет измерить.

**Нет твоей истории происшествий.** Правило, выведенное из разбора трёх своих аварий, поймает четвёртую. Правило из интернета поймает то, что случалось у автора.

Полезное применение у таких наборов всё же есть: **как список того, что вообще бывает.** Прочитать сорок правил, выбрать пять, переписать пороги — разумно. Поставить сорок и включить — нет.

## 6. Как проверять правила без Prometheus

```bash
promtool check rules rules.yml          # синтаксис и схема
promtool test rules tests.yml           # модульные тесты правил
```

Второе — недооценённая возможность: `promtool` умеет принять описание ряда во времени и проверить, что правило сработало в ожидаемый момент.

```yaml
tests:
  - interval: 15s
    input_series:
      - series: 'aurora_requests_total{code="500"}'
        values: '0+10x40'
    alert_rule_test:
      - eval_time: 11m
        alertname: AuroraHighErrorRate
        exp_alerts: [ ... ]
```

Это ровно тот же приём, что и всюду в курсе: **свойство проверяется на фикстуре, а не на живой системе.** Тест этой серии устроен так же, только читает YAML своими средствами — чтобы курсу не требовалось ставить Prometheus ради одной серии.
