## 1. Восемь часов, которые стоили одной команды

> *Конец первого года. Клиент жалуется: диск на 500 гигабайт забит, а «мы ничего не заливали». Мне поручают разобраться.*
>
> *Я иду по каталогам: `du -sh /var`, `du -sh /var/log`, `du -sh /var/log/nginx`… Записываю числа в блокнот, сравниваю, спускаюсь глубже. К обеду у меня три страницы цифр и подозрение на `/opt`. К вечеру я нахожу виновника — старый дамп базы, который кто-то положил «на минутку» полгода назад.*
>
> *Палыч слушает мой доклад до конца, потом спрашивает:*
>
> — Сколько ты потратил?
> — Часов восемь.
> — Смотри.
>
> *Он набирает одну строку — `find / -type f -size +1G 2>/dev/null` — и через полминуты на экране четыре пути. Верхний — мой дамп.*
>
> — Разница не в том, что я знаю команду, а ты нет. Разница в том, что ты искал глазами то, что описывается условием. «Файл больше гигабайта» — это условие. Не надо его искать, надо его СФОРМУЛИРОВАТЬ.

## 2. `find` — это условие, а не имя файла

Большинство знакомится с `find` как с «поиском по имени» и на этом останавливается. На деле это язык запросов к дереву: обход плюс набор предикатов, которые проверяются для каждого объекта.

```bash
find <где> <условия> <действие>
```

| Категория | Условия |
|---|---|
| тип | `-type f` файл, `-type d` каталог, `-type l` симлинк |
| имя | `-name '*.log'`, `-iname` (без учёта регистра), `-path '*/nginx/*'` |
| размер | `-size +1G`, `-size -100k`, `-empty` |
| время | `-mtime -1` (менялся за сутки), `-mmin -30`, `-newer файл` |
| владелец и права | `-user max`, `-group ops`, `-perm 777`, `-perm -002` |
| глубина | `-maxdepth 2`, `-mindepth 1` |

Условия по умолчанию соединяются логическим И. Для ИЛИ — `-o`, для отрицания — `!` или `-not`, для группировки — экранированные скобки `\( ... \)`.

```bash
find /var/log -type f \( -name '*.log' -o -name '*.gz' \) -size +50M
find /home -type f -perm -002        # world-writable — классика аудита безопасности
find /etc -type f -mtime -2          # что меняли за последние двое суток
```

Последний запрос — первое, что делают при разборе инцидента: «какие конфиги трогали перед тем, как всё сломалось».

## 3. Почему кавычки решают

```bash
find . -name *.conf      # ОПАСНО
find . -name '*.conf'    # верно
```

Оболочка раскрывает `*` **до** запуска команды. В каталоге с одним `app.conf` первая строка станет `find . -name app.conf`: команда отработает без ошибок и вернёт неполный ответ. Ошибка не заявляет о себе — она просто занижает результат.

Правило шире, чем `find`: если шаблон предназначен программе, а не оболочке, его берут в кавычки. То же касается `grep 'a*b'`, `rsync --exclude '*.tmp'` и любых аргументов с метасимволами.

## 4. `-exec` против `xargs`

```bash
find . -name '*.log' -exec gzip {} \;      # gzip запустится на каждый файл
find . -name '*.log' -exec gzip {} +       # gzip получит пачку файлов за вызов
find . -name '*.log' -print0 | xargs -0 gzip   # то же через xargs
```

`\;` — вызов на файл; для тысяч файлов это тысячи процессов. `+` и `xargs` собирают аргументы пачками и работают в разы быстрее.

Связка `-print0` / `xargs -0` существует ради имён с пробелами и переводами строк: обычный `xargs` разбивает вход по пробелам, и файл `my report.log` превратится в два несуществующих. `-print0` разделяет пути нулевым байтом — единственным символом, который в имени файла встретиться не может.

## 5. Переносимость: где `find` расходится между системами

Это ловушка, из-за которой «рабочий» скрипт падает у коллеги на макбуке.

| Приём | GNU (Linux) | BSD (macOS) |
|---|---|---|
| `-printf '%s %p\n'` | есть | **нет** |
| `-size +1G` | есть | есть (но `G` не везде) |
| `-regextype` | есть | иначе |
| `-delete` | есть | есть |
| `stat -c '%s'` | GNU | у BSD `stat -f '%z'` |

Переносимый способ получить размер — не флаг `find`, а внешняя команда: `du -k`, которая есть везде. Именно поэтому в задании размер считается через `du`, хотя `-printf '%s'` короче: план курса требует, чтобы тест давал одинаковый результат на разных платформах (§4.3), а «работает у меня» — не критерий.

## 6. Стоимость обхода

`find /` на большой файловой системе — это миллионы обращений к метаданным. На боевой машине под нагрузкой такой обход заметен: растёт нагрузка на диск, заполняется кэш inode.

Смягчающие приёмы:

- **Сузить область:** искать в `/var/log`, а не в `/`.
- **Ограничить глубину:** `-maxdepth 3`.
- **Отсечь чужие ФС:** `-xdev` не даст уйти в сетевые монтирования и в `/proc`.
- **Прибрать шум:** `2>/dev/null` уберёт `Permission denied` там, где прав нет.
- **Помнить про `locate`:** он отвечает мгновенно, потому что читает заранее построенную базу (`updatedb`), но эта база устаревает. `find` медленный и правдивый, `locate` быстрый и вчерашний.

## 7. Компромиссы

| Инструмент | Когда | Ограничение |
|---|---|---|
| `find` | точный ответ по любым условиям | обходит дерево, на `/` заметно нагружает |
| `locate` | быстро найти по имени | данные из базы, обновляется по расписанию |
| `ls -R` | глянуть небольшое дерево | нет условий, вывод не для скриптов |
| `tree` | наглядная картинка | обычно не установлен |
| `du -sh *` | что занимает место | размеры, но не поиск по критериям |

## 8. Метанавык: описывать вместо перебора

Разница между новичком и опытным администратором часто не в знании команд, а в постановке задачи. Новичок спрашивает «где лежит этот файл» и идёт смотреть. Опытный формулирует **свойство** — «файл больше гигабайта, изменённый за последние сутки, принадлежащий www-data» — и получает ответ одной строкой.

Тот же переход повторится в курсе несколько раз: от «посмотреть логи» к запросу с фильтрами (`grep`/`awk`, s01e10–11), от «проверить сервер» к перебору списка по условию (s01e08), от «настроить машины» к описанию желаемого состояния в Ansible (Season 4). Каждый раз меняется одно: вместо инструкции «как искать» ты пишешь описание «что считать искомым».
