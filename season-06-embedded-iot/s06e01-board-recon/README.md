> **LILITH:** *«На сервере архитектура — это то, о чём не думают: она всегда одна и та же. В embedded машина, где ты собираешь, и машина, где запускаешь, — разные, и это не деталь, а главное отличие. „Exec format error" — не про права. Это плата говорит: ты принёс мне слова чужого языка.»*

## Чему ты научишься

- Спрашивать плату о ней самой: `/proc/cpuinfo` и `/proc/device-tree` вместо догадок по наклейке.
- Списку `compatible` и его порядку — от частного к общему, и семи семантикам, которые из него следуют.
- Тому, что архитектура сборки и архитектура запуска — разные вещи, и кросс-компиляция начинается с этого.
- Метанавыку: **не гадай — спроси её саму**. Плата отвечает точнее, чем память о похожей плате.

Подробнее, с историей и подводными камнями, — в [`theory.md`](theory.md).

## Теория: три источника правды о железе

### `/proc/cpuinfo` — что процессор говорит о себе

```
processor       : 0          ← по строке на ядро; их число = количество ядер
CPU implementer : 0x41       ← кто сделал ядро: 0x41 = ARM Ltd
CPU part        : 0xd08      ← модель ядра — числом, не именем
Hardware        : BCM2711    ← SoC: микросхема, где процессор, GPIO и память
Model           : Raspberry Pi 4 Model B Rev 1.4
Serial          : 100000004f2b9c1e
```

Ключевая честность этого файла: имя ядра в нём **не написано**. `0xd08` — это Cortex-A72, но узнать это можно только по справочнику (`arch/arm64/include/asm/cputype.h` в исходниках ядра, `lscpu` в util-linux). Наизусть номера не помнит никто — их смотрят, и это нормальный рабочий навык, а не пробел в знаниях.

### `/proc/device-tree` — что ядро знает о железе

На x86 железо само себя перечисляет: шина PCI отвечает на опрос, и ядро находит устройства. На ARM опрашивать некого — там нет самоописывающей шины. Поэтому ядру дают **дерево устройств** (device tree): заранее составленное описание «что на плате есть и по каким адресам».

```
/proc/device-tree/model                        = Raspberry Pi 4 Model B Rev 1.4
/proc/device-tree/soc/gpio@7e200000/status     = okay
/proc/device-tree/soc/spi@7e204000/status      = disabled
```

`status` — это выключатель узла. `disabled` означает, что драйвер к устройству даже не подойдёт: для системы его нет. Отсюда классический embedded-вечер: датчик подключён верно, провода звонятся, а шина молчит — потому что её узел выключен **в описании**, и паяльник тут ни при чём.

### `compatible` — от частного к общему

```
compatible = "raspberrypi,4-model-b", "brcm,bcm2711"
              └ самое частное             └ самое общее
```

Список читается слева направо: сначала конкретная плата, затем семейство. Ядро ищет драйвер по первому совпадению и, не найдя, отступает к более общему. Смысл — новая плата на знакомом SoC работает сразу: частной строки драйвер не знает, общую знает.

Это седьмая по счёту семантика чтения в курсе, и она снова своя: `sshd_config` — побеждает первое вхождение, `sudoers` — последнее правило, `.gitignore` — последний шаблон, а `compatible` — **самое частное совпадение**. Общего правила нет; правило каждый раз читают в документации формата.

### Архитектура: где собираешь ≠ где запускаешь

```
ноутбук:  x86_64      gcc -dumpmachine → x86_64-linux-gnu
плата:    aarch64     нужен            → aarch64-linux-gnu-gcc
```

`file build/collector` показывает `ELF 64-bit LSB executable, x86-64` — файл собран под ноутбук. Плата не поймёт ни одной его инструкции: набор команд другой. Отсюда `Exec format error` — сообщение не про права и не про библиотеки, а про язык.

Лекарство — **кросс-компиляция**: компилятор работает на x86_64, а машинный код выпускает для aarch64. Префикс `aarch64-linux-gnu-` перед именем инструмента — это и есть «собери не для себя».

Про `lscpu`, `/proc/device-tree/chosen`, overlay дерева устройств, `dtc`, `qemu-user` и sysroot — в [`theory.md`](theory.md).

## Проверка: LILITH задаёт вопросы

**LILITH:** *«`chmod +x` стоит, файл на месте, а в ответ „Exec format error". Что не так?»*

<details>
<summary>Подумай 30 секунд</summary>

Не так — архитектура. Ядро прочитало заголовок ELF, увидело `x86-64` и отказалось: у процессора платы (aarch64) другой набор инструкций, исполнять этот файл физически нечем.

Права тут ни при чём — их проверяют до заголовка, и они прошли. Библиотеки тоже: до динамического компоновщика дело не дошло, файл отвергнут раньше. `file` на бинарнике и `uname -m` на плате отвечают на вопрос за две команды.

Отсюда рефлекс embedded-разработчика: **при непонятной ошибке запуска первым делом сравни архитектуру файла и машины.** На сервере они совпадают всегда, поэтому там об этом не думают. Здесь — не совпадают по умолчанию.
</details>

**LILITH:** *«Датчик припаян правильно, а шины SPI в системе нет. Куда смотреть до паяльника?»*

<details>
<summary>Ответ</summary>

В дерево устройств: `status` узла `spi@`. Если там `disabled`, драйвер к устройству не подойдёт — для системы шины не существует, сколько ни перепаивай.

Логика та же, что у выключенной службы: юнит есть, файл настроен, но `systemctl` его не запускал — значит, ничего не работает. Устройство в дереве со `status = disabled` — это ровно «описание есть, устройство выключено».

Отсюда порядок разбора в embedded: **сначала читаем описание, потом трогаем железо.** Проверка `status` стоит десять секунд; перепайка датчика — вечер, и она не поможет, если узел выключен.
</details>

## Разбор типичных ошибок

**Взять архитектуру со своего `uname -m`.** Ноутбук ответит `x86_64` — и это правда о ноутбуке. Про плату спрашивают у платы.

**Прочитать `0xd08` как имя.** Это номер части; имя ядра — из справочника. Значение, добытое по памяти, а не командой, ничем не отличается от догадки.

**Не посмотреть `status` у шины.** `disabled` в дереве объясняет молчание датчика лучше, чем любая проверка проводов.
