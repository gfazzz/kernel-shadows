## II. Теория: три зоны и граф

### Где живёт файл

```
рабочее дерево ──git add──► индекс ──git commit──► история
   (что вижу)              (что войдёт)          (что записано)
```

Три зоны, и `git status` рассказывает про все три сразу. Файл может быть изменён в дереве, при этом в индексе лежать в старой версии, а в истории — в позапрошлой.

```bash
git status              # что где
git diff                # дерево против индекса
git diff --staged       # индекс против истории
git add файл            # дерево → индекс
git commit              # индекс → история
git restore файл        # вернуть из индекса в дерево
git restore --staged ф  # убрать из индекса
```

### Коммит — снимок, а не разница

Каждый коммит хранит **полное состояние дерева** плюс ссылку на родителя. Разницы (`git diff`) вычисляются на лету, сравнением двух снимков.

Отсюда следствия:

- **история — это граф**, а не список: у коммита слияния два родителя;
- **коммит нельзя изменить** — можно только создать новый; хеш зависит от содержимого, включая родителя и дату;
- **удаление файла — тоже коммит**: он записывает, что теперь файла нет. Прошлые снимки при этом не меняются.

Последнее — самое важное на сегодня.

### Чтение истории

```bash
git log --oneline --graph --all     # граф с ветками
git log --format='%h %an %ad %s' --date=short
git log --no-merges                 # без коммитов слияния
git rev-list --count HEAD           # сколько коммитов
git show <хеш>                      # что именно изменилось
git show <хеш>:путь                 # СОДЕРЖИМОЕ файла в том коммите
git log --diff-filter=A -- путь     # когда файл появился
git log --diff-filter=D -- путь     # когда исчез
```

`git rev-list --count` считает честно; `git log | wc -l` считает строки вывода, а не коммиты.

### Ветка — это указатель

Ветка в git — не копия файлов, а **имя для коммита**. `git branch monitoring` создаёт указатель; переключение меняет рабочее дерево на снимок, куда он смотрит.

Отсюда неочевидное: после слияния ветка становится частью основной истории, и `git merge-base main monitoring` вернёт уже не точку расхождения, а вершину ветки. Настоящая точка расхождения — общий предок **двух родителей коммита слияния**.

Про `reflog`, `HEAD~` и `HEAD^`, `git blame` и `git bisect` — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Файл с паролем закоммитили, потом удалили и закоммитили удаление. Пароль в безопасности?»*

<details>
<summary>Подумай 30 секунд</summary>

Нет. Удаление — это новый коммит, говорящий «теперь файла нет». Все прежние снимки остались как были, и содержимое достаётся одной командой:

```bash
git log --all --diff-filter=A -- .env    # где появился
git show <тот коммит>:.env               # что там было
```

Если репозиторий куда-то отправляли, пароль надо считать скомпрометированным и менять. Чистка истории (`filter-repo`) переписывает хеши и не отменяет того, что кто-то уже склонировал.
</details>

**LILITH:** *«`git log --oneline | wc -l` показывает 13, а коллега говорит, что коммитов 12. Кто прав?»*

<details>
<summary>Ответ</summary>

Оба, и вопрос сформулирован неточно. Тринадцать — это все коммиты в текущей ветке; двенадцать — без коммита слияния, который не содержит собственных изменений и только соединяет две линии.

Считать правильнее так:

```bash
git rev-list --count HEAD              # 13
git rev-list --count --no-merges HEAD  # 12
```

`git log | wc -l` — вообще не счётчик коммитов: он считает строки, и при другом формате вывода даст другое число.
</details>

## IV. Задание: прочитать чужую историю

Репозиторий восстанавливается одной командой и получается **побитово одинаковым** при каждом запуске — включая хеши коммитов:

```bash
bash ../data/build_shadow_iac.sh /tmp/shadow_iac
cd /tmp/shadow_iac
```

Артефакт — заполненный `artifacts/history_report.txt`: объём, авторы, опорные точки, точка расхождения ветки — и тот самый неприятный вопрос Ханса.

```bash
cp starter/history_report.txt artifacts/history_report.txt
bash tests/test.sh
```

Вопросы и критерии — в [`mission.md`](mission.md). Один из вопросов требует не найти файл, а **достать его содержимое** из коммита, где его уже нет.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
git log --oneline --graph --all
git rev-list --max-parents=0 HEAD        # корневой коммит
git rev-list --merges -1 HEAD            # коммит слияния
git log --all --oneline --diff-filter=A -- .env
git show <хеш>:.env
```

Короткие хеши — ровно семь символов: `git rev-parse --short=7 <хеш>`.

Эталон — в `solution/`, там же команда над каждым значением.
</details>

### Три ошибки, которые здесь делают

**Считать коммиты через `git log | wc -l`.** Это счётчик строк вывода. При формате по умолчанию каждый коммит занимает несколько строк, при `--oneline` — одну, и совпадение с правильным числом случайно.

**Искать точку расхождения через `git merge-base main monitoring`.** После слияния ветка уже входит в историю main, и команда честно вернёт её вершину. Нужен общий предок двух родителей коммита слияния.

**Решить, что удалённого файла нет.** Он есть — во всех коммитах до удаления. Именно это и делает вопрос Ханса неприятным.

## V. Неприятный вопрос

Ты сдаёшь отчёт. Ханс читает его снизу вверх и останавливается на строке с паролем.

> — Прочитайте вслух.

> — `Sh4dow-Pr0d-2025!`

> — Это пароль от базы операции. Он лежит в репозитории с двадцать пятого октября. Файл удалили на следующий день — вот, вижу коммит. Кто-нибудь менял пароль?

Ты открываешь чат с Дмитрием. Ответ приходит через минуту: «нет, зачем? мы же его удалили».

Ханс кивает так, будто ожидал именно этого.

> — В CCC это называют «удалил и успокоился». Git устроен так, что записанное однажды остаётся. Это его главное достоинство и единственный способ вот так проиграть.

Он берёт маркер и пишет на доске два пункта.

```
1. Секрет, попавший в репозиторий, СКОМПРОМЕТИРОВАН. Менять, не обсуждать.
2. Чистить историю — потом. Сначала поменять.
```

> — И только третьим пунктом — сделать так, чтобы это не повторилось. Этим займёмся послезавтра.

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   История прочитана. Пароль найден там, где его «нет».       │
│                                                              │
│   Дмитрий уже поменял пароль на базе. Осталось понять,       │
│   как не отправить следующий — и что вообще стоит            │
│   проверять до того, как нажмёшь push.                       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
