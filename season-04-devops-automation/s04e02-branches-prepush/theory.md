# Теория — s04e02

## 1. Ветка, которой не было в списке

> *Я две недели делал большую правку. Ветка, тридцать коммитов, всё аккуратно. В пятницу отправил, в понедельник коллега пишет: «а где твои изменения?»*
>
> *`git log` показывал мои коммиты. `git status` говорил «up to date». На сервере их не было.*
>
> *Палыч попросил вывод одной команды:*
>
> ```
> $ git branch -vv
> * feature/parser  a3f19c2 [origin/feature/parser: ahead 30] обработка ошибок
>   main            8b2d4e1 [origin/main] базовая версия
> ```
>
> — Вот. Ты отправил ветку `feature/parser` в ветку `feature/parser`. Коллега смотрит `main`. Всё на месте, просто не там, где он ищет.
>
> *Я не сделал слияние. Мне казалось, что «отправил» и есть «готово».*
>
> — Заметь, что тебя обмануло, — сказал он. — Слова «up to date». Они означают «твоя ветка совпадает с её копией на сервере», и ничего больше. Не «работа доставлена», не «код в проде». Git отвечает ровно на тот вопрос, который ему задали, и вопрос был про одну ветку.
>
> *С тех пор `git branch -vv` — первое, что я набираю, когда что-то «не там». Он показывает все ветки, их копии и расхождение в обе стороны одной таблицей.*

## 2. Что такое ветка

Файл в `.git/refs/heads/` с сорока символами внутри — хешем коммита. Всё остальное следует из этого:

```bash
cat .git/refs/heads/main        # хеш коммита
git rev-parse main              # то же самое
```

- **создать ветку — мгновенно**: записать хеш в новый файл;
- **переключиться** — сменить `HEAD` и привести рабочее дерево к нужному снимку;
- **удалить ветку** — удалить указатель; коммиты остаются (см. `reflog`);
- **отправить ветку** — попросить чужой репозиторий передвинуть его указатель на наш коммит и забрать недостающие объекты.

```bash
git branch -vv                  # все ветки, их копии, расхождение
git switch -c feature           # создать и перейти
git switch -                    # вернуться на предыдущую
git branch -d feature           # удалить слитую
git branch -D feature           # удалить любую
```

## 3. Диапазоны

| Запись | Что означает |
|---|---|
| `A..B` | достижимое из B, кроме достижимого из A |
| `A...B` | симметричная разница: то, что есть только у одного |
| `B --not A` | то же, что `A..B` |
| `--left-right A...B` | с пометкой, с какой стороны коммит |

```bash
git log --oneline main..HEAD          # что уедет при push
git log --oneline HEAD..main          # что я не забрал
git log --left-right --oneline main...HEAD
git diff main...HEAD                  # суммарная разница от точки расхождения
```

**`git diff A..B` и `git diff A...B` — разные вещи.** Две точки сравнивают две вершины напрямую; три точки сравнивают B с **точкой расхождения**, то есть показывают только твои изменения, без чужих. При обзоре ветки почти всегда нужно второе.

## 4. Слияние и перебазирование

```bash
git merge feature               # коммит слияния с двумя родителями
git merge --no-ff feature       # даже если можно просто передвинуть указатель
git merge --squash feature      # все изменения одним коммитом, без истории ветки
git rebase main                 # перенести свои коммиты поверх main
git rebase -i HEAD~5            # переписать последние пять: объединить, переименовать
```

| | Слияние | Перебазирование |
|---|---|---|
| История | сохраняется как была | переписывается |
| Хеши твоих коммитов | те же | **новые** |
| Видно, что была ветка | да | нет |
| Безопасно после отправки | да | **нет** |

Правило: **не перебазировать то, что уже видели другие.** Их копии останутся со старыми хешами, и git при следующем обмене увидит две расходящиеся истории с одинаковым содержимым.

`git rebase -i` перед отправкой — другое дело: свои, ещё никем не виденные коммиты, привести в порядок полезно. «Исправил опечатку», «ещё раз», «точно последний» — не та история, которую стоит хранить годами.

## 5. Конфликты

```
<<<<<<< HEAD
наша версия
=======
их версия
>>>>>>> feature
```

```bash
git status                      # какие файлы в конфликте
git diff                        # что именно расходится
git checkout --ours   файл      # взять свою версию целиком
git checkout --theirs файл      # взять чужую
git add файл                    # пометить разрешённым
git merge --abort               # передумать и вернуться
git rerere                      # запоминать решения повторяющихся конфликтов
```

Конфликт — не поломка, а вопрос: обе стороны изменили одно место. Опасность не в нём, а в том, что маркеры **легко закоммитить**: файл выглядит правдоподобно, а ломается при запуске. Поэтому проверка на `<<<<<<<` входит в любой разумный набор перед отправкой.

## 6. Хуки

```
.git/hooks/pre-commit       перед созданием коммита
.git/hooks/commit-msg       проверка сообщения
.git/hooks/pre-push         перед отправкой
.git/hooks/pre-rebase       перед перебазированием
```

Обычный исполняемый файл, ненулевой код останавливает операцию. Хук получает данные на вход: `pre-push`, например, читает со стандартного ввода строки «локальная ссылка, локальный хеш, удалённая ссылка, удалённый хеш».

**Хуки не отправляются с репозиторием** — каталог `.git/hooks` не версионируется. Варианты обойти это:

```bash
git config core.hooksPath .githooks   # хуки лежат в репозитории и версионируются
pre-commit install                     # менеджер хуков, ставит из конфига
```

Но и это остаётся **локальной** защитой: каждый может отключить у себя, а `git commit --no-verify` пропускает хук вовсе. Настоящая проверка живёт на чужой машине — в конвейере.

## 7. Стратегии ветвления

| Схема | Как устроена | Кому подходит |
|---|---|---|
| trunk-based | одна основная ветка, короткие ветки на день-два | частые выкаты, есть тесты |
| GitHub flow | ветка на задачу → обзор → слияние в main | большинство команд |
| git flow | `develop`, `release/*`, `hotfix/*`, `main` | выпуск версиями, редкие релизы |

Общее у всех работающих схем одно: **в основную ветку не коммитят напрямую**, и в неё попадает только то, что прошло проверку. Остальное — вопрос вкуса и частоты выкатов.

Оборотная сторона длинных веток: чем дольше ветка живёт, тем больше конфликтов при слиянии, и растёт это нелинейно. Ветка на два дня сливается сама; ветка на два месяца сливается неделю.

## 8. Метанавык: защита, которая не требует памяти

Вся эта серия — про одно различие. Есть защита, которая требует, чтобы человек **помнил**: посмотреть перед отправкой, не закоммитить лишнее, проверить ветку. И есть защита, которая **срабатывает сама**: хук, конвейер, правило на сервере.

Первая работает ровно до первого аврала — то есть перестаёт работать именно тогда, когда нужна. Вторая работает всегда, и цена ей — время, потраченное один раз.

Практический критерий, который стоит применять к любому «надо не забыть»: **можно ли это проверить машиной?** Если да — инструкция в голове или в вики означает, что задачу просто не сделали.

И вторая половина того же правила: проверка, которая ругается слишком часто, эквивалентна отсутствию проверки. Её отключат, и это будет рациональным решением. Поэтому диапазон, а не вся история; поэтому предел размера ключом, а не константой; поэтому сообщение с именем файла, а не «найдены проблемы».
