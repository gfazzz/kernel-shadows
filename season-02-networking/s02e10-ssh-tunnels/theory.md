# Теория — s02e10

## 1. Ключ, который ходил без меня

> *На одном проекте у нас был бастион — единственная машина с внешним адресом. Ходить через него в две команды надоедало, и я нашёл «правильное» решение: `ForwardAgent yes`. Теперь ключ был доступен на бастионе, и оттуда я заходил куда угодно одной командой. Красиво.*
>
> *Через месяц безопасник прислал выписку: с бастиона моим ключом заходили на четыре машины в ночь, когда я спал.*
>
> *Бастион был скомпрометирован — не через меня, через старый пакет. Но воспользовались именно моим ключом.*
>
> — Понимаешь, что произошло? — спросил Палыч.
> — Украли ключ.
> — Нет. Ключ у тебя. Никуда он не делся, он и не мог: агент не отдаёт ключ, он подписывает запросы. Ты дал бастиону право **просить подписи**. Пока твоя сессия открыта, root на той машине может подписать что угодно и от твоего имени.
>
> *Он показал разницу на схеме:*
>
> ```
> ForwardAgent yes:  ты → [бастион ← сокет агента]  → цель
>                             ↑ root здесь всё может
> ProxyJump:         ты ────────(шифр)──────────────→ цель
>                             ↑ бастион пересылает байты
> ```
>
> — Второе решает ту же задачу и не задаёт вопроса о доверии. Бастиону нечего доверять.
>
> *С тех пор `ForwardAgent no` стоит у меня в `Host *` первой строкой. А когда проброс агента действительно нужен, он включается для одного хоста и только на время.*

## 2. Четыре направления

| Ключ | В конфиге | Что делает |
|---|---|---|
| `-J` | `ProxyJump` | дойти до цели через посредника |
| `-L` | `LocalForward` | порт у меня → сервис на той стороне |
| `-R` | `RemoteForward` | порт на сервере → сервис у меня |
| `-D` | `DynamicForward` | SOCKS-прокси: весь трафик приложения через сервер |

```bash
ssh -J bastion db
ssh -L 15432:127.0.0.1:5432 db
ssh -R 127.0.0.1:9000:127.0.0.1:3000 devbox
ssh -D 127.0.0.1:1080 moscow
ssh -N -f ...        # -N: не запускать оболочку, -f: уйти в фон
```

**Чей `localhost`?** Это главный источник путаницы:

```
LocalForward  15432 127.0.0.1:5432
              └ у меня  └ с точки зрения СЕРВЕРА

RemoteForward 127.0.0.1:9000 127.0.0.1:3000
              └ на сервере   └ с точки зрения МОЕЙ машины
```

Правило простое: **правая часть всегда разрешается той стороной, где туннель выходит**.

## 3. `ProxyJump` в подробностях

```
Host db
    HostName db.internal
    ProxyJump bastion
```

Что происходит: ssh открывает соединение с `bastion`, просит его установить TCP-соединение до `db.internal:22` и с этого момента гонит через него **свой собственный** зашифрованный сеанс. Ключи проверяются дважды: сначала бастиона, потом цели.

Следствия:

- ключ не покидает вашу машину;
- бастион не видит содержимое сессии;
- работают `scp`, `rsync`, `sftp`, графические клиенты — всё, что умеет ssh;
- цепочки: `ProxyJump bastion,relay` — сколько угодно посредников.

Старая форма `ProxyCommand ssh -W %h:%p bastion` делает то же самое. `-W` появился как раз для этого, а `ProxyJump` — чтобы не помнить синтаксис.

## 4. `~/.ssh/config`: как ssh его читает

```
Host db
    HostName db.internal
    User max

Host *
    User dmitry
```

**Действует ПЕРВОЕ найденное значение каждого параметра.** Блоки просматриваются сверху вниз, `Host *` совпадает с любым именем. Отсюда единственное жёсткое правило: **`Host *` идёт последним.**

Проверка не догадками, а командой:

```bash
ssh -G db                    # ВСЕ эффективные параметры для хоста db
ssh -G db | grep '^user '
ssh -v db                    # что происходит при подключении
```

`ssh -G` не подключается никуда — он только показывает, как ssh разобрал конфигурацию. Это то же, чем `sshd -T` является для серверной стороны.

**Шаблоны в `Host`:** `Host db*`, `Host *.ops.local`, `Host db ops-db` (несколько имён), `Host !prod *` (исключение). Ещё есть `Match` — совпадение по пользователю, адресу, результату команды:

```
Match host db user anna
    IdentityFile ~/.ssh/anna_ops
```

## 5. Настройки клиента, которые стоят своих строк

```
ForwardAgent no            # не давать чужой машине пользоваться вашим ключом
IdentitiesOnly yes         # предлагать только указанный ключ
IdentityFile ~/.ssh/id_ed25519_ops
StrictHostKeyChecking ask  # не молчать при смене ключа сервера
HashKnownHosts yes         # не хранить список машин открытым текстом
ServerAliveInterval 30     # напоминать о себе, чтобы NAT не забыл соединение
ServerAliveCountMax 3      # после трёх неответов — рвать
AddKeysToAgent yes         # добавлять ключ в агент при первом использовании
ControlMaster auto         # переиспользовать одно соединение
ControlPath ~/.ssh/cm-%r@%h:%p
ControlPersist 10m
```

**`IdentitiesOnly yes` важнее, чем кажется.** Без него агент предлагает серверу все известные ключи по очереди — и каждый считается попыткой аутентификации. На сервере с `MaxAuthTries 3` (см. [`s02e09`](../s02e09-ssh-hardening/)) третий ключ обрывает соединение, и вход не проходит при совершенно правильном ключе, лежащем четвёртым.

**`ControlMaster`** переиспользует уже открытое соединение: второй `ssh` к тому же хосту не проходит аутентификацию заново. Экономит секунды на каждой команде — заметно при `rsync` в цикле. Побочный эффект, о котором стоит знать: пока живёт мастер-сокет, изменения в конфиге не применяются.

## 6. Серверная сторона туннелей

```
# sshd_config
AllowTcpForwarding no        # запретить -L и -D вовсе
AllowStreamLocalForwarding no
GatewayPorts no              # -R слушает только localhost (умолчание)
PermitOpen 127.0.0.1:5432    # разрешить -L только к этому адресу
PermitTunnel no
```

`GatewayPorts no` — причина, по которой `RemoteForward` по умолчанию виден только на самом сервере. При `yes` порт открывается на всех интерфейсах, и явное `127.0.0.1:` в конфиге клиента становится единственной защитой.

`AllowTcpForwarding no` на боевом сервере — разумное умолчание: туннели нужны не всем, а сервер с включённым форвардингом легко превращается в прокси для того, кто получил на нём учётную запись.

## 7. Когда туннеля мало

Туннель хорош, когда нужен **один порт** и **на время сессии**. Он плох, когда:

- нужен весь трафик машины, а не отдельные порты;
- соединение должно пережить закрытие ноутбука и подниматься само;
- участников больше двух и им нужно видеть друг друга;
- нужен UDP (SSH переносит только TCP).

Для этого существует VPN — следующая серия. Разница по существу одна: туннель работает **поверх** установленной сессии, а VPN создаёт сетевой интерфейс, для которого весь остальной софт не видит разницы с обычной сетью.

## 8. Метанавык: спрашивать программу, а не файл

`~/.ssh/config` присоединяется к списку файлов, чьё содержимое и чей смысл — разные вещи: `sudoers`, `sshd_config`, unit-файлы systemd, `fstab`. Написанное там читается программой по правилам, которые не очевидны из вида файла, и «первое значение побеждает» — ровно такой случай.

Для каждого такого файла существует команда, отвечающая на вопрос «что программа поняла»:

| Файл | Команда |
|---|---|
| `~/.ssh/config` | `ssh -G хост` |
| `sshd_config` | `sshd -T` |
| `sudoers` | `sudo -l`, `visudo -c` |
| unit systemd | `systemctl show`, `systemctl cat` |
| `fstab` | `findmnt --verify` |
| `logrotate.d/*` | `logrotate -d` |

Привычка проверять этой командой сразу после правки стоит секунды и снимает целый класс ошибок — тех, где файл выглядит правильным и при этом не работает.
