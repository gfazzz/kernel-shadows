# Теория — s02e06

## 1. Как я отрезал себя от сервера в другом городе

> *Мне поручили закрыть тестовый сервер, торчавший в интернет всеми портами. Машина стояла в чужом дата-центре, доступ — только по SSH. Задача на пять минут.*
>
> *Набираю:*
>
> ```console
> $ sudo ufw default deny incoming
> $ sudo ufw enable
> Command may disrupt existing ssh connections. Proceed with operation (y|n)?
> ```
>
> *Читаю предупреждение. Думаю: «ну да, может разорвать, ничего страшного, переподключусь». Нажимаю `y`.*
>
> *Сессия висит. Переподключение — таймаут. Пинг идёт, порт закрыт. Правило `allow 22` я собирался добавить следующей командой.*
>
> *Дата-центр в трёхстах километрах. IPMI не настроен. Ждал до утра, пока дежурный подключит консоль.*
>
> *Палыч, когда я рассказал, не стал объяснять про порядок команд — я его уже выучил самым надёжным способом. Он спросил другое:*
>
> — Что ты сделал, когда прочитал предупреждение?
> — Согласился.
> — Ты его прочитал или посмотрел на него? Там написано ровно то, что произошло. Оно даже спросило разрешения.
>
> *Потом показал приём, который стоило знать до, а не после:*
>
> ```console
> $ echo 'ufw --force reset && ufw allow 22/tcp && ufw enable' | at now + 10 minutes
> ```
>
> — Ставишь себе откат заранее. Проверил, что связь жива, — отменил задание. Не проверил, потому что связи уже нет, — правила откатятся сами. Это стоит одну команду и покрывает весь класс ошибок, где ты рубишь сук, на котором сидишь.
>
> *С тех пор перед любым изменением, которое может отрезать доступ — фаервол, sshd, сеть, — я сначала ставлю таймер отката. Ни разу не понадобился. Именно поэтому и продолжаю.*

## 2. Как пакет проходит через фильтр

Ядро Linux фильтрует пакеты в точках, привязанных к пути пакета:

```
                 ┌── FORWARD ──┐        (транзит: маршрутизация)
входящий → PREROUTING          POSTROUTING → исходящий
                 └── INPUT → [процесс] → OUTPUT ─┘
```

| Цепочка | Через неё идёт |
|---|---|
| `INPUT` | пакеты, адресованные этой машине |
| `OUTPUT` | пакеты, порождённые этой машиной |
| `FORWARD` | транзитные — актуально для роутеров, шлюзов и Docker |
| `PREROUTING` / `POSTROUTING` | таблица `nat`: DNAT-проброс и SNAT/маскарад |

У каждой цепочки есть **политика по умолчанию** и упорядоченный список правил. Правила проверяются сверху вниз, срабатывает первое подошедшее — поэтому позиция правила важна не меньше его содержания. `-A` добавляет в конец, `-I` вставляет в начало.

**Состояние соединения.** Современные наборы правил не разрешают трафик в обе стороны вручную, а полагаются на отслеживание соединений:

```bash
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
```

Одно это правило пропускает все ответы на исходящие соединения, и дальше остаётся разрешить только новые входящие для нужных портов. Без него «исходящее работает, ответы не приходят» — самая частая загадка первого дня.

## 3. `ufw`: команды, которые нужны

```bash
sudo ufw status verbose            # правила + политики по умолчанию
sudo ufw status numbered           # с номерами — для удаления
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow from 10.50.0.0/24 to any port 3306 proto tcp
sudo ufw limit 22/tcp              # ограничение частоты новых подключений
sudo ufw deny from 185.220.101.52
sudo ufw delete 3                  # удалить правило №3
sudo ufw --dry-run allow 8080/tcp  # показать, что будет сделано, не делая
sudo ufw reset                     # сбросить всё
```

**`ufw limit`** заслуживает отдельного упоминания: он блокирует адрес, открывший больше шести соединений за тридцать секунд. Для SSH это дешёвая защита от перебора паролей, которая почти не мешает людям.

**`--dry-run`** показывает сгенерированные правила `iptables`, ничего не применяя, — привычка, которая пару раз спасёт.

**Порядок правил в `ufw`** менее очевиден, чем в `iptables`: команда `insert` позволяет задать позицию (`ufw insert 1 deny from …`), и для блокирующих правил это важно — правило `deny`, добавленное после `allow`, не сработает.

## 4. Под капотом: iptables и nftables

```bash
sudo iptables -L -n -v --line-numbers    # что реально в ядре
sudo iptables-save > /etc/iptables/rules.v4
sudo iptables-restore < /etc/iptables/rules.v4
```

Правила `iptables` живут в памяти ядра и **исчезают после перезагрузки** — сохраняет их пакет `iptables-persistent` (или `ufw`, который делает это сам). Ситуация «настроили, забыли сохранить, машина перезагрузилась через полгода» встречается регулярно.

**nftables** — современная замена: одна утилита `nft` вместо семейства `iptables`/`ip6tables`/`arptables`, единый синтаксис, атомарная загрузка набора правил. В большинстве дистрибутивов `iptables` сегодня — это оболочка поверх nftables. Знать `iptables` по-прежнему нужно (его синтаксис в половине документации мира), но новые конфигурации разумно писать на `nft`.

**Docker и `ufw`.** Docker добавляет собственные правила в цепочку `DOCKER-USER` и делает DNAT в `PREROUTING`. Пакет к опубликованному порту контейнера доходит **до** пользовательских правил `ufw` — то есть `ufw deny 5432` не закроет контейнер, запущенный с `-p 5432:5432`. Решения два: публиковать на петлю (`-p 127.0.0.1:5432:5432`) либо писать правила в `DOCKER-USER`. Это классический источник «у нас фаервол настроен, а порт открыт».

## 5. Что ищет аудит правил

| Признак | Почему это плохо |
|---|---|
| политика по умолчанию не `deny` для входящих | всё, что не запрещено явно, разрешено |
| чувствительный порт (3306, 5432, 6379, 27017, 9200, 11211) на `Anywhere` | база данных или кеш доступны из интернета |
| правило без указания порта с `ALLOW Anywhere` | фаервол фактически выключен для этого источника |
| `allow` шире, чем нужно (`0.0.0.0/0` вместо подсети) | лишняя поверхность без причины |
| правила, добавленные «на время отладки» | никто не помнит, зачем они, и никто не решается убрать |
| нет правила `limit` на SSH | перебор паролей ничем не ограничен |

Отдельная строка — **IPv6**. `ufw` управляет обоими стеками, если включён `IPV6=yes` в `/etc/default/ufw`, но правила, написанные напрямую в `iptables`, к IPv6-трафику не относятся вовсе. «Настроили `iptables`, а `ip6tables` пуст» — распространённая и совершенно бесшумная дыра.

## 6. Чего фаервол не умеет

Фаервол фильтрует по адресам, портам и состоянию соединения. Он не знает, что происходит внутри разрешённого соединения, — и потому не защищает от того, что приходит легально:

- запросы к веб-приложению по разрешённому 443 (это уровень WAF и самого приложения);
- перебор паролей в пределах разрешённой частоты (`fail2ban`, ключи вместо паролей — s02e08);
- объёмная атака, забивающая канал до сервера: пакет отбрасывается уже после того, как занял полосу (нужна фильтрация у провайдера);
- всё, что делает уже проникший внутрь.

Отсюда правило: фаервол — необходимый слой, а не достаточный. Он уменьшает поверхность, а не отменяет остальную защиту.

## 7. Метанавык: предусматривать откат

Изменение фаервола относится к классу операций, которые способны отрезать тебя от объекта изменения. В том же классе — правка `sshd_config`, перенастройка сети, обновление ядра, миграция базы.

Признак прост: **если операция может лишить меня доступа к системе, у меня должен быть путь назад, не требующий этого доступа**. Отложенный откат, консоль IPMI, снапшот, второй канал — что-то одно, но заранее.

Это же объясняет, почему инженеры так любят `--dry-run`, `plan` перед `apply` и режим проверки: не из осторожности как черты характера, а потому что цена ошибки в таких операциях измеряется не минутами, а доступностью.
