# s07e02 — теория: манифест и то, что кластер с ним делает

Дополнение к [`README.md`](README.md). Здесь — путь манифеста от файла до подов, единицы измерения, классы обслуживания, устройство `Secret` и поля, которые нельзя поменять.

---

## 1. Что происходит после `kubectl apply`

```
файл ──▶ API-сервер ──▶ etcd ──▶ контроллер Deployment ──▶ ReplicaSet ──▶ Pod
         (проверка,     (запись   (сравнивает желаемое
          умолчания)     факта)    с фактическим)
```

Ключевое: `apply` **не создаёт поды**. Он записывает желаемое состояние. Дальше работает цикл согласования — контроллер бесконечно сравнивает «что должно быть» с «что есть» и устраняет разницу. Поэтому удалённый вручную под возвращается: его никто не воскрешал, просто желаемое состояние не менялось.

Отсюда практическое следствие: **`kubectl apply` возвращает управление раньше, чем что-либо произошло.** «Команда прошла» и «выкат состоялся» — разные события, между ними минуты. Проверять надо `kubectl rollout status`, а не код возврата `apply`.

### Три способа сделать одно и то же

| Способ | Команда | Когда уместен |
|---|---|---|
| императивный | `kubectl create deployment …` | демонстрация, разовый эксперимент |
| императивный по файлу | `kubectl create -f` | ничего не даёт поверх `apply` |
| декларативный | `kubectl apply -f` | всё остальное |

Разница не в удобстве. `apply` запоминает поданную конфигурацию и при следующем применении вычисляет разницу трёх сторон: что было в файле раньше, что в файле теперь, что в кластере. Поэтому удалённое из файла поле исчезает и из кластера — а `create`/`replace` этого не умеют.

Полезная пара команд перед выкатом:

```bash
kubectl diff  -f deployment.yaml     # что изменится
kubectl apply -f deployment.yaml --dry-run=server   # примет ли API-сервер
```

`--dry-run=server` — это тот же режим проверки, что и `--check` у ansible в [`s04e10`](../../season-04-devops-automation/s04e10-ansible-check/): вопрос «что будет, если выполнить» задаётся до выполнения.

## 2. Почему правка шаблона создаёт новый ReplicaSet

Контроллер считает хеш от `spec.template` и добавляет его к именам: `aurora-api-7d4f8b6c9-2xk4l` — здесь `7d4f8b6c9` и есть хеш шаблона. Изменили образ или пределы — изменился хеш — появился новый `ReplicaSet`, и старый остаётся с нулём реплик как точка отката.

```bash
kubectl get rs -n aurora            # видно всю историю шаблонов
kubectl rollout undo deployment/aurora-api
```

Обратное тоже верно и полезно: **правка полей вне `spec.template` нового выката не вызывает.** `replicas` — вне шаблона, поэтому масштабирование не пересоздаёт поды.

## 3. Единицы, в которых легко ошибиться

| Запись | Значение | Ловушка |
|---|---|---|
| `256Mi` | 256 × 1024² = 268 435 456 байт | двоичная приставка |
| `256M` | 256 × 10⁶ = 256 000 000 байт | на 4.6 % меньше, чем `256Mi` |
| `1Gi` | 1024 Mi | |
| `500m` | 0.5 ядра | `m` — милли, не мега |
| `1` (для cpu) | одно ядро | целое без суффикса — ядра |
| `1` (для memory) | **один байт** | самая дорогая опечатка |

Последняя строка — не выдумка: `memory: 1` синтаксически верно, проходит проверку и даёт контейнер, который убивают немедленно. Правило простое: **у памяти всегда пишется суффикс.**

«Одно ядро» в терминах ядра Linux — это квота 100 000 микросекунд процессорного времени на период 100 000 микросекунд (`cfs_quota_us` / `cfs_period_us`). Отсюда и характер троттлинга: не «медленнее в среднем», а «работает первые N миллисекунд каждого стомиллисекундного окна, потом стоит».

## 4. Классы обслуживания и порядок выселения

| Класс | Условие | Когда узел под давлением |
|---|---|---|
| `Guaranteed` | `requests == limits` у всех контейнеров | выселяют последним |
| `Burstable` | `requests` заданы и меньше `limits` | выселяют вторым |
| `BestEffort` | ничего не задано | выселяют первым |

Механика внутри узла: kubelet выставляет процессам `oom_score_adj` по классу, и когда памяти не хватает **узлу целиком**, ядро выбирает жертву по этому счёту. Важное различение:

- **предел контейнера превышен** → убивают именно этот контейнер, `OOMKilled`, событие есть;
- **память кончилась у узла** → выселяют поды по классам, и пострадает не тот, кто виноват.

Второй случай — прямое следствие заниженных `requests`: планировщик поставил на узел больше, чем помещается, потому что ему так сказали.

## 5. `Secret` — это не шифрование

```bash
kubectl get secret aurora-db -o jsonpath='{.data.dsn}' | base64 -d
```

Одна команда, и пароль на экране. `Secret` хранится в `etcd` в base64 — то есть в открытом виде, просто в другой кодировке. Что реально защищает:

| Мера | Что даёт |
|---|---|
| RBAC на `secrets` | не всякий, у кого есть доступ к кластеру, прочитает |
| шифрование `etcd` (`EncryptionConfiguration`) | дамп диска перестаёт быть дампом паролей |
| внешнее хранилище (Vault, внешний оператор) | секрет вообще не лежит в кластере |
| `imagePullSecrets`, монтирование файлом | значение не попадает в `env` и не утекает в дамп процесса |

Чего `Secret` **точно** достигает и ради чего он в этой серии: **значение не лежит в git.** В манифесте остаётся имя ключа, и репозиторий можно показывать кому угодно. Та же мысль, что в [`s04e03`](../../season-04-devops-automation/s04e03-gitignore-secrets/), только средством кластера.

Отдельная тонкость: переменная окружения из `Secret` видна в `/proc/PID/environ` и попадает в дампы. Монтирование секрета файлом безопаснее — но требует, чтобы приложение умело читать файл. `aurora-api` не умеет, и это честная причина оставить `env`.

## 6. Именованные порты

```yaml
ports:
  - name: http
    containerPort: 8080
probes:
  httpGet: { port: http }
```

Порт можно указывать именем. Смысл появляется в `s07e03`: `Service` ссылается на `targetPort: http`, и смена номера порта в приложении правится **в одном месте** — в манифесте контейнера. Пока порт записан числом, он записан числом в четырёх местах, и однажды они разойдутся.

## 7. Поля, которые нельзя изменить

`spec.selector` у `Deployment` — неизменяемое поле. Попытка правки даёт отказ API-сервера, и лечится только пересозданием объекта.

Причина не в капризе. Селектор определяет, какими подами объект владеет. Разрешить его правку — значит разрешить `Deployment` в один момент забыть свои поды (они останутся сиротами и никем не будут управляться) и присвоить чужие. Ошибка была бы неисправимой, поэтому её сделали невозможной.

Практический вывод: **метки и селектор придумываются один раз и надолго.** Минимальный разумный набор — `app`, `component`, `version`, `part-of`; общепринятые имена — `app.kubernetes.io/*`.

## 8. Масштабирование: `replicas`, HPA и спор с тюнингом

`replicas` в манифесте — число, назначенное человеком. Горизонтальный
автомасштабировщик (`HorizontalPodAutoscaler`) назначает его сам, по
наблюдаемой величине:

```yaml
minReplicas: 3
maxReplicas: 12
metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

Занятость считается **в долях от `requests`**, а не от мощности узла. Отсюда
первое следствие, ломающее интуицию: занизив `requests`, ты получаешь
автомасштабирование, срабатывающее раньше, чем нужно, а завысив — не
срабатывающее вовсе. Автомасштабировщик у пода без `requests` не работает
никак, потому что делить не на что.

Второе следствие важнее и связывает эту серию с
[`s07e10`](../s07e10-tuning/): **автомасштабирование лечит не всякую
нагрузку.** Оно помогает, когда узкое место — процессор в самом приложении,
и не помогает, когда оно снаружи: пул соединений к базе, блокировка,
единственный диск. Добавив поды к исчерпанному пулу, ты получаешь больше
ожидающих на том же пуле — и ту же задержку при вдвое большем счёте.

| Что происходит | Помогает ли HPA |
|---|---|
| процессор приложения в потолке | да |
| очередь запросов растёт при свободном процессоре | нет, ищи внешнее ограничение |
| память течёт | нет, лечится исправлением |
| база на пределе | нет, станет хуже |

Отсюда правило, к которому сезон возвращается дважды: **сначала измерение,
потом изменение.** Автомасштабирование — такой же ответ на измеренное узкое
место, как правка `sysctl`, и такой же бесполезный без него.

Про интервалы: увеличение числа подов происходит быстро, уменьшение —
с задержкой (по умолчанию пять минут наблюдения), чтобы система не
раскачивалась. Раскачка — типичный отказ автомасштабирования: поды
добавляются, занятость падает, поды убираются, занятость растёт.

Вертикальный автомасштабировщик (VPA) правит не число подов, а `requests`
и `limits`, и потому **пересоздаёт поды**. Одновременно с HPA по той же
величине его не включают: два регулятора на одну величину — это генератор
колебаний.
