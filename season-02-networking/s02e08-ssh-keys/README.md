## II. Теория: как устроен вход по ключу

### Пара ключей

```bash
ssh-keygen -t ed25519 -C "max@shadow-ops"
# → ~/.ssh/id_ed25519      приватный — остаётся у тебя
# → ~/.ssh/id_ed25519.pub  публичный — кладётся на серверы
```

Публичный ключ добавляется в `~/.ssh/authorized_keys` на сервере (проще всего — `ssh-copy-id`). При подключении сервер отправляет случайный вызов, клиент подписывает его приватным ключом, сервер проверяет подпись публичным. Сам приватный ключ по сети не идёт никогда — даже в зашифрованном виде.

Отсюда практическое следствие: перехват соединения не даёт злоумышленнику ничего многоразового. Подпись сделана для одного конкретного вызова и в другом соединении бесполезна.

### Права на файлы — не формальность

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519       # приватный: только владелец
chmod 644 ~/.ssh/id_ed25519.pub   # публичный: читать могут все
```

Если у приватного ключа права шире, SSH **откажется** его использовать и напишет `UNPROTECTED PRIVATE KEY FILE`. Это не придирка: ключ, который может прочитать другой пользователь системы, уже нельзя считать своим.

Права слетают чаще всего при копировании — через архив без сохранения атрибутов, через общую папку, через сеть. Поэтому первое, что проверяют при загадочном «ключ не подходит», — не сам ключ, а его режим доступа.

### Какой тип выбрать

| | ed25519 | RSA 4096 | DSA |
|---|---|---|---|
| длина | короткая | длинная | короткая |
| скорость | высокая | ниже | — |
| стойкость | высокая | высокая | **недостаточная** |
| поддержка | OpenSSH 6.5+ (2014) | везде | отключён в новых версиях |

Правило простое: `ed25519` по умолчанию, `RSA 4096` — если на той стороне что-то очень старое, `DSA` — заменить немедленно.

Про `~/.ssh/config`, агент ключей, парольные фразы и `authorized_keys` — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Скопировал ключи на новую машину, и `ssh` пишет `UNPROTECTED PRIVATE KEY FILE`. Что произошло?»*

<details>
<summary>Подумай 20 секунд</summary>

При копировании потерялись права: файл стал доступен для чтения группе или всем (`644`, `664`). SSH намеренно отказывается использовать такой ключ — не потому, что что-то уже случилось, а потому, что гарантия единоличного владения нарушена.

Лечится `chmod 600 ~/.ssh/id_ed25519`. И стоит помнить, что каталог `~/.ssh` тоже проверяется — ему нужен режим `700`.
</details>

**LILITH:** *«Чем ключ лучше пароля, если SSH и так шифрует соединение?»*

<details>
<summary>Ответ</summary>

Тем, что секрет не покидает клиента. Пароль передаётся внутри защищённого канала — и достаточно одной ошибки (фишинговая страница, скомпрометированный сервер, введённый не туда пароль), чтобы он оказался у чужого. Приватный ключ не передаётся вообще: по сети идёт подпись, действительная ровно для одного вызова.

Плюс арифметика: пароль человек придумывает и запоминает, поэтому его энтропия невелика. Ключ ed25519 не подбирается перебором ни при каких вычислительных ресурсах.

И главное — при переходе на ключи парольный вход на сервере можно **отключить совсем**, и тогда перебор паролей перестаёт быть угрозой в принципе. Это следующая серия.
</details>

## IV. Задание: проверить свои ключи

Собери `ssh_key_check.sh` — проходит по каталогу ключей и проверяет права и тип:

```
  ✓ id_ed25519 — права 600 (ок)
     тип: ed25519 (рекомендуется)
  ⚠️ id_rsa — права 644 (НЕБЕЗОПАСНО, нужно 600)
     тип: rsa (ок для старых серверов; ed25519 лучше)
---
Ключей проверено: 3 | Проблем: 2
```

```bash
cp starter/ssh_key_check.sh artifacts/ssh_key_check.sh
# заменить TODO (права через stat + тип по имени)
bash artifacts/ssh_key_check.sh ~/.ssh
bash tests/test.sh
```

ТЗ и критерии — в [`mission.md`](mission.md). Фикстура теста содержит ключ с правильными правами, ключ с `644`, устаревший `id_dsa`, публичные ключи и посторонние файлы — всё это надо различать. Проверка прав делается кроссплатформенно: у `stat` разные флаги в Linux и macOS.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
perm_of() { stat -c '%a' "$1" 2>/dev/null || stat -f '%Lp' "$1" 2>/dev/null; }

for key in "$keydir"/id_*; do
    [ -f "$key" ] || continue
    case "$key" in *.pub) continue ;; esac
    perm="$(perm_of "$key")"
    [ "$perm" = "600" ] || [ "$perm" = "400" ] || issues=$((issues+1))
done
```

`stat -c` — GNU, `stat -f` — BSD и macOS; пара с `||` покрывает обе системы. Эталон — в `solution/`, открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Считать `.pub` приватным ключом.** Публичный ключ обязан быть доступен для чтения — на то он и публичный. Аудит, требующий от него `600`, выдаёт предупреждение на каждую машину и тем самым обесценивает настоящие предупреждения.

**Считать «строже — лучше» без границы.** `400` (только чтение владельцем) не хуже `600` — SSH принимает оба. А вот `000` или каталог `~/.ssh` с правами `777` — это уже другая проблема, и её стоит замечать отдельно.

**Использовать `stat` в одном варианте.** `stat -c '%a'` работает в Linux и падает на macOS, `stat -f '%Lp'` — наоборот. Скрипт, который «работает у меня», в чужой среде выдаст пустые права и объявит все ключи безопасными.

## V. Три из семи

Ты прогоняешь проверку на своей машине, потом — на общей, куда команда складывала ключи для отладки.

Из семи приватных ключей у трёх права `644`. Один из них — тот, которым Дмитрий заходит на прод, и лежит он на машине, где есть учётные записи ещё двух человек.

> — Я его туда копировал через архив, — говорит Дмитрий, посмотрев вывод. — В tar права сохраняются, а я его через веб-интерфейс перекладывал.
> — Ключ считаем скомпрометированным, — отвечает Алекс. — Не потому, что кто-то его взял. Потому что мы не можем доказать, что не взял.

К обеду вся команда перевыпускает ключи: `ed25519`, парольные фразы, старые публичные ключи вычищены из `authorized_keys` на всех серверах.

Виктор подводит итог совещания:

> — Ключи есть. Но сервер по-прежнему принимает пароли и пускает root напрямую. Пока это так, наши ключи — просто более удобный способ входа, а не защита.
