## 2. `xargs`: зачем он вообще нужен

Команды делятся на те, что читают **стандартный ввод**, и те, что принимают **аргументы**:

```bash
echo "nginx" | apt install       # НЕ работает: apt не читает stdin
echo "nginx" | xargs apt install # работает: xargs превратил строку в аргумент
```

`xargs` читает вход, режет его по пробелам и переводам строк и запускает команду, подставив полученное аргументами. Если аргументов слишком много для одного вызова (лимит `ARG_MAX`, обычно порядка двух мегабайт), он сам разобьёт их на несколько запусков.

| Флаг | Действие |
|---|---|
| `-n N` | не более N аргументов за вызов |
| `-I {}` | подставлять каждый аргумент в место `{}` (подразумевает `-n 1`) |
| `-P N` | до N параллельных процессов |
| `-r` | не запускать команду на пустом входе (GNU; на BSD поведение по умолчанию) |
| `-0` | разделитель — нулевой байт |
| `-t` | печатать команду перед выполнением — удобно для отладки |
| `-p` | спрашивать подтверждение на каждый запуск |

**Про пробелы в именах.** По умолчанию `xargs` считает разделителями пробелы, табуляции и переводы строк, а ещё разбирает кавычки — поэтому файл `отчёт за март.pdf` превратится в три аргумента. Каноническое решение — пара `-print0` / `-0`:

```bash
find . -name '*.log' -print0 | xargs -0 rm --
```

**Про `-P`.** Параллельный запуск ускоряет независимые операции (проверить сто хостов, сжать двести файлов), но перемешивает вывод и не годится там, где важен порядок или где команда меняет общее состояние. `apt` в несколько процессов запускать нельзя: база `dpkg` заблокирована одним из них, остальные упадут.

**Альтернатива — `find -exec`:**

```bash
find . -name '*.tmp' -exec rm {} \;   # по одному вызову на файл
find . -name '*.tmp' -exec rm {} +    # накопить аргументы, как xargs
```

Форма с `+` делает ровно то же, что `xargs`, и не требует конвейера. Форма с `\;` медленнее, но полезна, когда команде нужен ровно один файл.

## 3. Одна транзакция против N

Разница между `xargs apt install pkg1 pkg2 pkg3` и циклом — это разница между одной операцией и тремя.

`apt` за один вызов: читает индексы, строит граф зависимостей для **всех** запрошенных пакетов сразу, разрешает конфликты между ними, скачивает всё необходимое, распаковывает и настраивает в правильном порядке, при ошибке откатывается к согласованному состоянию.

Цикл делает это по разу на пакет. Последствия: время (граф строится N раз), блокировка (`/var/lib/dpkg/lock` берётся и отпускается N раз, а параллельный `unattended-upgrades` может вклиниться между), и главное — промежуточные состояния. Сбой на седьмом пакете из двенадцати оставляет систему в положении, которого нет ни в одном плане.

Та же логика дальше: один `INSERT` на тысячу строк вместо тысячи, одна декларация Ansible вместо серии команд, один `apply` вместо серии правок. Групповая операция не только быстрее — она атомарнее.

## 4. Что делает отчёт отчётом

**Шапка.** Дата и время запуска, машина, архитектура (`dpkg --print-architecture`), какой манифест проверялся. Без этого через месяц отчёт — просто список слов.

**Различимые состояния.** Установлен, отсутствует, установлен другой версии — три разные ситуации, и последняя часто важнее первых двух. Отчёт, где есть только «да» и «нет», прячет самый интересный случай.

**Итог, который считается по результатам.** Счётчик увеличивается там же, где принимается решение, — внутри ветки проверки. Любой другой источник числа (длина списка, `wc -l` манифеста) рано или поздно разойдётся с реальностью.

**Следующее действие.** Хороший отчёт заканчивается не диагнозом, а командой, которую можно выполнить. Строка `… | xargs sudo apt install -y` в конце превращает документ из наблюдения в инструмент.

## 5. Группировка и подоболочки — ещё раз

```bash
{ ... } > report.txt      # текущая оболочка: переменные переживут блок
( ... ) > report.txt      # ПОДОБОЛОЧКА: изменения переменных потеряются
```

Это та же ловушка, что с `cat file | while read`, в третьем за сезон обличье. Правило, которое стоит запомнить не как список случаев, а как принцип: **всё, что bash запускает в отдельном процессе — конвейер, круглые скобки, подстановка команд `$( )` — получает копию переменных, а не их самих.**

Отсюда же, почему счётчики в капстоуне работают: фигурные скобки — это группировка, а не процесс.

## 6. Идемпотентность: почему повтор должен быть безопасен

`apt install nginx` на машине, где nginx уже стоит, ничего не сломает — он сообщит «уже новейшая версия» и выйдет с нулевым кодом. Это свойство называется идемпотентностью: повторное применение операции не меняет результат.

Оно важнее, чем кажется. Скрипт установки запустят повторно — по ошибке, после сбоя, на новой машине из того же списка. Операция, безопасная только с первого раза, превращает каждый повтор в риск, и в итоге ею перестают пользоваться.

Проверка «сначала посмотреть, чего не хватает» из прошлой серии — ручной способ добиться того же. Ansible в Season 4 сделает это моделью: там описывают желаемое состояние, а не действия, и повтор по определению безопасен.

## 7. Метанавык сезона: инструменты вместо действий

Четырнадцать серий назад терминал был местом, где вводят команды по одной. Сейчас каждая серия оставляла после себя не действие, а вещь: скрипт проверки, монитор с журналом, фильтр, анализатор, отчёт.

Общее у них одно — их можно запустить второй раз. Это и есть граница между тем, кто пользуется системой, и тем, кто её администрирует: первый решает задачу, второй оставляет после себя то, чем задачу решат снова, включая его самого через полгода, когда он всё забудет.

Дальше масштаб растёт — сети, серверы, конфигурации, инфраструктура как код, — но движение остаётся тем же: сделал дважды — оформи как инструмент.
