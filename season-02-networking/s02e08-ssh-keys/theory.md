# Теория — s02e08

## 1. Ключ, который лежал в общей папке

> *Небольшая компания, общий сервер сборки. Чтобы не вводить пароли, деплой ходил на прод по ключу. Ключ лежал в домашнем каталоге технической учётки, права — `644`, потому что «иначе скрипт от другого пользователя его не читает».*
>
> *Работало год. Потом уволился человек, у которого был доступ к той машине, и служба безопасности задала вопрос: что он мог унести.*
>
> *Я честно ответил: приватный ключ от прода. Он мог его просто прочитать — команда `cat`, никаких прав root.*
>
> — И что, он его взял? — спросили меня.
> — Не знаю.
>
> *Вот это «не знаю» и стало ответом. Ключ пришлось считать скомпрометированным, перевыпускать, чистить `authorized_keys` на всех машинах, разбираться, где он ещё был прописан. Три дня работы из-за одной цифры в правах.*
>
> *Палыч потом сформулировал так:*
>
> — Права на приватном ключе — это не защита от злоумышленника. Злоумышленник может и не появиться. Это способ **иметь возможность утверждать**, что ключ не читал никто, кроме владельца. Как только права шире `600`, ты этой возможности лишаешься навсегда — независимо от того, случилось что-нибудь или нет.
>
> — А если скрипту от другого пользователя правда нужен доступ?
> — Значит, у скрипта должен быть свой ключ. Один ключ — один субъект. Ключ, который знают двое, — это не ключ, а пароль, и притом длинный.
>
> *С тех пор `chmod 600` для меня не про SSH, а про способность отвечать на вопрос «кто мог».*

## 2. Что происходит при подключении

1. Клиент и сервер согласуют алгоритмы и создают общий сеансовый ключ (Диффи–Хеллман). Всё дальнейшее уже шифруется.
2. Сервер предъявляет свой **хостовый ключ**; клиент сверяет его с `~/.ssh/known_hosts`. Именно здесь возникает вопрос «продолжить подключение?» при первом входе.
3. Клиент сообщает, каким публичным ключом хочет аутентифицироваться.
4. Сервер ищет его в `~/.ssh/authorized_keys` пользователя и, если находит, посылает случайный вызов.
5. Клиент подписывает вызов приватным ключом; сервер проверяет подпись публичным.

Приватный ключ на этом пути не передаётся ни разу. Подпись действительна только для конкретного вызова, поэтому перехват соединения не даёт ничего пригодного для повторного использования.

**Проверка хостового ключа — не формальность.** Предупреждение `REMOTE HOST IDENTIFICATION HAS CHANGED` означает, что на том адресе отвечает не та машина, что раньше: либо сервер переустановили, либо соединение перехвачено. Отвечать на него привычным удалением строки из `known_hosts` — распространённая и опасная привычка.

## 3. Права и почему SSH так строг

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
chmod 600 ~/.ssh/authorized_keys      # на сервере
chmod 600 ~/.ssh/config
```

SSH проверяет режим приватного ключа и отказывается работать, если он доступен группе или остальным. Причина сформулирована в воспоминании выше: доказуемость единоличного владения.

Отдельная тонкость на сервере: `sshd` при `StrictModes yes` (значение по умолчанию) отказывается читать `authorized_keys`, если домашний каталог пользователя или сам `~/.ssh` доступны на запись группе. Симптом — «ключ не работает, в логах ничего внятного»; лечится `chmod go-w ~ && chmod 700 ~/.ssh`.

| Файл | Режим | Почему |
|---|---|---|
| `~/.ssh` | 700 | никто другой не должен видеть содержимое |
| приватный ключ | 600 или 400 | доказуемое единоличное владение |
| публичный ключ | 644 | он и должен быть публичным |
| `authorized_keys` | 600 | чужая запись = добавление своего ключа |
| домашний каталог | без `w` для group/other | иначе `StrictModes` заблокирует вход |

## 4. Типы ключей

**ed25519** — эллиптическая кривая Curve25519, ключ 256 бит, подпись быстрая, реализация устойчива к целому классу ошибок по побочным каналам. Поддерживается с OpenSSH 6.5 (2014). Выбор по умолчанию.

**RSA** — при длине 3072 или 4096 бит остаётся стойким; нужен, когда на той стороне древний сервер или устройство. Ключи 1024 бит считаются небезопасными.

**ECDSA** — работает, но кривые NIST вызывают меньше доверия в сообществе, и генератор подписи чувствителен к качеству случайности.

**DSA** — 1024 бита, отключён по умолчанию начиная с OpenSSH 7.0. Если такой ключ найден, его не чинят, а заменяют.

**Парольная фраза.** `ssh-keygen` предлагает её задать, и это второй фактор: файл ключа без фразы бесполезен. Цена — необходимость вводить её при каждом использовании, что решается агентом:

```bash
eval "$(ssh-agent -s)"          # запустить агент
ssh-add ~/.ssh/id_ed25519       # ввести фразу один раз за сессию
ssh-add -l                      # какие ключи загружены
ssh-add -D                      # выгрузить все
```

Агент хранит расшифрованный ключ в памяти процесса. Отсюда предостережение про **проброс агента** (`ssh -A`): на промежуточном сервере root может воспользоваться твоим агентом, пока сессия открыта. Вместо `-A` современный способ — `ProxyJump`.

## 5. `~/.ssh/config` — рабочая конфигурация

```
Host shadow
    HostName 10.50.1.2
    User max
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

Host *.ops.internal
    User max
    ProxyJump bastion

Host bastion
    HostName bastion.example.com
    User max
    IdentityFile ~/.ssh/id_ed25519
```

Теперь `ssh shadow` заменяет длинную команду, а машины во внутренней сети доступны через бастион одной строкой конфигурации, без ручных туннелей.

**`IdentitiesOnly yes`** стоит упомянуть отдельно: без него клиент предлагает серверу все ключи из агента по очереди, и при большом их числе сервер разрывает соединение по превышению попыток аутентификации. Ошибка выглядит как «слишком много неудачных попыток», хотя нужный ключ есть.

## 6. Управление ключами в команде

Ключ — не файл, а **отношение**: «этот субъект имеет доступ к этим машинам». Отсюда практики, которые начинают иметь смысл с третьего человека в команде:

- **Один ключ — один субъект.** Общий ключ на команду лишает возможности понять, кто именно заходил, и делает отзыв доступа коллективной проблемой.
- **Отдельные ключи для автоматизации,** с ограничениями прямо в `authorized_keys`: `command="..."`, `no-port-forwarding`, `from="10.50.0.0/24"` — ключ, который умеет только одно и только с одного адреса.
- **Инвентаризация.** Список `authorized_keys` на серверах устаревает молча: люди уходят, ключи остаются. Регулярная сверка с актуальным списком сотрудников — то же по смыслу, что сверка портов и правил фаервола.
- **Сертификаты SSH** — следующая ступень для больших инфраструктур: удостоверяющий центр подписывает ключи с ограниченным сроком, и `authorized_keys` на машинах вообще не нужен.

## 7. Метанавык: доказуемость важнее факта

История с ключом в общей папке закончилась перевыпуском не потому, что кража доказана, а потому, что её **невозможно исключить**. Три дня работы стоила не утечка, а неопределённость.

Отсюда способ смотреть на безопасность, который экономит много времени: строить систему так, чтобы после инцидента можно было ответить на вопрос «что именно скомпрометировано» коротким списком, а не словами «непонятно, надо менять всё».

Права на файлы, отдельные ключи на субъект, ограниченные права автоматизации, журналы с метками времени (s01e09) — всё это работает не на предотвращение, а на **локализацию**. Предотвратить удаётся не всегда; ограничить область последствий — почти всегда.
