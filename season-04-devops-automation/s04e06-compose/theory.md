## 2. Из чего состоит файл

```yaml
services:      # что запускать
networks:      # кто кого видит
volumes:       # что переживает пересоздание контейнера
secrets:       # что не должно лежать в тексте
configs:       # то же для несекретных файлов
```

Ключ `version:` относился к схеме v1–v2 и **с 2020 года игнорируется**; современный compose печатает предупреждение. Имя файла — `compose.yaml` (старое `docker-compose.yml` тоже читается).

```bash
docker compose config            # эффективная конфигурация после всех подстановок
docker compose config --services
docker compose up -d
docker compose ps                # STATUS: Up против Up (healthy)
docker compose logs -f collector
docker compose down              # остановить; тома НЕ удаляются
docker compose down -v           # и тома тоже
```

`docker compose config` — та же команда «что программа поняла», что `ssh -G` и `systemctl show`. На ней же видно, что подстановка `${VAR}` уже произошла: секрет, спрятанный в переменную, печатается открытым текстом.

## 3. Сеть

Compose создаёт для проекта сеть и поднимает в ней резолвер: **имя службы разрешается в адрес контейнера**. `collector` обращается к `db:5432` — и всё.

```yaml
networks:
  backend:
    internal: true      # без маршрута наружу
  frontend:
services:
  db:
    networks: [backend]
  collector:
    networks: [backend, frontend]
```

| Что | Зачем |
|---|---|
| `internal: true` | служба не может обратиться в интернет вовсе |
| несколько сетей у службы | разделение «кто с кем говорит» |
| `ports` | публикация **наружу хоста**, не для связи между контейнерами |

**`ports` и `expose` — разные вещи.** `expose` документирует порт внутри сети (и ничего не делает); `ports` открывает его на хосте.

```yaml
ports:
  - "5432:5432"             # на всех интерфейсах хоста
  - "127.0.0.1:8080:8080"   # только локально
```

Первая форма означает «в интернете», если у машины белый адрес. Это то же самое различие, что `RemoteForward` с явным `127.0.0.1:` в [`s02e10`](../../season-02-networking/s02e10-ssh-tunnels/).

## 4. Данные

```yaml
services:
  db:
    volumes:
      - db_data:/var/lib/postgresql/data     # именованный том
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro   # bind, только чтение
volumes:
  db_data:
```

| Вид | Живёт | Когда применять |
|---|---|---|
| именованный том | до `down -v` | данные служб |
| bind-монтирование (`./путь:/путь`) | как файл на хосте | конфигурации, разработка |
| `tmpfs` | до остановки контейнера | временные файлы при `read_only` |
| ничего | до удаления контейнера | **никогда для данных** |

Без тома данные лежат в записываемом слое и исчезают при `docker compose down`. Bind-монтирования стоит помечать `:ro`, если запись не нужна: это единственное место, где контейнер может испортить файлы хоста.

## 5. Секреты

```yaml
services:
  db:
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
secrets:
  db_password:
    file: ./secrets/db_password
```

Файл монтируется в `/run/secrets/` внутри контейнера. Официальные образы понимают пару `*_FILE` именно для этого.

Почему не `environment` напрямую: значение печатают `docker inspect` и `docker compose config`, оно видно в `/proc/PID/environ` на хосте и попадает в журналы при старте. Подстановка `${DB_PASSWORD}` из `.env` не помогает — она разворачивается до всего перечисленного.

## 6. Порядок и готовность

```yaml
db:
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U ops -d ops"]
    interval: 10s
    timeout: 3s
    retries: 5
    start_period: 30s
collector:
  depends_on:
    db:
      condition: service_healthy
```

| Условие | Что означает |
|---|---|
| `service_started` | контейнер запущен (умолчание для списка) |
| `service_healthy` | healthcheck успешен |
| `service_completed_successfully` | контейнер завершился с кодом 0 (для миграций) |

`start_period` — время, в течение которого неудачи healthcheck не считаются: база может подниматься полминуты, и всё это время «не готова» — нормально.

Третий вариант, самый честный: **повтор подключения в приложении**. Никакой оркестратор не гарантирует порядок навсегда, и в Kubernetes `depends_on` нет вовсе.

## 7. Ограничение контейнера

```yaml
user: "10001:10001"
read_only: true
tmpfs: [/tmp]
cap_drop: [ALL]
cap_add: [NET_BIND_SERVICE]     # если нужен порт ниже 1024
security_opt: ["no-new-privileges:true"]
deploy:
  resources:
    limits: {cpus: "0.50", memory: 256M}
```

Тот же набор понятий, что `User=`, `ProtectSystem=strict`, `CapabilityBoundingSet=`, `MemoryMax=` в юните systemd из [`s03e05`](../../season-03-system-administration/s03e05-systemd-service/) — механизм в обоих случаях один (cgroups и capabilities ядра), меняется только синтаксис.

Чего не делают никогда:

- **`privileged: true`** — отключает почти всю изоляцию разом;
- **`- /var/run/docker.sock:/var/run/docker.sock`** — через сокет можно запустить контейнер с примонтированным корнем хоста, то есть это выдача root на машине;
- **`network_mode: host`** без веской причины — контейнер получает сеть хоста целиком.

## 8. Метанавык: умолчания пишет кто-то другой

История из начала — не про невнимательность. Строку `ports: "5432:5432"` пишут, потому что она стоит в первом примере документации, а задача звучала как «подключиться с ноутбука».

Умолчания в декларативных файлах — это **чужие решения, принятые заранее**, и почти всегда в пользу «чтобы заработало у всех», а не «чтобы было безопасно у вас»:

| Умолчание | Что означает на самом деле |
|---|---|
| `ports: "N:N"` | слушать на всех интерфейсах |
| `depends_on: [x]` | ждать контейнер, а не службу |
| нет `volumes` | данные исчезнут при `down` |
| нет `user` | root внутри контейнера |
| нет `restart` | после перезагрузки не поднимется |
| `latest` | «что окажется завтра» |

Общее у них одно: **умолчание никогда не сообщает о себе**. Файл без строки `user:` выглядит точно так же, как файл, где её обдуманно не поставили.

Отсюда привычка, полезная для всего класса декларативных конфигураций: прочитав готовый пример, спросить не «что здесь написано», а **«чего здесь не написано и что это означает»**. Второй список обычно длиннее первого.
