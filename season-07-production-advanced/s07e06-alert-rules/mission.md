## Обстановка

За месяц — семьдесят четыре срабатывания и три аварии, о которых
мониторинг не сообщил ни разу. Про первую узнали от соседней команды через
полчаса, про вторую из еженедельного отчёта, про третью не узнали вообще.

Действующие правила меряют загрузку процессора и объём памяти — то, чего
пользователь не видит, — и делают это без выдержки, то есть срабатывают на
первой же выборке.

## Приказ

Написать `artifacts/rules.yml`: пять правил, выведенных из разбора
происшествий.

```bash
cp starter/rules.yml artifacts/
bash tests/test.sh
```

| Файл в `data/` | Что в нём |
|---|---|
| `incidents.txt` | три происшествия, наблюдённые значения, согласованные пороги и выдержки |
| `required_alerts.txt` | что обязано быть и какой важности |
| `scrape.txt` | период сбора — отсюда минимальное окно `rate()` |
| `metrics_available.txt` | какие имена метрик существуют в хранилище |
| `promql_keywords.txt` | что именем метрики не является |
| `current_rules.yml` | как выглядит сейчас — не образец |

## Чем добывать

| Что нужно | Как |
|---|---|
| минимальное окно | `scrape_interval × 4` |
| доля ошибок | `sum(rate(…{code=~"5.."}[5m])) / sum(rate(…[5m]))` |
| перцентиль | `histogram_quantile(0.95, sum by (le) (rate(…_bucket[5m])))` |
| перезапуски | `increase(…[15m]) > 3` |
| «цель молчит» | `up{…} == 0` |
| «ряда нет вообще» | `absent(…)` |

## Критерии приёмки

- [ ] Все пять правил из `required_alerts.txt` присутствуют.
- [ ] У каждого задано `expr`, `for`, `labels.severity`, `annotations.summary` и `description`.
- [ ] Выдержки не меньше согласованных в разборе происшествий.
- [ ] Важность совпадает с разбором: будят только по симптомам, видимым пользователю.
- [ ] Пороги — те, что согласованы тикетом AUR-503.
- [ ] Все окна `rate()` не короче четырёх периодов сбора.
- [ ] Числитель и знаменатель доли считаются на одном окне.
- [ ] Все имена в выражениях существуют в `metrics_available.txt`.
- [ ] В `description` есть подстановка `{{ … }}` — дежурный должен увидеть числа.
- [ ] У группы задано имя и `interval`.
- [ ] `bash tests/test.sh` → 49 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep + sed |
| Сеть | не нужна |
| **Prometheus** | **не нужен** |
| `promtool` | не нужен |
| Внешние пакеты | нет |
| Изоляция теста | разбор YAML пишется в `mktemp -d`, данные только читаются |

Тест не сверяет текст с образцом: он берёт пороги и выдержки из
`incidents.txt`, минимальное окно — из `scrape.txt`, список имён — из
`metrics_available.txt`. Отдельно проверяется, что данные не выродились:
что согласованный порог действительно лежит между обычным и аварийным
значением, что в требованиях есть обе важности и что в нынешних правилах
действительно нет ни одной выдержки.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «нет for» | забыта выдержка | без неё будят на первой выборке |
| «выдержка меньше согласованной» | взято круглое число | значения в `incidents.txt` |
| «окна короче 60s» | окно назначено на глаз | `scrape_interval × 4` |
| «в выражении доли N разных окон» | числитель и знаменатель с разными окнами | привести к одному |
| «имён нет в metrics_available» | метрика придумана | сверить со списком |
| «описание без подстановки» | текст без `{{ }}` | дежурному нужны числа |
| «ночью будят: …» | правило по ресурсам с `page` | что дежурный сделает в три ночи? |
| YAML не разобрался | значение начинается с `{{` | взять в кавычки |

## После выполнения

Зелёный тест означает, что все три происшествия из разбора были бы
замечены: первое через десять минут вместо тридцати одной, второе через
пятнадцать вместо ста десяти, третье — вообще, а не через сутки.

Главное, что стоит унести: **внимание дежурного — конечный ресурс, и
каждое ложное срабатывание тратит его безвозвратно.** Мониторинг, на
который перестали смотреть, хуже отсутствующего: его молчание выглядит
как исправность. Отсюда и правило разделения: будят по симптому, который
видит пользователь, а причину дежурный найдёт сам.

И второе, менее очевидное: **тишина бывает двух видов.** Условие не
выполняется, потому что всё хорошо, и условие не выполняется, потому что
данных нет. Различить их умеют только `up` и `absent()`.

## Кумулятивность

Порог, взятый из наблюдения, а не из круглого числа, — прямое продолжение
[`s07e02`](../s07e02-deployment-manifest/): там так же выбирался предел
памяти, и по той же причине.

Метрики, на которые опираются правила, приведены в пригодный вид в
[`s07e05`](../s07e05-metrics-exporter/); `sum by (le)` работает только
потому, что корзины гистограммы там были починены.

Различение «сигнал существования» и «сигнал работоспособности» —
то же, что с `HEARTBEAT` в
[`s06e05`](../../season-06-embedded-iot/s06e05-mavlink-telemetry/) и с
колонками `STATUS`/`READY` в [`s07e01`](../s07e01-cluster-recon/).

Выдержка `for` как защита от дребезга — та же мысль, что у
[`s05e04`](../../season-05-security-pentesting/s05e04-fail2ban/), где
число неудачных попыток за окно отделяло опечатку от подбора.
