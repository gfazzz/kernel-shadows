# Теория — s01e12

## 1. Пятнадцать минут и один слэш

> *Первая настоящая работа, вторая неделя. Мне поручают безобидное: в конфигах веб-сервера заменить старый домен на новый. Файлов сорок, менять руками — вечер.*
>
> *Пишу одну строку и запускаю на всём каталоге:*
>
> ```console
> $ sed -i 's/old.example.com/new.example.com/g' /etc/nginx/sites-enabled/*
> ```
>
> *Проверяю — заменилось. Радуюсь ровно до момента, когда веб-сервер отказывается перезапускаться.*
>
> *Оказалось, в одном файле домен встречался внутри пути к сертификату, и путь после замены перестал существовать. Мелочь. Но исходников у меня больше не было: `-i` переписал файлы на месте, а каталог в тот момент не был под гитом.*
>
> *Палыч не ругался. Он спросил:*
>
> — Ты этот `sed` перед этим запускал?
> — Запускал, он же сработал.
> — Без `-i` запускал? Просто посмотреть, что получится?
> — Нет.
> — Вот это и есть ошибка. Не шаблон — шаблон у тебя почти правильный. Ошибка в том, что ты сразу писал, вместо того чтобы сначала посмотреть.
>
> *Он показал порядок, которым пользуюсь до сих пор:*
>
> ```console
> $ sed 's/old/new/g' file | diff file -     # что именно изменится
> $ sed -i.bak 's/old/new/g' file            # правим, оставляя копию
> ```
>
> — `sed` — это бензопила. Отличный инструмент, если стоишь правильно. Пятнадцать минут на проверку дешевле вечера на восстановление, и это ещё повезло, что вечера, а не бэкапа за прошлый месяц.

## 2. `sed`: адрес и команда

Каждая инструкция `sed` — это `[адрес]команда`. Нет адреса — команда применяется к каждой строке.

```bash
sed 's/a/b/'          # команда s (substitute) для всех строк
sed '3s/a/b/'         # только для третьей строки
sed '1,10s/a/b/'      # строки 1–10
sed '/ERROR/s/a/b/'   # строки, подходящие под шаблон
sed '$d'              # удалить последнюю строку
sed -n '/START/,/END/p'   # напечатать блок между двумя шаблонами
```

Основные команды: `s` — замена, `d` — удалить, `p` — напечатать (обычно с `-n`, иначе вывод задвоится), `a`/`i` — добавить строку после/перед, `q` — выйти.

Флаги замены: `g` (все вхождения в строке), `i` (без учёта регистра), число (`s/a/b/2` — только второе вхождение), `w файл` (записать изменённые строки в файл).

**Разделитель не обязан быть слэшем.** Для путей это спасение:

```bash
sed 's|/usr/local/bin|/opt/bin|g' file     # вместо экранирования каждого /
sed 's#old#new#g' file
```

**Обратные ссылки:**

```bash
sed -E 's/([0-9]{1,3}\.){3}[0-9]{1,3}/\1XXX/' access.log   # обезличить последний октет
sed -E 's/^([^ ]+) (.*)$/\2 \1/'                            # поменять местами первое поле и остаток
echo "hello" | sed 's/.*/[&]/'                              # & — вся совпавшая часть → [hello]
```

**Класс `[][]`.** Внутри `[...]` символ `]` теряет специальное значение, только если стоит первым. Поэтому `[][]` читается как «`]` или `[`», а `[[]]` — совсем не то. Аналогично `-` должен идти первым или последним (`[-a-z]`), иначе он задаст диапазон.

## 3. `sed` против `awk` против `grep`

| Задача | Инструмент |
|---|---|
| выбрать строки по шаблону | `grep` |
| заменить/удалить текст в строке | `sed` |
| работать с полями, считать, условия по колонкам | `awk` |
| переставить символы, сжать пробелы | `tr` |

Границы размыты — `sed` умеет фильтровать, `awk` умеет заменять, — но выбор по основному назначению делает команду читаемой. Строка `sed -n '/x/p'` работает, однако `grep x` понятнее любому, кто её увидит через год.

Есть и практическое соображение: `sed` работает со строкой как с текстом и не знает про поля, поэтому «заменить только в девятой колонке» на нём выражается мучительно, а на `awk` — естественно.

**`sed -i` не универсален.** GNU-версия принимает `-i` без аргумента, BSD/macOS требует суффикс: `sed -i '' 's/a/b/'`. Скрипт с голым `-i` на macOS съест следующий аргумент как суффикс и поведёт себя непредсказуемо. Переносимый вариант — писать во временный файл и переименовывать, либо всегда указывать суффикс: `-i.bak` работает в обоих.

## 4. Что такое Type B и зачем метка

Курс размечает серии по тому, **что именно** студент производит:

| Тип | Артефакт | Пример |
|---|---|---|
| **A — Automation** | скрипт-оркестратор | `server_monitor.sh` (s01e09) |
| **B — Configuration/Tools** | конфигурация или инструмент, собранный из готовых | `log_analyzer.sh` (эта серия) |
| **C — Investigation** | находки: файл с выводами, отчёт о состоянии системы | `recon.txt` (s01e02) |
| **D — Code** | программа на языке общего назначения | Season 6+ |

Метка нужна не для отчётности, а чтобы не сбиться на «курс по bash». Linux-администратор большую часть времени не программирует: он конфигурирует, наблюдает и соединяет существующее. Сезон, состоящий из одних Type A, учит писать скрипты — но не учит работать с системой.

Практический критерий Type B: **если строку отчёта можно получить одной готовой командой, скрипт не должен её вычислять сам.** `wc -l` вместо цикла со счётчиком, `sort -u | wc -l` вместо массива уникальных значений, `uniq -c` вместо ассоциативного массива.

## 5. Сборка вывода: группировка вместо кучи `>>`

```bash
{
    echo "заголовок"
    команда1
    команда2
} > "$report"
```

Фигурные скобки объединяют команды в группу, которая выполняется в **текущей** оболочке, а перенаправление применяется ко всей группе: файл открывается один раз. Круглые скобки `( … )` делают то же, но в подоболочке — переменные, изменённые внутри, снаружи не видны (та самая ловушка из s01e08).

Синтаксическая мелочь, на которой спотыкаются: после `{` нужен пробел, а перед `}` — точка с запятой или перевод строки. `{echo x}` — не группа, а попытка запустить команду `{echo`.

Полезный вариант, когда отчёт нужен и в файле, и на экране:

```bash
{ ... } | tee "$report"
```

## 6. Отчёт как документ

Три свойства, которые отличают отчёт от вывода команды:

**Самодостаточность.** Читатель не видел твоего терминала. В шапке — что анализировали (имя файла), когда (дата запуска), какой период покрывают данные (первая и последняя запись). Без этого через неделю никто, включая автора, не скажет, к чему относятся числа.

**Воспроизводимость.** Один запуск на тех же данных даёт тот же результат. Поэтому в отчёте не место случайным выборкам и «первым попавшимся» строкам, а дата анализа отделена от дат в данных.

**Различимые уровни.** Факты (посчитано), совпадения (адрес есть в базе угроз), рекомендации (что предлагается сделать) — разные вещи, и смешивать их нельзя. «Атака подтверждена» — это вывод, и делает его человек; отчёт даёт основания.

## 7. Метанавык: результат против инструмента

Разница между вчерашней ночью и сегодняшним днём не в знаниях — конвейеры те же. Разница в том, что ночью были **результаты**, а к вечеру появился **инструмент**.

Результат нельзя перезапустить, передать коллеге, применить к следующему инциденту. Он живёт в истории терминала и в памяти того, кто его получил. Инструмент переживает и то, и другое.

Это же различие дальше отделяет разовую починку от исправления в конфигурации, ручную установку от Ansible-роли, «я посмотрел глазами» от автотеста. Каждый раз вопрос один: то, что я сейчас сделал, повторится? Если да — оно должно стать инструментом сразу, а не на третий раз.
