## 1. У `Service` нет процесса

Самое частое заблуждение после «`Service` стоит перед `Deployment`»: где-то работает балансировщик, через который идёт трафик. Не работает. `ClusterIP` — это адрес, за которым **не стоит никто**.

Что происходит на самом деле: `kube-proxy` на каждом узле следит за списком адресов службы и переписывает правила ядра. Пакет на `10.43.201.14:8080` перенаправляется ядром на адрес одного из подов ещё до того, как выйдет с узла.

| Режим | Чем реализовано | Как выбирает под |
|---|---|---|
| `iptables` | цепочки `KUBE-SVC-*`, `KUBE-SEP-*` | случайно, с вероятностями |
| `IPVS` | таблицы IPVS в ядре | по алгоритму: rr, lc, sh… |
| `nftables` | наборы `nft` | как iptables, но масштабируется лучше |

Практические следствия, которые иначе выглядят загадкой:

- **Служба не может «упасть»** — падать нечему. Может опустеть список адресов.
- **Балансировка происходит на стороне клиента**, точнее на его узле, при установлении соединения. Долгоживущее соединение (gRPC, HTTP/2, пул к базе) прилипает к одному поду навсегда: балансируются соединения, а не запросы.
- Отсюда классическая беда: пять реплик, и вся нагрузка в одной. Лечится либо балансировкой в приложении, либо периодическим разрывом соединений, либо сервис-мешем.

Правила можно увидеть прямо на узле — это те же `iptables`, что в [`s02e06`](../../season-02-networking/s02e06-firewall-ufw/):

```bash
sudo iptables -t nat -L KUBE-SERVICES -n | head
sudo ipvsadm -Ln          # если режим IPVS
```

## 2. `Endpoints` и `EndpointSlice`

`Endpoints` — объект первого поколения: один объект на службу, внутри все адреса. При тысяче подов это один объект в несколько сотен килобайт, который перезаписывается целиком при каждом изменении и рассылается всем узлам.

`EndpointSlice` разрезает список на куски по сто адресов. Изменился один под — переписался один кусок.

```bash
kubectl get endpointslices -n aurora -l kubernetes.io/service-name=aurora-api
kubectl get endpointslice aurora-api-x7k2p -o yaml
```

В `yaml` видно то, чего нет в кратком выводе: у каждого адреса есть `conditions.ready`, `serving` и `terminating`. Различение тонкое и полезное: под, получивший `SIGTERM`, перестаёт быть `ready`, но какое-то время остаётся `serving` — чтобы доработать начатые запросы. Это и есть механизм мягкого вывода из-под нагрузки.

## 3. Служба без адреса и служба без селектора

**Безголовая служба** (`clusterIP: None`) не получает адреса и не балансирует. DNS-запрос к её имени возвращает адреса **всех** подов сразу:

```bash
$ nslookup aurora-db-headless
Address: 10.42.1.4
Address: 10.42.2.9
Address: 10.42.3.11
```

Зачем: клиенту, который сам умеет распределять нагрузку и знает про топологию, — базам, брокерам, всему, что живёт в `StatefulSet`. Каждый под там получает собственное имя `aurora-db-0.aurora-db-headless.aurora.svc.cluster.local`, и оно переживает перезапуск, в отличие от адреса.

**Служба без селектора** не ищет никого; адреса ей вписывают руками отдельным объектом `Endpoints`. Способ дать внутреннее имя внешней системе — базе за пределами кластера, чужому API. Приложение обращается к `aurora-db`, не зная, что тот живёт на железном сервере в соседней стойке; переезд в кластер потом не потребует правки конфигурации.

## 4. `ConfigMap` файлом, а не переменной

```yaml
volumes:
  - name: config
    configMap:
      name: aurora-config
containers:
  - volumeMounts:
      - name: config
        mountPath: /etc/aurora
```

| | `envFrom` / `env` | том |
|---|---|---|
| когда читается | один раз при старте контейнера | при каждом чтении файла |
| видно в `/proc/PID/environ` | да | нет |
| обновление при правке | никогда | через минуту-две, само |
| приложение должно уметь | ничего | перечитывать файл |

**Ловушка `subPath`.** Смонтировать одиночный файл в существующий каталог можно через `subPath` — и такой файл **перестаёт обновляться**. Обновление работает через подмену символической ссылки на каталог целиком; `subPath` копирует файл мимо этого механизма. Внешне выглядит как «конфигурация не применяется», и найти это тяжело, потому что монтирование каталогом рядом обновляется исправно.

## 5. Как заставить правку доехать

Задача: `ConfigMap` изменился, поды должны его увидеть. Четыре ответа, по возрастанию честности:

| Способ | Что делает | Чем плох |
|---|---|---|
| `kubectl rollout restart deployment/…` | пересоздаёт поды | руками, забудется |
| аннотация с хешом конфигурации в шаблоне пода | хеш изменился → изменился шаблон → выкат | требует шаблонизатора |
| перечитывание файла приложением по сигналу или таймеру | без перезапуска | надо уметь в приложении |
| `immutable: true` у `ConfigMap` | правка запрещена, вместо неё — новый объект | самый строгий и самый предсказуемый |

Приём с аннотацией стоит знать, он общепринят:

```yaml
template:
  metadata:
    annotations:
      checksum/config: "8f14e45fceea167a5a36dedd4bea2543"
```

Механика ровно та, что в [`s07e02/theory.md`](../s07e02-deployment-manifest/theory.md): контроллер считает хеш от `spec.template`, и любое изменение внутри шаблона — включая аннотацию — порождает новый `ReplicaSet` и обычный выкат со всеми его гарантиями.

`immutable: true` даёт вдобавок неочевидную выгоду: kubelet перестаёт следить за такими объектами, и на большом кластере это заметно снимает нагрузку с API-сервера.

## 6. Порядок, в котором это диагностируют

```bash
kubectl get endpoints SVC -n NS            # 1. служба вообще кого-то нашла?
kubectl get pods -l "$(селектор)" -n NS    # 2. если нет — есть ли такие поды?
kubectl get pods -n NS -o wide             # 3. если есть — они готовы?
kubectl describe svc SVC -n NS             # 4. порты и targetPort
kubectl run -it --rm probe --image=busybox --restart=Never -- \
        wget -qO- http://SVC:PORT/         # 5. проверка изнутри кластера
```

Порядок не случаен: первые две команды разделяют «служба ищет не то» и «искать нечего», и это две совершенно разные починки. Начинать с пятого шага — значит выяснить, что не работает, ничего не узнав о причине.

Та же логика, что в [`s02e03`](../../season-02-networking/s02e03-net-diagnostics/): диагностика идёт снизу вверх по слоям, а не с того слоя, где заметили симптом.
