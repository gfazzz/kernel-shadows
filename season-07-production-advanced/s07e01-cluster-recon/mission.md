## Обстановка

Панель мониторинга показывает четыре пода `Running` из пяти и трактует это
как «работают четверо». Один из четырёх имеет `READY 0/1` и сорок семь
перезапусков за три часа: он запущен, но трафик к нему не идёт.

В пространстве имён при этом **три разные поломки**, а не одна. Прежде чем
что-то чинить, надо их разделить.

## Приказ

Заполнить `artifacts/cluster_report.txt` — 21 значение.

```bash
cp starter/cluster_report.txt artifacts/
bash tests/test.sh
```

| Файл в `data/` | Что в нём |
|---|---|
| `pods.txt` | `kubectl get pods -o wide` |
| `nodes.txt` | `kubectl get nodes` + сведённые `Allocatable` |
| `events.txt` | `kubectl get events --sort-by=.lastTimestamp` |
| `describe_c9v7t.txt` | подробности «работающего» пода |
| `describe_dk3np.txt` | подробности падающего пода и его лог |
| `deployments.txt` | `kubectl get deploy` + фрагмент yaml и `status` |

## Требования

| Блок | Ключи | Что выяснить |
|---|---|---|
| обзор | `pods_total`, `pods_running`, `pods_ready`, `running_not_ready`, `nodes_ready` | сколько чего и где расхождение |
| причины | `pending_pod`, `pending_shortage`, `imagepull_pod`, `imagepull_tag`, `crashloop_pod`, `crashloop_exit_code`, `crashloop_missing_key` | три разные поломки |
| «работающий» | `max_restarts_pod`, `max_restarts_count`, `restart_reason`, `restart_exit_code`, `memory_limit`, `readiness_http_code` | почему он не работает |
| итог | `desired_replicas`, `available_replicas`, `serving_replicas` | сколько реально обслуживает |

## Чем добывать

| Что нужно | Как |
|---|---|
| готовность | `awk '{split($2,r,"/"); if (r[1]==r[2]) c++}'` |
| перезапуски | в колонке бывает `47 (2m ago)`: `gsub(/[^0-9]/,"",r)` |
| причина `Pending` | событие `FailedScheduling`, слова `Insufficient …` |
| тег образа | `manifest tagged by "…" is not found` |
| прошлое завершение | в `describe` блок `Last State`, а не `State` |
| ключ конфигурации | последняя строка лога `--previous` |
| реплики | `spec.replicas` и `status.availableReplicas` |

## Критерии приёмки

- [ ] `artifacts/cluster_report.txt` создан на основе `starter/`, 21 ключ заполнен.
- [ ] `pods_ready` считается по колонке `READY`, а не по `STATUS`.
- [ ] `running_not_ready` находит под-обманку.
- [ ] Названы три **разные** причины незапуска, а не одна общая.
- [ ] `restart_exit_code` = 137 опознан как `SIGKILL`, а не как ошибка приложения.
- [ ] `serving_replicas` меньше, чем число `Running`.
- [ ] Комментарии в файле сохранены.
- [ ] `bash tests/test.sh` → 26 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep + sed |
| Сеть | не нужна |
| **кластер** | **не нужен** — снимки лежат в `data/` |
| `kubectl` | не нужен |
| Внешние пакеты | нет |
| Изоляция теста | все значения пересчитываются из `data/` |

Тест не содержит зашитых значений: он разбирает те же снимки теми же
приёмами. Отдельно проверяется, что данные не выродились — что под
«`Running`, но не `Ready`» в снимке действительно есть и что счёт по
статусу даёт больше, чем счёт по готовности. Без этого расхождения серия
свелась бы к пересчёту строк.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `pods_ready` на единицу больше | посчитано по `STATUS` | считать по `READY` |
| `running_not_ready`=0 | не разделены статус и готовность | это разные колонки |
| `max_restarts_count` не проходит | взято `47 (2m` целиком | оставить только цифры |
| `restart_exit_code`=1 | взят код падающего пода | `137` — у того, кого убили |
| `crashloop_exit_code`=137 | взят код из другого `describe` | у падающего свой файл |
| `pending_shortage`=taint | прочитана первая причина отсева | узлов не хватило по памяти |
| `serving_replicas`=3 | посчитаны все `Running` подов приложения | только с полным `READY` |

## После выполнения

Зелёный тест означает, что сводка разобрана до фактов: работают двое из
пяти, поломок три, и все три разные. Ни одну из них не было видно из
панели — панель показывала следствие.

Стоит запомнить два принципа. Первый: **«запущен» и «готов» — разные
свойства, и инструмент, который их путает, всегда ошибается в
оптимистичную сторону.** То же различение уже встречалось с `HEARTBEAT`
дрона и с `retained`-сообщением мёртвого узла: сигнал существования не
равен сигналу работоспособности.

Второй: **первый шаг разбора аварии — не «почему всё сломалось», а
«сколько здесь разных поломок».** Склеивание нескольких причин в одну
гипотезу — самый быстрый способ потратить час впустую.
