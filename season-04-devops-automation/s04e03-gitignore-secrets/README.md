## I. «Не проверить, а не заметить»

Ханс рисует на доске три уровня.

```
1. заметить в истории          ← вчера, s04e01. Поздно: уже отправлено.
2. отказать при отправке       ← утром, s04e02. Лучше: но уже в коммите.
3. не увидеть файл вообще      ← сегодня.
```

> — Первые два — это ловушки. Третий — устройство. `git add .` не должен видеть `.env`. Не «должен пропустить» — не должен видеть.

Он открывает репозиторий Дмитрия и показывает `.gitignore`.

```
*.log
```

> — Одна строка. Добавлена двадцать шестого, то есть после того, как журналы уже засорили историю. Классический порядок: сначала мусор, потом правило.

> — А если написать сразу много правил?

> — Тогда начнётся вторая половина задачи. — Он пишет ниже: `*key*`. — Скажите, что попадёт под этот шаблон.

Ты думаешь.

> — Ключи. И… `keys.md`.

> — И `monkey.py`, и `turkey-config.yml`, и документация. Слишком широкое правило молча выбрасывает нужное — а обнаруживается это через полгода, когда файла не оказывается на другой машине.

> **LILITH:** *«`.gitignore` — единственный файл в репозитории, который отвечает не на вопрос «что хранить», а на вопрос «чего не замечать». Ошибка в нём в обе стороны тихая.»*

## II. Теория: как git читает правила

### Шесть правил чтения

```
*.log            любой .log на ЛЮБОЙ глубине
/build           только build в корне репозитория
secrets/         только каталог, не файл с таким именем
docs/*.md        .md прямо в docs, но не в docs/sub/
**/tmp           tmp на любой глубине (явно)
!.env.example    ОТМЕНА игнорирования
```

- шаблон **без слэша** совпадает на любой глубине;
- шаблон **со слэшем** привязан к каталогу, где лежит `.gitignore`;
- **слэш в конце** означает «только каталог»;
- **`!`** отменяет предыдущее совпадение;
- **побеждает последнее совпавшее правило** — как в `sudoers`, а не как в `sshd_config`;
- **ведущий пробел значим** и почти всегда означает опечатку.

Отсюда обязательный порядок для пары «прячем, но пример оставляем»:

```
.env
.env.*
!.env.example      ← ПОСЛЕ шаблона, который его захватывает
```

Поменяй местами — и `.env.example` исчезнет из репозитория вместе с единственной подсказкой о том, какие переменные нужны.

### Главное ограничение

**`.gitignore` действует только на то, что git ещё не отслеживает.** Файл, однажды закоммиченный, продолжит отслеживаться, сколько правил ни пиши:

```bash
git rm --cached .env        # перестать отслеживать, оставив на диске
git commit -m "убрать .env"
```

А в истории он останется — это разбиралось в [`s04e01`](../s04e01-git-history/). Для истории нужен `git filter-repo`, и это отдельная операция с переписыванием хешей.

### Проверять командой, а не глазами

```bash
git check-ignore -v путь     # какое правило и из какой строки сработало
git status --ignored         # что игнорируется прямо сейчас
git ls-files                 # что УЖЕ отслеживается
git add -n .                 # что добавилось бы (сухой прогон)
```

`git check-ignore -v` отвечает на вопрос точно: он называет файл правил, номер строки и сам шаблон.

### `.env.example`

Файл, который **должен** попасть в репозиторий: перечень нужных переменных без единого значения. Человек, склонировавший репозиторий, узнаёт состав, не спрашивая никого и не получая ни одного секрета.

Про `.git/info/exclude`, глобальный `core.excludesFile` и вложенные `.gitignore` — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Добавили `.env` в `.gitignore`, а `git status` всё равно показывает его изменения. Почему?»*

<details>
<summary>Подумай 30 секунд</summary>

Файл уже отслеживается — то есть был закоммичен раньше. Правила игнорирования на такие файлы не действуют вовсе.

```bash
git ls-files | grep .env      # да, отслеживается
git rm --cached .env          # перестать; файл останется на диске
```

И отдельно: содержимое всех прошлых коммитов при этом не меняется, поэтому секрет надо считать скомпрометированным и менять.
</details>

**LILITH:** *«В `.gitignore` есть `*.key` и `!docs/keys.md`. Второе правило нужно?»*

<details>
<summary>Ответ</summary>

Нет: `*.key` не совпадает с `keys.md`. Шаблон требует, чтобы имя **заканчивалось** на `.key`, а тут расширение `.md`.

Правило понадобилось бы, будь написано `*key*` — и вот это как раз тот случай, когда лишняя звёздочка тихо выбрасывает документацию.

Проверяется одной командой вместо рассуждений: `git check-ignore -v docs/keys.md` промолчит, если файл не игнорируется.
</details>

## IV. Задание: закрыть вопрос устройством

Артефакты — два файла в `artifacts/`: `gitignore` (лёг бы в репозиторий как `.gitignore`) и `env.example`.

```bash
cp starter/gitignore starter/env.example artifacts/
bash tests/test.sh
```

| Должно игнорироваться | Должно остаться |
|---|---|
| `.env`, `.env.local`, `secrets/`, `*.pem`, `*.key`, `vault_pass.txt` | `.env.example` |
| `*.tfstate`, `.terraform/`, `*.retry` | `README.md`, `deploy.sh` |
| `*.log` на любой глубине | `roles/common/tasks/main.yml` |
| `node_modules/`, `__pycache__/`, `.DS_Store`, `tmp/` | `docs/keys.md`, `docs/secrets-policy.md` |

Правый столбец — не украшение. Это проверка на то, что правила не шире, чем нужно.

Второй артефакт — пример конфигурации: те же переменные, что были в `.env`, и **ни одного значения**.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Проверяй не текст, а поведение:

```bash
cd /tmp && rm -rf t && mkdir t && cd t && git init -q
cp .../artifacts/gitignore .gitignore
mkdir -p docs && touch .env .env.example docs/keys.md
git check-ignore -v .env .env.example docs/keys.md
```

Строка с `!` должна стоять **после** того шаблона, который она отменяет.

Эталон — в `solution/`, там же комментарий к каждому решению.
</details>

### Три ошибки, которые здесь делают

**Поставить `!.env.example` выше `.env.*`.** Побеждает последнее совпавшее правило, поэтому отмена сверху не работает вовсе. Ошибки не будет — просто пример исчезнет из репозитория.

**Написать `*key*` вместо `*.key`.** Под шаблон попадёт документация. Слишком широкое правило — единственная ошибка в этом файле, которая обнаруживается через месяцы.

**Забыть про `*.tfstate`.** Состояние Terraform содержит значения переменных, включая те, что ты аккуратно вынес в vault. Это второй по частоте способ отправить секрет после `.env`.

## V. Финал эпизода: три уровня

Ты сдаёшь оба файла. Ханс прогоняет их своей командой:

```
$ git check-ignore -v .env .env.example docs/keys.md
.gitignore:11:.env      .env
```

Одна строка вывода из трёх запрошенных путей: игнорируется только `.env`.

> — Хорошо. Теперь соберём вместе, что вы сделали за два дня.

Он стирает доску и пишет заново.

```
1. .gitignore        секрет не попадает в коммит
2. хук pre-push      если всё-таки попал — не уедет с этой машины
3. ???               если уехал — узнаем не через полгода
```

> — Третьего у вас пока нет, и хук его не даёт: он лежит в `.git` и работает только у вас. Дмитрий склонирует репозиторий — и не получит ни строчки вашей защиты.

> — Значит, нужна проверка, которая выполняется не у меня.

> — Нужна проверка, которая выполняется **у всех и всегда**, на машине, которую нельзя уговорить. Это называется конвейер, и мы вернёмся к нему через два дня. — Он смотрит на часы. — А сейчас — самолёт.
