## Обстановка

Всё, что настроено вручную, исчезает вместе с питанием. Шину SPI при этом
нельзя включить службой: дерево устройств фиксируется до старта ядра, и то,
чего в нём нет, для системы не существует.

Настройка переезжает туда, где её читают раньше всех: в два текстовых файла
на загрузочном разделе. Обратной связи при ошибке не будет — неверный
`config.txt` не даёт сообщения, плата просто молчит.

## Приказ

Собрать `artifacts/config.txt` и `artifacts/cmdline.txt` для узла
shadow-node-07.

```bash
cp starter/config.txt starter/cmdline.txt artifacts/
bash tests/test.sh
```

| Файл в `data/` | Что в нём |
|---|---|
| `board_facts.txt` | факты платы из `s06e01`: семейство, `PARTUUID`, тип ФС, скорость консоли |
| `sensors.txt` | какие датчики подключены и на какой шине |

## Требования

| Файл | Требование |
|---|---|
| `config.txt` | включить шины, нужные датчикам из `sensors.txt`, — и **только их** |
| `config.txt` | 1-wire через overlay с номером ножки из `sensors.txt` |
| `config.txt` | `enable_uart=1`, действующий на любой плате |
| `config.txt` | безголовый режим: `gpu_mem` ≤ 64, без заставки, без задержки |
| `config.txt` | секция `[семейство]` для платозависимого; `dtoverlay=disable-bt` внутри неё |
| `config.txt` | после платозависимой секции — `[all]` |
| `config.txt` | никаких дублей параметров в одной секции |
| `cmdline.txt` | ровно одна непустая строка, без комментариев |
| `cmdline.txt` | `root=PARTUUID=…` и `rootfstype=` из `board_facts.txt` |
| `cmdline.txt` | `console=serial0,<скорость>`, `rootwait`, `fsck.repair=yes` |
| `cmdline.txt` | без одноразового `init=…init_resize.sh` |

## Чем добывать

| Что нужно | Как |
|---|---|
| нужные шины | `awk '!/^#/ {print $2}' data/sensors.txt \| sort -u` |
| ножка 1-wire | третья колонка строки с `w1` |
| семейство платы | `grep '^family=' data/board_facts.txt` |
| `PARTUUID`, ФС, скорость | `root_partuuid`, `rootfstype`, `console_speed` там же |

## Критерии приёмки

- [ ] `artifacts/config.txt` и `artifacts/cmdline.txt` созданы на основе `starter/`.
- [ ] Включённые шины совпадают с множеством шин из `sensors.txt` — ни одной лишней.
- [ ] `w1-gpio` привязан к ножке из `sensors.txt`, а не к произвольной.
- [ ] `enable_uart=1` не спрятан внутрь платозависимой секции.
- [ ] `disable-bt` находится **в** секции семейства: на других платах он не нужен.
- [ ] Файл не заканчивается открытой платозависимой секцией.
- [ ] `cmdline.txt` — одна строка; перенос молча теряет параметры.
- [ ] `root=PARTUUID` и скорость консоли совпадают с фактами платы.
- [ ] `bash tests/test.sh` → 24 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep |
| Сеть | не нужна |
| **плата** | **не нужна** — конфигурация проверяется как текст |
| Внешние пакеты | нет |
| Изоляция теста | требования вычисляются из `data/` |

Тест не содержит зашитых требований. Набор шин он выводит из
`data/sensors.txt`: убери оттуда SPI-датчик — и включённый `spi` станет
ошибкой «лишняя шина занимает ножки». `PARTUUID`, тип ФС, скорость консоли
и семейство платы читаются из `data/board_facts.txt`.

Разбор `config.txt` учитывает секции-фильтры: параметр относится к той
секции, в которой стоит, и «после `[pi4]`» — это не «для всех». Отдельно
проверяется, что файл не заканчивается открытой платозависимой секцией.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «лишняя шина» | включено больше, чем нужно датчикам | сверить с `sensors.txt` |
| `w1-gpio` не проходит | нет `gpiopin=` или не тот номер | номер — из `sensors.txt` |
| `enable_uart` «спрятан в фильтр» | строка стоит после `[pi4]` | перенести выше первой секции или в `[all]` |
| `disable-bt` «не в секции» | задан для всех плат | на других моделях он не нужен и вреден |
| «ниже ещё N параметров» | нет `[all]` в конце | закрыть платозависимую секцию |
| `cmdline`: «две строки» | параметры перенесены для читаемости | всё в одну строку |
| `root=` не совпал | взят `/dev/mmcblk0p2` | `PARTUUID` из `board_facts.txt` |

## После выполнения

Зелёный тест означает, что узел просыпается уже настроенным: шины включены,
консоль работает на стабильной скорости, корень монтируется по идентификатору,
а не по порядку обнаружения. Карту можно тиражировать на остальные узлы.

Стоит запомнить принцип, который дальше работает во всём системном
администрировании: **настройка должна стоять на том слое, который читается
достаточно рано.** Шину включают до ядра, корень задают при старте ядра,
службы настраивают после. Параметр, поставленный слоем выше, чем нужно, не
ошибочен — он просто опоздал, и это самый трудный для диагностики вид
неработающей конфигурации, потому что выглядит он правильным.

## Кумулятивность

Выключенный `spi@` в дереве устройств обнаружен в
[`s06e01`](../s06e01-board-recon/) — здесь он наконец включается, и это
объясняет, почему припаянный датчик молчал. Карта гребёнки из
[`s06e02`](../s06e02-gpio-sysfs/) объясняет, почему нельзя включать шины
«на всякий случай»: каждая забирает ножки.

`rootwait` — тот же класс проблемы, что ожидание готовности при
развёртывании в
[`s04e08`](../../season-04-devops-automation/s04e08-deploy-rollback/):
ресурс появляется асинхронно, и код, полагающийся на «оно уже есть»,
работает через раз. Идентификатор вместо имени устройства (`PARTUUID`
вместо `/dev/mmcblk0p2`) — та же мысль, что монтирование по UUID и
предсказуемые имена интерфейсов из
[`s03e10`](../../season-03-system-administration/s03e10-fstab/): имя должно
принадлежать объекту, а не порядку его обнаружения.
