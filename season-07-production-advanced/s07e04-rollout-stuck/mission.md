## Обстановка

Версию `v2.5.0` выкатили полчаса назад. `kubectl apply` вернул успех,
приложение доступно, панель зелёная — и работает старая версия. Новая
реплика висит в `Pending` девять минут: ей некуда встать, а убрать старую
кластер не имеет права, потому что `maxUnavailable` равен нулю.

Кластер не считает это ошибкой. Он считает это ожиданием и готов ждать
сколько угодно.

## Приказ

Написать `artifacts/rollout_check.sh` — скрипт, который по снимку
состояния отвечает, идёт выкат или встал, и если встал, то почему.

```bash
cp starter/rollout_check.sh artifacts/
bash artifacts/rollout_check.sh data/case-02-no-room
bash tests/test.sh
```

| Каталог в `data/` | Что в нём |
|---|---|
| `case-01-complete` | выкат доехал |
| `case-02-no-room` | новой реплике негде встать |
| `case-03-not-ready` | новая версия не проходит готовность |
| `case-04-progressing` | обычный выкат посередине |

В каждом — `deploy.txt`, `rs.txt`, `pods.txt`, `events.txt` и `truth.txt`
с результатом настоящего `kubectl rollout status`. Скрипт **не должен**
открывать `truth.txt`: тест ищет это имя в его тексте.

## Договор

Восемь строк вывода, в этом порядке:

```
VERDICT     complete | progressing | stuck
CAUSE       none | scheduling | image | readiness | deadline
DESIRED     <n>
UPDATED     <n>
AVAILABLE   <n>
NEW-RS      <имя>
OLD-RS      <имя> <реплик>
PROGRESSING <статус> <причина>
```

Код возврата: `0` — идёт или доехал, `1` — встал, `2` — снимок не разобрать
(нет аргумента, нет каталога, нет файлов).

## Чем добывать

| Что нужно | Как |
|---|---|
| «доехал» | `updatedReplicas == availableReplicas == replicas == spec.replicas` |
| признание неудачи | условие `Progressing`, статус и причина |
| безнадёжность до дедлайна | повторяющиеся `Warning` в `events.txt` |
| новый `ReplicaSet` | самый молодой по `AGE`: `50s`, `14m`, `6h`, `2d` |
| его поды | хеш из имени `ReplicaSet` внутри имени пода |

## Критерии приёмки

- [ ] Все четыре снимка получают тот же вердикт, что и настоящий `kubectl rollout status`.
- [ ] Причины остановки различены: размещение и готовность — не одно и то же.
- [ ] `truth.txt` в тексте скрипта не упоминается.
- [ ] Без аргумента и с несуществующим каталогом — код 2 и сообщение в `stderr`.
- [ ] Застрявший выкат — код 1, остальные — код 0.
- [ ] Числа совпадают со снимком.
- [ ] Новый и старый `ReplicaSet` различены; новый определён по возрасту.
- [ ] Два прогона подряд дают одинаковый вывод; `stderr` пуст на исправном снимке.
- [ ] `bash tests/test.sh` → 48 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep |
| Сеть | не нужна |
| **кластер** | **не нужен** — снимки в `data/` |
| `kubectl` | не нужен |
| Внешние пакеты | нет |
| Изоляция теста | вывод скрипта пишется в `mktemp -d`, снимки только читаются |

Тест сверяет вердикт с `truth.txt`, а числа считает из `deploy.txt`
самостоятельно. Отдельно проверяется, что набор снимков не выродился: в
нём есть все три исхода и не менее двух разных причин остановки. Без этого
скрипт, всегда печатающий `stuck`, проходил бы половину проверок.

## Выполнение

```bash
cd season-07-production-advanced/s07e04-rollout-stuck
cp starter/rollout_check.sh artifacts/
$EDITOR artifacts/rollout_check.sh
for c in data/case-*; do echo "== $c"; bash artifacts/rollout_check.sh "$c"; done
bash tests/test.sh
```

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `VERDICT progressing` на `case-02` | ждём условия `Progressing=False` | до него десять минут; смотреть события |
| `VERDICT stuck` на `case-04` | предупреждением сочтено обычное событие | останавливают только `Warning` о подах нового RS |
| `CAUSE deadline` вместо `readiness` | не посмотрели на поды нового RS | `Running` при неполном `READY` |
| `NEW-RS` не тот | сравнение возрастов по строкам | в awk после `sub` нужно `+ 0` |
| «два прогона дают разный вывод» | в вывод попало время или `ls` без сортировки | убрать всё, что зависит от среды |
| «пишет в stderr» | отладочная печать осталась | убрать или увести в файл |
| код 0 у `stuck` | забыт `exit 1` | вердикт и код должны совпадать |

## После выполнения

Зелёный тест означает, что вопрос «доехал ли выкат» больше не требует
ожидания: ответ читается из состояния и превращается в код возврата,
который понимает конвейер.

Главное, что стоит унести: **у неудачного выката нет момента отказа.**
Есть момент, когда ожидание перестало иметь смысл, и определяет его
человек — потому что система, бесконечно стремящаяся к желаемому
состоянию, не умеет сдаваться. `Available=True` и `Progressing=False`
одновременно — это норма для застрявшего выката, а не противоречие.
