## Обстановка

Панель мониторинга дата-центра показывает 47 % неуспешных разрешений имён и
два десятка зафиксированных попыток отравления кеша. Атакующему незачем ломать
сервер, если можно изменить ответ на вопрос «где этот сервер».

Прежде чем ловить подмену, нужно уверенно читать сам DNS: какие записи бывают,
что означает пустой ответ и почему `dig` иногда расходится с тем, что видит
программа.

## Приказ

Собрать `dns_lookup.sh` — делает запрос через `dig` и показывает результат с
количеством записей:

```
$ ./dns_lookup.sh google.com MX
=== google.com [MX] ===
5 gmail-smtp-in.l.google.com.
10 alt1.gmail-smtp-in.l.google.com.
Записей: 2
```

Использование: `./dns_lookup.sh DOMAIN [TYPE]`, тип по умолчанию — `A`.
Работу делает `dig`; скрипт оформляет запрос и результат — это Type B.

## Данные

| Что | Как |
|---|---|
| домен / тип | `"${1:?…}"`, `"${2:-A}"` |
| запрос | `dig "$domain" "$type" +short 2>/dev/null` |
| пустой ответ | `[ -z "$ans" ]` → сообщение и `exit 1` |
| количество | `printf '%s\n' "$ans" \| grep -c .` — считает непустые строки |

`dig` завершается кодом `0` и когда записи нет: с его точки зрения запрос прошёл
успешно, просто ответ пуст. Проверять надо содержимое, а не код возврата.

## Критерии приёмки

- [ ] `artifacts/dns_lookup.sh` создан, есть shebang, `bash -n` без ошибок.
- [ ] Без второго аргумента запрашивается тип `A`.
- [ ] Явно указанный тип (`MX`, `NS`, `TXT`) передаётся в `dig`.
- [ ] Все значения многозначного ответа выводятся, а не только первое.
- [ ] `Записей: N` совпадает с числом выведенных строк.
- [ ] Пустой ответ → сообщение и ненулевой код возврата.
- [ ] На пустом ответе счётчик не печатается как `1`.
- [ ] Несуществующий тип записи у существующего домена тоже даёт ненулевой код.
- [ ] `bash tests/test.sh` → 11 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash; для реального запуска — `dig` из `dnsutils`/`bind-utils` |
| Сеть | **не нужна** — тест подменяет `dig` |
| systemd / Docker / k8s | не нужны |
| Внешние пакеты | в реальном запуске `dig`; в тесте подменяется |
| Изоляция теста | мок-`dig` в `PATH`, временный каталог |

Мок отдаёт: домен с одной записью `A`, домен с двумя записями `MX`, домен с
`TXT`, несуществующий домен и существующий домен с отсутствующим типом.
Ожидаемые значения тест берёт из самого мока.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| пустой ответ считается успехом | проверяется код возврата `dig` | проверять `[ -z "$ans" ]` |
| «Записей: 1» при пустом ответе | считается `wc -l` | `grep -c .` |
| выводится только первая запись | взят `head -1` | печатать весь ответ |
| тип игнорируется | аргумент не передан в `dig` | `dig "$domain" "$type" +short` |
| `dig: command not found` | не установлен пакет | `sudo apt install dnsutils` |
| ответ отличается от того, что видит браузер | вмешался `/etc/hosts` | сравнить с `getent hosts` |

## После выполнения

Зелёный тест означает, что ты умеешь спрашивать DNS и отличать «нет записи» от
«ошибка». `dns_lookup.sh` — DNS-модуль `netshield` (см. [`PROJECTS.md`](../../PROJECTS.md)).

Дальше — вопрос, на который умение спрашивать не отвечает: полученный ответ
правдив? Классический DNS не подписан, и подменённый ответ выглядит точно так же,
как настоящий. Ловить его придётся сравнением — это капстоун эпизода.
