## II. Теория: как устроена проверяемая программа

### Логика отдельно, ввод-вывод отдельно

```
┌──────────── трогает мир ────────────┐   ┌──── чистая логика ────┐
read_device(path)   time.time()           parse_w1(text)
publish(topic, msg) os.environ            plausible(v, lo, hi)
                                          build_message(...)
                                          Backoff, Spool
```

Слева — то, что нельзя вызвать в тесте без датчика, сети и ожидания. Справа — то, что можно вызвать миллион раз за миллисекунду. **Задача проектирования — сделать правую часть как можно больше.**

Приём один и тот же везде: то, что программа берёт из мира, она принимает **параметром**.

```python
def run_cycle(state, raw_text, publish, now):   # текст, отправитель и время — снаружи
class Backoff:
    def __init__(self, ..., rand=None):         # источник случайности — снаружи
```

`now` параметром вместо `time.time()` внутри означает, что шаг можно проверить в 1731920400 и в любой другой момент. `rand` параметром означает, что «случайная» задержка проверяема: подставили `lambda: 0.0` и `lambda: 1.0` — увидели границы разброса.

Это не тестовая уловка, а свойство хорошего кода: **зависимость, переданная явно, видна; взятая изнутри — скрыта.**

### `None` — это не ноль

```python
def parse_w1(text):
    ...
    return None      # показания нет
```

Ноль градусов — валидное измерение. «Датчик не ответил» — не измерение вовсе. Функция, возвращающая `0.0` в обоих случаях, теряет различие, которое дальше уже не восстановить.

То же различие есть везде: пустая строка и отсутствие строки, `0` и `NULL`, «пришло `false`» и «не пришло ничего». Каждый раз, когда они сливаются, появляется ошибка, которую невозможно диагностировать по результату.

### Три способа получить неверное показание

| Что | Как выглядит | Чем ловится |
|---|---|---|
| битые данные | `crc=3a NO`, но `t=` на месте | проверка первой строки **до** разбора |
| датчик не мерил | `85.0`, CRC в порядке | сравнение с известным особым значением |
| выход за физику | `-273`, `+200` | диапазон площадки |

Порядок важен: сначала CRC, потом смысл. Разбирать данные, о которых уже известно, что они битые, бессмысленно.

### Разброс при переповторе

```
попытка 1:  1 с      попытка 4:   8 с
попытка 2:  2 с      попытка 5:  16 с
попытка 3:  4 с      попытка 6:  32 с → потолок 60 с
```

Экспоненциальный рост убирает нагрузку с брокера при долгом отказе. Потолок не даёт задержке уйти в часы. А **разброс** решает другую задачу: развести узлы во времени.

```python
delay = raw - spread + 2 * spread * rand()      # ±jitter от расчётной
```

Без последней строки двадцать семь узлов, потерявших связь одновременно, вернутся тоже одновременно. Явление известно как «стадо»: восстановление службы само становится причиной следующего отказа.

### Очередь ограничена, и отбрасывается старое

```python
while len(self._items) > self.capacity:
    self._items.pop(0)          # выбрасываем самое старое
    self.dropped += 1
```

Неограниченная очередь на узле с двумя гигабайтами памяти — это отложенный `OOM`: связи нет час, память кончилась.

Что именно отбрасывать — решение по смыслу данных. Для телеметрии свежее ценнее: потребителю нужна текущая температура. Для команд или платежей было бы наоборот — там теряют новое, а не старое. **Реализация не должна выбирать это за тебя.**

### Метка времени ставится источником

Сообщение может пролежать в очереди час, пройти через брокер и достаться подписчику как `retained` через сутки — ровно то, что разобрано в [`s06e08`](../s06e08-mqtt-dump/). Единственный, кто знает время измерения, — тот, кто измерял.

Про `paho-mqtt`, `asyncio`, systemd-юниты, `WatchdogSec` и упаковку клиента в образ — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Почему `now` передаётся параметром? Внутри же есть `time.time()`.»*

<details>
<summary>Подумай 30 секунд</summary>

Потому что функция, берущая время изнутри, даёт разный результат при каждом вызове, и проверить её можно только приблизительно: «поле `ts` похоже на текущее время». Такая проверка пропускает и неверный формат, и сдвиг на часовой пояс, и деление на тысячу не там.

С параметром результат становится **функцией от входа**: подставили `1731920400` — получили ровно `1731920400`. Проверяется точным сравнением, без допусков.

Общее правило: **всё, что делает результат непредсказуемым, передаётся снаружи** — время, случайность, окружение, сеть, файловая система. Тогда ядро программы становится обычной функцией, и её можно проверять как арифметику. Это же свойство помогает и в работе: воспроизвести жалобу «в три часа ночи пришло странное значение» можно, подставив то самое время.
</details>

**LILITH:** *«Очередь переполнилась. Почему выбрасываем старое, а не отказываемся принимать новое?»*

<details>
<summary>Ответ</summary>

Потому что это телеметрия, и её ценность падает со временем. Потребителю нужна текущая температура; значение часовой давности не нужно никому, кроме архива, а архив всё равно не получит его целиком.

Но правильного ответа «вообще» здесь нет — есть правильный ответ **для этих данных**. Если бы в очереди лежали команды устройству, выбрасывать старое было бы недопустимо: пропущенная команда «выключить насос» не заменяется следующей. Для платежей нельзя выбрасывать ни то, ни другое — там очередь обязана быть надёжной, и это уже не очередь в памяти, а журнал на диске.

Отсюда мысль, которая переживёт эту серию: **у переполнения всегда есть политика, и она принимается осознанно.** Реализация, которая молча растёт до `OOM`, тоже приняла политику — просто худшую из возможных, и не спросив тебя.
</details>

## IV. Задание: `sensor.py`

Артефакт — `artifacts/sensor.py`.

```bash
cp starter/sensor.py artifacts/
bash tests/test.sh
```

| Что реализовать | Требование |
|---|---|
| `parse_w1(text)` | CRC проверяется **до** разбора; `None` при любой негодности |
| `plausible(v, lo, hi)` | диапазон площадки и особое значение `85.0` |
| `topic_for(schema, ...)` | схема приходит извне, в коде не дублируется |
| `build_message(...)` | JSON с `value`-числом, целым `ts`, `unit`, `seq` |
| `Backoff` | рост, потолок, разброс; источник случайности параметром |
| `Spool` | ограничена; отбрасывает старое; считает потери |
| `run_cycle(...)` | негодное не публикуется и не тратит номер; при обрыве — в очередь |
| `credentials(env)` | из окружения; ни одного пароля в исходнике |
| импорт | молчит и ничего не запускает |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Пределы, ёмкость очереди и параметры задержки — в `data/limits.txt`; схема тем — в `data/topic_schema.txt`.

`parse_w1`: разбить на строки, проверить хвост первой, найти `t=` во второй, поделить на 1000.

`Backoff.next_delay`: `raw = min(base * factor**attempt, cap)`, затем разброс `raw ± raw*jitter`, затем снова обрезать по `cap`.

`run_cycle`: сначала отдать накопленное, потом свежее; на первом отказе вернуть остаток в очередь **по порядку**.

Эталон — в `solution/`, там у каждого решения написано, что оно предотвращает.
</details>

### Три ошибки, которые здесь делают

**Искать `t=` и не смотреть CRC.** Битая строка содержит `t=`, и в сеть уходит правдоподобный мусор.

**Взять время и случайность изнутри функций.** Программа перестаёт быть проверяемой, и единственным тестом становится эксплуатация.

**Оставить очередь неограниченной.** Час без связи — и узел падает по памяти, унося с собой и то, что накопил.
