## Теория: SSH-ключи (один концепт: доступ без паролей)

Ключевая пара: приватный ключ (у тебя) + публичный (на серверах). Подпись приватным проверяется публичным — вход без пароля:

```bash
ssh-keygen -t ed25519 -C "max@shadow-ops"   # id_ed25519 + id_ed25519.pub
```

**Права критичны:**

```bash
chmod 600 ~/.ssh/id_ed25519      # приватный: только владелец
```

Если у приватного ключа права шире `600` — **SSH откажется его использовать** («UNPROTECTED PRIVATE KEY FILE»): ключ, доступный другим, считается скомпрометированным. `ed25519` предпочтительнее RSA (короче, быстрее); `dsa` устарел. Про `~/.ssh/config` (алиасы) — в [`theory.md`](theory.md).

> **LILITH:** *«Приватный ключ никогда не покидает твою машину. Публичный — кладёшь на серверы. Потерял приватный — потерял всё; дал слишком широкие права — SSH тебя же и остановит.»*

## Проверка «в мире сюжета»

**Алекс:** *«Ты скопировал ключи на новую машину, а `ssh` ругается „UNPROTECTED PRIVATE KEY FILE". Почему?»*

<details>
<summary>Подумай 20 секунд</summary>

При копировании слетели права — приватный ключ стал, например, `644` (читают все). SSH намеренно отказывается использовать ключ, доступный другим пользователям (он скомпрометирован). Лечится `chmod 600 ~/.ssh/id_ed25519`. Поэтому проверка прав — первое при проблемах с ключом.
</details>

**Анна:** *«Почему ключи сильнее паролей против Крылова?»*

<details>
<summary>Ответ</summary>

Пароль передаётся и может быть перехвачен/подобран (слабые пароли, брутфорс, фишинг). При ключах по сети идёт только подпись-доказательство, а сам приватный ключ никогда не передаётся. Подобрать 256-битный ed25519 вычислительно невозможно. Плюс на сервере можно вовсе запретить парольный вход (следующая серия).
</details>

<details>
<summary>Подсказка (после попытки)</summary>

```bash

[ "$perm" = "600" ] || [ "$perm" = "400" ] || { echo "⚠️ небезопасно"; issues=$((issues+1)); }
```
