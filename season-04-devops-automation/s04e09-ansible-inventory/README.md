На экране — Клаус Шмидт, из Темпельхофа: бывший берлинский аэропорт, теперь машинный зал на четыре тысячи серверов. За спиной ряды стоек.

Дмитрий открывает файл. Пятьдесят строк, по одной на хост, и четыре группы: `web`, `db`, `cache`, `monitoring`.

Пауза.

> — То есть никак. — Клаус разворачивает свой файл. — Инвентарь — это не список машин. Это ответ на вопрос **«чем они друг от друга отличаются»**. Если различие есть в голове, но не в файле, автоматика его не видит.

Он показывает свой инвентарь: те же машины, но каждая попадает в две группы сразу — одна отвечает на вопрос «что этот сервер делает», вторая — «где он стоит».

## II. Теория: две оси и один спор

### Инвентарь в YAML

```yaml
all:
  vars:
    ansible_user: ops           # общее для всех — один раз
  children:
    web:
      hosts:
        prod-web[01:27].shadow.io:    # диапазон, а не 27 строк
        stg-web[01:08].shadow.io:
      vars:
        ops_role: web
```

`children` — группы внутри группы; `hosts` — машины; `vars` — переменные группы. Диапазон `[01:27]` разворачивается в имена с ведущими нулями: `prod-web01`, …, `prod-web27`.

### Две оси

Сервер отвечает на два независимых вопроса, и на каждый — своей группой:

| Ось | Группы | Что задаёт |
|---|---|---|
| роль: что машина делает | `web`, `db`, `cache`, `monitoring` | пакеты, порты, службы |
| контур: где машина стоит | `production`, `staging` | уровень журналирования, сроки хранения, доступы |

Смешивать их в одну группу (`prod-web`) заманчиво и стоит дорого: чтобы перевести машину из стенда в бой, придётся переписывать структуру, а не поменять одну строку.

### Кто выигрывает спор

Хост `prod-web01` попал и в `web`, и в `production`. Что будет, если обе группы задают `log_level`?

```yaml
web:         { vars: { log_level: info } }
production:  { vars: { log_level: warn } }
```

Правила Ansible, по возрастанию силы:

```
переменные группы all
  → переменные группы-предка
    → переменные группы-потомка
      → переменные хоста
```

А если группы **несравнимы** — ни одна не предок другой, как `web` и `production`? Тогда побеждает та, **чьё имя позже по алфавиту**. `production` < `web`, значит в бою окажется `log_level: info`.

Это не ошибка Ansible. Это честное правило: порядок должен быть определён хоть как-то. Ошибка — рассчитывать, что победит «более важная» группа: важность существует только у вас в голове.

> Курс к этому месту назвал шесть семантик чтения конфигураций, и ни одна не совпадает с другой: `sshd_config` — первое вхождение; `sudoers` — последнее подходящее правило; `ssh_config` — первое полученное значение; `.gitignore` — последний подходящий шаблон; systemd и журнал выкатов — последнее присваивание; инвентарь Ansible — потомок сильнее предка, а среди равных решает алфавит.

Отсюда практическое правило, которое снимает вопрос целиком: **одна переменная задаётся только на одной оси**. `ops_role` и `open_ports` — свойства роли. `ops_env` и `log_level` — свойства контура. Пересечений нет, спорить не о чем.

Про `host_vars`, `group_vars`, `ansible_group_priority` и динамический инвентарь — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«`log_level` задан в `web` (`info`) и в `production` (`warn`). Хост `prod-web01` в обеих. Какое значение получит?»*

<details>
<summary>Подумай 30 секунд</summary>

`info` — из группы `web`.

Группы несравнимы: `production` не родитель `web` и наоборот. Ansible применяет их в алфавитном порядке, и последняя переписывает предыдущую. `w` идёт после `p`.

Проверить это на своей машине можно за десять секунд:

```bash
ansible-inventory -i inventory.yml --host prod-web01.shadow.io
```

Команда печатает итоговый набор переменных — то же самое «что программа поняла», что `ssh -G`, `systemctl show` и `docker compose config` в предыдущих сериях. Спорить с ней бессмысленно, и именно поэтому её стоит спросить до, а не после.
</details>

**LILITH:** *«Зачем разводить роль и контур, если можно завести группу `prod-web` и не думать?»*

<details>
<summary>Ответ</summary>

Пока машины не переезжают — можно. Вопрос в том, что происходит, когда стенд надо превратить в боевой контур или наоборот.

С двумя осями это перенос имени хоста из одной группы в другую: одна строка, и все переменные пересчитываются сами. С группой `prod-web` это переименование группы, правка всех переменных, которые в ней смешаны, и ручная проверка, что ничего не забыли.

Признак того, что оси смешаны: имя группы содержит союз «и» при чтении вслух. «Веб-серверы **и** боевые» — две группы, а не одна.
</details>

## IV. Задание: переписать инвентарь

Артефакт — `artifacts/inventory.yml`.

```bash
cp starter/inventory.yml artifacts/
bash tests/test.sh
```

| Требование | Почему |
|---|---|
| ровно 50 хостов, записанных диапазонами | пятьдесят строк невозможно вычитать глазами |
| группы по роли (не меньше трёх), у каждой `ops_role` и `open_ports` | это свойства того, что машина делает |
| две группы-контура с `ops_env` | это свойство того, где она стоит |
| ни одна группа не задаёт обе оси | иначе машину нельзя переставить |
| каждый хост ровно в одной группе каждой оси | иначе непонятно, чей он |
| ни одна переменная не задана в двух несравнимых группах | спор решит алфавит |
| `ansible_user` один раз, в `all`, и не `root` | общее живёт наверху; права повышают там, где нужно |
| ни одного пароля | файл лежит в репозитории |
| без `StrictHostKeyChecking=no` | подмена сервера должна оставаться заметной |
| в боевом контуре `log_level` не `debug` | объём и лишние данные в журнале |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Диапазон: `prod-web[01:27].shadow.io:` — с ведущими нулями, ширина берётся из первого числа.

Один и тот же хост перечисляется дважды: один раз в группе-роли, один раз в группе-контуре. Это нормально и есть способ попасть в две группы.

Эталон — в `solution/`, там прокомментировано, почему какая переменная стоит на своей оси.
</details>

### Три ошибки, которые здесь делают

**Продублировать `ansible_user` в каждой группе.** Работает — пока однажды не поменяется в трёх местах из четырёх. Общее живёт в `all` ровно один раз.

**Завести группу `prod` и группу `production`.** Или `db` и `database`. Две группы, означающие одно и то же, — самый дешёвый способ получить конфигурацию, которая применяется к половине машин.

**Считать, что «более конкретная» группа сильнее.** Конкретность — не то свойство, по которому Ansible принимает решение. Сильнее потомок; равные разбираются по алфавиту.
