## I. Возвращение к десяти гигабайтам

Лийза кладёт перед тобой распечатку `lsof` из Таллина двухдневной давности.

```
rsyslogd  709  root  7w  REG  253,3  10737418240  0  /var/log/ops/audit.log.1 (deleted)
```

> — Вы это нашли и починили одним `reload`. Хорошо. А теперь скажите: почему так получилось?

> — Кто-то повернул журнал вручную.

> — Не вручную. — Она открывает `/etc/logrotate.d/ops`. — Вот кто. Каждую ночь, полгода подряд.

```
/var/log/ops/*.log {
    daily
    rotate 3
    compress
}
```

> — Три строчки, и все три правильные по отдельности. `logrotate` переименовывает файл, создаёт новый и уходит. А `rsyslogd` про это не знает: у него открытый дескриптор, а не имя. Он продолжает писать в переименованный файл. Потом, через три цикла, `logrotate` этот файл удаляет — и `rsyslogd` продолжает писать в удалённый.

> — И новый журнал остаётся пустым.

> — Именно. Полгода `/var/log/ops/audit.log` был пустым файлом, а всё писалось в невидимый. Вы этого не заметили, потому что смотрели в журнал через `journalctl`, а не в файл. Заметили только по месту.

> **LILITH:** *«Ротация журнала состоит из двух действий: переименовать файл и сообщить тому, кто в него пишет. Второе никогда не происходит само.»*

## II. Теория: как устроен logrotate

### Блок на каждый набор журналов

```
/var/log/ops/*.log {
    daily                 # когда поворачивать
    rotate 14             # сколько поколений хранить
    missingok             # нет файла — не ошибка
    notifempty            # пустой не поворачивать
    compress              # сжимать старые
    delaycompress         # но не самый свежий
    dateext               # суффикс -2025-10-23 вместо .1
    create 0640 syslog adm  # права нового файла
    sharedscripts         # скрипт один раз на весь блок
    postrotate
        /usr/lib/rsyslog/rsyslog-rotate
    endscript
}
```

### Два способа не сломать пишущую службу

**`postrotate` + сигнал.** Файл переименовывается, создаётся новый, службе посылают сигнал перечитать дескрипторы:

| Служба | Чем сказать |
|---|---|
| rsyslog | `/usr/lib/rsyslog/rsyslog-rotate` (внутри `kill -HUP`) |
| nginx | `kill -USR1 $(cat /run/nginx.pid)` |
| Apache | `apachectl graceful` |
| произвольная под systemd | `systemctl reload имя.service` |

**`copytruncate`.** Файл копируется, а оригинал обнуляется — дескриптор при этом остаётся действительным, и сигнал не нужен. Цена: строки, записанные между копированием и обнулением, теряются молча. Годится для программ, которые не умеют перечитывать дескрипторы.

Смешивать `copytruncate` с `create` бессмысленно: файл не пересоздаётся, создавать нечего.

### `sharedscripts` — не косметика

Путь `*.log` относится к нескольким файлам. **Без `sharedscripts` скрипт `postrotate` выполняется после каждого**: пять журналов — пять сигналов службе. С ним — один раз, после поворота всех.

### `delaycompress` — тоже не косметика

Свежеповёрнутый файл (`.1`) сжимается на следующем цикле, а не сразу. Это нужно ровно тем службам, что узнают о повороте с задержкой: пока процесс не перечитал дескрипторы, он ещё пишет в `.1`, и сжимать его рано.

### Чем запускается

```bash
systemctl status logrotate.timer   # современные системы — таймером
cat /etc/cron.daily/logrotate      # старые — задачей cron
logrotate -d /etc/logrotate.d/ops  # разбор и план, ничего не делается
logrotate -f /etc/logrotate.d/ops  # принудительный поворот
cat /var/lib/logrotate/status      # когда что поворачивалось в прошлый раз
```

Про `su`, `olddir`, `maxsize`, `dateformat`, а также про то, чем ротация journald отличается от logrotate, — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Журнал поворачивается каждую ночь, а `/var/log/app.log` уже неделю пустой. При этом место на диске уходит. Что происходит?»*

<details>
<summary>Подумай 30 секунд</summary>

Служба пишет в переименованный (а потом удалённый) файл: в блоке нет ни `postrotate` с сигналом, ни `copytruncate`.

Проверяется одной командой: `lsof +L1 | grep app` — покажет дескриптор с `NLINK=0` и настоящим размером.

Лечится сначала `reload` службы (место вернётся немедленно), потом строкой `postrotate` в конфигурации — иначе всё повторится следующей ночью.
</details>

**LILITH:** *«В блоке есть `postrotate` с `systemctl reload nginx` и путь `/var/log/nginx/*.log`. Что не так?»*

<details>
<summary>Ответ</summary>

Нет `sharedscripts`: `reload` выполнится столько раз, сколько журналов в каталоге. У nginx их обычно два (`access.log`, `error.log`), у сервера с десятком сайтов — двадцать.

Каждый `reload` сам по себе безобиден, но двадцать подряд в три часа ночи — это всплеск, который потом ищут в графиках задержек.

Директива `sharedscripts` ровно про это: выполнить скрипт один раз, после поворота всех файлов блока.
</details>

## IV. Задание: переписать ротацию

Артефакт — `artifacts/ops`, файл для `/etc/logrotate.d/`:

```bash
cp starter/ops artifacts/ops
bash tests/test.sh
```

Стартер — действующая конфигурация: та самая, из-за которой десять гигабайт оказались без имени. Описан только один журнал из двух, хранится три поколения, службе никто ничего не сообщает.

Нужно: оба набора журналов (`/var/log/ops` и `/var/log/nginx`), глубина хранения не меньше недели, сжатие с отложенным первым, права нового файла не шире `0640`, отсутствие шума на пустых файлах — и, главное, уведомление службы.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Два блока, по одному на службу. В каждом: периодичность, `rotate`, `missingok`, `notifempty`, `compress`, `delaycompress`, `create` с правами и владельцем, `sharedscripts` и `postrotate … endscript`.

Сигналы разные: `rsyslog` — через `/usr/lib/rsyslog/rsyslog-rotate`, `nginx` — `kill -USR1` по PID-файлу.

Эталон — в `solution/`, там же комментарий к каждому решению.
</details>

### Три ошибки, которые здесь делают

**Оставить `rotate 3`.** Три дня меньше, чем время обнаружения инцидента. Разбор 17 октября упёрся ровно в это: события 14-го уже почти ушли. Две недели — минимум, при котором понедельничный разбор пятничного происшествия возможен.

**Поставить `compress` без `delaycompress`.** Свежий файл сожмут в тот момент, когда служба ещё в него пишет. Получится сжатый файл, который растёт, и `.gz`, который не открывается.

**Забыть `sharedscripts` при пути с шаблоном.** Ошибка не даёт никакого симптома, кроме лишних перезагрузок службы каждую ночь.
