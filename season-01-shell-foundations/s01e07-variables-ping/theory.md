# Теория — s01e07

## 1. Скрипт, который всегда говорил «всё хорошо»

> *Первая зима в ЦОДе. Мне поручают ночной обход: проверить два десятка машин и записать, кто отвечает. Я пишу скрипт, гоняю, отчитываюсь: все живы.*
>
> *Утром выясняется, что одна машина лежала с полуночи.*
>
> *Палыч открывает мой скрипт и молча показывает на строку:*
>
> ```bash
> ping -c 1 $host
> echo "$host: OK"
> ```
>
> — Где здесь проверка?
> — Ну… пинг же.
> — Пинг — да. А `echo` печатает «OK» независимо от того, что пинг ответил. Ты написал не проверку, ты написал печатающую машинку.
>
> *Он дописывает две строки — `code=$?` и `if`.*
>
> — Команда всегда докладывает, чем кончила. Одним числом. Если ты его не спросил — ты не проверял, ты делал вид.

## 2. Переменные: что это на самом деле

Переменная в bash — это **строка**. Не число, не список, не объект: строка. `count=5` кладёт туда символы `5`, а арифметика возникает только в специальных конструкциях (`$(( ))`, `let`, `[ -eq ]`).

```bash
name="Max"          # присваивание — без пробелов вокруг =
echo "$name"        # подстановка — через $
echo "${name}ов"    # фигурные скобки задают границу имени
unset name          # удалить переменную
```

Область видимости: переменная живёт в текущей оболочке и **не видна** запущенным из неё программам, пока её не экспортируют:

```bash
GREETING="hi"
bash -c 'echo "$GREETING"'      # пусто: дочерний процесс не знает
export GREETING
bash -c 'echo "$GREETING"'      # hi
```

Отсюда `export` в `~/.bashrc` для `PATH`, `EDITOR`, `LANG`: экспортированные переменные наследуются дочерними процессами. Это и есть «переменные окружения» — тот же механизм, просто помеченный для передачи.

## 3. Кавычки: три вида и зачем каждый

| Форма | Что делает |
|---|---|
| `"$var"` | подставляет значение, сохраняя его целым (пробелы не разрывают) |
| `'$var'` | ничего не подставляет — строка как есть |
| `$var` | подставляет и **разбивает по пробелам**, плюс раскрывает шаблоны |

Третья форма — источник большинства аварий в скриптах. Она безопасна ровно до первого значения с пробелом, а такие значения приходят извне: имена файлов, аргументы, строки из конфигов.

```bash
files="report 2024.txt"
ls $files      # ls report 2024.txt  — два несуществующих файла
ls "$files"    # ls "report 2024.txt" — один существующий
```

Правило простое: **в кавычки берётся всё, кроме случаев, когда разбиение нужно осознанно.**

## 4. Код возврата: соглашение всего Unix

Каждый процесс завершается числом от 0 до 255. Ноль означает успех — и только ноль; все остальные значения означают разные виды неудачи. Логика обратная привычной («ноль — это ложь»), но у неё есть причина: успех один, а способов провалиться много, и номер кода их различает.

```bash
grep -q root /etc/passwd; echo $?    # 0 — нашёл
grep -q zzz  /etc/passwd; echo $?    # 1 — не нашёл
grep -q x    /nonexistent;  echo $?  # 2 — ошибка выполнения
```

Типичные соглашения: `1` — общая ошибка, `2` — неверное использование, `126` — файл не исполняемый, `127` — команда не найдена, `130` — прервано по Ctrl+C. Свой скрипт завершают явно: `exit 0` при успехе, `exit 1` при неудаче.

Именно на кодах возврата работают `if`, `&&` и `||`:

```bash
if ping -c 1 host >/dev/null; then ...   # if смотрит на КОД, а не на вывод
command_a && command_b                    # b выполнится, только если a вернула 0
command_a || echo "не вышло"              # сработает при ненулевом коде
```

## 5. `ping`: что он проверяет и чего не проверяет

```bash
ping -c 1 -W 2 example.com >/dev/null 2>&1
```

- `-c 1` — один пакет (без него `ping` на Linux будет слать до прерывания);
- `-W 2` — сколько ждать ответа. На Linux это **секунды**, на macOS `-W` задаётся в **миллисекундах** — классическое расхождение, из-за которого скрипт «работает у меня»;
- `>/dev/null 2>&1` — глушим и обычный вывод, и ошибки: нужен только код.

Что означает ненулевой код: ICMP-ответ не пришёл за отведённое время. Это **не тождественно** «сервер мёртв». Возможные причины: ICMP заблокирован файрволом (частая политика), потерян один-единственный пакет, недоступен маршрут, сервер жив, но перегружен.

Поэтому в реальном мониторинге `ping` — первая, самая грубая проверка. За ней идут проверка порта (`nc -z host 22`), запрос к приложению (HTTP-код), и только совокупность даёт вывод. В этой серии мы строим первый слой — и честно называем его первым.

## 6. Почему тест подменяет `ping`

Тест серии кладёт в `PATH` собственный `ping`, который отвечает по правилу «`up-*` — успех, остальные — неудача».

Причин две. Первая: тест не должен зависеть от сети — в CI её может не быть, а сборка не должна краснеть из-за чужого файрвола. Вторая: результат должен быть **одинаковым** на любой машине, иначе «зелёный» ничего не значит.

Приём общий: если инструмент лезет наружу, в тесте его заменяют предсказуемой заглушкой. Дальше в курсе так же подменяются `ss`, `dig`, `dpkg`.

## 7. Компромиссы проверки доступности

| Способ | Что подтверждает | Чего не видит |
|---|---|---|
| `ping` | хост отвечает на ICMP | заблокированный ICMP, мёртвый сервис на живой машине |
| `nc -z host port` | порт принимает соединение | приложение может отвечать ошибками |
| HTTP-запрос | приложение отвечает | внутренние сбои, медленную БД |
| агент на машине | внутренние метрики | требует установки и доверия |

## 8. Метанавык: спрашивать результат, а не наблюдать процесс

Ошибка из воспоминания — не про bash. Она про разницу между **наблюдением** и **проверкой**. Наблюдение: команда что-то напечатала, значит, наверное, сработала. Проверка: команда сообщила результат, я его прочитал и принял решение.

Дальше в курсе это повторится на каждом уровне: `sshd -t` перед перезапуском вместо «вроде поправил конфиг» (S2), код возврата `ansible --check` вместо «плейбук вроде прошёл» (S4), health-check контейнера вместо «в логах не видно ошибок» (S7). Каждый раз одно и то же: у системы есть способ сказать «да» или «нет» явно — и надёжнее спросить, чем догадываться по косвенным признакам.
