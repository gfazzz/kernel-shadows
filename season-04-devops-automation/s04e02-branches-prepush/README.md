## I. «Вы будете делать это каждый день»

Ханс приходит с кофе и сразу к делу.

> — Пароль поменяли. Хорошо. Теперь скажите, что помешает завтра отправить следующий?

> — Внимательность?

> — Внимательность работает до первого дедлайна. — Он ставит кофе. — В CCC есть правило: если защита требует, чтобы человек каждый раз помнил, — это не защита, а пожелание. Защита — то, что срабатывает само.

Он открывает терминал и печатает то, что ты видел вчера в его истории команд:

```bash
git log origin/main..HEAD --stat
```

> — Вот что я смотрю перед каждой отправкой. Не «что я делал», а **что именно уедет**. Это разные множества, и второе почти всегда меньше, чем кажется.

> — А если забыть посмотреть?

> — Тогда пусть смотрит машина. Вы напишете скрипт, и мы повесим его на хук.

> **LILITH:** *«Ветка — это указатель. Отправка — это перенос указателя вместе со всем, до чего он дотягивается. Понять «что уедет» значит понять, какие коммиты достижимы отсюда и недостижимы оттуда.»*

## II. Теория: диапазон коммитов

### Две точки

```bash
git log main..HEAD          # что есть здесь и нет в main
git log HEAD..main          # обратное: что есть в main и нет здесь
git log main...HEAD         # симметричная разница: то и другое
```

Запись `A..B` читается как «достижимое из B, кроме достижимого из A». Это множество, а не отрезок времени: коммиты могут быть старыми по дате, но новыми для `main`.

Ровно это и уедет при `git push`. Отсюда привычка, которую стоит завести:

```bash
git log --oneline main..HEAD        # список
git diff main...HEAD                # суммарная разница
git log main..HEAD --stat           # что и насколько изменилось
```

### Ветка, слияние, перебазирование

```bash
git switch -c feature        # создать ветку и перейти
git switch main && git merge feature
git rebase main              # перенести свои коммиты поверх main
```

**Слияние** сохраняет историю как была и добавляет коммит с двумя родителями. **Перебазирование** переписывает ваши коммиты поверх чужих — история становится линейной, но хеши меняются.

Правило, о котором спорят, а нарушать всё равно не стоит: **не перебазировать то, что уже отправлено**. Чужие копии останутся со старыми хешами, и дальше начинается расхождение, которое чинят вручную.

### Конфликт — не поломка

```
<<<<<<< HEAD
наша версия
=======
их версия
>>>>>>> feature
```

Это не ошибка git, а вопрос к человеку: обе стороны изменили одно и то же место, и выбрать может только тот, кто знает, чего хотел. Опасность в другом — маркеры легко закоммитить, не заметив. Файл при этом выглядит правдоподобно и ломается только при запуске.

### Хуки

```
.git/hooks/pre-commit      перед созданием коммита
.git/hooks/pre-push        перед отправкой
```

Обычный исполняемый файл; ненулевой код останавливает операцию. Хуки **не отправляются** вместе с репозиторием — это локальная защита, и её ставит себе каждый сам (или раскладывает `core.hooksPath`).

Про `git bisect`, `blame`, `cherry-pick` и стратегии ветвления — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«`git log --oneline | wc -l` показывает 47 коммитов. Сколько уедет при `git push`?»*

<details>
<summary>Подумай 30 секунд</summary>

Неизвестно — вопрос про другое множество. Уедет то, чего нет на той стороне:

```bash
git log --oneline origin/main..HEAD | wc -l
```

Может быть один коммит из сорока семи, а может быть все сорок семь — если ветку ещё ни разу не отправляли.

Отсюда и смысл проверки перед отправкой: она должна смотреть на **диапазон**, а не на всю историю. Иначе она будет ругаться на то, что давно отправлено и уже не изменится.
</details>

**LILITH:** *«Скрипт-проверка нашёл секрет в коммите, который уже есть в `main`. Что делать?»*

<details>
<summary>Ответ</summary>

Прежде всего — понять, что проверка написана неправильно: она смотрит на всю историю вместо диапазона. Ругаться на отправленное бессмысленно, потому что отправка этого не изменит.

С самим секретом — отдельная история: он скомпрометирован, его надо менять, а не прятать. Но это не задача проверки перед отправкой; её задача — не пустить **новое**.

Практическое следствие: проверка, которая ругается всегда, перестаёт работать через неделю. Её отключат.
</details>

## IV. Задание: проверка до отправки

Артефакт — `artifacts/prepush_check.sh`: скрипт смотрит на коммиты, которых нет в базовой ветке, и отказывает, если среди них есть то, что отправлять нельзя.

```bash
cp starter/prepush_check.sh artifacts/prepush_check.sh
bash artifacts/prepush_check.sh --repo /tmp/shadow_iac
bash tests/test.sh
```

| Что ловить | Почему |
|---|---|
| работу прямо в основной ветке | изменения вносят через отдельную ветку |
| секреты в содержимом | `PASSWORD=`, `API_TOKEN=`, `BEGIN … PRIVATE KEY`, `ghp_…` |
| запрещённые имена файлов | `.env`, `*.pem`, `*.key`, `id_rsa` |
| слишком большие файлы | предел задаётся ключом |
| конфликтные маркеры | `<<<<<<<`, `=======`, `>>>>>>>` |

Каждая находка называет **коммит и файл**. Код возврата ненулевой, если найдено хоть что-то.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Список коммитов к отправке: `git rev-list "${BASE}..HEAD"`. Файлы коммита:
`git show --pretty=format: --name-only "${c}"`. Содержимое файла в коммите:
`git show "${c}:${f}"`. Размер: `git cat-file -s "${c}:${f}"`.

Удалённые файлы пропускаются — их содержимое в этом коммите не существует:
`git cat-file -e "${c}:${f}" || continue`.

Эталон — в `solution/`. Открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Проверять всю историю вместо диапазона.** Скрипт начнёт ругаться на то, что отправлено полгода назад и уже не изменится. Через неделю его отключат — и он не поможет тогда, когда понадобится.

**Искать секреты только по именам файлов.** `config.ini` с паролем внутри пройдёт. Имя — быстрый признак, содержимое — надёжный; нужны оба.

**Возвращать ноль при находках.** Хук смотрит **только** на код возврата. Подробный список проблем при `exit 0` не увидит никто, и отправка пройдёт.

## V. Хук

Ты сдаёшь скрипт. Ханс проверяет его на своём репозитории — там находится один `.pem`, забытый в старой ветке, — и одобрительно хмыкает.

> — Теперь ставим.

```bash
cp prepush_check.sh .git/hooks/pre-push
chmod +x .git/hooks/pre-push
```

> — И сразу скажу, чего это **не** даёт. Хук лежит в `.git`, а `.git` не отправляется. У Дмитрия его не будет, у Анны не будет. Это защита для вас, а не для команды.

> — А для команды?

> — Для команды — то же самое, но в конвейере, который выполняется на чужой машине и который нельзя отключить локально. Это послезавтра, в Берлине. — Он допивает кофе. — Сегодня осталось третье: сделать так, чтобы `.env` вообще не попадал в коммит. Не «проверить и отказать», а «не заметить».

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   Проверка стоит, хук на месте, отправка под контролем.      │
│                                                              │
│   Но всё это ловит секрет уже В КОММИТЕ. А лучше бы он       │
│   туда не попадал — и для этого есть один файл, который      │
│   в репозитории Дмитрия появился слишком поздно.             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
