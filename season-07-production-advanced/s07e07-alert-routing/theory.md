# s07e07 — теория: что Alertmanager делает с оповещением

Дополнение к [`README.md`](README.md). Здесь — путь оповещения от Prometheus до сообщения, устройство группы, `continue`, шаблоны уведомлений, кластер Alertmanager и то, чем заглушение отличается от всего остального.

---

## 1. Оповещение — это HTTP-запрос

```
Prometheus ──POST /api/v2/alerts──▶ Alertmanager
   каждые evaluation_interval, пока условие выполняется
```

Prometheus **шлёт оповещение повторно**, примерно каждую минуту, всё время, пока оно горит. Alertmanager хранит его с отметкой `endsAt` в будущем и считает погасшим, если повторов не приходит.

Отсюда две неожиданности:

**Перезапуск Alertmanager не теряет оповещения.** Через минуту Prometheus пришлёт их снова. Теряется только состояние групп и таймеров — то есть первое сообщение после перезапуска может прийти раньше, чем следовало.

**«Оповещение погасло» — это отсутствие повторов, а не событие.** Если Prometheus умер, все его оповещения тихо погаснут через `resolve_timeout`, и Alertmanager разошлёт уведомления о разрешении. Выглядит как «всё починилось». Ровно от этого и защищает `Watchdog` (см. [`s07e06/theory.md`](../s07e06-alert-rules/theory.md)).

---

## 2. Группа и её таймеры

Группа — это набор оповещений с одинаковыми значениями меток из `group_by`. У каждой группы свой независимый набор таймеров:

```
первое оповещение группы
   │
   ├── group_wait ───▶ сообщение №1 (всё, что накопилось)
   │
   ├── пришло новое оповещение в ту же группу
   │      └── group_interval с момента последнего сообщения ──▶ сообщение №2
   │
   └── ничего не менялось
          └── repeat_interval ──▶ напоминание
```

Тонкость, из-за которой настройки кажутся непредсказуемыми: `group_interval` отсчитывается **от последнего отправленного сообщения**, а не от прихода нового оповещения. Три новых оповещения в течение `group_interval` дадут одно сообщение, а не три.

Вторая тонкость: `repeat_interval` не может быть меньше `group_interval` — Alertmanager просто не будет отправлять чаще.

## 3. `continue` и ветки, которых не заметили

```yaml
routes:
  - matchers: [severity = page]
    receiver: oncall-phone
    continue: true          # ← спуск продолжается
  - matchers: [namespace = aurora]
    receiver: aurora-team-chat
```

По умолчанию спуск останавливается на первой подошедшей ветке. `continue: true` заставляет проверять остальные — так одно оповещение попадает и на телефон, и в чат команды.

Обратная сторона: **порядок веток имеет значение, и это не видно из файла.** Ветка `namespace = aurora`, поставленная выше `severity = page`, перехватит всё и оставит телефон без звонков. Проверять надо инструментом, а не глазами:

```bash
amtool config routes test --config.file=alertmanager.yml \
      severity=page namespace=aurora alertname=AuroraTargetDown
```

Команда печатает приёмники, в которые попадёт оповещение с такими метками. Это и есть модульный тест дерева — тот же приём «проверить свойство на фикстуре», что и в тесте этой серии.

## 4. Шаблоны: что дежурный увидит в три ночи

```
{{ define "slack.title" }}
[{{ .Status | toUpper }}] {{ .CommonLabels.namespace }} — {{ .Alerts | len }} шт.
{{ end }}
```

Сообщение собирается из группы, а не из одного оповещения: `.Alerts` — список, `.CommonLabels` — метки, общие для всех, `.CommonAnnotations` — общие пояснения.

Что стоит класть в сообщение, по убыванию полезности:

| Что | Зачем |
|---|---|
| что сломалось и где | `CommonLabels`: кластер, пространство имён, служба |
| сколько оповещений в группе | масштаб виден сразу |
| значения из `description` | числа, а не текст (см. [`s07e06`](../s07e06-alert-rules/)) |
| ссылка на инструкцию | `annotations.runbook_url` |
| ссылка на панель и на заглушение | чтобы не искать руками в три ночи |

Чего класть не стоит: полный список меток. В три часа ночи это шум, из которого приходится выуживать одну строку.

## 5. Alertmanager в нескольких экземплярах

Одиночный Alertmanager — единственная точка отказа всей конструкции: Prometheus может быть два, правила продублированы, а сообщение отправляет один процесс.

Решение необычное: экземпляры объединяются в кластер по протоколу сплетен и **договариваются, кто уже отправил**.

```
alertmanager-0 ◀──gossip──▶ alertmanager-1 ◀──gossip──▶ alertmanager-2
```

Дубликаты при этом всё же возможны — протокол даёт «не более одного в обычных условиях», а не строгую гарантию. Это сознательный выбор: лишнее сообщение лучше пропущенного, и распределённый консенсус ради оповещений — цена, которую платить не стоит.

Ровно та же логика, что у `retained`-сообщения брокера в [`s06e09`](../../season-06-embedded-iot/s06e09-mqtt-broker/): в системах доставки выбирают между «хотя бы раз» и «не более раза», и выбор зависит от того, что дороже — дубликат или пропажа.

## 6. Заглушение — инструмент человека, а не файла

```bash
amtool silence add alertname=AuroraHighLatency namespace=aurora \
       --duration=2h --comment="плановая миграция базы, тикет AUR-517"
```

| | подавление (`inhibit`) | заглушение (`silence`) |
|---|---|---|
| где живёт | в файле настройки | в состоянии Alertmanager |
| кто заводит | инженер, один раз | дежурный, по случаю |
| срок | постоянно | обязателен, до даты |
| смысл | «это следствие вот того» | «мы знаем, идут работы» |

Обязательный срок — не формальность. Бессрочное заглушение — самый популярный способ незаметно выключить мониторинг: его заводят на час, а снимают через год, обнаружив, что оповещение не приходило.

Практика, которую стоит завести: **заглушение без комментария и без тикета не заводится.** Через неделю никто не помнит, почему это выключено, а снимать страшно.
