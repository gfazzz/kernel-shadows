## II. Теория: куда идёт вывод и как поставить время

### Три потока

У каждой запущенной программы есть три канала: вход (`stdin`, 0), обычный вывод (`stdout`, 1) и вывод ошибок (`stderr`, 2). По умолчанию оба вывода идут на экран, поэтому кажется, что канал один.

```bash
echo "строка"  > file      # перезаписать файл содержимым stdout
echo "строка" >> file      # ДОПИСАТЬ в конец
команда 2> errors.log      # только ошибки
команда > out.log 2>&1     # и вывод, и ошибки в один файл
команда | tee -a run.log   # на экран И в файл (append)
```

Разница между `>` и `>>` — это разница между «файл содержит последнюю строку» и «файл содержит историю». Для журнала всегда `>>`.

> **LILITH:** *«Один потерянный символ — и вместо истории у тебя последняя строка. `>` открывает файл и обрезает его в ноль ещё до того, как команда начнёт писать. Не после — до.»*

Почему `stderr` существует отдельно: он позволяет отделить результат от жалоб. `команда > result.txt` положит в файл только полезный вывод, а ошибки останутся на экране — их видно сразу, и они не портят данные.

### Время: `date` и почему формат важен

```bash
date '+%Y-%m-%d %H:%M:%S'     # 2025-10-04 16:47:03
date -Iseconds                # 2025-10-04T16:47:03+07:00 (ISO 8601)
```

Формат `ГГГГ-ММ-ДД` выбран не случайно: такие строки **сортируются как текст** в хронологическом порядке. `04.10.2025` этим свойством не обладает — сортировка перемешает месяцы, и `sort` по журналу станет бесполезен.

Метку удобно вынести в функцию — тогда формат гарантированно одинаков во всех записях:

```bash
ts() { date '+%Y-%m-%d %H:%M:%S'; }
echo "[$(ts)] [UP] $host" >> "$log"
```

Про часовые пояса, UTC в распределённых системах, `logger`, ротацию и почему `tail -f` иногда замирает — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Скрипт пишет `echo "$line" > monitor.log` в цикле. Что окажется в файле после пятидесяти строк?»*

<details>
<summary>Подумай 20 секунд</summary>

Одна строка — последняя. Каждая итерация заново открывает файл на запись и обрезает его до нуля.

Правильно — `>>` внутри цикла. Либо, что чище, перенаправить **весь цикл** один раз: `done >> "$log"` — тогда файл открывается однократно, а не пятьдесят раз.
</details>

**LILITH:** *«Зачем в журнале время, если строки и так идут по порядку?»*

<details>
<summary>Ответ</summary>

Порядок говорит «что раньше», время — «когда именно» и «как долго». Без него нельзя ответить ни на один вопрос инцидента: когда началось, сколько длилось, совпало ли с деплоем, попадает ли в SLA.

Плюс журналы сопоставляют между машинами: строки из разных источников имеет смысл сливать только по времени. Поэтому же метку берут в едином формате, а на распределённых системах — в UTC.
</details>

## IV. Задание: мониторинг с журналом

Собери `server_monitor.sh` — капстоун второго эпизода. Он объединяет всё, что ты написал за день: переменные, код возврата, условие, цикл по списку — и добавляет память.

```
[2025-10-04 16:47:03] [UP]   shadow-server-01
[2025-10-04 16:47:05] [DOWN] shadow-server-31
[2025-10-04 16:47:07] SUMMARY: UP=2 DOWN=1
[2025-10-04 16:47:07] ALERT: 1 server(s) DOWN!
```

Каждая строка уходит и на экран, и в журнал; повторный запуск **дописывает**, а не затирает; при наличии недоступных узлов появляется `ALERT`.

```bash
cp starter/server_monitor.sh artifacts/server_monitor.sh
# заменить TODO (ts() + >> + tee + ALERT)
bash tests/test.sh
```

ТЗ и критерии — в [`mission.md`](mission.md). Тест проверяет наличие меток времени в формате `ГГГГ-ММ-ДД ЧЧ:ММ:СС`, верный итог, `ALERT` при падениях и — отдельной проверкой — что второй запуск **увеличил** файл, а не обнулил его.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
ts() { date '+%Y-%m-%d %H:%M:%S'; }
echo "[$(ts)] [UP]   $host" | tee -a "$log"
...
[ "$down" -gt 0 ] && echo "[$(ts)] ALERT: $down server(s) DOWN!" | tee -a "$log" >&2
```

`tee -a` пишет в файл и одновременно отдаёт строку дальше — на экран. Эталон — в `solution/`, открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Перепутать `>` и `>>`.** Разобрано выше и стоит того, чтобы повторить: это единственная ошибка серии, которая уничтожает данные, а не просто портит вывод. Причём молча.

**Ставить время один раз в начале.** Метка, вычисленная до цикла, будет одинаковой у всех пятидесяти строк. Проверка сорок девятого сервера окажется помечена временем первого — и разбор инцидента поедет на минуты. Время берут в момент записи.

**Слать `ALERT` только на экран.** Тревога, которой нет в журнале, существует ровно до закрытия терминала. В журнал она должна попасть обязательно; на экран (точнее, в `stderr`) — дополнительно, чтобы человек заметил сразу.
