# Теория — s04e01

## 1. Коммит, которого не было

> *Я потерял день работы. Написал большой кусок, не коммитил, потом решил «прибраться» и сделал `git checkout .`. Всё несохранённое исчезло — в этом git честен, он предупреждал.*
>
> *Хуже было в другой раз. Я делал `git reset --hard` на чужой ветке, перепутав окно терминала. Три коммита коллеги перестали быть видны. `git log` их не показывал. Я был уверен, что уничтожил чужую работу.*
>
> *Палыч посмотрел на экран секунд десять и набрал команду, о которой я не знал:*
>
> ```
> $ git reflog
> a3f19c2 HEAD@{0}: reset: moving to HEAD~3
> 8b2d4e1 HEAD@{1}: commit: обработка ошибок
> 5c9a7f3 HEAD@{2}: commit: тесты для парсера
> ```
>
> — Вот твои три коммита. `git reset --hard 8b2d4e1`, и всё на месте.
>
> — Но `git log` их не показывал!
> — `git log` показывает, что достижимо из текущей ветки. Коммиты никуда не делись — на них просто перестало указывать имя. Git почти ничего не выбрасывает сразу; удалённое живёт недели, пока не приберёт сборщик мусора.
>
> *И потом фраза, которую я записал:*
>
> — Запомни разницу. Коммит — это единственное действие в git, которое сохраняет. Всё остальное — перемещение указателей, и почти всё обратимо. Пока ты закоммитил, ты в безопасности. Пока не закоммитил — не в безопасности вообще.

## 2. Что такое коммит

```
commit ────► tree (снимок всего каталога)
   │            ├── blob  README.md
   │            └── tree  hosts/
   │                        └── blob servers.txt
   ├── parent ──► предыдущий commit
   ├── author + дата
   ├── committer + дата
   └── сообщение
```

Хеш коммита — SHA-1 от всего этого вместе. Отсюда три свойства:

- **изменить коммит невозможно** — любая правка даёт другой хеш, то есть другой коммит;
- **хеш зависит от родителя**, значит, вся цепочка защищена: подменив старый коммит, вы меняете все следующие;
- **автор и коммиттер — разные поля**. При слиянии, `rebase` или применении чужого патча они расходятся.

Одинаковое содержимое хранится один раз: два файла с одним текстом — один blob. Поэтому репозиторий с историей часто меньше, чем кажется.

## 3. Три зоны

```bash
git status              # состояние всех трёх сразу
git status --short      # компактно: XY путь
git diff                # дерево ↔ индекс
git diff --staged       # индекс ↔ HEAD
git diff HEAD           # дерево ↔ HEAD
```

В `git status --short` два символа: первый — состояние в индексе, второй — в дереве. `MM` означает «изменён, добавлен в индекс и снова изменён» — в коммит попадёт средняя версия, а не та, что на диске.

```bash
git add -p              # добавлять по кускам, а не файлами целиком
git restore файл        # вернуть из индекса в дерево (было: checkout --)
git restore --staged ф  # убрать из индекса, оставив в дереве (было: reset)
```

`git add -p` стоит попробовать один раз: он превращает «закоммитил всё подряд» в осмысленный коммит, где каждое изменение относится к делу.

## 4. Ссылки на коммиты

| Запись | Что означает |
|---|---|
| `HEAD` | текущая позиция |
| `HEAD~3` | три коммита назад по **первому** родителю |
| `HEAD^2` | **второй** родитель (у слияния — сливаемая ветка) |
| `main@{yesterday}` | где была ветка вчера (по reflog) |
| `abc1234` | короткий хеш |
| `:/сообщение` | последний коммит, чьё сообщение содержит текст |

`~` идёт вглубь, `^` выбирает родителя. У обычного коммита родитель один, и `HEAD~1` = `HEAD^1` = `HEAD^`.

## 5. Чтение истории

```bash
git log --oneline --graph --all --decorate
git log --format='%h %an %ad %s' --date=short
git log --no-merges --author=Max
git log --since='2 weeks ago' --until=yesterday
git log -S 'DB_PASSWORD'        # коммиты, где менялось число вхождений строки
git log -p -- путь              # история файла с разницей
git log --follow -- путь        # то же, сквозь переименования
git show <хеш>:путь             # содержимое файла в том коммите
git rev-list --count HEAD
git shortlog -sn                # кто сколько закоммитил
```

**`git log -S` («кирка»)** ищет коммиты, где строка появилась или исчезла, — быстрый способ найти, когда именно завёлся секрет или откуда взялась странная настройка.

**`--diff-filter`** отбирает по типу изменения: `A` добавлен, `D` удалён, `M` изменён, `R` переименован. `git log --diff-filter=D -- .env` отвечает на вопрос «когда убрали».

## 6. Ветки и слияние

Ветка — файл в `.git/refs/heads/` с хешем внутри. Всё.

```bash
git switch -c monitoring        # создать и перейти (было: checkout -b)
git branch -vv                  # где какая ветка
git merge --no-ff monitoring    # слияние отдельным коммитом
git merge-base A B              # общий предок
git log --first-parent          # только основная линия, без деталей веток
```

`--no-ff` заставляет создать коммит слияния даже там, где можно просто передвинуть указатель. Спорная привычка: с ним видно, что работа шла в ветке; без него история линейнее.

**Точка расхождения после слияния.** `git merge-base main monitoring` вернёт вершину `monitoring`, потому что та уже стала предком `main`. Настоящая развилка — общий предок двух родителей коммита слияния:

```bash
M=$(git rev-list --merges -1 HEAD)
git merge-base "$M^1" "$M^2"
```

## 7. Что делать, когда всё сломалось

```bash
git reflog                      # куда указывал HEAD последние недели
git reset --hard <хеш>          # вернуть ветку и дерево на этот коммит
git restore --source=<хеш> путь # достать один файл из прошлого
git stash / git stash pop       # отложить незакоммиченное
git fsck --lost-found           # осиротевшие объекты
```

`git reflog` — журнал перемещений `HEAD` в **вашем** репозитории, локальный и не отправляемый. Он живёт девяносто дней и вытаскивает почти любую «потерю»: `reset --hard`, удалённую ветку, неудачный `rebase`.

Правило, вытекающее из всего этого: **закоммиченное почти невозможно потерять; незакоммиченное не защищено ничем.** Отсюда привычка коммитить часто и мелко — история чистится потом, работа не восстанавливается никогда.

## 8. Метанавык: история как источник фактов

Репозиторий — единственное место в проекте, где записано не мнение, а событие: кто, когда, что именно изменил. Это делает его инструментом расследования, а не только хранилищем.

Вопросы, на которые он отвечает за минуту и на которые иначе не ответит никто:

| Вопрос | Команда |
|---|---|
| когда сюда попала эта строка | `git log -S 'строка'` |
| кто последний трогал эту функцию | `git blame -L 40,60 файл` |
| когда сломалось | `git bisect` |
| что менялось в проде за неделю | `git log --since='1 week' --oneline` |
| что было в файле до удаления | `git show <хеш>:путь` |

И обратная сторона того же свойства: **всё, что попало в репозиторий, попало туда навсегда.** Пароль, ключ, дамп с персональными данными, размер зарплат в старой версии таблицы. История не только помогает — она ещё и помнит то, о чём вы предпочли бы забыть.

Отсюда практическое правило, ради которого написана эта серия: перед первым `push` в общий репозиторий имеет смысл посмотреть, что именно вы отправляете. После — поздно.
