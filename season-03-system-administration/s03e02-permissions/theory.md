# Теория — s03e02

## 1. `chmod 777`, который сделал хуже

> *Сайт на общем хостинге не мог писать в каталог загрузок. Я тогда знал ровно один способ починить права и применил его: `chmod -R 777 uploads`. Заработало.*
>
> *Через две недели в этом каталоге появился `.php`-файл, которого мы не клали. Веб-сервер его исполнил.*
>
> *Разбирались с Палычем. Он не стал спрашивать, зачем я поставил 777, — спросил другое:*
>
> — От чьего имени работает веб-сервер?
> — `www-data`.
> — А владелец каталога кто?
> — Тоже `www-data`.
> — То есть ему и так можно было писать. Что именно ты чинил?
>
> *Я не знал. Ошибка была не в правах вообще: в каталоге не хватало бита `x` на одном из родительских каталогов, и до `uploads` процесс просто не доходил. `777` эту проблему обошёл заодно со всеми остальными — и открыл запись всему миру.*
>
> — Запомни различие, — сказал Палыч. — «Не работает» и «не хватает прав» — не одно и то же. `chmod 777` не чинит права, он выключает вопрос. Ты перестаёшь видеть, чего не хватало, и заодно раздаёшь всё остальное.
>
> *Правильный порядок он показал тогда же: `sudo -u www-data ls каталог` — посмотреть **от имени того, кому нужен доступ**, и увидеть, на каком шаге путь обрывается. Занимает секунды и отвечает на настоящий вопрос.*

## 2. Девять бит и как их читают

```
rwx rwx rwx
 │   │   └ other  — все остальные
 │   └ group      — члены группы-владельца
 └ user           — владелец
```

Значения `r`=4, `w`=2, `x`=1 складываются внутри тройки. Отсюда `750` = `rwxr-x---`.

**Для каталога буквы значат другое, и это главный источник путаницы:**

| Бит | На файле | На каталоге |
|---|---|---|
| `r` | читать содержимое | получить список имён (`ls`) |
| `w` | изменять содержимое | **создавать и удалять** записи внутри |
| `x` | выполнять | входить, обращаться к файлам по имени |

Следствия, которые стоит осознать один раз:

- **Каталог с `r`, но без `x`**: `ls` покажет имена, но открыть ничего нельзя — даже файл с правами `777`.
- **Каталог с `x`, но без `r`**: список не получить, но если имя известно, файл откроется. Так делают «непубличные, но доступные по ссылке» каталоги.
- **Удаление определяется каталогом.** Файл с правами `444`, принадлежащий root, спокойно удаляется пользователем, у которого есть `w` на каталог.

## 3. Три специальных бита

```bash
chmod u+s file      # SUID  → 4000
chmod g+s file      # SGID  → 2000
chmod +t dir        # sticky → 1000
chmod 4755 file     # то же восьмерично
```

**SUID** меняет effective UID процесса на владельца файла. Без него не работали бы `passwd` (пишет в `/etc/shadow`), `su`, `sudo`, `mount`. Заглавная `S` вместо `s` означает, что бит установлен, а `x` нет — обычно это ошибка.

**SGID на файле** — то же для группы. **SGID на каталоге** делает совсем другое: новые файлы внутри наследуют группу каталога, а не основную группу создателя. Это стандартный способ организовать общую папку команды: `chgrp ops-logs /var/log/ops && chmod 2770 /var/log/ops`.

**Sticky на каталоге** запрещает удалять чужие файлы: удалить может владелец файла, владелец каталога или root. Именно поэтому `/tmp` — `1777`, а не `777`.

**Почему SUID на скриптах не работает.** Linux игнорирует бит SUID у файлов, исполняемых интерпретатором: между проверкой прав и запуском интерпретатора есть окно, в которое подставляется другой файл (классическая гонка). Поэтому `-rwsr-xr-x root root script.sh` бесполезен — а вот скомпилированная обёртка или `sudo` с правилом работают.

## 4. `umask`: откуда берутся права новых файлов

Права при создании — это `666` для файлов и `777` для каталогов **минус** маска:

```bash
umask            # 0022 — типичное значение
umask -S         # u=rwx,g=rx,o=rx
```

| umask | файл | каталог | где встречается |
|---|---|---|---|
| `022` | 644 | 755 | значение по умолчанию |
| `027` | 640 | 750 | ужесточённая политика: «остальные» не видят ничего |
| `002` | 664 | 775 | схема UPG, где группа = один человек |
| `077` | 600 | 700 | домашние каталоги на многопользовательской машине |

Маска — свойство процесса, наследуется потомками и задаётся в `/etc/login.defs`, `/etc/profile` или в юните systemd (`UMask=`). Файл, созданный демоном, получает маску **демона**, а не администратора — отсюда сюрпризы вида «скрипт создаёт логи с правами 644, хотя я ставил 027».

## 5. Инструменты и приёмы

```bash
chmod u+rw,go-rwx file        # символьная запись — понятнее и безопаснее
chmod -R u+rwX,go-w dir       # заглавная X: x только каталогам и уже исполняемым
chown max:ops-logs file       # владелец и группа
chgrp -R ops-logs /var/log/ops
stat -c '%a %U %G %n' file    # права восьмерично и владельцы одной строкой
find / -xdev -perm -4000 -type f -ls        # все SUID
find /home -xdev -perm -002 -type f -ls     # доступные всем на запись
find / -xdev -nouser -o -nogroup            # файлы без владельца (см. s03e01)
```

Заглавная `X` в `chmod -R u+rwX` заслуживает отдельной строки: она выставляет `x` только каталогам и файлам, у которых бит выполнения уже был. Рекурсивный `chmod -R 755` без этого делает исполняемыми все текстовые файлы подряд.

**ACL — когда трёх категорий мало.** Классическая модель отвечает на вопрос «владелец, группа, все». Если нужно «плюс вот этот один человек на чтение», начинают либо плодить группы, либо ставить `777`. Правильный ответ — списки доступа:

```bash
getfacl /var/log/ops
setfacl -m u:anna:r-x /var/log/ops
setfacl -m d:g:ops-logs:rwx /var/log/ops   # d: — правило по умолчанию для новых файлов
```

Наличие ACL видно по плюсу в конце строки `ls -l`: `drwxrws---+`. Не заметить его — обычная причина расхождения «права выглядят правильно, а доступ есть».

## 6. Атрибуты файловой системы — уровень ниже прав

Права отвечают на вопрос «кому можно». Атрибуты ext4 отвечают на другой — «что вообще возможно», и действуют даже на root:

```bash
lsattr /etc/passwd            # показать атрибуты
chattr +i /etc/sudoers        # immutable: файл нельзя изменить, удалить, переименовать
chattr +a /var/log/audit.log  # append-only: можно только дописывать
chattr -i /etc/sudoers        # снять
```

`chattr +i` не даёт изменить файл **никому**, включая root, пока атрибут не снят. Отсюда два применения, зеркальных друг другу:

- **защита**: `+i` на ключевых конфигурациях, `+a` на журнале аудита — случайная или автоматическая правка не пройдёт;
- **закрепление**: тот же `+i` на подсаженном файле. Администратор пытается его удалить, получает «Operation not permitted» от root и обычно решает, что это сбой файловой системы.

Проверка занимает секунду и в разборе инцидента не пропускается: `lsattr -R /etc /home 2>/dev/null | grep -v '^-\{20\}'`.

## 7. Что ищут в правах при разборе инцидента

| Находка | Чем плоха |
|---|---|
| SUID-файл вне `/usr`, владелец root | закладка: даёт root любому запустившему |
| копия `bash`, `python`, `find` с SUID | то же, и не требует эксплойта вовсе |
| каталог `777` без sticky | любой удаляет чужое |
| `/etc/*` доступен всем на запись | подмена конфигурации без прав root |
| приватный ключ с правами шире `600` | ключ читается всеми на машине |
| файл без владельца (`-nouser`) | остался от удалённой учётки, ждёт нового UID (s03e01) |

Список короткий и проверяется четырьмя командами `find` — поэтому его стоит прогонять не только после инцидента.

## 8. Метанавык: минимальные права как рабочая гипотеза

Принцип наименьших привилегий формулируют как правило безопасности, но полезнее считать его **инструментом отладки**. Когда доступ не работает, есть два пути: расширять права, пока не заработает, или выяснить, какого именно бита не хватает.

Первый путь короче и всегда приводит к `777`. Второй занимает на пять минут больше и заканчивается знанием: не хватало `x` на промежуточном каталоге, или процесс работает от другого пользователя, или дело в ACL, которого не видно без `getfacl`.

Разница между этими путями — та же, что между «сделал, чтобы прошло» и «понял, что происходит». В правах она видна особенно ясно, потому что расширенные права не откатывают: они остаются жить, и через год никто уже не помнит, почему каталог открыт всему миру.
