## Обстановка

Первый из двадцати семи узлов сети `shadow_mesh`. На плате нет наклеек, в
коробке нет документации, а собранный на ноутбуке `collector` отвечает
`Exec format error`. Прежде чем что-то ставить, паять или прошивать, надо
выяснить, что это за железка: какой процессор, какая архитектура, что на
ней включено, а что выключено.

Снимки уже сняты и лежат в `data/` — самой платы для задания не требуется.

## Приказ

Заполнить `artifacts/board_report.txt` — 18 значений из снимков в `data/`.

```bash
cp starter/board_report.txt artifacts/
bash tests/test.sh
```

| Файл в `data/` | Что в нём |
|---|---|
| `cpuinfo_node7.txt` | `/proc/cpuinfo` платы |
| `devicetree_node7.txt` | обход `/proc/device-tree` (путь = значение) |
| `uname_node7.txt` | `uname -a`, снятый на плате |
| `build_host.txt` | рабочая машина Макса и собранный им бинарник |
| `arm_cpu_parts.txt` | справочник ARM: implementer + part → имя ядра |

## Требования

| Блок | Ключи | Что выяснить |
|---|---|---|
| плата | `model`, `soc`, `serial`, `board_arch`, `cores` | что это и сколько в нём ядер |
| процессор | `cpu_part`, `cpu_core` | номер части и имя ядра по справочнику |
| `compatible` | `compatible_specific`, `compatible_generic` | самое частное и самое общее описание |
| периферия | `gpio_status`, `spi_status`, `buses_okay`, `console` | что включено и куда плата говорит |
| сборка | `host_arch`, `binary_arch`, `runs_on_board`, `cross_prefix` | почему бинарник не пошёл |

## Чем добывать

| Что нужно | Как |
|---|---|
| модель | `awk -F' = ' '$1 ~ /device-tree\/model$/{print $2}' data/devicetree_node7.txt` |
| SoC, серийный | `awk -F': ' '/^Hardware/{print $2}'`, `/^Serial/` |
| архитектура платы | предпоследнее поле в `uname -a` платы |
| число ядер | `grep -c '^processor' data/cpuinfo_node7.txt` |
| имя ядра | `awk '$1=="0x41" && $2=="0xd08"{print $3}' data/arm_cpu_parts.txt` |
| `compatible` | первый и последний элемент списка корня дерева |
| включённые узлы | `grep '/soc/.*/status = okay' data/devicetree_node7.txt \| wc -l` |
| консоль | значение `console=` из строки `bootargs` целиком |
| архитектура бинарника | вторая запятая в строке `file build/collector` |

## Критерии приёмки

- [ ] `artifacts/board_report.txt` создан на основе `starter/`, 18 ключей заполнены.
- [ ] `board_arch` взят с платы (`aarch64`), а не с рабочей машины.
- [ ] `cpu_core` получен соединением `cpuinfo` со справочником, а не по памяти.
- [ ] `compatible_specific` — первый элемент списка, `compatible_generic` — последний.
- [ ] `spi_status` отражает, что узел выключен в дереве.
- [ ] `runs_on_board` следует из сравнения архитектур бинарника и платы.
- [ ] Комментарии в файле сохранены — отчёт объясняет, откуда каждое значение.
- [ ] `bash tests/test.sh` → 24 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep |
| Сеть | не нужна |
| **плата** | **не нужна** — разбираются снимки в `data/` |
| Внешние пакеты | нет |
| Изоляция теста | все ответы пересчитываются из `data/` |

Тест не содержит зашитых значений. Имя ядра он получает тем же соединением
со справочником, что и студент; `runs_on_board` — сравнением архитектуры
файла с архитектурой платы. Подмени снимки — тест будет ждать другие ответы.
Отдельно сверяется, что серийный номер совпал в двух независимых источниках
(`cpuinfo` и дерево устройств).

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `board_arch=x86_64` | спросили свой `uname -m` | архитектура платы — в `uname_node7.txt` |
| `cpu_core` не проходит | имя взято по памяти | соединить implementer + part со справочником |
| `compatible_*` перепутаны | список прочитан справа налево | первый элемент — частный, последний — общий |
| `buses_okay` больше ожидаемого | посчитаны все узлы | считать только `status = okay` |
| `console=ttyS0` | отрезана скорость | значение `console=` берётся целиком |
| `runs_on_board=yes` | сравнили не то | `x86-64` бинарника против `aarch64` платы |
| `binary_arch=ELF` | взято первое поле `file` | архитектура — после `64-bit LSB executable,` |

## После выполнения

Зелёный тест означает, что незнакомая плата опознана целиком — по её
собственным ответам, а не по наклейке на коробке. Заодно объяснён
`Exec format error`: дело не в правах и не в библиотеках, а в том, что
машина сборки и машина запуска — разные.

Стоит запомнить принцип, который дальше работает весь сезон: **в embedded
нельзя предполагать среду.** На сервере архитектура, набор устройств и
включённые шины одинаковы годами, поэтому о них не думают. Здесь каждая
плата — отдельный набор фактов, и каждый факт добывается командой.

## Кумулятивность

`collector`, который не запустился, — тот самый сборщик, которому в
[`s05e11`](../../season-05-security-pentesting/s05e11-hardening/) писали
профиль AppArmor: теперь его надо доставить на плату, и это отдельная
задача. Приём «сверить два независимых источника» (серийный номер в
`cpuinfo` и в дереве устройств) — прямое продолжение
[`s05e09`](../../season-05-security-pentesting/s05e09-forensics-snapshot/),
где `ps` сверяли с `/proc`. Формат Type C — отчёт из значений, добытых
командами, — тот же, что в
[`s05e07`](../../season-05-security-pentesting/s05e07-pentest-triage/).

Порядок чтения `compatible` («самое частное совпадение») — седьмая
семантика разрешения конфликтов в курсе после `sshd_config`, `ssh_config`,
`sudoers`, `.gitignore`, журнала systemd и инвентаря Ansible
([`s04e09`](../../season-04-devops-automation/s04e09-ansible-inventory/)).
Общего правила по-прежнему нет: каждый формат объявляет своё, и его читают
в документации.
