## Теория: `apt` + `dpkg` (один концепт: управлять пакетами)

**`apt`** — высокий уровень: находит, ставит, обновляет, удаляет, тянет зависимости из репозиториев.

```bash
sudo apt update            # обновить индекс (регулярно!)
apt search nmap            # найти
sudo apt install nmap      # поставить (+ зависимости)
sudo apt remove nmap       # убрать
```

**`dpkg`** — низкий уровень, под капотом apt. Им удобно **проверять статус**:

```bash
dpkg -l nmap               # строка "ii" = установлен корректно
dpkg -L nmap               # какие файлы принёс пакет
```

Репозитории (`/etc/apt/sources.list`), PPA и GPG-ключи, флаги apt и dpkg — в [`theory.md`](theory.md).

> **T3-фикс.** Раньше этот эпизод заставлял ставить `docker-ce` из кастомного репозитория до того, как Docker вообще объясняется. В v2.0 Docker ставится там, где преподаётся — в **Season 4**. Здесь — apt/dpkg на безопасных, сразу нужных пакетах.

## Проверка «в мире сюжета»

**Виктор:** *«Почему „напиши bash-скрипт, который устанавливает пакеты" — плохая идея в этом эпизоде?»*

<details>
<summary>Подумай 30 секунд</summary>

Потому что apt уже делает это — с разрешением зависимостей, GPG-проверкой, откатами. Обёртка на bash повторит малую часть и добавит багов. Type B: администратор пользуется готовым инструментом (`sudo apt install ...`), а скриптует только то, чего нет из коробки (например, отчёт о статусе).
</details>

**Виктор:** *«`dpkg -l nmap` показал строку, начинающуюся с `rc`. Пакет установлен?»*

<details>
<summary>Ответ</summary>

Нет. `ii` — установлен корректно; `rc` — пакет **удалён**, но остались его конфиги (removed, config-files present). Поэтому проверять статус надёжнее по префиксу `^ii`, а не просто «есть строка».
</details>
