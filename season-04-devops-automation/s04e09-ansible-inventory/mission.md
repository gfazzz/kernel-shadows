## Обстановка

Пятьдесят серверов записаны в файл по одному, разложены по четырём группам
и подключаются от root с паролем в том же файле. Определить по инвентарю,
какие из этих машин боевые, нельзя: различие есть только в именах хостов,
то есть в голове у того, кто их придумал.

## Приказ

Переписать `artifacts/inventory.yml`.

```bash
cp starter/inventory.yml artifacts/
bash tests/test.sh
```

## Требования

| Что | Почему |
|---|---|
| ровно 50 хостов, записанных диапазонами `имя[01:27].домен` | полсотни строк невозможно вычитать глазами |
| не меньше трёх групп по роли, у каждой `ops_role` и `open_ports` | это свойства того, что машина делает |
| ровно две группы-контура с `ops_env` | это свойство того, где она стоит |
| ни одна группа не задаёт обе оси сразу | иначе машину нельзя переставить между контурами |
| каждый хост ровно в одной группе каждой оси | иначе непонятно, чьи политики к нему применятся |
| ни одна переменная не задана в двух несравнимых группах | спор решит алфавит имён, а не смысл |
| `ansible_user` задан один раз, в `all`, и не `root` | общее живёт наверху; права повышают по месту |
| `ansible_port` доступен всем хостам по наследованию | проверка того, что цепочка групп собрана |
| ни одного пароля в файле | инвентарь лежит в репозитории |
| без `StrictHostKeyChecking=no` | подмена сервера должна оставаться заметной |
| в боевом контуре `log_level` не `debug` | объём журнала и лишние данные в нём |

## Чем добывать

| Что нужно | Как |
|---|---|
| диапазон хостов | `prod-web[01:27].shadow.io:` — ширина по первому числу |
| группа внутри группы | блок `children:` |
| переменные группы | блок `vars:` внутри группы |
| попасть в две группы | перечислить хост в обеих |
| посмотреть дерево (на своей машине) | `ansible-inventory -i inventory.yml --graph` |
| посмотреть итог по хосту | `ansible-inventory -i inventory.yml --host ИМЯ` |

## Критерии приёмки

- [ ] `artifacts/inventory.yml` создан на основе `starter/`, отступы — пробелы, кратно двум.
- [ ] Разобрано не меньше четырёх групп; уникальных хостов ровно 50.
- [ ] Хосты записаны диапазонами (не больше 15 строк с хостами).
- [ ] Не меньше трёх групп с `ops_role`; ровно две с `ops_env`.
- [ ] Ни одна группа не задаёт `ops_role` и `ops_env` одновременно.
- [ ] Каждый хост ровно в одной ролевой группе и ровно в одной группе-контуре.
- [ ] Ни одна переменная не задана в двух несравнимых группах.
- [ ] `ansible_user` встречается один раз и не равен `root`.
- [ ] Паролей нет; `StrictHostKeyChecking=no` нет.
- [ ] Контуры различаются по `ops_env`; в боевом `log_level` не `debug`.
- [ ] У каждой ролевой группы задан `open_ports`.
- [ ] `ansible_port` доходит до всех хостов по цепочке групп.
- [ ] `bash tests/test.sh` → 21 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + coreutils |
| Сеть | не нужна |
| `ansible` | **не нужен** — файл проверяется как текст |
| Внешние пакеты | нет |
| Изоляция теста | разбор по отступам, кратным двум: группа — хост — переменная |

Тест разворачивает диапазоны вида `host[01:27]` и считает то же, что считал
бы Ansible: в какие группы попал каждый хост (включая группы-предки) и какая
группа задаёт ему какую переменную. Главная проверка — неоднозначность:
если переменная задана в двух группах, ни одна из которых не предок другой,
тест называет обе и говорит, какая победит по алфавиту.

Тест дополнительно проверяет, что в стартере остались исходные ошибки: вход
от root с паролем и полсотни хостов, перечисленных по одному.

## Выполнение

```bash
cd season-04-devops-automation/s04e09-ansible-inventory
cp starter/inventory.yml artifacts/
$EDITOR artifacts/inventory.yml
bash tests/test.sh
```

Если ansible установлен, стоит посмотреть на результат его глазами:

```bash
ansible-inventory -i artifacts/inventory.yml --graph
ansible-inventory -i artifacts/inventory.yml --host prod-web01.shadow.io
```

Вторая команда — способ закончить любой спор о приоритете переменных
за десять секунд.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «отступ не кратен двум» | смешаны 2 и 4 пробела | привести к двум |
| «хостов не 50» | диапазон задан неверно | проверить границы; `[01:27]` — это 27 машин |
| «хосты перечислены по одному» | диапазоны не использованы | свернуть |
| «групп с ops_env — 0» | нет групп-контуров | добавить `production` и `staging` |
| «группа задаёт обе оси» | `ops_role` и `ops_env` в одной группе | развести |
| «хост вне ровно одной группы (0)» | забыт в одной из осей | перечислить в обеих |
| «неоднозначность: X в группах A и B» | переменная на двух осях | оставить на одной |
| «ansible_user задан в 4 местах» | продублирован по группам | поднять в `all` |
| «ansible_port не достаётся хостам» | цепочка групп разорвана | группы должны быть внутри `all.children` |

## После выполнения

Зелёный тест означает, что инвентарь стал моделью, а не списком: по нему
видно, чем машины отличаются, и любое различие можно применить или
проверить.

Стоит запомнить правило, которое переносится далеко за пределы Ansible:
**одна сущность отвечает на один вопрос**. Имя группы, читающееся через
союз «и» («веб **и** боевые»), — это две группы, склеенные заранее, и
расклеивать их придётся тогда, когда машин станет не пятьдесят, а пятьсот.

## Кумулятивность

Приоритет переменных — шестая семантика чтения конфигураций, названная в
курсе, и она не совпадает ни с одной предыдущей: `sshd_config` —
[`s02e09`](../../season-02-networking/s02e09-ssh-hardening/), `ssh_config` —
[`s02e10`](../../season-02-networking/s02e10-ssh-tunnels/), `sudoers` —
[`s03e03`](../../season-03-system-administration/s03e03-sudo/), systemd —
[`s03e05`](../../season-03-system-administration/s03e05-systemd-service/),
`.gitignore` — [`s04e03`](../s04e03-gitignore-secrets/). Запрет на
`StrictHostKeyChecking=no` продолжает
[`s02e08`](../../season-02-networking/s02e08-ssh-keys/): ключ хоста — это
единственная проверка, что вы разговариваете с тем же сервером, что вчера.
Отказ от входа под root — то же решение, что `User=` в юните
[`s03e05`](../../season-03-system-administration/s03e05-systemd-service/) и
`user:` в [`s04e06`](../s04e06-compose/). А хранение общих значений в одном
месте вместо копий — то же, что вынос зависимостей отдельным слоем в
[`s04e05`](../s04e05-dockerfile/).
