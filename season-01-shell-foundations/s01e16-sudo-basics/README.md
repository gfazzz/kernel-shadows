## Три команды, которых ты не видел

Файл от Дмитрия открывается в четыре раздела. Первые два ты видишь впервые.

```
=== whoami ===
max

=== id ===
uid=1000(max) gid=1000(max) groups=1000(max),4(adm),1101(ops-logs)
```

Тебя тут не просто зовут `max`. У тебя есть номер и три группы, и ни одну из них ты себе не выбирал.

Третий раздел — знакомый `ls -l`, но владельцы в нём чужие: `root`, `viktor`, `dmitry`. Твоё имя встречается ровно один раз — в последней строке, у файла, который ты сам туда положил вчера вечером.

Четвёртый раздел — `sudo -l`, и он самый неожиданный.

```
User max may run the following commands on ops-moscow-01:
    (root) /usr/bin/apt update
    (root) /usr/bin/apt install *
    (root) /usr/bin/systemctl status ops-collect
```

Три строки. Не «sudo работает» и не «sudo не работает» — **список**.

А ниже, в журнале, красным:

```
max : user NOT in sudoers ; COMMAND=/bin/cat /srv/ops/plan.txt
```

Ты пытался прочитать чужой файл через `sudo`, и `sudo` отказал. Не система — именно он, по своему списку.

> **LILITH:** *«`sudo` — не «режим администратора». Это программа, которая смотрит в файл со списком и решает, разрешено ли тебе именно это. Список написал человек. Обычно — не ты.»*

## Теория: кто ты на машине

### `whoami`, `id`, `groups`

```bash
whoami        # только имя
id            # имя, номер, все группы
groups        # только группы
id anna       # то же про другого пользователя
```

```
uid=1000(max) gid=1000(max) groups=1000(max),4(adm),1101(ops-logs)
     │             │              └ все группы, включая основную
     │             └ основная группа: её получают создаваемые вами файлы
     └ номер пользователя; имя — это подпись к нему
```

Система работает с **номерами**, а не с именами: имя ищется в `/etc/passwd` при выводе. Отсюда `ls -l` иногда показывает вместо владельца просто число — значит, такого пользователя на этой машине нет.

**Ловушка в подсчёте групп:** основная группа перечислена и в `gid=`, и в списке `groups=`. Считать надо по одному списку, иначе получится на одну больше.

### Три уровня доступа на практике

```
-rw-r--r--  root  root      README        читают все
-rw-r-----  root  adm       access.log    читают root и группа adm
-rw-------  viktor viktor   plan.txt      читает только viktor
```

Один и тот же каталог, три разных ответа. Ты прочитаешь `README` как «остальные», `access.log` — потому что состоишь в `adm`, а `plan.txt` — никак. **`sudo` тут не поможет, если в списке нет `cat`.**

### `sudo` — программа со списком

```bash
sudo -l              # что разрешено лично мне
sudo apt update      # выполнить разрешённое от имени root
sudo -u anna ls      # от имени anna, если разрешено
```

Что происходит при `sudo команда`:

1. `sudo` спрашивает **твой** пароль — чтобы убедиться, что за терминалом ты;
2. читает список правил и ищет, разрешена ли тебе **именно эта команда**;
3. если да — запускает её от имени указанного пользователя (обычно `root`);
4. записывает в журнал: кто, когда, что.

Пароль спрашивается твой, а не root'а, — и это принципиально. У root в современных дистрибутивах пароля обычно нет вовсе: войти под ним напрямую нельзя, а `sudo` работает.

### Чем `sudo` отличается от `su`

| | `su -` | `sudo команда` |
|---|---|---|
| Пароль | root'а — один на всех, кто его знает | свой, личный |
| Объём прав | всё | ровно то, что в списке |
| Журнал | одна запись о входе | каждая команда отдельно |
| Отозвать доступ | сменить пароль у всех | убрать строку из списка |

Отсюда практика: `sudo` для конкретного действия, а не «зайду под root и поработаю». Разница видна в журнале — по нему потом восстанавливают, что происходило.

Про `/etc/sudoers`, `visudo` и то, как этот список пишут, — в [`theory.md`](theory.md); подробно — в Season 3.

## Проверка: LILITH задаёт вопросы

**LILITH:** *«`cat файл` отвечает `Permission denied`. Помогает ли `sudo cat файл`?»*

<details>
<summary>Подумай 30 секунд</summary>

Только если `cat` есть в твоём списке `sudo -l`. Иначе ты получишь `user NOT in sudoers` — и это будет записано в журнал.

`sudo` не «обходит права». Он запускает разрешённую команду от имени того, у кого прав больше. Если запускать нечего — прав не прибавится.

Перед `sudo` полезнее посмотреть `ls -l` и `id`: возможно, файл вообще не предназначен тебе, и правильный вопрос не «как прочитать», а «зачем он мне понадобился».
</details>

**LILITH:** *«Почему `sudo` спрашивает мой пароль, а не пароль root?»*

<details>
<summary>Ответ</summary>

Потому что проверяется не «знаешь ли ты секрет root», а «ты ли это». Пароль root при таком подходе вообще не нужен — и в Ubuntu, например, его нет: учётная запись заблокирована для входа.

Практическая выгода: доступ выдаётся и отзывается по одному человеку, правкой одной строки. При общем пароле root его пришлось бы менять всем сразу каждый раз, когда кто-то уходит.

Побочная: в журнале видно **кто именно** выполнил команду. При работе через `su` там был бы только «вошёл root».
</details>

## Разбор типичных ошибок

**Посчитать группы дважды.** Основная группа стоит и в `gid=`, и в списке `groups=`. Складывать их не надо — получится четыре вместо трёх.

**Посчитать все строки журнала со своим именем.** Их три, но одна — отказ (`user NOT in sudoers`). Успешных вызовов два, и разница между этими числами и есть смысл журнала.

**Решить, что `sudo` даёт доступ ко всему.** Список из `sudo -l` — это ровно три команды. Всё остальное, включая `cat` чужого файла, окажется в журнале как отказ.
