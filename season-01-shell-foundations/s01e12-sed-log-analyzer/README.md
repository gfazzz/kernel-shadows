## Теория: `sed` и сборка из готового

### `sed` — правка на лету

`sed` читает поток построчно, применяет к каждой строке команду и выдаёт результат в stdout. **Исходный файл не меняется** — если не попросить явно:

```bash
sed 's/error/ERROR/'   file     # заменить ПЕРВОЕ вхождение в строке
sed 's/error/ERROR/g'  file     # заменить все (g — global)
sed 's/error/ERROR/gi' file     # + без учёта регистра
sed '/^$/d'            file     # удалить пустые строки
sed '/^#/d'            file     # удалить комментарии
sed -n '10,20p'        file     # напечатать только строки 10–20
```

Для отчёта нужен ровно один приём — снять квадратные скобки с поля времени:

```bash
awk '{print $4}' access.log | head -1 | sed 's/[][]//g'
# было: [05/Oct/2025:03:47:23    стало: 05/Oct/2025:03:47:23
```

Запись `[][]` — это класс символов «`]` или `[`». Закрывающая скобка сразу после открывающей считается обычным символом, а не концом класса, — единственное место в регулярных выражениях, где порядок внутри скобок важен.

Флаг `-i` меняет файл на месте, и об этом подробно — в [`theory.md`](theory.md). Коротко: на боевых данных `-i` без резервной копии не пишут.

### Type B: инструмент из инструментов

Отчёт состоит из строк, каждую из которых ты уже умеешь получить — причём получал руками в двух прошлых сериях:

```bash
echo "Всего запросов: $(wc -l < "$log")"
echo "Уникальных IP:  $(awk '{print $1}' "$log" | sort -u | wc -l)"
awk '{print $1}' "$log" | sort | uniq -c | sort -rn | head -10
awk -F'"' '{print $3}' "$log" | awk '{print $1}' | sort | uniq -c | sort -rn
```

Роль bash здесь — собрать их вывод в один файл. Делается это одним перенаправлением на группу команд, а не пятьюдесятью `>>`:

```bash
{
    echo "=== ОТЧЁТ ==="
    echo "Всего запросов: $(wc -l < "$log")"
    ...
} > "$report"
```

> **Ольга:** *«Скрипт, который переписывает `grep` на bash, — это не мастерство, это незнание того, что `grep` уже написан. Мастерство в том, чтобы соединить пять готовых вещей и остановиться.»*

## Проверка: LILITH задаёт вопросы

**LILITH:** *«Почему `log_analyzer.sh` на bash — нормально, а „перепиши `grep` на чистом bash" — нет?»*

<details>
<summary>Подумай 30 секунд</summary>

Потому что это разные роли. В первом случае bash — оркестратор: он вызывает специализированные инструменты и склеивает их вывод. Во втором — реализация алгоритма, который уже реализован на C, отлажен за полвека и работает на порядки быстрее.

Оркестрация — сильная сторона оболочки. Вычисления — слабая. Type B про то, чтобы не путать одно с другим.
</details>

**LILITH:** *«`sed -i 's/x/y/g' prod.log` — что здесь опасного?»*

<details>
<summary>Ответ</summary>

`-i` правит файл на месте, немедленно и без подтверждения. Ошибка в шаблоне означает испорченный боевой журнал без возможности отката — а журнал часто и есть единственное свидетельство того, что произошло.

Порядок безопасный: сначала запустить **без** `-i` и посмотреть на stdout, потом — `sed -i.bak`, чтобы рядом осталась копия. И никогда не отлаживать шаблон сразу с `-i`.
</details>

## Разбор типичных ошибок

**Открывать файл отчёта на каждой строке.** Пятьдесят `>> "$report"` подряд работают, но читаются плохо и легко ломаются: достаточно один раз написать `>` вместо `>>` в середине — и всё, что выше, исчезнет. Группа `{ … } > "$report"` открывает файл один раз и делает намерение очевидным.

**Считать адрес найденным по подстроке.** `grep -c "$ip" log` для адреса `10.0.0.5` посчитает и `10.0.0.50`, и `110.0.0.5`. В отчёте, который прикладывают к делу, это не мелочь: точка в шаблоне значит «любой символ», а границ у подстроки нет. Минимум — `grep -c -w`, аккуратнее — сравнивать первое поле.

**Писать в отчёт то, чего не проверял.** Соблазн добавить строку «Атака подтверждена» велик — она выглядит solidно. Но отчёт отвечает только за то, что посчитано: сколько запросов, каких статусов, какие адреса совпали с базой. Вывод делает человек, и он должен видеть, из чего вывод следует.
