## II. Теория: что описывает compose

### Файл целиком

```yaml
services:      # что запускать
networks:      # кто кого видит
volumes:       # что переживает пересоздание
secrets:       # что не должно лежать в тексте
```

Ключа `version:` больше нет: он относился к схеме v1–v2 и с 2020 года игнорируется. Файл начинается со `services`.

### Порты: публикация — это не «дать доступ»

```yaml
ports:
  - "5432:5432"            # слушать на ВСЕХ интерфейсах хоста
  - "127.0.0.1:8080:8080"  # только локально
```

Внутри одной сети контейнеры видят друг друга **по имени службы** без всякой публикации: `collector` обращается к `db:5432`, и этого достаточно. `ports` нужен только тому, к кому приходят снаружи хоста.

Отсюда правило: **публиковать порт базы не нужно никогда.** Если очень надо подключиться руками — туннель из [`s02e10`](../../season-02-networking/s02e10-ssh-tunnels/).

### Сети

```yaml
networks:
  backend:
    internal: true    # без выхода наружу
  frontend:
```

Служба, подключённая только к `internal`-сети, не может обратиться в интернет вовсе. Для базы это правильное умолчание: ей некуда ходить.

### Секреты

```yaml
environment:
  POSTGRES_PASSWORD: пароль        # видно в docker inspect и compose config
  POSTGRES_PASSWORD_FILE: /run/secrets/db_password   # правильно
secrets:
  - db_password
```

Официальные образы понимают пару `*_FILE` именно для этого: значение читается из файла, смонтированного в `/run/secrets/`, и не попадает ни в метаданные, ни в список процессов хоста.

### Порядок запуска

```yaml
depends_on:
  db:
    condition: service_healthy
```

Простой список `depends_on: [db]` означает только очерёдность **запуска контейнеров**. Дождаться готовности службы можно единственным способом — через `healthcheck` у зависимости и `condition` у зависящего.

### Данные

```yaml
volumes:
  - db_data:/var/lib/postgresql/data
```

Без именованного тома данные живут в записываемом слое контейнера и исчезают вместе с ним при `docker compose down`. Именованный том переживает пересоздание и виден в `docker volume ls`.

Про `read_only`, `cap_drop`, `docker compose config` и профили — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Приложение иногда падает при старте с «connection refused», а при перезапуске работает. `depends_on` настроен. Почему?»*

<details>
<summary>Подумай 30 секунд</summary>

`depends_on` без `condition` ждёт **запуска контейнера**, а не готовности службы. Контейнер базы стартует мгновенно, сама база — через несколько секунд.

Приложение успевает обратиться в этот промежуток и получить отказ. При перезапуске база уже готова, и всё работает — отсюда «иногда».

Лечится парой: `healthcheck` у базы и `condition: service_healthy` у зависящего. Второй способ, если healthcheck негде взять, — повтор подключения в самом приложении, что честнее, но требует править код.
</details>

**LILITH:** *«Убрали `ports` у базы. Как теперь до неё достучится приложение?»*

<details>
<summary>Ответ</summary>

По имени службы: `db:5432`. Внутри общей сети compose поднимает встроенный резолвер, и имена служб разрешаются в адреса контейнеров.

`ports` вообще не про доступ между контейнерами — он про **публикацию наружу хоста**. Публиковать порт базы означает открывать её всему, что видит эту машину.

Проверить: `docker compose exec collector getent hosts db`.
</details>

## IV. Задание: собрать стек

Артефакт — `artifacts/compose.yaml`: две службы, сети, тома, секреты.

```bash
cp starter/compose.yaml artifacts/compose.yaml
bash tests/test.sh
```

| Требование | Почему |
|---|---|
| нет `version:` | устарел и игнорируется |
| образы с точной версией | завтра `latest` будет другим |
| у базы нет `ports` | внутри сети её видно по имени |
| публикуемый порт с адресом `127.0.0.1:` | иначе слушает на всех интерфейсах |
| пароль через `secrets` и `*_FILE` | `environment` видно в `inspect` |
| именованный том для данных базы | иначе исчезнут при `down` |
| `healthcheck` + `condition: service_healthy` | «контейнер запущен» ≠ «база готова» |
| `user`, `read_only`, `cap_drop` | то же, что `User=` и `ProtectSystem=` в юните |
| `internal: true` у внутренней сети | базе некуда ходить |
| `restart` у всех служб | после перезагрузки хоста стек должен вернуться |

Плюс убрать `privileged: true` и монтирование `docker.sock`.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

`healthcheck` для postgres: `test: ["CMD-SHELL", "pg_isready -U ops -d ops"]`.

`read_only: true` требует `tmpfs: [/tmp]` — иначе программе некуда писать временные файлы.

Эталон — в `solution/`, там же комментарий к каждому решению.
</details>

### Три ошибки, которые здесь делают

**Оставить `depends_on` списком.** Это самая незаметная из трёх: стек «работает», просто иногда падает при старте, и списывают на сеть.

**Спрятать пароль в `environment` через переменную `${DB_PASSWORD}`.** Выглядит аккуратно, но `docker compose config` подставит значение и напечатает его, а `docker inspect` покажет в метаданных контейнера. Нужен `secrets`.

**Смонтировать `docker.sock`, «чтобы контейнер видел контейнеры».** Через этот сокет можно запустить контейнер с примонтированным корнем хоста. Это не «немного прав», это root на машине.

## V. Финал эпизода: что значит «проверено»

Ты сдаёшь файл. Софи поднимает стек у себя и показывает вывод:

```
$ docker compose ps
NAME             STATUS
ops-db-1         Up 12 seconds (healthy)
ops-collector-1  Up 6 seconds
```

> — Видишь разницу? У базы написано `healthy`, у сборщика просто `Up`. Первое означает, что кто-то проверил; второе — что процесс существует.

Она пробует достучаться до базы снаружи:

```
$ psql -h 145.100.19.7 -U ops
psql: error: connection to server ... failed: Connection refused
```

> — А вчера это работало, и Дмитрий считал, что так и надо.

Приходит сообщение от Анны: «Проверила шесть образов с ключом. Все собраны в один день, все с одной машины — сборочной. Это не предатель, это один Dockerfile, который скопировали шесть раз».
