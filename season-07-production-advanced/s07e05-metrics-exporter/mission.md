## Обстановка

Приложение отдаёт метрики. Среди них — счётчик с идентификатором заказа в
метке: двадцать четыре ряда за минуту наблюдения и двести тысяч через
неделю. Плюс время ответа в миллисекундах там, где весь остальной кластер
в секундах, счётчик без `_total`, метрика без `HELP`, метрика без `TYPE` и
гистограмма без корзины `+Inf`.

Ни одно из этого не мешает приложению работать. Всё это мешает им
пользоваться — и мешать будет годами, потому что имена метрик не меняют.

## Приказ

Написать `artifacts/check_metrics.sh` — аудит выдачи `/metrics` по
соглашениям команды.

```bash
cp starter/check_metrics.sh artifacts/
bash artifacts/check_metrics.sh data/dirty/metrics.txt data/limits.txt
bash tests/test.sh
```

| Файл в `data/` | Что в нём |
|---|---|
| `dirty/metrics.txt` | выдача, написанная в спешке |
| `clean/metrics.txt` | она же после разбора |
| `*/answers.txt` | что нашёл `promtool` — для сверки, скрипту читать нельзя |
| `limits.txt` | порог кардинальности, базовые и запрещённые единицы |

## Договор

```
ISSUE <код> <семейство> <пояснение>
SUMMARY <n> issues, <m> metrics, <k> series
```

Коды: `no-help`, `no-type`, `unit`, `counter-suffix`, `histogram`,
`cardinality`. Семейство — имя без `_bucket`, `_sum`, `_count`.
Код возврата: `0` — чисто, `1` — есть нарушения, `2` — вход не разобрать.

## Чем добывать

| Что нужно | Как |
|---|---|
| у кого есть `HELP` и `TYPE` | строки `# HELP имя …` и `# TYPE имя тип` |
| ряды | всё, что не начинается с решётки |
| метки | между первой `{` и последней `}` |
| разные значения метки | разные пары `ключ="значение"`, а не разные ряды |
| порог и единицы | `limits.txt`, а не число в коде |

## Критерии приёмки

- [ ] На грязной выдаче найдены ровно те нарушения, что в `answers.txt`, — все шесть видов.
- [ ] На чистой выдаче нарушений нет.
- [ ] `answers.txt` в тексте скрипта не упоминается.
- [ ] Сводка печатает число нарушений, семейств и рядов, и все три совпадают с выдачей.
- [ ] Код возврата: 1 при нарушениях, 0 без них, 2 при неразобранном входе.
- [ ] Порог кардинальности и список единиц берутся из файла: тест меняет их и проверяет, что вывод изменился.
- [ ] Метки `le` и `quantile` в кардинальности не участвуют.
- [ ] Два прогона подряд дают одинаковый вывод; `stderr` пуст.
- [ ] `bash tests/test.sh` → 28 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep + sed |
| Сеть | не нужна |
| **Prometheus** | **не нужен** — выдачи сняты и лежат в `data/` |
| `promtool` | не нужен |
| Внешние пакеты | нет |
| Изоляция теста | вывод пишется в `mktemp -d`, выдачи только читаются |

Тест сверяет найденное с разбором `promtool`, а число семейств и рядов
считает из выдачи сам. Отдельно проверяется, что данные не выродились: в
грязной выдаче не меньше пяти разных нарушений и есть метка сверх порога,
в чистой — ни одного и кардинальность в пределах. И отдельно — что пороги
действительно читаются из файла, а не зашиты: тест поднимает порог и
объявляет плохой заведомо хорошую единицу.

```bash
bash tests/test.sh
```

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «лишнее: cardinality …» на чистой | считаются `le` или `quantile` | их набор задан определением |
| «не найдено: histogram …» | проверено только наличие `_bucket` | нужна именно корзина `+Inf` |
| «не найдено: no-type …» | семейство взято из `TYPE`, а не из рядов | искать надо по рядам |
| «в сводке … , а семейств …» | `_bucket`/`_sum`/`_count` посчитаны отдельно | свести к семейству |
| «порог из файла не используется» | число зашито в скрипт | читать из `limits.txt` |
| «два прогона дают разный вывод» | обход `for (k in arr)` в awk | отсортировать перед печатью |
| «пишет в stderr» | осталась отладка | убрать |

## После выполнения

Зелёный тест означает, что выдачу можно ставить в конвейер сборки — рядом
с проверками из Season 4 — и метрика с идентификатором в метке больше не
доедет до production.

Главное, что стоит унести: **метрика — это интерфейс, который нельзя
поменять.** На имена сошлются панели, оповещения и чужие запросы, и через
полгода переименование обойдётся дороже ошибки, которую оно исправляет.
Из шести нарушений пять — неудобство, а кардинальность — расход, который
не отменить: ряд, у которого была хоть одна точка, живёт до истечения
хранения.

## Кумулятивность

Проверка, встроенная в сборку, — продолжение
[`s04e07`](../../season-04-devops-automation/s04e07-ci-pipeline/): тот же
приём, что с линтером и тестами, применённый к метрикам.

Соглашения, вынесенные в файл, а не зашитые в скрипт, — та же мысль, что
в [`s05e12`](../../season-05-security-pentesting/s05e12-cis-check/), где
проверяемые пункты лежали отдельно от проверяющего.

Модель «Prometheus приходит сам» объясняет запас поверх измеренного пика
из [`s07e02`](../s07e02-deployment-manifest/): максимум снят с шагом в
тридцать секунд, и всплеск короче шага в него не попал.

Разделение «метрика против журнала» продолжает
[`s05e05`](../../season-05-security-pentesting/s05e05-access-log-trace/) и
[`s03e12`](../../season-03-system-administration/s03e12-logrotate/): там
журнал отвечал на вопрос «что именно случилось тогда», здесь ему этот
вопрос и оставляют.
