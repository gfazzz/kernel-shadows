## Обстановка

Ночью сервер Виктора принял около 4500 запросов в секунду. Он выстоял, но в
журнале доступа осталось больше ста мегабайт записей — и где-то среди них следы
того, кто на самом деле искал вход, пока все смотрели на график нагрузки.

Читать это глазами невозможно и не нужно. Нормальный запрос отвечает статусом
`200`; всё остальное — `401`, `403`, `404`, `5xx` — заслуживает взгляда.

## Приказ

Собрать `filter_attack.sh` — принимает путь к журналу, печатает подозрительные
строки (статус **не** `200`) и в конце их количество:

```
185.220.101.47 - - [...] "GET /admin HTTP/1.1" 403 0
185.220.101.47 - - [...] "POST /login HTTP/1.1" 401 0
Подозрительных запросов: 4
```

Использование: `./filter_attack.sh access.log`.

## Данные

| Что | Как |
|---|---|
| путь к журналу | первый аргумент — `"${1:?…}"` |
| проверка файла | `[ -f "$log" ]` до работы, иначе stderr + `exit 1` |
| фильтр | `grep -vE ' 200 ' "$log"` — пробелы вокруг числа обязательны |
| подсчёт | `count=$(grep -vE ' 200 ' "$log" \| wc -l)` |
| вывод итога | `echo "Подозрительных запросов: ${count}"` |

Формат строки — Apache Combined: `IP - - [дата] "запрос" статус размер`.
Статус стоит девятым полем; адресоваться к полю по номеру научимся в s01e11,
пока фильтруем по строке.

## Критерии приёмки

- [ ] `artifacts/filter_attack.sh` создан, есть shebang, `bash -n` без ошибок.
- [ ] Подозрительные строки попадают в вывод целиком.
- [ ] Нормальные `200`-запросы в вывод **не** попадают (фильтр реально фильтрует).
- [ ] Строка, где `200` встречается в размере ответа или в адресе, не считается нормальной по ошибке.
- [ ] Количество считается конвейером и совпадает с числом напечатанных строк.
- [ ] Отсутствующий файл → сообщение в stderr и ненулевой код возврата.
- [ ] Журнал без единой подозрительной строки → `0` и код `0`, а не молчание.
- [ ] `bash tests/test.sh` → 10 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + grep + coreutils |
| Сеть | не нужна |
| systemd / Docker / k8s | не нужны |
| Внешние пакеты | нет (`grep`, `wc`) |
| Изоляция теста | фикстура-журнал во временном каталоге |

Фикстура теста: нормальные запросы, атакующие с разными статусами и ловушки —
строка со статусом `403` и размером `1200`, строка с адресом `10.0.200.5`.
Ожидаемое число тест **считает по фикстуре**, а не хранит константой.

## Выполнение

```bash
cp starter/filter_attack.sh artifacts/filter_attack.sh
# заменить TODO
bash artifacts/filter_attack.sh ../data/access.log | head -20
bash tests/test.sh
```

Перед тем как верить числу — посмотри строки. `| head -20` занимает пять секунд
и один раз убережёт от отчёта, в котором всё сходится, кроме сути.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| в выводе есть нормальные запросы | фильтр не инвертирован | `grep -v`, а не `grep` |
| пропали атакующие строки со статусом 403 и размером 1200 | шаблон без пробелов ловит `200` внутри `1200` | `grep -vE ' 200 '` |
| `grep 'a\|b'` ничего не находит | базовый regex | добавить `-E` |
| скрипт молча завершается, когда совпадений нет | `set -e` + `grep`, вернувший 1 | убрать `-e` либо `\|\| true` |
| число не сходится с количеством строк | считается по другому шаблону | вынести шаблон в переменную и использовать её дважды |
| нет файла → «Подозрительных: 0» | нет проверки входа | `[ -f "$log" ]` до фильтра, иначе `exit 1` |

## После выполнения

Зелёный тест означает, что сто мегабайт превратились в список, который можно
прочитать. Это первое звено конвейера анализа логов в `shadow_toolkit`
(см. [`PROJECTS.md`](../../PROJECTS.md)).

Анне этого не хватит: ей нужны не строки, а адреса и частота — кто стучался чаще
всех. Для этого строку надо разложить на поля и посчитать повторы, а `grep`
работает со строкой целиком. Инструмент, который видит в строке колонки, — в
следующей серии.
