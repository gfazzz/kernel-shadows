## II. Теория: `find` — обход с условиями

`find` устроен не как «поиск по имени», а как **обход дерева с фильтрами**: он спускается во все подкаталоги и проверяет условия для каждого объекта.

```bash
find /etc                          # всё дерево целиком
find /etc -type f                  # только обычные файлы
find /etc -type d                  # только каталоги
find /etc -name '*.conf'           # по шаблону имени
find /etc -type f -name '*.conf'   # условия складываются: И то, И другое
find . -name '.*'                  # скрытые (имя начинается с точки)
```

Три вещи, которые стоит понять сразу.

**Кавычки вокруг шаблона обязательны.** В `find . -name *.conf` шаблон раскроет **оболочка** — ещё до запуска `find`, по текущему каталогу. Получится либо ошибка, либо тихо неверный результат. Кавычки передают шаблон самому `find`, и он применяет его на каждом уровне.

**`-name` смотрит на имя, а не на путь.** Файл `/etc/nginx/nginx.conf` для `-name '*.conf'` — это `nginx.conf`. Если нужен путь целиком — `-path '*/nginx/*'`.

**Условия комбинируются и отрицаются:**

```bash
find . -type f -size +1M           # больше мегабайта
find . -type f -mtime -1           # изменённые за последние сутки
find . -type f ! -name '*.log'     # всё, кроме логов
find . -type f \( -name '*.conf' -o -name '*.cfg' \)   # -o = ИЛИ
```

Найденное можно сразу обработать — `-exec`:

```bash
find . -type f -name '*.log' -exec du -k {} +    # размер каждого лога
```

`{}` подставляет найденный путь; `+` собирает аргументы пачками (быстро), `\;` запускает команду на каждый файл отдельно (медленно, но иногда необходимо). Про `-exec` против `xargs`, `-print0` и почему `-printf` нельзя брать в переносимые скрипты — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«`find . -name *.conf` — без кавычек. Что произойдёт?»*

<details>
<summary>Подумай 30 секунд</summary>

Шаблон раскроет оболочка ещё до запуска `find`, подставив имена `.conf`-файлов **из текущего каталога**.

Если такой файл там ровно один, команда превратится в `find . -name app.conf` — и ты получишь правдоподобный результат, отвечающий не на твой вопрос. Если файлов несколько — `find` выдаст ошибку про лишние аргументы. Если ни одного — шаблон уйдёт в `find` как есть, и всё сработает верно.

Хуже всего первый случай: команда молча ищет не то. Поэтому кавычки здесь не стилистика.
</details>

**LILITH:** *«Чем `-exec cmd {} +` отличается от `-exec cmd {} \;` на десяти тысячах файлов?»*

<details>
<summary>Ответ</summary>

`\;` запустит команду **десять тысяч раз** — по разу на файл. `+` соберёт аргументы пачками и запустит её несколько раз, передавая сотни путей за вызов.

На большом дереве разница — секунды против минут. Поэтому `+` предпочтителен везде, где команда принимает много аргументов (`du`, `rm`, `grep`). Форма `\;` нужна, когда команда обрабатывает строго один файл за раз.
</details>

## IV. Задание: инструмент инвентаризации

Собери `audit_tree.sh` — инструмент, отвечающий на четыре вопроса Дмитрия о **любом** дереве:

```
files=<всего обычных файлов>
configs=<из них *.conf>
hidden=<скрытых файлов>
largest=<имя самого большого файла>
```

Это `Type A`, и автоматизация здесь оправдана: вопросы повторяются, деревьев будет много, руками это не считается.

```bash
cp starter/audit_tree.sh artifacts/audit_tree.sh
# заменить TODO (find с условиями)
bash tests/test.sh
```

ТЗ и критерии — в [`mission.md`](mission.md). Тест кладёт файлы на разной глубине и пересчитывает эталон независимо, а отдельной проверкой запускает твой скрипт на **другом** дереве: инструмент, который считает верно только на одной фикстуре, — не инструмент.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
files=$(find "$dir" -type f | wc -l)
configs=$(find "$dir" -type f -name '*.conf' | wc -l)
hidden=$(find "$dir" -type f -name '.*' | wc -l)
largest=$(find "$dir" -type f -exec du -k {} + | sort -rn | head -1 | cut -f2- | xargs basename)
```

`du -k` даёт размер в килобайтах, `sort -rn` ставит крупное наверх, `basename` отрезает путь. Эталон — в `solution/`, открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Забыть кавычки в `-name`.** Разобрано выше: шаблон съедает оболочка, и скрипт начинает молча врать. Самая частая ошибка при работе с `find`.

**Считать каталоги вместе с файлами.** Без `-type f` в подсчёт попадут и каталоги — числа окажутся больше на количество папок. Инвентаризация, где «файлов» больше, чем файлов, бесполезна.

**Взять `find -printf` для размера.** Соблазнительно коротко — и работает только на GNU: на macOS и BSD такого флага нет, скрипт там просто упадёт. В переносимом варианте размер берут через `du` (или `stat` с проверкой платформы).
