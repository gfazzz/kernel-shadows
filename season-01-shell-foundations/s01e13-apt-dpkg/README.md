## II. Теория: два уровня одного механизма

### `apt` — то, чем пользуются

`apt` знает про репозитории, зависимости, версии и подписи. Он решает задачу «мне нужен `nmap`» целиком:

```bash
sudo apt update                # обновить индекс: что вообще есть в репозиториях
apt search nmap                # найти по имени и описанию
apt show nmap                  # версия, размер, зависимости, описание
sudo apt install nmap          # поставить вместе с зависимостями
sudo apt remove nmap           # удалить, конфиги оставить
sudo apt purge nmap            # удалить вместе с конфигами
sudo apt autoremove            # убрать зависимости, ставшие ненужными
```

`apt update` не обновляет программы — он обновляет **список** того, что доступно. Программы обновляет `apt upgrade`. Путаница между этими двумя — самая частая ошибка первого месяца, и она объясняет загадочное «пакет не найден» на свежей системе.

### `dpkg` — то, что под ним

`apt` не устанавливает пакеты сам: он скачивает `.deb` и передаёт их `dpkg` — низкоуровневому менеджеру, который умеет распаковать пакет и записать его в базу установленного, но ничего не знает ни про репозитории, ни про зависимости.

Напрямую `dpkg` удобен, когда нужно **спросить**, а не изменить:

```bash
dpkg -l nmap             # статус: строка начинается с «ii», если установлен
dpkg -L nmap             # какие файлы принёс пакет
dpkg -S /usr/bin/nmap    # какому пакету принадлежит файл
```

Первые два символа вывода `dpkg -l` — это состояние: `ii` — установлен нормально, `rc` — удалён, но конфиги остались, `iU` — распакован, но не настроен. Поэтому проверка «есть ли строка про пакет» неверна: строка есть и у удалённого. Проверять надо префикс `^ii`.

Репозитории, PPA, GPG-подписи и почему `apt-get` живёт рядом с `apt` — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«`dpkg -l htop` вывел строку, начинающуюся с `rc`. Пакет установлен?»*

<details>
<summary>Подумай 20 секунд</summary>

Нет. `rc` означает `removed` + `config-files`: программу удалили, конфигурационные файлы остались. Бинарника нет, запустить нечего.

Именно поэтому в скрипте проверяют `dpkg -l "$pkg" | grep -q '^ii'`, а не просто наличие вывода. Разница между «строка нашлась» и «пакет работает» здесь стоит ложного отчёта о готовности системы.
</details>

**LILITH:** *«Почему „напиши bash-обёртку, которая ставит пакеты" — плохая идея?»*

<details>
<summary>Ответ</summary>

Потому что она уже написана и называется `apt`. Установка — это разрешение зависимостей, проверка подписей, порядок распаковки, откат при сбое и обработка конфликтов. Обёртка воспроизведёт процента три от этого и добавит собственных ошибок.

Это и есть смысл метки Type B: администратор пользуется готовым инструментом и пишет только то, чего в нём нет. Здесь нет — сверки списка нужного с тем, что стоит. Её и пишем.
</details>

## IV. Задание: что уже стоит

Собери `pkg_check.sh` — читает список пакетов и для каждого говорит, установлен он или нет:

```
  ✓ git — установлен
  ✓ curl — установлен
  ✗ htop — НЕ установлен
---
Установлено: 3 | Отсутствует: 2
```

Список — реальный: с шапкой-комментарием, пустыми строками и пояснениями после имени пакета.

```bash
cp starter/pkg_check.sh artifacts/pkg_check.sh
# заменить TODO (dpkg -l "$pkg" | grep -q '^ii')
bash artifacts/pkg_check.sh ../data/required_tools.txt
bash tests/test.sh
```

ТЗ и критерии — в [`mission.md`](mission.md). Тест подменяет `dpkg` заглушкой, поэтому проходит на любой машине — Ubuntu не нужна, root не нужен. В заглушке есть пакет в состоянии `rc`: скрипт, проверяющий просто наличие вывода, тест не пройдёт.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
pkg="${line%% *}"
if dpkg -l "$pkg" 2>/dev/null | grep -q '^ii'; then
    installed=$((installed + 1))
fi
```

Чтение списка с пропуском мусора — из s01e08, счётчики — оттуда же. Новое здесь только `dpkg`. Эталон — в `solution/`, открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Считать пакет установленным по наличию вывода.** `dpkg -l` печатает строку и для удалённого пакета, и для пакета, оставшегося наполовину настроенным. Инвентаризация, которая считает такие установленными, врёт ровно в ту сторону, в которую врать нельзя: «всё готово».

**Проверять через `which`.** Соблазн заменить `dpkg` на `which nmap` понятен, но проверяет он другое: наличие исполняемого файла в `PATH`. Многие пакеты вообще не приносят бинарников (библиотеки, конфигурации, шрифты), а иные приносят под другим именем. Вопрос «установлен ли пакет» адресуют менеджеру пакетов.

**Ставить всё подряд из списка.** Список — это то, что должно быть в итоге, а не то, что надо выполнить. Переустановка поверх работающего пакета может подтянуть новую версию, поменять конфиг и сломать то, что работало утром. Сначала выясняют разницу, потом закрывают только её.
