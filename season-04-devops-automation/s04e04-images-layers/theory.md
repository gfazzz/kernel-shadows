# Теория — s04e04

## 1. Сборка, которая шла двадцать минут

> *У нас была сборка на двадцать минут. Каждый раз. Правишь одну строку в коде — двадцать минут. Все привыкли и уходили за кофе.*
>
> *Палыч посмотрел Dockerfile и спросил, что в нём меняется чаще всего.*
>
> — Код.
> — А где он копируется?
> — Во второй строке.
>
> ```dockerfile
> FROM python:3.11
> COPY . /app
> RUN pip install -r /app/requirements.txt
> ```
>
> — Ты кладёшь код перед установкой зависимостей. Любая правка кода меняет слой `COPY`, а значит, все слои после него собираются заново. Каждый раз ты ставишь пакеты, которые не менялись месяц.
>
> *Он переставил две строки:*
>
> ```dockerfile
> FROM python:3.11
> COPY requirements.txt /app/
> RUN pip install -r /app/requirements.txt
> COPY . /app
> ```
>
> *Сборка стала занимать сорок секунд.*
>
> — Заметь, что мы не оптимизировали ничего. Ни одной команды не убрали. Просто расставили в порядке «что меняется реже — то выше». Кеш работает сверху вниз и ломается на первом изменении.
>
> *И добавил то, что я потом объяснял многим:*
>
> — Порядок инструкций в Dockerfile — это не стиль. Это единственное, что определяет, будете вы ждать сорок секунд или двадцать минут.

## 2. Что такое образ

```
образ = стопка слоёв (только чтение) + метаданные
контейнер = образ + тонкий записываемый слой сверху
```

Каждая инструкция, меняющая файловую систему (`RUN`, `COPY`, `ADD`), создаёт слой — **разницу** относительно предыдущего состояния. Слои хранятся отдельно, адресуются по содержимому и переиспользуются между образами: две сборки на одной базе делят её слои физически.

```bash
docker history образ            # слои, сверху вниз
docker inspect образ            # метаданные: User, Env, Cmd, WorkingDir
docker image ls                 # что лежит; считать по IMAGE ID, не по строкам
docker system df                # сколько занято и сколько можно освободить
docker save образ | tar -tv     # содержимое слоёв
```

Метаданные (`ENV`, `CMD`, `WORKDIR`, `USER`, `LABEL`) весят `0B` — они меняют не файловую систему, а конфигурацию.

## 3. Кеш

Слой берётся из кеша, если совпали инструкция и её вход. Для `RUN` вход — сама строка; для `COPY` — содержимое копируемых файлов. Первое расхождение обесценивает **всё, что ниже**.

Отсюда практика:

```dockerfile
# 1. база
FROM python:3.11-slim
# 2. системные пакеты — меняются раз в полгода
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
# 3. зависимости — меняются раз в неделю
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
# 4. код — меняется каждый раз
COPY . /app
```

`&& rm -rf /var/lib/apt/lists/*` **в той же инструкции** — важная деталь: отдельной инструкцией удаление ничего не даст, кеш apt останется в предыдущем слое.

## 4. Почему удаление не уменьшает образ

Файловая система образа — наложение слоёв. Удаление в верхнем слое записывает специальную пометку (whiteout), которая скрывает файл от верхнего уровня. **Данные остаются ниже.**

```dockerfile
COPY deploy_key /tmp/key      # слой: 3.24kB
RUN rm -rf /tmp/key           # слой: 0B, ключ по-прежнему в образе
```

Способы не создавать такой слой:

```dockerfile
# 1. секрет только на время инструкции, в слой не попадает
RUN --mount=type=secret,id=key cat /run/secrets/key | ...

# 2. многоступенчатая сборка: в итог переносится только результат
FROM golang:1.22 AS build
COPY . /src
RUN cd /src && go build -o /out/app

FROM gcr.io/distroless/static
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
```

Вторая ступень начинается с чистой базы; всё, что было в первой — исходники, компилятор, ключи, — в итоговый образ не попадает.

## 5. `.dockerignore`

```
.git
.env
*.pem
node_modules
__pycache__
```

Работает как `.gitignore`, но для **контекста сборки** — того, что отправляется демону при `docker build`. Без него `COPY . /app` затягивает внутрь `.git` со всей историей (включая удалённые секреты), локальные ключи и мусор.

Это ровно тот случай из этой серии: `deploy_key` мог попасть в образ не отдельной инструкцией, а вместе с `COPY . /app`.

## 6. Базовый образ

| База | Размер | Когда |
|---|---|---|
| `python:3.11` | ~1 ГБ | почти никогда: полный Debian с компиляторами |
| `python:3.11-slim` | ~130 МБ | обычный выбор |
| `python:3.11-alpine` | ~50 МБ | если зависимости собираются под musl |
| `distroless` | ~20 МБ | только рантайм, без оболочки |
| `scratch` | 0 | статически слинкованный бинарник |

Размер здесь — не главное. Главное — **поверхность**: каждая программа в образе может содержать уязвимость, и сканер честно посчитает их все. Разница между `3.11` и `3.11-slim` в этой серии — шестьдесят одна уязвимость против девяти.

`alpine` стоит выбирать осознанно: там musl вместо glibc, и часть пакетов Python собирается из исходников — сборка дольше, а иногда и не собирается вовсе.

## 7. Теги, дайджесты и воспроизводимость

```bash
FROM python:3.11                       # плавает: 3.11.6 сегодня, 3.11.9 завтра
FROM python:3.11.6-slim                # точнее
FROM python@sha256:9b8c1e…             # ровно тот образ, навсегда
```

`latest` — обычный тег, а не «самое свежее»: он указывает туда, куда его поставили, и это могли сделать вчера. Сборка, которая «вчера работала, а сегодня нет», при неизменном коде почти всегда объясняется плавающим тегом базы.

Дайджест даёт полную воспроизводимость и ту же цену, что везде: обновления безопасности надо забирать явно.

## 8. Метанавык: третий раз одно и то же

За три дня один и тот же вывод пришёл трижды, каждый раз с новым механизмом:

| Где | Что не убирает удаление | Как достать |
|---|---|---|
| git | коммит с файлом | `git show <хеш>:путь` |
| docker | слой с файлом | `docker save` + распаковать |
| файловая система | открытый дескриптор | `/proc/PID/fd/N` (`s03e08`) |

Общее устройство: система хранит **историю состояний**, а не текущее состояние. Удаление — это новая запись «теперь этого нет», а не стирание прошлого. Так работает почти всё, что умеет откатываться назад, — и это цена, которую платят за возможность отката.

Практический вывод один и тот же в трёх случаях: **секрет, попавший в такую систему, скомпрометирован.** Не «надо почистить», а «надо сменить, а потом уже чистить». Чистка меняет только то, что увидит следующий; у того, кто скачал раньше, всё осталось.
