## 1. Почему именно такой протокол

MQTT придумывали для нефтепроводов: спутниковый канал, оплата за байт, устройства с крошечной памятью. Отсюда свойства:

| Свойство | Как выражено |
|---|---|
| минимальный заголовок | 2 байта на пакет в простейшем случае |
| постоянное соединение | одно TCP-соединение, все сообщения через него |
| развязка сторон | издатель не знает подписчиков |
| работа на плохом канале | QoS 1/2, keepalive, сохранённые сессии |
| дешёвый клиент | реализация помещается в микроконтроллер |

Сравнение с соседями:

| Протокол | Модель | Где уместен |
|---|---|---|
| MQTT | публикация/подписка через брокер | много устройств, один центр |
| HTTP/REST | запрос-ответ | редкие обращения, богатая семантика |
| CoAP | запрос-ответ поверх UDP | очень ограниченные устройства |
| AMQP | очереди с маршрутизацией | корпоративная интеграция |
| Kafka | журнал с перемоткой | потоки данных, аналитика |

Ключевое отличие MQTT от Kafka, которое часто упускают: **у MQTT нет истории.** Брокер не хранит поток; подключившийся позже не увидит того, что было. Retained — единственное исключение, и оно хранит ровно одно последнее сообщение на тему.

## 2. Пакеты

| Пакет | Кто шлёт | Смысл |
|---|---|---|
| `CONNECT` / `CONNACK` | клиент / брокер | подключение, учётные данные, `will`, `clean_session` |
| `PUBLISH` | оба | сообщение в тему |
| `PUBACK`, `PUBREC`, `PUBREL`, `PUBCOMP` | оба | подтверждения QoS 1 и 2 |
| `SUBSCRIBE` / `SUBACK` | клиент / брокер | подписка |
| `UNSUBSCRIBE` / `UNSUBACK` | клиент / брокер | отписка |
| `PINGREQ` / `PINGRESP` | клиент / брокер | keepalive |
| `DISCONNECT` | клиент | корректное отключение |

Флаги `PUBLISH`, видимые в журнале:

```
(d0, q1, r1, m17, 'тема', ... (5 bytes))
 │   │   │   └ идентификатор сообщения (нужен для подтверждений)
 │   │   └ retained
 │   └ QoS
 └ dup: повторная отправка
```

Флаг `dup=1` — признак, что канал теряет пакеты: брокер или клиент отправляет сообщение повторно, не дождавшись подтверждения. Много `d1` в журнале — повод смотреть на сеть, а не на приложение.

## 3. Уровни доставки в деталях

### QoS 0 — «отправил и забыл»

```
клиент ──PUBLISH──▶ брокер
```

Один пакет, ноль подтверждений. Потеря не обнаруживается никем.

### QoS 1 — «хотя бы раз»

```
клиент ──PUBLISH──▶ брокер
клиент ◀──PUBACK─── брокер
```

Нет подтверждения — отправитель шлёт снова с `dup=1`. Отсюда **возможны дубликаты**, и обработчик должен быть идемпотентным: «установить температуру 22» повторить безопасно, «увеличить счётчик на 1» — нет.

### QoS 2 — «ровно раз»

```
PUBLISH ─▶  ◀─ PUBREC  ─▶ PUBREL  ◀─ PUBCOMP
```

Четыре пакета, двухфазная фиксация. Дороже вчетверо и медленнее; нужен там, где дубликат так же вреден, как потеря.

### Важная тонкость

QoS согласуется **на каждом участке отдельно**: издатель → брокер и брокер → подписчик. Публикация с QoS 2 не гарантирует, что подписчик получит её с QoS 2, — он получит минимум из QoS публикации и QoS своей подписки. Сквозной гарантии «ровно раз» от издателя до подписчика в MQTT нет вообще; она достигается идемпотентностью на стороне получателя.

## 4. Сессии и `clean_session`

| Флаг | Поведение |
|---|---|
| `clean_session=true` (`c1`) | сессия удаляется при отключении: подписки и неотправленные сообщения теряются |
| `clean_session=false` (`c0`) | брокер хранит подписки и копит сообщения QoS 1/2 до возвращения клиента |

Сочетание `clean_session=true` с QoS 1 — распространённое недоразумение: клиент просит гарантию доставки и тут же разрешает брокеру всё выбросить, пока его нет. Гарантия работает только внутри соединения.

Для узла, который отваливается и возвращается, обычно нужно `clean_session=false` плюс постоянный `client_id`. Ценой становится память на брокере: очередь копится всё время отсутствия клиента, и её надо ограничивать.

В MQTT 5 это заменено более честной парой: `Clean Start` (начать с чистого листа) и `Session Expiry Interval` (сколько хранить сессию после отключения).

## 5. Схема тем

Правила, экономящие месяцы:

| Правило | Почему |
|---|---|
| без ведущего `/` | `/shadow/...` создаёт пустой первый уровень |
| от общего к частному | `shadow/07/telemetry/temp`, а не `temp/07/shadow` |
| идентификатор ближе к началу | удобно подписываться на «всё про устройство» |
| не класть данные в имя темы | `.../temp` со значением в нагрузке, а не `.../temp/23.5` |
| отдельная ветка для команд | `shadow/07/cmd/...` — чтобы ACL мог разделить чтение и запись |
| одна тема — одна величина | иначе подписчик разбирает лишнее |

Разделение `telemetry/` и `cmd/` — не косметика: именно оно позволяет выдать узлу право писать в свою телеметрию и только читать команды, а панели — наоборот. Без такого разделения ACL выразить невозможно.

Полезно закладывать версию схемы: `shadow/v1/07/telemetry/temp`. Менять схему на работающей сети из двадцати семи устройств иначе нельзя — придётся останавливать всё.

## 6. Служебные темы `$SYS`

```bash
mosquitto_sub -h broker -t '$SYS/#' -v
```

| Тема | Что показывает |
|---|---|
| `$SYS/broker/clients/connected` | сколько клиентов сейчас |
| `$SYS/broker/messages/received` | принято сообщений |
| `$SYS/broker/load/messages/received/1min` | нагрузка |
| `$SYS/broker/subscriptions/count` | число подписок |

Подписка на `#` эти темы **не** покрывает — они выделены намеренно. Это стандартный способ мониторинга брокера; и это же первое место, куда стоит заглянуть, чтобы увидеть незваного клиента.

## 7. Мосты и общие подписки

**Мост** — соединение двух брокеров: локальный на площадке пересылает часть тем в центральный.

```
connection to-central
address central.example:8883
topic shadow/# out 1 "" ""
bridge_cafile /etc/mosquitto/certs/ca.crt
```

Полезно ровно тем же, чем полезен буфер: при обрыве канала до центра локальный брокер продолжает принимать данные узлов и отдаст их позже.

**Общие подписки** (MQTT 5): `$share/группа/тема` — сообщения распределяются между подписчиками группы, а не дублируются каждому. Так масштабируют обработчиков.

## 8. MQTT 5: что добавили

| Возможность | Зачем |
|---|---|
| коды причин в ответах | вместо «отказано» — почему именно |
| `Session Expiry`, `Message Expiry` | явные сроки жизни вместо булева флага |
| пользовательские свойства | метаданные рядом с нагрузкой |
| `Response Topic`, `Correlation Data` | запрос-ответ поверх публикации/подписки |
| общие подписки | горизонтальное масштабирование потребителей |
| `Topic Alias` | экономия на длинных именах тем |

Поддержка есть в mosquitto 2.x, но старые клиенты остаются на 3.1.1, и брокер обслуживает обе версии одновременно.

## 9. Инструменты

```bash
# послушать всё (на своём брокере!)
mosquitto_sub -h 10.30.4.11 -t '#' -v

# опубликовать retained
mosquitto_pub -h 10.30.4.11 -t 'shadow/07/telemetry/status' -m online -r -q 1

# СТЕРЕТЬ retained: пустая нагрузка с флагом r
mosquitto_pub -h 10.30.4.11 -t 'shadow/03/telemetry/status' -n -r

# подробный журнал брокера
mosquitto -c /etc/mosquitto/mosquitto.conf -v
```

Стирание retained пустым сообщением — единственный способ убрать застрявшее значение; сам по себе retained не истекает никогда (в MQTT 5 появился `Message Expiry`, но по умолчанию его нет).
