## II. Теория: как имя превращается в адрес

### Иерархия и путь запроса

Доменное имя читается справа налево: `mail.example.com.` — это корень (точка в конце), зона `com`, зона `example`, узел `mail`. Каждый уровень знает, кто отвечает за уровень ниже.

Резолвер, не имея ответа в кеше, спрашивает корневые серверы, те отсылают к серверам `com`, те — к серверам `example.com`, и уже последние дают ответ. Это видно целиком:

```bash
dig +trace example.com
```

### `dig` — основной инструмент

```bash
dig example.com A +short      # только значения
dig example.com MX +short     # почтовые серверы с приоритетами
dig example.com               # полный ответ: секции, TTL, какой сервер ответил
dig @8.8.8.8 example.com      # спросить конкретный резолвер
dig -x 8.8.8.8                # обратный запрос: адрес → имя
```

| Тип | Что хранит |
|---|---|
| `A` / `AAAA` | адрес IPv4 / IPv6 |
| `MX` | почтовые серверы с приоритетом |
| `NS` | серверы имён, отвечающие за зону |
| `CNAME` | алиас: «это имя на самом деле то имя» |
| `TXT` | произвольный текст: SPF, DKIM, подтверждения владения |
| `PTR` | обратная запись: адрес → имя |

**Приоритет MX устроен наоборот интуиции**: `5 mail-b` важнее, чем `10 mail-a`. Меньшее число — выше приоритет, и отправитель пробует сначала его.

### Порядок резолва на самой машине

Прежде чем спросить DNS, система заглядывает в локальные источники. Порядок задан в `/etc/nsswitch.conf`:

```
hosts: files dns
```

`files` — это `/etc/hosts`, и он идёт **первым**. Одна строка в этом файле переопределяет любой ответ DNS, и `dig` этого не покажет: он спрашивает DNS напрямую, минуя системный резолвер.

```bash
cat /etc/hosts                # локальные переопределения
cat /etc/resolv.conf          # какие резолверы использует система
resolvectl query example.com  # запрос через системный резолвер (Ubuntu)
```

Разница между `dig example.com` и `getent hosts example.com` — ровно в этом: первый спрашивает DNS, второй проходит весь путь, каким пойдёт настоящая программа.

> **Эрик:** *«Первое место, куда я смотрю на подозрительной машине, — не логи и не сеть. `/etc/hosts`. Это две секунды, и это самый дешёвый способ перенаправить трафик, который знают все.»*

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«MX вернул `10 mail-a` и `5 mail-b`. Какой сервер попробует отправитель первым?»*

<details>
<summary>Подумай 20 секунд</summary>

`mail-b`. У записей MX меньшее число означает более высокий приоритет: `5` — основной сервер, `10` — резервный.

Перепутать легко, и последствия тихие: почта продолжит доставляться, но через резервный узел — с задержками, другими лимитами и, возможно, мимо ожидаемых политик фильтрации.
</details>

**LILITH:** *«Домен резолвится в незнакомый адрес, но `dig` показывает правильный. Где ещё мог вмешаться атакующий?»*

<details>
<summary>Ответ</summary>

В `/etc/hosts`. Он имеет приоритет над DNS согласно `nsswitch.conf`, а `dig` его вообще не читает — отсюда и расхождение между «инструмент показывает правильно» и «браузер идёт не туда».

Проверять надо тем, что проходит настоящий путь: `getent hosts домен`. Если его ответ отличается от `dig +short`, разница объясняется локальными файлами — и это уже повод для разговора.
</details>

## IV. Задание: научиться спрашивать

Это **расследование**: инструмент писать не нужно, нужно прочитать ответы. Эрик уже снял их с резолвера дата-центра и положил в [`data/dig_capture_ops.txt`](../data/dig_capture_ops.txt) — восемь запросов с полными ответами, включая заголовки. Сеть для работы не понадобится.

Артефакт — заполненный `artifacts/dns_report.txt`:

```
a_records=10.50.1.100,10.50.1.101
mx_count=3
mx_primary=mail-primary.ops.internal.
www_cname_target=ops.internal.
nxdomain_name=backup.ops.internal
noerror_empty_type=AAAA
```

```bash
cp starter/dns_report.txt artifacts/dns_report.txt
# заполнять, вырезая нужную секцию снимка и читая ответ
bash tests/test.sh
```

Два последних поля просят различить **два разных «нет»**: имя, которого не существует, и имя, у которого нет записи запрошенного типа. В `dig +short` оба выглядят как пустота; отличить их можно только по заголовку полного ответа. Это и есть главное в серии.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
C=../data/dig_capture_ops.txt
sec() { awk -v h=";; ===== dig $1 =====" '$0==h{f=1;next} /^;; =====/{f=0} f' "$C"; }

sec "ops.internal MX"                       # секция целиком
sec "ops.internal MX" | awk '$4=="MX"'      # только записи нужного типа
grep -B1 'status:' "$C"                     # заголовки всех ответов подряд
```

В строке ответа поля такие: имя, TTL, класс, тип, значение. Эталон — в `solution/`, открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Искать по всему файлу вместо секции.** Адрес `10.50.1.100` встречается дважды: в ответе на запрос зоны и в ответе про `www`, где он пришёл следом за `CNAME`. `grep` по файлу целиком посчитает его два раза, и это не ошибка данных — это ответ на другой вопрос.

**Брать первую запись MX за основную.** В ответе они идут в произвольном порядке, и первым в снимке стоит сервер с приоритетом `20`. Приоритет — это число перед именем, и **меньшее** из них важнее.

**Считать пустой ответ отсутствием домена.** `NOERROR` с нулём записей означает, что имя существует, просто у него нет записи запрошенного типа — типичная история с `AAAA` там, где IPv6 не настроен. `NXDOMAIN` означает, что имени нет вовсе. Первое лечится другим запросом, второе — разговором с тем, кто ведёт зону.

## V. Шестьдесят секунд

Ты проходишь снимок секцию за секцией, и картина собирается за полчаса.

У зоны два адреса и два сервера имён — нормально. Три записи MX, приоритетный из них не тот, что стоит первым в ответе. `www` оказывается алиасом на вершину зоны. SPF заканчивается на `-all`: всё, что не с наших адресов, считать подделкой.

Два запроса не дали адреса, и по заголовкам видно, что это разные вещи: `backup.ops.internal` не существует вовсе, а у `ops.internal` просто нет записи `AAAA`.

А потом ты доходишь до `shadow-05` и останавливаешься.

Адрес публичный — `185.220.101.52`, хотя сервер стоит в московской стойке. И TTL шестьдесят секунд против трёхсот у всех остальных записей зоны.
