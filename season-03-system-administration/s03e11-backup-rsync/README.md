## Теория: как делают копии

### Полный, инкрементный, дифференциальный

| | Что копирует | Восстановление | Место |
|---|---|---|---|
| Полный | всё | из одного архива | много |
| Инкрементный | изменения с прошлого раза | полный + **все** инкременты по порядку | мало |
| Дифференциальный | изменения с последнего полного | полный + один последний | средне |

У инкрементного есть неприятное свойство: потеря одного звена цепочки делает нечитаемым всё, что после него. Именно поэтому существует четвёртый вариант.

### Снимок с жёсткими ссылками

```bash
rsync --archive --delete --link-dest=../latest ИСТОЧНИК/ СНИМОК/
```

`--link-dest` говорит: если файл не изменился по сравнению с указанным каталогом — не копируй, а сделай **жёсткую ссылку** на тот же inode.

В результате каждый снимок выглядит как полная копия — со всеми файлами, датами и правами, — а место занимает только под изменившееся. Восстановление из любого снимка не требует цепочки: он самодостаточен.

```
2025-10-21/  a.txt(inode 100)  b.txt(inode 101)
2025-10-22/  a.txt(inode 100)  b.txt(inode 205)   ← изменился только b
             └ та же ссылка       └ новый файл
```

Удаление старого снимка при этом безопасно: файл исчезнет только когда исчезнет последняя ссылка на него.

### Ключи `rsync`, которые нужны всегда

```bash
--archive        # = -rlptgoD: рекурсия, права, владельцы, время, ссылки, устройства
--hard-links     # сохранять жёсткие ссылки внутри источника
--delete         # удалять в копии то, чего нет в источнике
--numeric-ids    # не переводить UID в имена (на другой машине они другие)
--exclude-from=  # список того, что копировать не надо
--dry-run        # показать, что будет сделано, ничего не делая
```

Про `--delete` стоит помнить отдельно: он делает копию **зеркалом**, а не архивом. Удалили файл случайно — ближайший бэкап удалит его и в копии. Именно поэтому снимков держат несколько.

**Косая черта в конце источника значима:** `rsync src/ dst/` копирует содержимое, `rsync src dst/` создаёт `dst/src/`. Это источник половины сюрпризов с rsync.

### Манифест

```bash
find . -type f | LC_ALL=C sort | while read -r f; do sha256sum "$f"; done > .manifest.sha256
sha256sum -c .manifest.sha256      # проверка
```

Манифест отвечает на вопрос, на который сам факт наличия каталога не отвечает: **всё ли доехало и не побилось ли**. Пути в нём должны быть относительными — иначе сверить его с копией, восстановленной в другое место, невозможно.

Про 3-2-1-T, шифрование, `--bwlimit`, бэкап через SSH и то, почему снимок LVM не бэкап, — в [`theory.md`](theory.md).

## Проверка: LILITH задаёт вопросы

**LILITH:** *«Скрипт бэкапа запускается раз в сутки и идёт четыре часа. Однажды он завис. Что произойдёт на следующий день?»*

<details>
<summary>Подумай 30 секунд</summary>

Запустится второй экземпляр — и два `rsync` начнут писать в один каталог назначения. С `--delete` это заканчивается копией, в которой часть файлов удалена одним процессом, пока второй их писал.

Защита — блокировка: каталог или файл, создаваемый в начале и снимаемый в конце. Каталог (`mkdir`) удобен тем, что его создание атомарно на любой файловой системе, без внешних утилит.

Отдельно нужен таймаут: зависший бэкап должен падать, а не держать блокировку вечно.
</details>

**LILITH:** *«Бэкап лежит в `/srv/backup` на том же сервере. От чего он защищает?»*

<details>
<summary>Ответ</summary>

От удаления файла по ошибке — и всё.

Не защищает: от отказа диска (тот же диск), от шифровальщика (те же права), от того, кто получил root (стирает и оригинал, и копию), от пожара в датацентре.

Правило 3-2-1 отвечает ровно на это: **три** копии, на **двух** разных носителях, **одна** — вне площадки. Копия рядом с оригиналом считается за половину, потому что закрывает один сценарий из пяти.
</details>

## Задание: скрипт бэкапа

Артефакт — `artifacts/backup.sh`: инкрементальный снимок каталога с манифестом.

```bash
cp starter/backup.sh artifacts/backup.sh
bash tests/test.sh
```

Стартер — то, что написал Дмитрий: `cp -r` в каталог с датой. Работает, пока каталог небольшой и пока никто не спрашивает, из какого снимка восстанавливаться.

Что должно уметь получиться: снимок через `rsync --link-dest`, манифест с контрольными суммами и относительными путями, символьная ссылка `latest`, блокировка от одновременного запуска, список исключений, холостой прогон, ограничение числа хранимых снимков, сообщения об ошибках в stderr.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Каркас: разбор ключей `--source/--dest/--name/--exclude-from/--keep/--dry-run`, проверки входных данных, блокировка через `mkdir` с `trap` на выходе, сборка массива аргументов `rsync`, запуск, манифест, `latest`, ротация.

Массив удобнее строки: `args=(--archive --delete)`, потом `args+=(--link-dest=…)` по условию, и запуск `rsync "${args[@]}"`.

Эталон — в `solution/`. Открывай после попытки.
</details>

## Разбор типичных ошибок

**Сделать `latest` копией, а не ссылкой.** Тогда место занимает лишний полный снимок, а `--link-dest` перестаёт работать: он сравнивает inode, а у копии они другие.

**Записать в манифест абсолютные пути.** Восстанавливать будут в другое место — во временный каталог, на другую машину, — и сверить манифест с восстановленным деревом уже не получится.

**Не поставить блокировку.** Пока бэкап идёт двадцать секунд, это незаметно. Проблема появляется ровно тогда, когда бэкап начинает идти дольше интервала запуска, — то есть когда данных стало много.

> — А это важнее. Знаете, что чаще всего ломается в бэкапах? Не диск. Молчаливая порча: один блок, одна строка в базе, один файл скопировался наполовину, потому что его в этот момент писали. Копия есть, размер правильный, а внутри мусор. Без контрольных сумм вы узнаете об этом в момент восстановления.

> — А с ними?

> — А с ними — в момент проверки. Которую надо ещё не забыть делать.

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   Снимки делаются, место экономится, суммы посчитаны.        │
│                                                              │
│   Осталось то, из-за чего всё это и затевалось: кто-то       │

│                                                              │
└──────────────────────────────────────────────────────────────┘
```
