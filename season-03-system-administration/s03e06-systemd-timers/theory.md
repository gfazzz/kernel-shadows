# Теория — s03e06

## 1. Задача, которая работала только у меня

> *Написал скрипт выгрузки отчётов, проверил, положил в `crontab -e`, ушёл домой. Утром отчётов нет. Запускаю руками — есть. Ставлю в cron — нет.*
>
> *Полдня я добавлял в скрипт вывод в файл, пока не увидел строку:*
>
> ```
> line 4: psql: command not found
> ```
>
> — Cron даёт задаче почти пустое окружение, — сказал Палыч, когда я принёс это ему. — `PATH` там обычно `/usr/bin:/bin`, и ничего из того, что ты настроил в `.bashrc`, нет. Ты проверял скрипт в своей сессии со своим окружением, а cron запускает его в чужой.
>
> *Он показал два способа. Первый — писать полные пути. Второй, который он назвал правильным, — начинать скрипт со строки, задающей всё, на что он рассчитывает, и падать, если чего-то нет:*
>
> ```bash
> set -euo pipefail
> command -v psql >/dev/null || { echo "psql не найден" >&2; exit 1; }
> ```
>
> — Разница в том, что во втором случае ты узнаешь причину из первой строки лога, а не из четвёртой. И это, — добавил он, — единственная реальная защита от «у меня работает».

## 2. Cron и таймеры: что изменилось

| | cron | systemd.timer |
|---|---|---|
| Где описано | одна строка в crontab | два файла: `.timer` и `.service` |
| Догон пропущенного | нет (для этого ставили `anacron`) | `Persistent=true` |
| Когда следующий запуск | нигде не видно | `systemctl list-timers` |
| Результат прошлого запуска | письмо на локальный ящик, если настроено | `systemctl status`, журнал |
| Окружение | почти пустое, `PATH` урезан | как у любой службы, задаётся явно |
| Ограничение прав и ресурсов | нет | все директивы `systemd.exec` |
| Зависимости | нет | `After=`, `Wants=` |
| Разброс по времени | вручную (`sleep $RANDOM`) | `RandomizedDelaySec=` |
| Порог входа | одна строка | два файла и `daemon-reload` |

Последняя строка честная: для «раз в сутки почистить каталог» cron проще, и это не преступление. Таймеры выигрывают там, где важно знать, что задача **не** отработала.

## 3. Календарные выражения

Формат: `ДЕНЬ_НЕДЕЛИ ГОД-МЕСЯЦ-ЧИСЛО ЧАС:МИНУТА:СЕКУНДА`. Пропущенные части подставляются как `*`, лишняя точность необязательна.

| Выражение | Смысл |
|---|---|
| `minutely`, `hourly`, `daily`, `weekly`, `monthly`, `yearly` | готовые сокращения |
| `*:0/5` | каждые 5 минут |
| `*:0/15` | каждые 15 минут |
| `*-*-* 03:30:00` | ежедневно в 03:30 |
| `Mon..Fri 09:00` | по будням в 9 утра |
| `Sat,Sun 12:00` | по выходным в полдень |
| `*-*-01 00:00:00` | первого числа каждого месяца |
| `*-*-* *:00/30:00` | каждые полчаса |
| `2026-01-01 00:00:00` | однократно, в конкретный момент |

```bash
systemd-analyze calendar 'Mon..Fri 09:00'
systemd-analyze calendar --iterations=5 '*:0/5'
```

Вывод показывает нормализованную форму и ближайшие срабатывания. Ошибиться в календарном выражении легко, а обнаружить ошибку без этой команды можно только по отсутствию результата.

**Часовой пояс.** Выражения считаются в локальном времени системы, и это касается перевода часов: задача, назначенная на 02:30, в день перехода может не выполниться или выполниться дважды. Спасает `OnCalendar=… UTC` или монотонный таймер.

## 4. Монотонные таймеры

```ini
OnBootSec=15min           # через 15 минут после загрузки
OnStartupSec=5min         # через 5 минут после старта самого systemd
OnActiveSec=1h            # через час после активации таймера
OnUnitActiveSec=6h        # через 6 часов после ПОСЛЕДНЕГО запуска службы
OnUnitInactiveSec=1h      # через час после ЗАВЕРШЕНИЯ службы
```

Разница между двумя последними существенна для долгих задач. `OnUnitActiveSec=6h` у бэкапа, идущего пять часов, означает запуск через час после завершения предыдущего. `OnUnitInactiveSec=6h` — ровно шесть часов паузы между запусками, независимо от длительности.

Комбинация `OnBootSec=` + `OnUnitActiveSec=` — стандартный способ сказать «первый раз вскоре после загрузки, дальше раз в столько-то».

## 5. Точность и разброс

```ini
AccuracySec=1s              # умолчание — 1min
RandomizedDelaySec=30
```

По умолчанию systemd вправе сдвинуть срабатывание на минуту вперёд, чтобы собрать таймеры в пачки: это экономит пробуждения процессора и заметно на ноутбуках. Для интервала в пять минут минута — 20 % расписания, поэтому её задают явно.

`RandomizedDelaySec=` добавляет случайную задержку. На одной машине это незаметно; на двадцати — разница между «все ушли в один сетевой сервис в :00» и равномерной нагрузкой.

## 6. Служба, которую запускает таймер

```ini
[Service]
Type=oneshot
ExecStart=/usr/local/bin/ops-check.sh
TimeoutStartSec=120
```

- **`Type=oneshot`** — systemd ждёт завершения и знает код возврата. У `simple` служба считается запущенной в момент создания процесса, и результат теряется.
- **`Restart=` не задаётся.** Для `oneshot` systemd не примет `Restart=always`; повторные запуски — работа таймера.
- **`TimeoutStartSec=` обязателен по смыслу.** Пока экземпляр активен, следующий запуск не происходит: одна зависшая задача останавливает расписание насовсем, без единой ошибки.
- **Секция `[Install]` не нужна.** Включается таймер. `[Install]` в службе означает, что она вдобавок стартанёт при загрузке — расписание окажется описано в двух местах.

Для нескольких шагов подряд: `ExecStart=` можно повторять, они выполняются по порядку; `ExecStartPre=`/`ExecStartPost=` — подготовка и уборка; префикс `-` перед путём означает «не считать ошибкой ненулевой код».

## 7. Инструменты

```bash
systemctl list-timers --all              # что настроено, когда следующий и прошлый запуск
systemctl status ops-check.timer         # состояние таймера
systemctl status ops-check.service       # результат ПОСЛЕДНЕГО запуска
journalctl -u ops-check.service --since today
systemctl start ops-check.service        # проверить задачу, не дожидаясь расписания
systemd-analyze calendar '*:0/5'
systemctl edit ops-check.timer           # drop-in: изменить расписание чужого таймера
```

Пакетные таймеры (`logrotate.timer`, `fstrim.timer`, `apt-daily.timer`) правят только через drop-in: `systemctl edit` создаёт `override.conf`, который переживёт обновление пакета.

Отладка задачи начинается не с расписания, а с `systemctl start` службы вручную: если так она не работает, таймер ни при чём.

## 8. Метанавык: отсутствие события — тоже событие

Мониторинг ловит то, что произошло: ошибку, всплеск, падение. Задачи по расписанию ломаются иначе — они просто перестают происходить, и в журнале не появляется ничего. Отсутствие записей выглядит точно так же, как спокойная ночь.

Отсюда практика, которая стоит дороже любого расписания: у каждой периодической задачи должен быть способ ответить на вопрос «когда она отработала в прошлый раз» — отметка времени в файле состояния, запись в журнале, строка в `list-timers`. И должен быть кто-то, кто задаёт этот вопрос: проверка «последний успешный запуск был больше N назад» — обычно та самая, которую забывают написать.

`Persistent=true` из этой же логики: он не делает задачу надёжнее, он делает пропуск видимым и исправимым.
