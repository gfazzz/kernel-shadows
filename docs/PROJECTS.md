# PROJECTS — сквозные сезонные проекты и кумулятивность

**Назначение.** Ввести то, чего у курса сейчас нет: **кумулятивность через артефакты**.
Сейчас кумулятивность только нарративная — решения не переиспопьзуют артефакты
предыдущих серий, сезонных проектов нет (Season 4 README прямо пишет «Нет отдельного
финального проекта»). План рефакторинга вводит **единый растущий артефакт** — инфраструктурный
репозиторий/тулкит студента, который расширяется от S1 к S8.

> **Статус:** канон зафиксирован. Имена ниже стоят в сериях, сезонных README
> и критериях приёмки; `shadow_iac`, `shadow_mesh`, `aurora` и `shadow_core`
> собираются по сериям своих сезонов, а не пишутся с нуля в конце.

## 1. Канон сезонных deliverables

| Сезон | Проект | Что это | Что растёт / на что опирается |
|-------|-----------------------------|---------|-------------------------------|
| **S1** Shell | `shadow_toolkit` | bash-библиотека: логирование, проверки, общие функции | базовый слой — его `source`'ят поздние серии |
| **S2** Networking | `netshield` | конфиги firewall / DNS / VPN | использует `shadow_toolkit` |
| **S3** SysAdmin | `fleet_admin` | управление users / systemd / LVM / backup | + `shadow_toolkit` |
| **S4** DevOps | `shadow_iac` ⭐ | git + docker + CI + ansible — **интегрирующий репозиторий** | управляет артефактами S1–S3 |
| **S5** Security | `hardening_kit` | аудит / IR / harden поверх fleet | применяется к `shadow_iac` |
| **S6** Embedded | `shadow_mesh` ✅ | edge-узлы: плата, дрон, MQTT, модуль ядра | автономная ветка (edge), сдаёт телеметрию в S7 |
| **S7** Production | `aurora` ✅ | контур эксплуатации: манифесты, метрики, оповещения, SLO | принимает телеметрию `shadow_mesh`, измеряет всё вышеперечисленное |
| **S8** Final | `shadow_core` ✅ | приёмка инфраструктуры: 12 фаз, по одной на сезон | **проверяет всё** в капстоуне `s08e12` |

⭐ `shadow_iac` — центральный кумулятивный артефакт: с S4 инфраструктура студента
описывается как код и дальше только наращивается (S5 её защищает, S7 мониторит, S8 обороняет).

✅ — имя зафиксировано в сериях сезона, а не предложено. `shadow_mesh` собирается
по сериям S6, `aurora` — по сериям S7; схемы сборки в README соответствующих сезонов.

## 2. Как работает кумулятивность (механика)

- **`source` вместо копипаста.** Поздние серии подключают `shadow_toolkit`
  (`source lib/shadow_toolkit.sh`), а не переопределяют функции. Монолитный
  `ultimate_defense.sh`, который был размечен «Season 1…7» и ничего не
  `source`'ил, выведен в `personal/retired-s08/` вместе с остальными монолитами;
  его роль занял `shadow_core.py` — приёмка, а не копипаст.
- **Конфиги под управлением IaC.** Конфиги из S2–S3 с S4 попадают под Ansible/CI
  (`shadow_iac`), а не живут разрозненно.
- **Капстоуны сезонов.** Каждый сезон завершается вкладом в сквозной артефакт
  (не «отдельный финальный проект с нуля»). Это часть критериев приёмки серии.
- **Финал.** `shadow_core` (`s08e12`) — приёмка: двенадцать фаз, каждая проверяет
  свойство своего сезона и возвращает pass/fail. Не 117 строк «в вакууме», а
  прогон, который возвращает ноль или не возвращает (сделано 2026-08-24).

## 4. Метка Type A / B (обязательна в каждой серии)

Педагогическая таксономия курса — сохраняем и делаем явной в шапке README и `mission.md`:

- **Type A — Bash Automation.** Оправданная автоматизация; финал серии — скрипт-оркестратор
  (напр. ep11 «Type A — Bash Automation OK»).
- **Type B — Linux Configuration.** Акцент на конфигурировании инструментов
  (logrotate / ufw / systemctl); bash — только glue (напр. Season 3 «Type B подход»).

При дроблении осознанно выделять оправданные automation-серии, чтобы курс не свалился
целиком в конфиги. Баланс A/B — часть критериев приёмки. (Текущая коллизия: ep11 помечен
и как season-Type B, и как episode-Type A — согласовать при пересборке.)
