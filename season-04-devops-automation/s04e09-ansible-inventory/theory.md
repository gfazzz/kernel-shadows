# Теория — s04e09

## 1. Группа, которой не было

> *Мы разнесли серверы по группам: `web`, `db`, `backup`. Красиво. Потом появились две машины, которые были и `web`, и `backup`, — на них крутился сайт и лежали копии.*
>
> *Их записали в `web`, потому что «в основном они веб». Через месяц политика хранения копий поменялась, playbook прошёл по группе `backup`, и эти две машины его не увидели.*
>
> — Сколько копий потеряли? — спросил Палыч.
> — Ни одной. Просто они остались со старым сроком хранения. Заметили через полгода, при аудите.
> — То есть полгода вы считали, что у вас одна политика, а было две.
>
> *А потом сказал то, что я с тех пор проверяю первым делом:*
>
> — Вы записали машину в группу по тому, чем она **в основном** является. Групп не бывает «в основном». Либо признак есть, либо его нет. Если машина одновременно и то и другое — значит, признаков два, и групп тоже должно быть две.

## 2. Что такое инвентарь

Список машин и утверждений о них. Форматов два: `ini` (старый, компактный) и `yaml` (вложенность видна). В курсе — `yaml`.

```yaml
all:
  vars: { … }        # общее для всех
  children:
    имя_группы:
      hosts: { … }   # машины
      vars: { … }    # утверждения об этих машинах
      children: { … }# вложенные группы
```

Две группы существуют всегда: `all` (все машины) и `ungrouped` (те, кто не попал никуда). Вторая полезна как проверка: если в ней кто-то есть, инвентарь неполон.

```bash
ansible-inventory -i inventory.yml --graph          # дерево групп
ansible-inventory -i inventory.yml --host ИМЯ       # итоговые переменные хоста
ansible all -i inventory.yml --list-hosts           # кого затронет
ansible web -i inventory.yml -m ping                # проверка связи
```

`--host` — та же команда «что программа поняла», что `ssh -G`, `systemctl show` и `docker compose config`. Спрашивать её надо до запуска, а не после.

## 3. Диапазоны и шаблоны

```yaml
hosts:
  prod-web[01:27].shadow.io:     # 27 имён, ведущие нули по ширине первого числа
  db-[a:c].shadow.io:            # буквенный диапазон: db-a, db-b, db-c
```

Отдельно — **шаблоны выбора** в командной строке, они не то же самое, что группы:

| Шаблон | Кого выберет |
|---|---|
| `web` | группу целиком |
| `web:db` | объединение |
| `web:&production` | пересечение — веб-машины боевого контура |
| `web:!prod-web01*` | исключение |
| `~prod-web[0-9]+` | по регулярному выражению |

Пересечение `роль:&контур` — то, ради чего оси разводятся. С группой `prod-web` такой запрос невозможен.

## 4. Где живут переменные

| Место | Когда применять |
|---|---|
| `vars:` в инвентаре | немного значений, они про структуру |
| `group_vars/имя.yml` | обычный случай: файл на группу |
| `host_vars/имя.yml` | исключение для одной машины |
| `--extra-vars` | разовый запуск, сильнее всего |

`group_vars/` и `host_vars/` — каталоги рядом с инвентарём. Имя файла = имя группы или хоста. Это не «другой способ», а тот же самый: Ansible складывает их с тем, что в инвентаре.

## 5. Приоритет

По возрастанию силы (сокращённо; полный список в документации содержит 22 уровня):

```
1. переменные роли по умолчанию (defaults/)
2. переменные группы all
3. переменные групп-предков
4. переменные групп-потомков
5. переменные хоста (host_vars)
6. переменные задачи, потом --extra-vars
```

Спорный случай — **несравнимые группы**: ни одна не предок другой. Тогда порядок применения алфавитный по имени группы, и последняя переписывает предыдущую.

```yaml
web:        { vars: { log_level: info } }     # применится второй
production: { vars: { log_level: warn } }     # применится первой
```

Хост в обеих получит `info`. Изменить порядок можно переменной `ansible_group_priority` (больше — применяется позже, то есть побеждает), но это лечение симптома. Здоровый вариант — не создавать спор: одна переменная задаётся на одной оси.

Отдельно стоит запомнить: `ansible_group_priority` **сама** должна быть задана на уровне группы и не наследуется. Правило, у которого есть исключение из правил, — плохое место для того, чтобы на него опираться.

## 6. Чего в инвентаре быть не должно

| Что | Почему |
|---|---|
| `ansible_password`, `ansible_become_pass` | файл в репозитории; пароли — в vault |
| `ansible_user: root` | вход сразу с полными правами; повышают через `become` по месту |
| `StrictHostKeyChecking=no` | отключает единственную проверку, что это тот самый сервер ([`s02e08`](../../season-02-networking/s02e08-ssh-keys/)) |
| адреса вместо имён без нужды | инвентарь перестаёт читаться человеком |
| «временный» хост вне групп | не получит ни одной политики |

## 7. Дрейф: описанное и существующее

Инвентарь и playbook описывают, какими машины **должны быть**. Расхождение с тем, какие они есть, называется дрейфом и появляется всегда, когда кто-то заходит руками — обычно по уважительной и срочной причине.

Дрейф не лечится дисциплиной; он лечится тем, что описание регулярно применяется заново, а перед применением спрашивают, что изменится. Это и есть `--check --diff` — следующая серия.

## 8. Метанавык: одна ось за раз

Ошибка `prod-web` как имени группы — не про Ansible. Это общая ошибка классификации: **одна сущность отвечает сразу на два вопроса**, и дальше её нельзя изменить по одному из них, не задев другой.

| Смешано | Разведено |
|---|---|
| группа `prod-web` | `web` + `production` |
| ветка `feature-hotfix-v2` | ветка + метка + версия |
| каталог `2025-отчёты-финал` | дата + тип + состояние |
| роль `admin-backup` | право + область |

Признак смешения слышен на слух: имя читается через союз «и». «Веб **и** боевые», «правка **и** срочная **и** вторая версия». Каждое «и» — отдельная ось, и её стоит вынести раньше, чем список станет длинным: разделять десять сущностей дёшево, пятьсот — уже проект.
