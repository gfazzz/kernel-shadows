## Чему ты научишься

- Девяти битам прав и восьмеричной записи; тому, что для каталога `rwx` значат совсем другое.
- `chmod` и `umask`: откуда берутся права у только что созданного файла.
- Почему `chmod 777` — не «дать права», а выключить вопрос.
- Метанавыку: `Permission denied` — это сообщение, а не препятствие, и не повод набрать `sudo`.

Подробнее, с историей и подводными камнями, — в [`theory.md`](theory.md).

## Теория: как читается строка

```
-rwxr-x---  1  max  ops-logs  3120  Oct  8 16:02  collect.sh
│└─┬─┘└┬┘└┬┘     │      │
│  │   │  └ остальные — все, кто есть на машине
│  │   └ группа
│  └ владелец
└ тип: «-» файл, «d» каталог, «l» ссылка
```

Три группы по три буквы. В каждой: **r** — читать, **w** — изменять, **x** — выполнять.

### Восьмеричная запись

Каждая буква — это число: `r`=4, `w`=2, `x`=1. Сумма внутри тройки даёт одну цифру:

| Символьно | Цифрами | Что означает |
|---|---|---|
| `rwx------` | `700` | владелец делает всё, остальные ничего |
| `rw-------` | `600` | только владелец читает и пишет |
| `rw-r--r--` | `644` | обычный файл: пишет владелец, читают все |
| `rwxr-xr-x` | `755` | обычная программа: запускают все, меняет владелец |
| `rwxr-x---` | `750` | группа может читать и запускать, посторонние нет |

Отсюда `chmod 600 ключ` — не заклинание, а «читать и писать может только владелец». Программы, работающие с секретами, эту цифру проверяют и отказываются брать файл, который может прочитать кто-то ещё; самый известный такой случай разберём в [`s02e08`](../../season-02-networking/s02e08-ssh-keys/) (предпросмотр).

### Для каталога буквы значат другое

Это главная путаница, и её стоит пройти один раз:

- **`r`** — можно получить список имён (`ls`);
- **`w`** — можно **создавать и удалять** файлы внутри;
- **`x`** — можно войти внутрь и обратиться к файлу по имени.

Отсюда неочевидное: каталог с `r`, но без `x` покажет имена и не даст открыть ни одного файла. А право **удалить** файл даёт не файл, а каталог, в котором он лежит.

### `chmod`

```bash
chmod 700 secrets/           # цифрами: сразу всё
chmod u+x collect.sh         # символьно: добавить x владельцу
chmod go-rwx secrets/.env    # отнять всё у группы и остальных
chmod -R u+rwX,go-rwx ops/   # рекурсивно; заглавная X — только каталогам
```

Заглавная `X` заслуживает отдельной строки: она ставит `x` только каталогам и тем файлам, у которых он уже был. Обычный `chmod -R 755` делает исполняемыми все текстовые файлы подряд.

### Почему `Permission denied` — не повод набрать `sudo`

Именно с этим ты сталкивались в [`s01e01`](../s01e01-terminal-awakening/): `./whereami.sh` отвечал `Permission denied`, и в диагностике было сказано «запускай `bash whereami.sh`, про права — позже». Позже наступило: нет бита `x`, и `chmod u+x` решает вопрос без всякого root.

Про `umask`, откуда берутся права новых файлов, и про то, чем `chmod 777` вредит, — в [`theory.md`](theory.md).

## Проверка: LILITH задаёт вопросы

**LILITH:** *«У файла права `rw-------`, владелец `max`. Пользователь `anna` пытается его прочитать. Что она увидит?»*

<details>
<summary>Подумай 30 секунд</summary>

`Permission denied` — если у неё есть доступ в каталог. А если у каталога нет бита `x` для неё, она получит ту же ошибку **ещё на подходе**, не добравшись до файла.

Проверка идёт по пути целиком: сначала можно ли войти в каждый каталог, потом можно ли открыть файл. Отсюда частая загадка «права на файл правильные, а не читается» — дело в каталоге выше.
</details>

**LILITH:** *«Скрипт написан, запускается через `bash script.sh`, а через `./script.sh` — нет. Почему и что сделать?»*

<details>
<summary>Ответ</summary>

Нет бита `x`. `bash script.sh` запускает **интерпретатор** и передаёт ему файл как обычный текст — читать файл разрешено. `./script.sh` просит ядро **выполнить файл**, а на это нужен `x`.

Лечится `chmod u+x script.sh`. Заодно нужна первая строка `#!/usr/bin/env bash` — иначе ядро не знает, чем его выполнять.

`sudo` тут не при чём: файл твой, и права на нём ставишь ты.
</details>

## Задание: собрать рабочий каталог

Артефакт — `artifacts/setup_workspace.sh`: скрипт создаёт структуру каталога операции и выставляет права.

```bash
cp starter/setup_workspace.sh artifacts/setup_workspace.sh
bash artifacts/setup_workspace.sh --root /tmp/ops
ls -l /tmp/ops
bash tests/test.sh
```

| Каталог | Права | Почему |
|---|---|---|
| `scripts/` | `700` | свои инструменты: читать, писать и запускать только владельцу |
| `secrets/` | `700` | туда лягут ключи; посторонним нечего даже перечислять |
| `reports/` | `755` | отчёты отдают другим, значит их читают |
| `logs/` | `750` | журналы читает группа, посторонние нет |

Файлы внутри: в `secrets/` — `600`, скрипты в `scripts/` — `700`, отчёты — `644`.

**Главное требование:** скрипт должен не только создавать, но и **приводить к нужному виду**. Каталог, где кто-то уже поставил `777`, он обязан починить — и не сломать то, что уже правильно.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Полезно завести одну функцию: «сделать так, чтобы у пути были такие права» — она смотрит текущие через `stat`, сравнивает и вызывает `chmod` только при расхождении. Тогда повторный запуск молчит, а испорченное чинится.

`stat` отличается в Linux и macOS: `stat -c '%a'` против `stat -f '%Lp'`. Переносимо — попробовать первое, при неудаче второе.

Эталон — в `solution/`. Открывай после попытки.
</details>

## Разбор типичных ошибок

**Только создавать.** `mkdir -p` на существующем каталоге молчит и прав не трогает. Скрипт, который «работает» на пустом месте, ничего не сделает с каталогом, который уже испорчен, — а именно ради этого его и пишут.

**Поставить `chmod 777`, чтобы «наверняка».** Это не «дать нужные права», а выключить вопрос: писать в каталог сможет любой пользователь машины. Через неделю там появится файл, которого ты не клал.

**Потянуться к `sudo`.** Каталог твой, файлы твои — root не нужен ни для одной команды в этом задании. Тест это проверяет отдельно.
