# s07e01 — теория: как устроено то, что вы читаете

Дополнение к [`README.md`](README.md). Здесь — жизненный цикл пода, пробы, планировщик, ресурсы, инструменты разбора и то, чем чтение кластера отличается от чтения сервера.

---

## 1. Из чего состоит кластер

```
Deployment ──▶ ReplicaSet ──▶ Pod ──▶ Container(s)
    │              │            │
 «хочу 5»    «слежу за 5»   «единица   «то, что
                             планирования»  реально работает»
```

| Объект | За что отвечает |
|---|---|
| `Deployment` | желаемое состояние и стратегия обновления |
| `ReplicaSet` | поддержание нужного числа подов одной версии |
| `Pod` | группа контейнеров с общими сетью и томами |
| `Node` | машина, на которой поды исполняются |
| `Service` | стабильный адрес для меняющегося набора подов |

Практическое следствие для разбора: **вопрос «почему не работает» задаётся на разных уровнях, и ответы там разные.** `Deployment` скажет, сколько доступно; `ReplicaSet` — сколько создано; под — почему не запустился; контейнер — с каким кодом умер.

## 2. Жизненный цикл пода

```
Pending ──▶ ContainerCreating ──▶ Running ──▶ Succeeded / Failed
   │                                  │
   └ не назначен на узел              └ контейнеры запущены
```

| Фаза | Означает |
|---|---|
| `Pending` | под принят, но не все контейнеры запущены (часто — нет узла) |
| `Running` | под назначен, хотя бы один контейнер запущен |
| `Succeeded` | все контейнеры завершились успешно |
| `Failed` | все завершились, хотя бы один — с ошибкой |
| `Unknown` | состояние узла недоступно |

`CrashLoopBackOff` и `ImagePullBackOff` — **не фазы**, а причины ожидания внутри контейнера; в колонке `STATUS` `kubectl` показывает их вместо фазы, потому что так полезнее.

### `BackOff` — это выдержка, а не отказ

Кластер не перезапускает падающий контейнер бесконечно быстро: задержка растёт (10 с, 20 с, 40 с… до 5 минут). Тот же приём, что `Backoff` у клиента-датчика в [`s06e10`](../../season-06-embedded-iot/s06e10-sensor-client/), только применённый к контейнерам.

Отсюда полезное наблюдение: под, падающий давно, перезапускается **редко**, и «47 рестартов за 3 часа» означает, что выдержка ещё не выросла до предела — то есть между падениями он какое-то время работал.

## 3. Три пробы

| Проба | Вопрос | Что делает кластер при неудаче |
|---|---|---|
| `startupProbe` | «уже запустился?» | ждёт, не запуская остальные пробы |
| `readinessProbe` | «можно давать трафик?» | убирает под из `Service` |
| `livenessProbe` | «он ещё жив?» | **перезапускает контейнер** |

Три ошибки, которые делают почти все:

**Одна проба на две роли.** Если `liveness` и `readiness` смотрят на один и тот же путь, временная неготовность (прогрев, потеря зависимости) превращается в перезапуск. Приложение, которое ждёт базу, будет убито вместо того, чтобы подождать.

**Нет `startupProbe` у медленного старта.** `liveness` начинает проверять раньше, чем приложение поднялось, и убивает его в цикле. Внешне выглядит как `CrashLoopBackOff` без причины.

**`liveness`, проверяющая зависимости.** Проба живости должна отвечать «мой процесс не завис». Если она ходит в базу, то падение базы перезапустит все поды приложения разом — и добавит к аварии ещё одну.

```yaml
startupProbe:   { httpGet: {path: /healthz, port: 8080}, failureThreshold: 30, periodSeconds: 2 }
readinessProbe: { httpGet: {path: /ready,   port: 8080}, periodSeconds: 5 }
livenessProbe:  { httpGet: {path: /healthz, port: 8080}, periodSeconds: 10 }
```

Это ровно то различение «жив» и «здоров», что встречалось с `HEARTBEAT` в [`s06e05`](../../season-06-embedded-iot/s06e05-mavlink-telemetry/): сигнал «процесс существует» и сигнал «он способен работать» — разные, и путать их дорого.

## 4. Планировщик и ресурсы

```yaml
resources:
  requests: { cpu: 250m, memory: 256Mi }   # чем планировщик считает место
  limits:   { cpu: 500m, memory: 256Mi }   # чем ограничивается потребление
```

| Поле | Кто использует |
|---|---|
| `requests` | планировщик: под влезет туда, где столько свободно |
| `limits` | ядро узла: превышение CPU — троттлинг, превышение памяти — `OOMKill` |

Ключевая асимметрия: **процессорный предел тормозит, предел памяти убивает.** CPU — сжимаемый ресурс, память — нет. Отсюда практика: `limits.cpu` ставить осторожно (или не ставить), `limits.memory` — обязательно, но по измерению, а не наугад.

`FailedScheduling` читается буквально:

```
0/4 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane},
                         3 Insufficient memory
```

Четыре узла: один отсеян по `taint` (управляющий, на нём не размещают нагрузку), три — по памяти. Сообщение всегда перечисляет **все** причины отсева, и читать его надо целиком: часто узлов не хватает по разным поводам.

### Классы качества обслуживания

| Класс | Условие | Кого убьют первым при нехватке памяти |
|---|---|---|
| `Guaranteed` | `requests == limits` у всех контейнеров | последним |
| `Burstable` | `requests < limits` | вторым |
| `BestEffort` | ничего не задано | первым |

То есть отсутствие `requests` — не «без ограничений», а «в очереди на выселение первым».

## 5. Инструменты разбора

```bash
kubectl get pods -o wide                        # где что лежит
kubectl get pods --field-selector=status.phase=Pending
kubectl get events --sort-by=.lastTimestamp     # хронология
kubectl describe pod POD                        # пределы, пробы, прошлые завершения
kubectl logs POD --previous                     # лог упавшего контейнера
kubectl logs POD -c CONTAINER --tail=50 -f
kubectl top pods                                # текущее потребление (нужен metrics-server)
kubectl get pod POD -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'
```

`-o jsonpath` и `-o yaml` — то, чем разбор превращается из чтения глазами в скрипт. `describe` удобен человеку, но не машине: его формат не гарантирован между версиями, а `yaml` — гарантирован.

Отсюда правило для автоматизации: **человеку — `describe`, скрипту — `-o yaml`/`-o json`.** Разбор `describe` регулярными выражениями ломается на следующем обновлении кластера.

## 6. Чем кластер отличается от сервера

| | сервер | кластер |
|---|---|---|
| где работает приложение | известно | где найдётся место |
| адрес | постоянный | меняется при каждом перезапуске |
| «перезапустить» | `systemctl restart` | удалить под, кластер создаст новый |
| правка на месте | возможна | бессмысленна: под пересоздадут из манифеста |
| источник правды | состояние машины | манифест в системе контроля версий |

Последняя строка — главное. Изменение, сделанное `kubectl edit`, живёт до следующего выката. Это та же неизменяемость, что у корня `ro` в [`s06e04`](../../season-06-embedded-iot/s06e04-readonly-root/) и у описанного состояния в [`s04e11`](../../season-04-devops-automation/s04e11-iac-audit/): **состояние описано, а не накоплено.**

Отсюда и смысл этой серии: чтение кластера — это всегда сверка двух картин. Что **описано** (манифест) и что **происходит** (снимки). Расхождение между ними — и есть находка.

## 7. Откуда берётся кластер

Серия читает готовый кластер и намеренно не занимается его установкой. Стоит
всё же знать, что скрывается за словом «кластер», когда его ставят.

| | k3s | полный Kubernetes |
|---|---|---|
| дистрибутив | один двоичный файл ~70 МБ | набор компонентов |
| хранилище состояния | SQLite по умолчанию (etcd — опция) | etcd, обычно три узла |
| что вырезано | облачные драйверы, устаревшие API, часть надстроек | ничего |
| запуск | `curl … \| sh -` и через минуту готово | `kubeadm init` плюс сеть, плюс хранилище |
| где уместен | край сети, стенд, одна машина, IoT | несколько узлов, отказоустойчивость |

Разница не в «настоящий против игрушечного»: k3s проходит те же тесты
соответствия, и манифесты из этой серии применяются в нём без единой правки.
Разница в том, **сколько отказов кластер обязан пережить сам**. SQLite на одном
узле означает, что управляющий слой умирает вместе с этим узлом; поды при этом
продолжают работать, но новые не появятся и упавшие не восстановятся.

Отсюда практическое: узел управления и рабочие узлы разделяют не из
эстетики. Пока `kube-apiserver` и приложение делят память, всплеск нагрузки
на приложение отнимает у кластера способность реагировать — именно тогда,
когда реагировать нужнее всего.

Локальный стенд под манифесты — `kind` или `minikube`; оба поднимают кластер
внутри контейнеров, живут минуты и удаляются целиком. Для проверки
манифеста этого достаточно, для проверки поведения под нагрузкой — нет: в
одном узле не воспроизводится ни планирование по нескольким машинам, ни
выселение, ни сетевые задержки между узлами.
