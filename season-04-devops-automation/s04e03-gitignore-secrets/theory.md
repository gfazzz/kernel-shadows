# Теория — s04e03

## 1. Файл, который пропал на полгода

> *Мы завели в проекте правило: всё, что генерируется, в репозиторий не кладём. Я написал `.gitignore` и, чтобы наверняка, добавил строку `*cache*`. Логика была простая: кеши нам не нужны.*
>
> *Через полгода новый человек не смог собрать проект. Не хватало файла `cache-policy.md` — документа, в котором описано, что и как кешируется. Он существовал у меня на диске и не существовал в репозитории.*
>
> — Как ты его добавлял? — спросил Палыч.
> — `git add .`, как обычно.
> — И git тебе честно ничего не сказал, потому что игнорировать — это не ошибка.
>
> *Он показал ключ, о котором я не знал:*
>
> ```
> $ git add -n .
> $ git status --ignored
> $ git check-ignore -v docs/cache-policy.md
> .gitignore:14:*cache*   docs/cache-policy.md
> ```
>
> — Вот номер строки и вот шаблон. Четырнадцатая строка, написанная тобой полгода назад.
>
> *И потом главное:*
>
> — Заметь асимметрию. Слишком узкое правило ты обнаружишь сразу — в репозиторий попадёт мусор, кто-нибудь заметит. Слишком широкое не обнаружишь никогда, потому что отсутствие файла ничем не пахнет. Поэтому в `.gitignore` ошибаются в сторону узкого: лучше дописать правило потом, чем полгода не знать, что чего-то нет.

## 2. Синтаксис

| Шаблон | Что совпадает |
|---|---|
| `*.log` | любой `.log` на любой глубине |
| `/build` | только `build` в корне репозитория |
| `build/` | только каталог с таким именем, на любой глубине |
| `docs/*.md` | `.md` прямо в `docs`, но не в `docs/sub/` |
| `docs/**/*.md` | `.md` в `docs` на любой глубине |
| `**/tmp` | `tmp` на любой глубине (то же, что просто `tmp`) |
| `?.txt` | один любой символ |
| `[abc].txt` | один символ из набора |
| `!важное.log` | отмена игнорирования |
| `\#файл` | файл, чьё имя начинается с решётки |

Правила чтения:

- **шаблон без слэша внутри** ищется на любой глубине; **со слэшем внутри** — от каталога, где лежит `.gitignore`;
- **побеждает последнее совпавшее правило** — поэтому `!` ставят ниже того, что отменяют;
- **ведущие пробелы значимы**, хвостовые — нет (если не экранированы);
- **пустые строки и строки с `#`** игнорируются самим файлом.

**Отмена не работает через каталог.** Если игнорируется `secrets/`, правило `!secrets/public.txt` не поможет: git не заходит внутрь исключённого каталога вовсе. Обходится так:

```
secrets/*
!secrets/public.txt
```

## 3. Где ещё живут правила

| Файл | Область | Отправляется |
|---|---|---|
| `.gitignore` в корне | весь репозиторий | да |
| `.gitignore` в подкаталоге | этот подкаталог и ниже | да |
| `.git/info/exclude` | только этот клон | **нет** |
| `core.excludesFile` (обычно `~/.config/git/ignore`) | все репозитории пользователя | нет |

Разделение полезное: общие для проекта правила — в репозиторий; личное (`.idea/`, `.DS_Store`, ваш редактор) — в глобальный файл, чтобы не навязывать другим.

Правила из подкаталога перекрывают корневые для своего поддерева — это удобно, когда в одном месте нужно хранить то, что везде игнорируется.

## 4. Главное ограничение

**Правила действуют только на неотслеживаемые файлы.**

```bash
git ls-files | grep .env        # отслеживается — правила не помогут
git rm --cached .env            # перестать отслеживать, оставив на диске
git rm -r --cached .            # и то же самое разом для всего репозитория
git add . && git commit -m "применить .gitignore"
```

Последняя пара команд — стандартный приём «применить `.gitignore` задним числом»: снять с учёта всё и добавить заново, уже с правилами. В коммит попадёт удаление тех файлов, которые теперь игнорируются.

И это по-прежнему **не удаляет их из истории**. Секрет, побывавший в коммите, скомпрометирован; порядок действий — сначала сменить, потом прятать (см. [`s04e01`](../s04e01-git-history/)).

## 5. Проверять, а не предполагать

```bash
git check-ignore -v путь…      # правило, файл правил и номер строки
git status --ignored           # полная картина, включая игнорируемое
git add -n .                   # что добавилось бы (ничего не делая)
git ls-files --others --ignored --exclude-standard | head
```

`git check-ignore -v` отвечает точно и молчит, если файл не игнорируется. Это тот же класс команд, что `ssh -G`, `sshd -T`, `sudo -l`, `systemctl show` — «что программа поняла» вместо «что написано».

## 6. `.env.example` и родня

Файл, который **должен** попасть в репозиторий: состав переменных без значений.

```
DB_HOST=
DB_USER=
DB_PASSWORD=
API_TOKEN=
```

Зачем: человек, склонировавший репозиторий, узнаёт, что нужно настроить, не спрашивая никого и не получая ни одного секрета. Заодно это документация, которая не устаревает — она в том же коммите, что и код, который её читает.

Ошибка, которую делают: сделать пример копированием рабочего файла и «почистить» его. Чистят обычно не всё.

Соседние приёмы того же ряда: `config.example.yml`, `terraform.tfvars.example`, `inventory.example.ini`. Правило общее — **пример не содержит ни одного настоящего значения**, включая адреса и имена пользователей, если они не публичны.

## 7. Что ещё утекает через репозиторий

| Источник | Почему опасно |
|---|---|
| `*.tfstate` | состояние Terraform содержит значения переменных, в том числе пароли |
| `*.retry`, `.ansible/` | пути и имена хостов |
| `.vscode/`, `.idea/` | иногда строки подключения и токены плагинов |
| дампы базы | персональные данные целиком |
| скриншоты в issues | токены в адресной строке |
| `history` файлы оболочки | пароли, набранные в командах |

Список стоит один раз просмотреть глазами и добавить в свой глобальный `~/.config/git/ignore` — тогда он будет работать во всех проектах, включая чужие.

## 8. Метанавык: тихие ошибки

`.gitignore` относится к небольшому классу настроек, где **обе ошибки тихие**:

- слишком узко — в репозиторий попадает лишнее; заметно, но не сразу;
- слишком широко — из репозитория выпадает нужное; **не заметно никогда**, пока файл не понадобится на другой машине.

Общее свойство таких мест: результат — это **отсутствие** чего-то, а отсутствие не подсвечивается ничем. Тот же класс: правило фаервола, которое ничего не блокирует; `logrotate` без `postrotate`; проверка бэкапа, которая проверяет наличие файла.

Приём против этого один и тот же во всех случаях: **проверять не намерение, а результат, и проверять в обе стороны**. Не только «игнорируется ли то, что должно», но и «не игнорируется ли то, что должно остаться». Второй вопрос задают редко, и именно он ловит дорогие ошибки.
