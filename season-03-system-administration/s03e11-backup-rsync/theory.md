# Теория — s03e11

## 1. Архив, который открывался только у меня

> *Я настроил бэкап базы: `pg_dump`, `gzip`, `scp` на второй сервер. Проверил — файл на месте, размер правильный, растёт каждый день. Отчитался.*
>
> *Через полгода база легла по-настоящему. Я взял вчерашний архив и попробовал развернуть.*
>
> ```
> gzip: stdin: unexpected end of file
> ```
>
> *Взял позавчерашний. То же самое. Взял недельной давности — то же.*
>
> *Оказалось, `scp` копировал файл, который в этот момент ещё писался: `pg_dump` шёл двадцать минут, а `scp` запускался через пятнадцать. Каждый архив был обрезан на трёх четвертях. Все двести дней.*
>
> — Сколько раз ты открывал хоть один? — спросил Палыч.
> — Ни разу. Я проверял, что файл есть.
> — Ты проверял, что процесс идёт. Это разные вещи. «Файл есть» — свойство твоего скрипта. «Из файла разворачивается база» — свойство бэкапа. Ты полгода мониторил не то.
>
> *Он тогда сформулировал правило, которое я с тех пор ставлю в каждый бэкап-скрипт первым пунктом:*
>
> — Резервная копия существует не тогда, когда её сделали, а тогда, когда из неё восстановились. Всё, что между, — предположение.

## 2. 3-2-1-T

```
3 копии     — оригинал и две резервных
2 носителя  — разные устройства (не два каталога на одном диске)
1 вне       — другая площадка: офис, облако, другой датацентр
T tested    — восстановление проверено, и известно, когда в последний раз
```

Каждая цифра закрывает свой сценарий:

| Что случилось | Спасает |
|---|---|
| удалили файл по ошибке | любая копия |
| отказал диск | второй носитель |
| шифровальщик, компрометация root | копия вне досягаемости учётной записи |
| пожар, изъятие, отказ площадки | копия вне площадки |
| копия испорчена или неполна | **проверка восстановлением** |

Последняя строка — единственная, которую нельзя закрыть настройкой; она требует регулярного действия.

## 3. Типы копий

| | Что копирует | Что нужно для восстановления |
|---|---|---|
| полная | всё | один архив |
| инкрементная | изменения с прошлого раза | полная + все инкременты по порядку |
| дифференциальная | изменения с последней полной | полная + последняя дифференциальная |
| снимок с жёсткими ссылками | изменения | **только сам снимок** |

Инкрементная цепочка ломается целиком, если потеряно одно звено, и восстановление тем дольше, чем дальше от полной копии. Схема с `--link-dest` даёт то же место при простоте полной копии — и стала стандартом для файловых бэкапов.

## 4. `rsync` в подробностях

```bash
rsync -a --delete --link-dest=/srv/backup/latest /var/log/ops/ /srv/backup/2025-10-23/
```

| Ключ | Что делает |
|---|---|
| `-a` (`--archive`) | `-rlptgoD`: рекурсия, символьные ссылки, права, время, группа, владелец, устройства |
| `-H` (`--hard-links`) | сохранить жёсткие ссылки внутри источника |
| `--delete` | удалить в приёмнике то, чего нет в источнике |
| `--delete-excluded` | и то, что попало под исключения |
| `--numeric-ids` | не переводить UID/GID в имена |
| `--link-dest=DIR` | неизменившееся — жёсткой ссылкой на DIR |
| `--exclude-from=F` | шаблоны исключений из файла |
| `--partial --append-verify` | докачивать прерванное |
| `--bwlimit=10M` | ограничить полосу |
| `-z` | сжатие при передаче (для локального копирования вредно) |
| `-n` (`--dry-run`) | показать, ничего не делая |
| `-i` (`--itemize-changes`) | подробно: что именно изменилось в каждом файле |

**Косая черта в конце источника:**

```bash
rsync -a src/ dst/     # содержимое src → в dst
rsync -a src  dst/     # сам каталог src → dst/src
```

Ошибка в этом месте создаёт `dst/src/src/…` и не даёт никакого предупреждения.

**Коды возврата** стоит различать: `0` — успех, `23` — часть файлов не передана (обычно нет прав), `24` — файлы исчезли во время передачи (нормально для активных каталогов), `30` — таймаут. Скрипт, считающий успехом только `0`, будет ложно тревожиться на живой системе; скрипт, игнорирующий все коды, промолчит о настоящей проблеме.

## 5. Согласованность копии

Файлы, которые пишут в момент копирования, попадают в копию наполовину. Для баз данных это означает нерабочую копию.

Три способа, от простого к правильному:

1. **Остановить службу** на время копирования. Честно и неприемлемо для production.
2. **Штатная выгрузка**: `pg_dump`, `mysqldump`, `redis-cli --rdb`. База сама делает согласованный снимок. Копировать надо результат, и только после его завершения.
3. **Снимок файловой системы**: LVM (`lvcreate -s`), ZFS, btrfs. База получает команду «сбросить буферы», делается снимок за секунду, копирование идёт уже с него.

Ошибка из воспоминания выше — из первой категории: копирование началось до того, как выгрузка закончилась. Лечится последовательностью в одном скрипте, а не двумя задачами в расписании.

## 6. Куда класть копию

```bash
rsync -a -e 'ssh -i /root/.ssh/backup_key' /srv/backup/ backup@offsite:/srv/ops/
```

Ключ для бэкапа стоит ограничить в `authorized_keys` на приёмной стороне:

```
command="rrsync -ro /srv/ops",no-agent-forwarding,no-port-forwarding,no-pty ssh-ed25519 AAAA...
```

Так скомпрометированный сервер-источник не сможет ни удалить чужие копии, ни зайти на приёмник в обычную оболочку. Это ровно та же логика наименьших привилегий, что в [`s03e03`](../s03e03-sudo/), только для ключа.

**Почему снимок LVM — не бэкап:** он лежит в той же группе томов, на тех же дисках, и исчезнет вместе с ними. Его роль — дать согласованное состояние для копирования, а не хранить копию.

## 7. `tar`: когда копия должна быть одним файлом

`rsync` даёт дерево файлов, которое можно открыть обычным `ls`. Иногда нужно
обратное — **один файл**: чтобы отправить, зашифровать или положить в объектное
хранилище. Это делает `tar`.

```bash
tar -czf архив.tar.gz каталог/      # создать со сжатием gzip
tar -tzf архив.tar.gz               # ПОСМОТРЕТЬ содержимое, ничего не распаковывая
tar -xzf архив.tar.gz -C /куда      # распаковать в указанный каталог
tar -czf - каталог/ | ssh узел 'cat > копия.tar.gz'   # сразу на другую машину
```

Ключи читаются как слова: `c` create, `t` list, `x` extract, `f` file,
`z` gzip (`j` bzip2, `J` xz), `v` verbose, `-C` — куда.

Три вещи, которые стоит знать сразу:

- **`-t` перед `-x`.** Архив может распаковаться в текущий каталог, а не в
  подкаталог, и рассыпать сотню файлов вам под ноги. `tar -tzf` показывает,
  что внутри, за секунду.
- **`tar` сохраняет права и владельцев**, но при распаковке не от root
  владелец станет вашим. Для переноса между машинами это чаще хорошо, чем
  плохо; для восстановления системы — важно распаковывать от root.
- **`-t` — это ещё и проверка целостности сжатия**: битый архив на нём
  и споткнётся. Что внутри архива цело — он не скажет (см. `s03e13`).

Что `tar` **не** делает: не хранит несколько версий, не умеет докачивать и не
экономит место на неизменившихся файлах. Для регулярных копий это `rsync`
из этой серии; `tar` — для «упаковать состояние и унести».

## 8. Шифрование и сжатие

```bash
tar -c данные | zstd -3 | age -r age1... > копия.tar.zst.age
restic backup /var/log/ops      # готовые решения: дедупликация + шифрование
borg create repo::snapshot /var/log/ops
```

Копия, уезжающая наружу, должна быть зашифрована — иначе «вне площадки» означает «у кого-то ещё». Ключ при этом хранится **не** на копируемой машине: иначе тот, кто получил её, получил и всё остальное.

`restic` и `borg` решают ту же задачу, что скрипт из этой серии, плюс дедупликацию и шифрование. Писать своё имеет смысл, когда важна прозрачность — снимок из `--link-dest` можно открыть обычным `ls` без всякой утилиты, и это его главное достоинство при восстановлении в панике.

## 9. Метанавык: отличать процесс от результата

Бэкап — самый чистый пример системы, где легко мониторить не то. «Скрипт отработал», «файл создан», «размер растёт», «места хватает» — всё это свойства **процесса**. Единственное свойство результата: из копии восстанавливается работающая система.

Проверка стоит дёшево и почти никогда не делается: развернуть вчерашнюю копию во временный каталог, сверить контрольные суммы, для базы — поднять её и выполнить один запрос. Пятнадцать минут раз в месяц.

Тот же разрыв между процессом и результатом встречается везде: тесты проходят (процесс) ≠ программа работает (результат); мониторинг зелёный ≠ пользователи довольны; сертификат обновляется ≠ сайт открывается. Полезная привычка — на каждую систему задавать вопрос: «какое наблюдение подтвердит, что она сделала то, ради чего существует» — и убедиться, что это наблюдение кто-то делает.
