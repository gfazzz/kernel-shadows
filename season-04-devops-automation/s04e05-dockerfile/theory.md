# Теория — s04e05

## 1. Контейнер, который не останавливался

> *Мы выкатывали новую версию, и каждый выкат занимал на десять секунд больше, чем должен. Ровно на десять. Я списывал на сеть.*
>
> *Однажды посмотрел внимательнее: `docker stop` возвращался через десять секунд и писал, что контейнер остановлен. В журнале приложения при этом не было ни одной строки о завершении — а мы их писали.*
>
> — Что делает `docker stop`? — спросил Палыч.
> — Останавливает контейнер.
> — Как именно?
> — Посылает SIGTERM… и через десять секунд SIGKILL.
> — Вот. Он посылает SIGTERM ПЕРВОМУ процессу. Покажи, что у тебя PID 1.
>
> ```
> $ docker exec app ps -o pid,comm
> PID COMMAND
>   1 sh
>   7 python
> ```
>
> — Твой PID 1 — оболочка. Она получает сигнал, ничего с ним не делает и не завершается. Через десять секунд прилетает KILL, и питон умирает, не успев ничего записать.
>
> *Причина была в одной строке: `CMD python app.py` вместо `CMD ["python", "app.py"]`.*
>
> — И заметь, — сказал он, — это не «мелочь оформления». Разница между двумя записями — обрабатывает твоё приложение сигналы или нет. Каждый выкат вы теряли соединения клиентов, просто никто не связал это с квадратными скобками.

## 2. Инструкции и слои

| Инструкция | Создаёт слой | Что делает |
|---|---|---|
| `FROM` | — | база |
| `RUN` | **да** | выполняет команду при сборке |
| `COPY`, `ADD` | **да** | кладёт файлы внутрь |
| `ENV`, `ARG` | нет | переменные |
| `WORKDIR` | нет | рабочий каталог (создаётся, если нет) |
| `USER` | нет | от кого выполняются следующие инструкции и `CMD` |
| `EXPOSE` | нет | **документация**, портов не открывает |
| `CMD`, `ENTRYPOINT` | нет | что запускать |
| `HEALTHCHECK` | нет | как проверять живость |

`EXPOSE` стоит запомнить отдельно: он ничего не публикует. Порт наружу открывает `-p` при запуске или `ports:` в compose.

**`ADD` против `COPY`:** `ADD` умеет скачивать по URL и распаковывать архивы. Обе способности неявные и потому нежелательные — по умолчанию используют `COPY`.

## 3. Кеш сборки

Слой берётся из кеша, если совпали инструкция и её вход: для `RUN` — сама строка, для `COPY` — содержимое копируемых файлов. Первое расхождение обесценивает всё, что ниже.

```dockerfile
RUN apt-get …             # раз в полгода
COPY requirements.txt .   # раз в неделю
RUN pip install -r …
COPY . /app               # каждый раз
```

Полезные приёмы:

```bash
docker build --progress=plain .     # видно, какие слои взяты из кеша
docker build --no-cache .           # собрать заново целиком
```

`ARG`, использованный в `RUN`, тоже участвует во входе: смена аргумента ломает кеш с этого места.

## 4. Многоступенчатая сборка

```dockerfile
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN go build -o /out/app ./cmd/app

FROM gcr.io/distroless/static
COPY --from=build /out/app /app
USER 10001
ENTRYPOINT ["/app"]
```

Вторая ступень начинается с чистой базы; в итоговый образ попадает только то, что скопировано явно. Компилятор, исходники, кеши и любые секреты остаются в промежуточной ступени, которая никуда не уезжает.

Для интерпретируемых языков выигрыш меньше, но есть: собрать зависимости в одной ступени, перенести готовое дерево в другую.

```bash
docker build --target build .       # собрать только до нужной ступени
```

## 5. Секреты при сборке

```dockerfile
# BuildKit: файл существует только во время этой инструкции
RUN --mount=type=secret,id=pip_token \
    pip install --index-url "https://$(cat /run/secrets/pip_token)@..." -r req.txt
```

```bash
docker build --secret id=pip_token,src=./token .
```

Чего делать **нельзя**:

- `COPY key .` + `RUN … && rm key` — файл остаётся в слое;
- `ARG TOKEN` + `RUN использовать $TOKEN` — аргумент виден в `docker history`;
- `ENV PASSWORD=…` — виден в `inspect` у любого, кто получил образ.

Секреты **рантайма** передают при запуске: `--env-file`, `docker secret`, механизмы оркестратора. В образ они не попадают вовсе.

## 6. Пользователь и права

```dockerfile
RUN useradd --system --create-home --uid 10001 collector
COPY --chown=collector:collector . /app
USER collector
```

- **создать пользователя обязательно** — `USER` на несуществующее имя не даст контейнеру стартовать;
- **числовой UID задают явно**: Kubernetes с `runAsNonRoot: true` проверяет номер, а имя ему неизвестно;
- **`USER` после установки, до `CMD`**: `apt-get` и `pip` в системные каталоги требуют root;
- **`COPY --chown`** вместо отдельного `RUN chown`: иначе появляется лишний слой размером со всё приложение.

Отдельно: root **внутри** контейнера — это root ядра хоста, если не включён user namespace. «Он же в контейнере» не является ответом; ровно поэтому `USER` и нужен.

## 7. `.dockerignore`

```
.git
.env
*.pem
node_modules
__pycache__
```

Ограничивает **контекст сборки** — то, что отправляется демону при `docker build .`. Без него `COPY . /app` затягивает внутрь `.git` со всей историей (включая удалённые секреты) и всё, что лежало в каталоге.

Побочная выгода — скорость: контекст на гигабайт отправляется демону при каждой сборке.

Синтаксис похож на `.gitignore`, но правила чуть другие (нет вложенных файлов, отрицание работает иначе). Проверять стоит тем же способом — попробовать и посмотреть на размер контекста в выводе сборки.

## 8. Метанавык: цена каждой строки

Ни одна из четырёх находок предыдущей серии не была ошибкой синтаксиса. Все четыре строки делали ровно то, что написано. Проблема была в том, что автор не знал цены:

| Строка | Что делает | Чем платит |
|---|---|---|
| `FROM python:3.11` | берёт базу | +870 МБ, +52 уязвимости |
| `ENV PASSWORD=…` | задаёт переменную | видна каждому, у кого есть образ |
| `COPY key .` | копирует файл | навсегда в слое |
| `USER root` | задаёт пользователя | root ядра хоста внутри контейнера |
| `CMD строкой` | запускает | приложение не получает сигналы |

Это общее свойство декларативных языков — Dockerfile, unit systemd, `compose.yaml`, playbook Ansible. Синтаксис прост настолько, что кажется, будто понимать нечего; ошибки в них не синтаксические, а **ценовые**, и проявляются далеко от места, где написаны.

Отсюда привычка, полезная для всего этого класса: написав строку, спросить не «работает ли», а **«чем я за это плачу и когда счёт придёт»**. Для Dockerfile ответы почти всегда одни и те же — размер, поверхность атаки, время сборки, поведение при остановке.
