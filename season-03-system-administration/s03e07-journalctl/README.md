## «Шесть дней это лежало и ждало»

Борис ставит перед тобой ноутбук с одной командой в истории.

```bash
journalctl --since '2025-10-14 21:00' --until '2025-10-15 00:35' -o short-iso
```

> — Мы шесть дней разбирали следствия. Учётные записи, права, процессы, юниты. Всё это — то, что осталось **после**. А вот здесь лежит то, что происходило. Целиком, по секундам, с самого начала.

Он не выводит результат на экран. Вместо этого спрашивает:

> — Прежде чем смотреть: как вы думаете, что мы увидим?

> — Взлом.

> — Не увидите. Взлом — это ваше слово. Журнал не знает такого события. Он знает «Failed password», «Accepted publickey», «new user», «Created symlink». Всё это по отдельности — совершенно обычные строки, каждая из которых происходит на любом сервере сотни раз в день.

Он наконец нажимает Enter.

> — Работа состоит в том, чтобы поставить их в порядке и увидеть, что вместе они означают. Это и есть разница между «читать логи» и «разбирать инцидент».

> **LILITH:** *«В журнале нет ни одной строки со словом „атака“. Есть семьдесят строк, из которых четырнадцать складываются в неё. Умение — не в поиске, а в том, чтобы отличить эти четырнадцать от остальных пятидесяти шести.»*

## Чему ты научишься

- Отбору записей в `journalctl`: по времени, юниту, приоритету — вместо `grep` по всему подряд.
- Тому, что приоритеты означают на самом деле, и почему `Failed password` — не то же самое, что слово «invalid».
- Восстанавливать хронологию: кто перебирал, под кем вошли, что делали через `sudo`.
- Метанавыку: **хронология вместо поиска**. Поиск отвечает только на уже придуманную гипотезу.

Подробнее, с историей и подводными камнями, — в [`theory.md`](theory.md).

## Теория: journald

### Один журнал вместо каталога файлов

Раньше нужно было знать, куда смотреть: `/var/log/auth.log` — входы, `/var/log/syslog` — всё остальное, `/var/log/nginx/error.log` — веб-сервер. journald собирает всё в один бинарный журнал с метаданными и позволяет резать его по любому признаку:

```bash
journalctl -u sshd                     # по юниту
journalctl _PID=6623                   # по процессу
journalctl _UID=1004                   # по пользователю
journalctl -p err                      # по приоритету
journalctl --since '21:00' --until '00:35'
journalctl -k                          # только сообщения ядра
journalctl -f                          # следить в реальном времени
journalctl -b -1                       # предыдущая загрузка
```

Фильтры складываются: `journalctl -u sshd --since today -p warning`.

### Приоритеты

```
0 emerg   1 alert   2 crit   3 err   4 warning   5 notice   6 info   7 debug
```

`-p err` означает «err и всё, что серьёзнее». Здесь кроется главная ошибка при разборе инцидента: **записи о входе и о sudo не являются ошибками.** Неудачная попытка входа — `notice`, успешный вход — `info`, команда через `sudo` — `notice`. Фильтр по приоритету показывает поломки, а не вторжения; ищущий атаку через `-p err` не найдёт ничего и решит, что всё чисто.

### Форматы вывода

```bash
journalctl -o short-iso     # время в ISO — удобно сортировать и сравнивать
journalctl -o verbose       # ВСЕ поля записи, включая _SYSTEMD_UNIT и _EXE
journalctl -o json-pretty   # то же машиночитаемо
journalctl -o cat           # только текст сообщения
```

`-o verbose` — то, чем отличают источник по-настоящему: в поле `_EXE` лежит путь к исполняемому файлу, записанный **ядром**, а не тег, который процесс выбрал себе сам (см. [`s03e04`](../s03e04-processes/)).

### Журнал можно потерять

```bash
journalctl --disk-usage
journalctl --list-boots
```

По умолчанию во многих дистрибутивах `Storage=auto`: если каталога `/var/log/journal` нет, журнал живёт в `/run` и **исчезает при перезагрузке**. Первое, что стоит проверить на своём сервере, — существует ли этот каталог.

Про `Storage=persistent`, ограничение размера, `--vacuum-time`, `--verify`, пересылку на удалённый хост и защиту от подчистки — в [`theory.md`](theory.md).

## Проверка: LILITH задаёт вопросы

**LILITH:** *«Ищем следы вторжения. Команда `journalctl --since yesterday -p err` не показала ничего интересного. Что это значит?»*

<details>
<summary>Подумай 30 секунд</summary>

Только то, что ничего не ломалось.

Вход, `sudo`, создание пользователя, включение юнита — это `notice` и `info`. Успешная атака вообще не порождает ошибок: всё, что делает атакующий, система выполняет штатно и записывает как обычную работу.

Ошибки полезны для другого — они показывают неудачные попытки: перебор паролей, отказы `sudo`, падения служб. Но след успешного действия придётся искать среди обычных записей.
</details>

**LILITH:** *«В журнале две строки: `sshd[2201]: Failed password for root` и `sshd[6623]: connection from …`. Обе от sshd. Можно ли считать их записями одной службы?»*

<details>
<summary>Ответ</summary>

Нет, и в этом весь смысл `-o verbose`.

Тег `sshd` в короткой строке — это `SYSLOG_IDENTIFIER`, который процесс сообщает о себе сам. Поля `_SYSTEMD_UNIT` и `_EXE` заполняет journald по данным ядра, и подделать их изнутри процесса нельзя.

Для PID 6623 из [`s03e04`](../s03e04-processes/) там оказалось бы `_SYSTEMD_UNIT=sshd-helper.service` и `_EXE=/tmp/.ICE-unix/sshd`. Отсюда практический приём: искать не по тегу, а по юниту — `journalctl -u sshd` покажет только настоящий.
</details>

## Разбор типичных ошибок

**Считать неудачные попытки через `grep -i 'invalid user'`.** Таких строк шесть, а попыток четыре: на каждое имя приходится пара сообщений (`Invalid user X` и `Failed password for invalid user X`), а четвёртая попытка была под существующим `root` и слова `invalid` не содержит вовсе.

**Считать команды `sudo` через `grep -c sudo`.** Получится семнадцать вместо пяти: на каждую команду `pam_unix` пишет ещё две строки об открытии и закрытии сессии. Команду обозначает `COMMAND=`.

**Путать `enable` и `start`.** «Created symlink …/multi-user.target.wants/…» — это включение в автозагрузку, «Started SSH connection helper» — запуск. Между ними три секунды и вся разница: первое означает, что служба вернётся после перезагрузки.

## Debriefing

**Четырнадцать строк из семидесяти**

Ты выписываешь хронологию, и она занимает десять минут вечера 14 октября.

```
21:56–21:57  четыре неудачные попытки: admin, oracle, test, root
21:58:47     Accepted publickey for dmitry — ключ подошёл с первого раза
22:01:03     sudo: useradd -u 0 -o -g 0 devops
22:02:11     sudo: usermod -aG sudo devops
22:03:40     sudo: cp /bin/bash /home/devops/.cache/bash
22:03:41     sudo: chmod 4755 …
22:06:55     sudo: systemctl enable --now sshd-helper.service
22:08:12     сессия закрыта
```

Десять минут. Всё, что ты искал шесть дней, было сделано за десять минут и записано с точностью до секунды.

Борис показывает на строку `21:58:47`.

> — Вот единственное место, где что-то могло пойти иначе. Три имени перебрали наугад, четвёртое — root, тоже наугад. А потом сразу подошёл ключ Дмитрия. Не подобрали — просто подошёл.

> — Отпечаток совпадает с ключом из снимка прав, — говоришь ты. — Тот, что лежал с правами `644`.

> — Совпадает. Ключ, который мог прочитать любой, у кого была учётная запись на любой из машин операции. — Он закрывает ноутбук. — Обратите внимание, что произошло дальше. Ни одной ошибки. Ни одной записи уровня выше `notice`. Система работала идеально и всё это время честно писала, что именно она делает.

Он собирается, потом добавляет — уже без всякой лекторской интонации:

> — Логи не для того, чтобы найти виноватого. Они для того, чтобы в какой-то момент можно было ответить на вопрос «что произошло» — не догадкой, а по секундам. Всё остальное вторично.

```

│   /var/log — 95 %. Через час встанет база. Билеты            │
```
