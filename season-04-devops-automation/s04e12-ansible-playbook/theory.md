# Теория — s04e12

## 1. Скрипт, который работал только первый раз

> *Я написал playbook на пятнадцать задач. Всё через `shell`: я же знаю нужные команды, зачем учить модули.*
>
> *Прогнал — сработало. Прогнал второй раз, чтобы показать коллеге, — сломалось. Пользователь уже существовал, каталог уже был, строка в конфиг добавилась второй раз, и служба не поднялась.*
>
> — Что ты написал? — спросил Палыч.
> — Playbook.
> — Ты написал скрипт установки. Он отвечает на вопрос «что сделать на чистой машине». А playbook отвечает на другой: «как должно быть».
>
> *Я сказал, что разница вроде бы небольшая. Он ответил:*
>
> — Разница в том, сколько раз это можно запустить. Скрипт установки — один. Описание — сколько угодно, и в этом весь смысл: ты перестаёшь помнить, что уже сделал.

## 2. Из чего состоит playbook

```yaml
- name: имя плея
  hosts: production        # кому (шаблон из инвентаря)
  gather_facts: true       # собирать ли сведения о машине
  become: false            # от кого по умолчанию
  vars: { … }
  handlers: [ … ]          # что сделать, если что-то изменилось
  tasks: [ … ]             # что должно быть
```

Задача — это вызов **модуля** с параметрами. Модуль выполняется на целевой машине, получает описание состояния и сам решает, надо ли что-то менять.

```yaml
- name: человекочитаемое имя
  ansible.builtin.file:      # модуль
    path: /etc/ops           # его параметры
    state: directory
    mode: "0750"
  become: true               # ключевые слова задачи
  when: ansible_os_family == "Debian"
  notify: перезапустить sshd
  tags: [ops]
```

Имя модуля пишут полностью (`ansible.builtin.file`, а не `file`): коротких имён несколько, и какое из них сработает, зависит от установленных коллекций.

## 3. Идемпотентность на практике

| Приём | Что даёт |
|---|---|
| `state:` вместо действия | «должно быть так», а не «сделай это» |
| `lineinfile` с `regexp:` | строка заменяется, а не дописывается |
| `template` вместо `cat >>` | файл целиком, значит лишнего в нём не останется |
| `creates:` у команды | «не запускать, если файл уже есть» |
| `changed_when: false` | «эта задача только смотрит» |
| `check_mode: false` | «её можно выполнять и в режиме проверки» |

Проверка одна, и она не требует чтения кода: **второй прогон подряд должен дать `changed=0`**. Всё, что меняется во второй раз, описано как действие.

## 4. Handlers

```yaml
handlers:
  - name: перезапустить sshd
    ansible.builtin.systemd: { name: sshd, state: restarted }
```

Handler выполняется **один раз в конце плея** и только если его позвали через `notify` — сколько бы задач его ни звало. Отсюда его смысл: перезапуск описывается как следствие изменения файла, а не как отдельный шаг.

Тонкости, о которые спотыкаются:

- по умолчанию handler **не выполняется**, если плей упал раньше; `--force-handlers` меняет это;
- `notify` сопоставляется с handler по **имени** — опечатка не ошибка, просто ничего не произойдёт;
- `listen:` позволяет звать группу handlers одним именем;
- `meta: flush_handlers` вызывает накопленные handlers прямо сейчас — нужно, когда следующая задача зависит от перезапуска.

## 5. Шаблоны

```yaml
- name: доверенные ключи доступа
  ansible.builtin.template:
    src: authorized_keys.j2
    dest: /home/ops/.ssh/authorized_keys
    mode: "0600"
```

```jinja
{# authorized_keys.j2 — файл собирается целиком, поэтому чужой ключ исчезнет #}
{% for k in trusted_keys %}
{{ k.type }} {{ k.data }} {{ k.comment }}
{% endfor %}
```

Ключевое свойство — **файл собирается целиком**. Дописывание (`lineinfile`, `blockinfile`) оставляет всё, чего в описании нет; шаблон не оставляет ничего.

`--diff` для шаблона показывает результат подстановки, а не сам шаблон, — удобный способ увидеть, какие значения переменных на самом деле доехали.

## 6. Роли

Когда задач становится больше двух десятков, их раскладывают по ролям:

```
roles/common/
  tasks/main.yml         # что делать
  handlers/main.yml      # чем реагировать
  templates/             # шаблоны
  files/                 # файлы как есть
  defaults/main.yml      # переменные с самым низким приоритетом
  vars/main.yml          # переменные с высоким приоритетом
```

```yaml
- hosts: production
  roles:
    - common
    - { role: web, when: ops_role == 'web' }
```

Разница между `defaults/` и `vars/` — не в назначении, а в приоритете: первое перебивается почти чем угодно, второе — почти ничем. Всё, что предполагается настраивать, кладут в `defaults/`.

## 7. Секреты

```bash
ansible-vault encrypt group_vars/production/secrets.yml
ansible-vault edit    group_vars/production/secrets.yml
ansible-playbook harden.yml --vault-password-file ~/.vault_pass   # файл вне репозитория
```

Зашифрованный файл лежит в репозитории, пароль от него — нет ([`s04e11`](../s04e11-iac-audit/) проверяет именно это). В самом playbook секрет появляется только как имя переменной, а задача, которая его использует, помечается `no_log: true`: иначе значение напечатается в выводе прогона и в `--diff`.

## 8. Что запускать и чем проверять

```bash
ansible-playbook -i inventory.yml harden.yml --check --diff      # что изменится
ansible-playbook -i inventory.yml harden.yml --limit prod-web27* # одна машина
ansible-playbook -i inventory.yml harden.yml --tags ssh          # одна тема
ansible-lint harden.yml                                          # разбор до запуска
```

Разумный порядок на незнакомом парке: `--check --diff --limit одна_машина` → одна машина по-настоящему → группа → всё. Метки (`tags`) — то, что делает второй и третий шаг возможными.

## 9. Метанавык: описание состояния против списка действий

Разница между `shell: chmod 700 …` и `file: mode=0700` — частный случай различия, которое встречается в курсе постоянно:

| Список действий | Описание состояния | Что даёт второе |
|---|---|---|
| `mount /dev/vdb1 /data` | строка в `/etc/fstab` ([`s03e10`](../../season-03-system-administration/s03e10-fstab/)) | переживает перезагрузку |
| скрипт запуска демона | юнит systemd ([`s03e05`](../../season-03-system-administration/s03e05-systemd-service/)) | состояние известно системе |
| `docker run` с флагами | `compose.yaml` ([`s04e06`](../s04e06-compose/)) | воспроизводимо и читаемо |
| «не коммить этот файл» | `.gitignore` ([`s04e03`](../s04e03-gitignore-secrets/)) | действует у всех |
| `chmod` в playbook | модуль `file` | можно спросить, что изменится |

Признак, по которому различаются эти два способа думать, один и он проверяемый: **можно ли спросить систему, что изменится, не меняя ничего**. Если да — вы описали состояние. Если нет — вы записали действия, и единственный способ узнать результат остаётся прежним: выполнить и посмотреть.
