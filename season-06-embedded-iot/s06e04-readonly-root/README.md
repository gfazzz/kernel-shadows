## I. Три карты в коробке

Ли Вэй высыпает на стол горсть SD-карт.

> — Это узлы прошлого проекта. Стояли на крышах, работали по восемь месяцев. Три из двенадцати не читаются вообще, ещё четыре — с побитой файловой системой. Знаешь, что их убило?

> — Питание?

> — Питание — половина. Вторая половина — запись. Ячейка флеш-памяти переживает около тысячи перезаписей, а у карты нет умного контроллера, как у SSD. Ты пишешь журналы, временные файлы, время последнего доступа к каждому прочитанному файлу — и через полгода карта кончается. Не ломается, а **изнашивается**, как подшипник.

Он показывает замер: 478 мегабайт в сутки на узел.

> — Из этих четырёхсот семидесяти восьми пережить перезагрузку обязаны два. Всё остальное — мусор, который нужен только пока узел работает. И ты пишешь его на носитель, который от этого умирает, да ещё и подставляешь под сбой питания.

> — А если просто не писать?

> — Вот. Корень монтируешь только для чтения. Всё, что должно писаться, — в память. Что обязано выжить — на отдельный маленький раздел. И тогда выдёргивание питания перестаёт что-либо значить: писать было нечего, ломаться нечему.

> **LILITH:** *«На сервере с RAID и ИБП запись — это данность, о которой не думают. Здесь запись — расходуемый ресурс, у которого есть счётчик. Вопрос „а обязана ли эта запись случиться?" в embedded задают к каждой строке журнала.»*

## II. Теория: как не писать на носитель

### Три судьбы у записываемого пути

| Режим | Что происходит | Кому подходит |
|---|---|---|
| **tmpfs** | каталог живёт в памяти, при старте пуст | `/tmp`, `/var/log`, `/var/tmp` |
| **overlay** | видно исходное содержимое, записи — в память | `/etc`: система должна видеть свои файлы |
| **persist** | отдельный раздел на карте, переживает перезагрузку | состояние, которое нельзя потерять |

Выбор режима — не техническое, а смысловое решение: **обязаны ли эти данные пережить перезагрузку.** Ответ «нет» встречается гораздо чаще, чем кажется.

### tmpfs: память вместо карты

```
tmpfs  /var/log  tmpfs  rw,nosuid,nodev,noexec,size=512M,mode=0755  0  0
```

`size=` обязателен. Без него tmpfs может вырасти до половины оперативной памяти и на узле без свопа закончиться `OOM`. Сумма всех `size` — это память, которую ты **разрешил** отобрать у приложений; на плате с 2 ГБ разумный потолок — около половины.

Обратная сторона очевидна и с ней надо смириться: журналы исчезают при перезагрузке. Поэтому на узле, который надо диагностировать, журналы отправляют по сети — но это уже другая серия.

### overlay: нижний слой ro, верхний в памяти

`/etc` нельзя просто сделать tmpfs: система должна видеть свои файлы. Нужно и читать исходное, и иметь возможность писать. Это и есть overlayfs:

```
overlay  /etc  overlay  rw,nosuid,nodev,\
  lowerdir=/etc,upperdir=/run/overlay/etc/upper,workdir=/run/overlay/etc/work  0  0
```

```
      чтение          запись
        │               │
   ┌────▼───────────────▼────┐
   │ upperdir  (в памяти, rw)│ ← сюда попадают все изменения
   ├─────────────────────────┤
   │ lowerdir  (на карте, ro)│ ← отсюда читается всё остальное
   └─────────────────────────┘
```

Чтение идёт из верхнего слоя, а если файла там нет — из нижнего. Любая запись создаёт копию в верхнем. Удаление файла из нижнего слоя записывает в верхний специальную метку «этого больше нет».

`workdir` — служебный каталог на **той же файловой системе**, что и `upperdir`: overlayfs использует его для атомарных операций. Оба должны лежать в памяти, иначе смысл теряется и запись снова идёт на карту.

Тот же механизм лежит под слоями образов контейнеров из [`s04e04`](../../season-04-devops-automation/s04e04-images-layers/) — там нижние слои общие для всех контейнеров, а верхний свой у каждого.

### `noatime`: запись, о которой не подозревают

По умолчанию файловая система обновляет время последнего доступа при **чтении** файла. То есть каждое чтение — это запись. На сервере это мелочь, на SD-карте — постоянный фоновый износ на ровном месте.

```
ro,noatime
```

`noatime` отключает это полностью. Промежуточный вариант — `relatime` (обновлять не чаще раза в сутки) — стоит по умолчанию в большинстве систем, но на карте не нужен и он.

### `nofail`: узел должен подняться в любом случае

```
PARTUUID=…  /var/lib/shadow-mesh  ext4  rw,noatime,nosuid,nodev,nofail  0  2
```

Без `nofail` повреждённый раздел данных останавливает загрузку: система уходит в аварийный режим и ждёт пароль root у консоли. На узле, стоящем на крыше в другом районе города, ждать этого пароля некому.

С `nofail` узел поднимется без раздела данных: он потеряет состояние, но будет доступен — и его можно будет починить удалённо. Это общий принцип для всего, что стоит далеко: **лучше подняться частично, чем не подняться совсем.**

Про журналирование ext4 и `commit=`, `f2fs`, выравнивание разделов, TRIM, `zram`, и почему у промышленных карт другой ресурс — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Корень только для чтения. Кажется, что это ломает половину системы. Что на самом деле ломается?»*

<details>
<summary>Подумай 30 секунд</summary>

Гораздо меньше, чем ожидается. Программам почти всегда нужны на запись `/tmp`, `/var/log`, `/var/tmp`, `/run` — и все они закрываются tmpfs. Остаётся `/etc`, куда пишут некоторые службы при старте, и он закрывается overlay.

Ломается ровно одно: **установка пакетов и изменение системы на живом узле.** И это не побочный ущерб, а цель. Узел, который нельзя изменить на ходу, невозможно испортить на ходу — ни ошибкой, ни атакой из [`s05e09`](../../season-05-security-pentesting/s05e09-forensics-snapshot/), где бэкдор писался в `/tmp` и в автозагрузку.

Обновление такого узла — замена образа целиком, а не правка на месте. Это тот же переход, что от настройки серверов руками к неизменяемой инфраструктуре из [`s04e11`](../../season-04-devops-automation/s04e11-iac-audit/): состояние описано, а не накоплено.
</details>

**LILITH:** *«Почему `upperdir` и `workdir` обязаны лежать на одной файловой системе, и почему обязательно в памяти?»*

<details>
<summary>Ответ</summary>

На одной — потому что overlayfs использует `workdir` для атомарного переименования при копировании файла из нижнего слоя в верхний. Атомарное переименование возможно только внутри одной файловой системы; между разными это копирование, и атомарность теряется. Ядро просто откажется монтировать такой overlay.

В памяти — потому что иначе всё теряет смысл: любая запись в `/etc` уйдёт на карту, ради избавления от чего всё и затевалось. `upperdir` в `/run` (а это tmpfs) означает, что изменения живут до перезагрузки и не касаются носителя.

Побочный эффект стоит понимать заранее: **изменения в `/etc` не переживают перезагрузку.** Пароль, изменённый на живом узле, вернётся к прежнему. Для узла из двадцати семи одинаковых это правильно: единственный источник правды — образ, а не то, что кто-то поправил руками в три часа ночи.
</details>

## IV. Задание: `fstab`

Артефакт — `artifacts/fstab`.

```bash
cp starter/fstab artifacts/
bash tests/test.sh
```

| Требование | Почему |
|---|---|
| `/` и `/boot` — `ro`, по `PARTUUID` | нечего портить сбоем питания, нечего изнашивать |
| режим каждого пути — как в `data/write_paths.txt` | решение принято по смыслу данных |
| у каждого tmpfs — `size=` не меньше суточной записи | без предела съест память, с малым — переполнится |
| сумма tmpfs ≤ половины ОЗУ | свопа на узле нет |
| overlay: `lowerdir` = сам путь, `upperdir`/`workdir` в памяти | иначе запись снова идёт на карту |
| раздел данных: `nofail`, `noatime`, по `PARTUUID` | узел должен подняться даже с побитым разделом |
| `noatime` везде, `nosuid,nodev` на записываемом | чтение не должно порождать запись |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Поля `fstab`: `устройство  точка  тип  опции  dump  pass`.

Режим пути: третья колонка `data/write_paths.txt`; суточная запись — вторая.

Идентификаторы разделов — `data/partitions.txt` и `data/board_facts.txt`.

У tmpfs поле `pass` = `0`: проверять fsck нечего.

Эталон — в `solution/`, там у каждой строки объяснено, что она предотвращает.
</details>

### Три ошибки, которые здесь делают

**tmpfs без `size=`.** Каталог вырастет до половины памяти, и узел без свопа встретит `OOM` в самый неподходящий момент.

**`upperdir` на карте.** Overlay смонтируется, всё будет работать — и всё так же изнашивать носитель. Ошибка не проявляется никак, кроме мёртвой карты через полгода.

**Раздел данных без `nofail`.** Один повреждённый раздел — и удалённый узел не поднимается вообще, вместо того чтобы подняться без данных.
