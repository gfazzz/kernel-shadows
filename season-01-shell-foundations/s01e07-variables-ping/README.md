## II. Теория: коробка с наклейкой и доклад команды

### Переменная — это коробка с наклейкой

```bash
host="shadow-server-01"     # положили значение
echo "$host"                 # достали через $
```

Правило, на котором спотыкаются все: **пробелов вокруг `=` быть не должно.** `host = "x"` bash поймёт как «запусти команду `host` с аргументами `=` и `"x"`».

Второе правило важнее первого: **переменную в кавычки.**

```bash
file="my report.txt"
rm $file        # bash видит ДВА аргумента: my и report.txt
rm "$file"      # один аргумент, как задумано
```

Без кавычек значение разрывается по пробелам. На учебных данных это незаметно; на боевых заканчивается удалением не того файла.

### Код возврата — доклад о выполнении

Каждая команда, завершившись, возвращает число: `0` — успех, любое другое — неудача. Это **не** её вывод, это отдельный канал — как краткий доклад «сделал» или «не смог».

```bash
ping -c 1 -W 2 "$host" >/dev/null 2>&1
code=$?                       # забрали доклад ПОСЛЕ команды
```

`$?` хранит код **последней** выполненной команды, поэтому его забирают сразу: любая следующая команда перезапишет значение.

Тут и появляется смысл переменных: `$?` живёт одно мгновение, `code` — сколько нужно.

Про `ping`, ICMP, флаги `-c`/`-W` и то, почему неответ не всегда значит «сервер мёртв», — в [`theory.md`](theory.md).

> **Сергей:** *«Молодые всё время смотрят на то, что команда напечатала. Печать — для человека. Для скрипта команда говорит одно число, и это число надо взять сразу, пока его не затёрли. Печать врёт, форматы меняются. Код возврата — не врёт.»*

## III. Проверка: Сергей задаёт вопросы

**Сергей:** *«Ты написал `rm $file`, а в `file` лежит „my report.txt". Что удалится?»*

<details>
<summary>Подумай 20 секунд</summary>

Bash подставит значение и разобьёт его по пробелам — команда станет `rm my report.txt`, то есть попытается удалить **два** файла: `my` и `report.txt`. Настоящий `my report.txt` останется, а вот случайно оказавшийся рядом `report.txt` — нет.

Кавычки (`rm "$file"`) передают значение одним аргументом. Это не про стиль: это разница между «удалил что просили» и «удалил что подвернулось».
</details>

**Сергей:** *«Почему `code=$?` надо писать сразу после команды, а не через строчку?»*

<details>
<summary>Ответ</summary>

`$?` всегда содержит код **последней** завершившейся команды. Любая строка между ними — даже безобидный `echo` — перезапишет его своим кодом.

```bash
ping -c 1 host >/dev/null
echo "проверяю..."     # эта строка тоже вернула 0
code=$?                # и мы взяли код echo, а не ping
```

Отсюда правило: сначала забрать значение в переменную, потом делать что угодно.
</details>

## IV. Задание: проверить один узел

Собери `check_host.sh` — инструмент, который пингует хост и докладывает результат:

```
HOST: shadow-server-01
STATUS: UP
EXIT_CODE: 0
```

Это `Type A`: то же действие повторится для пятидесяти машин, значит его пора оформить командой.

```bash
cp starter/check_host.sh artifacts/check_host.sh
# заменить TODO (ping → $? → status)
bash tests/test.sh
```

ТЗ и критерии — в [`mission.md`](mission.md). Тест **подменяет `ping`** своей версией: хосты `up-*` отвечают, остальные молчат. Живая сеть не нужна, а результат одинаков на любой машине.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
host="${1:?нужно имя хоста}"
ping -c 1 -W 2 "$host" >/dev/null 2>&1
code=$?
if [ "$code" -eq 0 ]; then status="UP"; else status="DOWN"; fi
```

`>/dev/null 2>&1` глушит вывод: нас интересует только код возврата. Эталон — в `solution/`, открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Смотреть на вывод вместо кода.** Соблазн разобрать текст `ping` (`grep '64 bytes'`) велик, но текст зависит от локали, версии и платформы. Код возврата не зависит ни от чего.

**Захардкодить `UP`.** Скрипт, который всегда печатает `UP`, проходит беглый взгляд и не проходит тест: там есть заведомо мёртвый хост. Инструмент, который не умеет сказать «плохо», бесполезен именно тогда, когда плохо.

**Забыть `set -e` — или, наоборот, поставить его.** Здесь `set -e` навредит: неудачный `ping` — штатная ситуация, а с `set -e` скрипт молча завершится на первом же недоступном хосте. Поэтому в шаблоне `set -uo pipefail` без `-e`.
