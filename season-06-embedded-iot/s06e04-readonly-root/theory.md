# s06e04 — теория: флеш-память, overlayfs и неизменяемый узел

Дополнение к [`README.md`](README.md). Здесь — как именно изнашивается карта, чем отличаются файловые системы для флеша, устройство overlayfs и что делать с журналами, которых больше нет.

## 1. Почему SD-карта умирает

### Ячейка имеет счётчик

Флеш-память стирается блоками и имеет конечное число циклов стирания:

| Тип | Бит на ячейку | Циклов перезаписи |
|---|---|---|
| SLC | 1 | ~100 000 |
| MLC | 2 | ~3 000 |
| TLC | 3 | ~1 000 |
| QLC | 4 | ~300 |

Дешёвые потребительские карты — TLC или QLC. Это не брак: они рассчитаны на фотоаппарат, где карту заполняют и читают, а не на сервер, который пишет непрерывно.

### Усиление записи

Записать один байт нельзя: минимальная единица стирания — блок в сотни килобайт. Изменение одного байта означает «прочитать блок, стереть блок, записать блок». Отношение реально стёртого к логически записанному называется **усилением записи** и на SD-картах достигает десятков.

Отсюда неочевидное следствие: **много мелких записей вреднее, чем одна большая.** Журнал, дописывающий по строчке раз в секунду, изнашивает карту сильнее, чем гигабайт, записанный разом.

### Выравнивание износа — и почему его мало

Контроллер карты распределяет запись по ячейкам, чтобы они изнашивались равномерно. Но у дешёвой карты этот алгоритм примитивный и работает только по свободному пространству. Заполненная на 90% карта имеет вдесятеро меньше места для манёвра.

Практический вывод: **оставляйте запас.** Карта на 32 ГБ с образом на 8 ГБ проживёт заметно дольше, чем карта на 8 ГБ с тем же образом.

### Прикидка ресурса

```
запись в сутки × усиление записи × 365
──────────────────────────────────────  = лет до износа
    ёмкость × циклы перезаписи
```

Для 478 МБ/сутки при усилении 10 на карте 32 ГБ с ресурсом 1000 циклов получается порядка 18 лет — казалось бы, много. Но это при **идеальном** выравнивании износа по всей карте; на практике запись концентрируется в области журналов, и умирает она за месяцы. Именно поэтому важно не «сколько всего», а «сколько раз в одно и то же место».

### Промышленные носители

Промышленные SD и eMMC (индустриальный температурный диапазон, SLC/pSLC) стоят в разы дороже и живут в десятки раз дольше. Для узла, который дорого обслуживать, это дешевле, чем выезд. Но и они не отменяют правила: **лучший способ не изнашивать носитель — не писать на него.**

## 2. Файловые системы и флеш

| ФС | Особенности |
|---|---|
| `ext4` | универсальная; журнал даёт стойкость к сбоям, но добавляет записи |
| `f2fs` | спроектирована под флеш: пишет последовательно, дружит с контроллером |
| `btrfs` | сжатие снижает объём записи; сложнее и требовательнее к памяти |
| `squashfs` | сжатая, **только для чтения** — идеальна для неизменяемого корня |
| `overlayfs` | не хранит данные сама, а комбинирует другие ФС |

### Настройки ext4, снижающие запись

```
ro,noatime                          корень: не пишем вообще
rw,noatime,commit=60                данные: сбрасывать журнал раз в минуту
```

`commit=60` вместо стандартных 5 секунд уменьшает частоту записи журнала в 12 раз. Цена честная: при сбое питания теряется до минуты изменений. Для узла, чьи данные — телеметрия, это приемлемо; для базы с деньгами — нет.

Отключать журнал (`data=writeback`, `^has_journal`) на узле со срывами питания **не стоит**: journal и есть то, что позволяет пережить срыв без ручного `fsck`.

## 3. overlayfs подробнее

### Устройство

```
mount -t overlay overlay \
  -o lowerdir=/lower,upperdir=/upper,workdir=/work /merged
```

| Каталог | Роль |
|---|---|
| `lowerdir` | база, только чтение; может быть несколько через `:` |
| `upperdir` | слой записи |
| `workdir` | служебный, на той же ФС, что `upperdir` |
| точка монтирования | объединённый вид |

### Правила видимости

1. Файл есть в `upper` → виден он.
2. Файла нет в `upper`, есть в `lower` → виден из `lower`.
3. Запись в файл из `lower` → он целиком копируется в `upper` (copy-up), дальше работа с копией.
4. Удаление файла из `lower` → в `upper` создаётся символ-заглушка (whiteout), файл пропадает из объединённого вида, но остаётся в `lower`.

Copy-up — важная деталь для производительности: изменение одного байта в большом файле копирует **весь файл** в верхний слой. На узле с tmpfs-верхом это ещё и расход памяти.

### Несколько нижних слоёв

```
lowerdir=/layer3:/layer2:/layer1
```

Слева — верхние, справа — нижние. Так устроены образы контейнеров: каждая инструкция сборки даёт слой, а контейнер добавляет свой записываемый верх. Отсюда и совет из [`s04e04`](../../season-04-devops-automation/s04e04-images-layers/): порядок инструкций определяет, какие слои переиспользуются.

### Ограничения

- `upperdir` и `workdir` — на одной ФС, иначе монтирование не пройдёт;
- нельзя использовать сетевую ФС как `upperdir`;
- `lowerdir` нельзя менять «из-под» смонтированного overlay: результат непредсказуем;
- жёсткие ссылки между слоями не сохраняются при copy-up.

### Как это делает `raspi-config`

На Raspberry Pi готовый переключатель (`Performance → Overlay File System`) собирает initramfs, который монтирует весь корень как overlay с tmpfs-верхом. Удобно и работает, но менее прозрачно, чем явные строки в `fstab`: понимать стоит механику, пользоваться можно готовым.

## 4. Журналы, которых больше нет

Перевод `/var/log` в tmpfs означает: после перезагрузки история потеряна. Варианты, что с этим делать:

| Подход | Суть |
|---|---|
| `journald` в память | `Storage=volatile` в `journald.conf` — честно и явно |
| отправка по сети | `systemd-journal-upload`, `rsyslog`, `promtail` — журнал уезжает с узла |
| кольцевой буфер на диске | ограниченный `SystemMaxUse=` на разделе данных |
| «последний сбой» | сохранять на диск только при аварии, а не постоянно |

Для сети из двадцати семи узлов правильный ответ почти всегда — **отправлять**: локальный журнал на узле всё равно недоступен, когда узел не поднялся. Тот же принцип, что вынос наблюдателя за пределы наблюдаемой системы из [`s05e08`](../../season-05-security-pentesting/s05e08-auditd/).

Ограничить журнал в памяти:

```ini
# /etc/systemd/journald.conf
Storage=volatile
RuntimeMaxUse=64M
```

## 5. `zram`: память вместо свопа

Свопа на карте быть не должно — это самый быстрый способ её убить. Но память кончается. Компромисс — `zram`: сжатый блочный своп **в самой памяти**.

```bash
modprobe zram
echo lz4 > /sys/block/zram0/comp_algorithm
echo 512M > /sys/block/zram0/disksize
mkswap /dev/zram0 && swapon -p 100 /dev/zram0
```

Сжатие типичных данных — 2–3 раза, то есть 512 МБ zram дают эффективно около 1–1.5 ГБ. Расплата — процессорное время на сжатие. На четырёхъядерной плате это выгодный обмен.

## 6. Неизменяемый узел как принцип

Корень `ro` — частный случай подхода, который в серверном мире называется неизменяемой инфраструктурой:

| Изменяемая система | Неизменяемая |
|---|---|
| правки на месте, накопленное состояние | образ целиком, состояние описано |
| «а кто это поменял?» | ответ в git |
| дрейф между узлами | двадцать семь одинаковых |
| откат = вспомнить и отменить | откат = прежний образ |

Плюсы для безопасности прямые: атака из [`s05e09`](../../season-05-security-pentesting/s05e09-forensics-snapshot/) писала бэкдор в `/tmp` и закреплялась через файлы в `/etc`. На узле с `ro` корнем и tmpfs-`/tmp` оба шага не переживают перезагрузку — закрепиться негде.

Минусы честные:
- обновление требует конвейера сборки образов, а не `apt upgrade`;
- отладка «по-быстрому на живом узле» становится неудобной — намеренно;
- любое изменение, сделанное руками, исчезнет, и об этом надо помнить.

Практический приём: держать переключатель. Одна команда переводит корень в `rw` для сервисного окна, вторая возвращает обратно:

```bash
mount -o remount,rw /
# … работа …
mount -o remount,ro /
```
