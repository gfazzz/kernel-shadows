## 2. Как sudo принимает решение

При каждом вызове sudo ищет правила, совпадающие по четвёрке **пользователь — хост — runas — команда**, и применяет **последнее** из совпавших. Отсюда следствия:

- порядок строк значим, и значим он именно с конца;
- узкое правило ниже широкого ничего не отнимает;
- если ни одно правило не совпало — отказ и запись в журнал.

Совпадение по команде — это совпадение **пути и аргументов**:

| Правило | `sudo systemctl restart nginx` | `sudo systemctl edit nginx` |
|---|---|---|
| `/usr/bin/systemctl` | ✅ | ✅ |
| `/usr/bin/systemctl restart nginx` | ✅ | ❌ |
| `/usr/bin/systemctl restart *` | ✅ | ❌ |
| `/usr/bin/systemctl ""` | ❌ (только без аргументов) | ❌ |

Пустые кавычки `""` — способ разрешить команду **только** без аргументов. Звёздочка разрешает что угодно на её месте, включая пробелы, — поэтому `/usr/bin/systemctl *` не ограничивает почти ничего.

Команда без абсолютного пути не совпадёт никогда: sudo сравнивает полный путь, а не имя.

## 3. Файлы политики

```bash
visudo                       # правит /etc/sudoers с проверкой синтаксиса
visudo -f /etc/sudoers.d/ops-team   # то же для отдельного файла
visudo -c                    # проверить всё, ничего не открывая
visudo -c -f ops-team        # проверить файл до установки
sudo -l                      # что разрешено лично мне
sudo -l -U anna              # что разрешено анне (нужен root)
```

`/etc/sudoers` заканчивается строкой `@includedir /etc/sudoers.d`, и всё, что там лежит, читается по порядку имён. Отсюда практика: не трогать основной файл, а класть по файлу на роль или на команду.

Права на файлы политики — `0440`, владелец `root:root`. При других правах sudo откажется работать целиком, и это не придирка: файл, доступный на запись кому-то ещё, — это выдача root этому кому-то.

Файлы с точкой в имени и с суффиксом `~` игнорируются. `ops-team.bak` не прочитается, `ops-team.disabled` — тоже; а вот `ops-team-old` прочитается, и это регулярный источник сюрпризов.

**Синтаксическая ошибка в `/etc/sudoers` ломает sudo целиком** — вплоть до невозможности его починить. Отсюда `visudo`, который проверяет файл до сохранения, и привычка держать открытой вторую root-сессию, пока правишь.

## 4. Теги

```
NOPASSWD:  не спрашивать пароль
PASSWD:    спрашивать (возврат к умолчанию в середине списка)
NOEXEC:    запретить программе запускать другие программы
SETENV:    разрешить передавать переменные окружения
```

Тег действует на все команды после него в списке, пока не встретится противоположный:

```
anna ALL=(root) NOPASSWD: /usr/bin/journalctl --no-pager, PASSWD: /usr/sbin/reboot
```

`NOEXEC:` — недооценённый тег: он подгружает библиотеку, перехватывающую `exec*()`, и `:!sh` из редактора перестаёт работать. Спасает не всегда (обходится через прямые системные вызовы), но превращает «выдал vim = выдал root» в «выдал vim и надо постараться».

## 5. Окружение

`env_reset` (умолчание в современных дистрибутивах) очищает окружение перед запуском команды, оставляя короткий белый список (`env_keep`). Это не гигиена, а защита:

```
Defaults env_keep += "LD_PRELOAD"     # выдача root любому, у кого есть правило
```

`LD_PRELOAD` заставляет загрузчик подгрузить произвольную библиотеку в процесс — который здесь запускается от root. Того же класса `PYTHONPATH`, `PERL5LIB`, `BASH_ENV`, `IFS`.

`secure_path` задаёт `PATH`, с которым запускается команда. Он нужен не столько для поиска самой команды — её sudo сверяет по абсолютному пути, — сколько для всего, что она запустит **дальше**. Разрешённый скрипт, вызывающий внутри `grep` или `systemctl` по имени, возьмёт их из `PATH`; если туда попал каталог пользователя, от root выполнится чужой `grep`. Правило `/usr/bin/backup.sh` при этом выглядит совершенно безобидно.

## 6. Что писать в журнал

```
Defaults        logfile="/var/log/sudo.log"
Defaults:max    log_input, log_output
Defaults!/usr/bin/journalctl !log_output
```

Обычный журнал sudo (в syslog или `logfile`) фиксирует **факт**: кто, когда, какую команду. `log_input`/`log_output` пишут **сессию целиком** — всё, что было набрано и показано; воспроизводится через `sudoreplay`.

Включать запись сессии всем подряд не стоит: в вывод попадают пароли, ключи и содержимое файлов, а сам журнал становится новой мишенью. Разумный компромисс — писать сессии тех, у кого полный доступ, и исключать заведомо шумные команды (третья строка выше).

## 7. Почему `su` — не то же самое

`su -` переключает на root целиком: дальше в журнале одна запись о входе и ни одной о том, что происходило. Разница с sudo не в удобстве:

| | `su -` | `sudo команда` |
|---|---|---|
| Пароль | root'а — общий для всех, кто его знает | свой, личный |
| Журнал | факт входа | каждая команда отдельно |
| Объём прав | всё | ровно перечисленное |
| Отзыв доступа | смена root-пароля у всех | правка одной строки |

Именно поэтому в дистрибутивах у root нет пароля вовсе (`!` в поле пароля `/etc/shadow`, см. `s03e01`): войти под root напрямую нельзя, а `sudo` работает.

## 8. Метанавык: право как утверждение, которое кто-то проверит

Политика доступа — это документ, который читают редко и в плохих обстоятельствах: во время инцидента, при увольнении, при аудите. Единственное, что от неё требуется в этот момент, — быть **читаемой целиком**.

Отсюда практический критерий, заменяющий длинные рассуждения о безопасности: если на вопрос «что может Анна?» нельзя ответить, посмотрев в файл минуту, политики фактически нет — есть накопленный слой разрешений.

Второй критерий — обратный: по каждой строке должно быть понятно, **что сломается, если её убрать**. Строка, про которую этого не знает никто, уже не защищает работу; она защищает только чью-то давнюю спешку.
