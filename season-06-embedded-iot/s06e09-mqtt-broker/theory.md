# s06e09 — теория: брокер, сертификаты и разграничение доступа

Дополнение к [`README.md`](README.md). Здесь — устройство конфигурации mosquitto, работа с сертификатами, взаимная аутентификация, мосты и общие принципы разграничения доступа.

---

## 1. Структура `mosquitto.conf`

Файл плоский: `директива значение`, по одной на строку. Особенность — **секции слушателей**:

```
# глобальные настройки
persistence true
log_dest file /var/log/mosquitto/mosquitto.log

listener 8883                  ← начало секции
cafile   /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/broker.crt
keyfile  /etc/mosquitto/certs/broker.key
```

Всё после `listener` относится к нему, пока не встретится следующий `listener`. Настройка, дописанная в конец файла «глобально», на самом деле достаётся последнему слушателю — та же ловушка, что незакрытая секция `[pi4]` в [`s06e03`](../s06e03-boot-config/).

Директива `per_listener_settings true` меняет правила: тогда `password_file`, `acl_file` и `allow_anonymous` задаются **отдельно для каждого слушателя**. Это мощно и опасно: забытый `password_file` во второй секции означает слушателя без аутентификации. Если нужен один набор правил на всех — проще держать один слушатель.

### Часто используемые директивы

| Директива | Смысл |
|---|---|
| `listener ПОРТ [АДРЕС]` | слушать порт (и, опционально, только на одном адресе) |
| `allow_anonymous` | пускать ли без учётных данных |
| `password_file` | файл учётных записей (`mosquitto_passwd`) |
| `acl_file` | файл прав по темам |
| `persistence`, `persistence_location` | сохранять сессии и retained на диск |
| `autosave_interval` | как часто сбрасывать состояние на диск |
| `max_queued_messages` | предел очереди отключённого клиента |
| `max_inflight_messages` | сколько неподтверждённых сообщений одновременно |
| `message_size_limit` | предел размера сообщения |
| `max_connections` | предел числа клиентов |
| `log_dest`, `log_type` | куда и что писать |
| `connection_messages` | писать ли в журнал подключения с именами клиентов |

`max_queued_messages` заслуживает внимания: для клиента с сохраняемой сессией брокер копит сообщения QoS 1/2 всё время его отсутствия. Двадцать семь узлов, пропавших на сутки, без предела — это гарантированный `OOM` на брокере. Ограничение переводит проблему из «брокер умер» в «часть сообщений потеряна», что несравнимо лучше.

## 2. Учётные записи

```bash
mosquitto_passwd -c /etc/mosquitto/passwd dashboard   # -c создаёт файл заново!
mosquitto_passwd    /etc/mosquitto/passwd shadow-node-07
mosquitto_passwd -b /etc/mosquitto/passwd recorder 'пароль'   # для скриптов
mosquitto_passwd -D /etc/mosquitto/passwd старый-клиент       # удалить
```

Ключ `-c` затирает файл целиком — классический способ потерять двадцать семь учётных записей одной командой. Внутри хранятся хеши, а не пароли:

```
shadow-node-07:$7$101$Zk3...$q9F...
```

Для парка устройств пароли обычно генерируются при подготовке образа и раскладываются вместе с ним, а файл `passwd` собирается тем же конвейером — то есть тем же способом, что и любая другая конфигурация из [`s04e12`](../../season-04-devops-automation/s04e12-ansible-playbook/).

## 3. Синтаксис ACL

```
# правила анонимных клиентов — до первого user/pattern
topic read public/#

user dashboard
topic read  shadow/+/telemetry/#
topic write shadow/+/cmd/#

user recorder
topic read shadow/+/telemetry/#

# правила для всех, с подстановкой
pattern write shadow/%u/telemetry/#
pattern read  shadow/%u/cmd/#
```

| Форма | Значение |
|---|---|
| `topic ТЕМА` | доступ на чтение и запись (по умолчанию `readwrite`) |
| `topic read ТЕМА` | только чтение |
| `topic write ТЕМА` | только публикация |
| `pattern ... %u` | подстановка имени пользователя |
| `pattern ... %c` | подстановка идентификатора клиента |

Правила **разрешающие**: что не разрешено, то запрещено. Это тот же default-deny, что в профиле AppArmor из [`s05e11`](../../season-05-security-pentesting/s05e11-hardening/), и то же свойство: перечисляется нужное, а не запрещается лишнее.

### `%u` против `%c`

`%u` — имя пользователя из `CONNECT`, `%c` — идентификатор клиента. `%c` заманчив (не надо заводить учётные записи), но идентификатор клиент выбирает сам и может назваться кем угодно. Разграничение по `%c` без аутентификации — это разграничение по честному слову.

### Проверка ACL

Прямого «проверь этот файл» у mosquitto нет; проверяют поведением:

```bash
mosquitto_sub -h broker -p 8883 --cafile ca.crt \
  -u shadow-node-07 -P пароль -t 'shadow/shadow-node-12/telemetry/#' -v
# ожидаем отказ или тишину
```

Именно поэтому в этой серии тест **моделирует** разрешение: он проходит по правилам той же логикой, что брокер, и отвечает на вопросы «может ли узел X писать в тему Y». Проверка конфигурации безопасности по смыслу, а не по тексту, — общий приём: текст говорит, что написано, модель — что из этого следует.

## 4. Сертификаты

### Минимальный набор

```bash
# свой удостоверяющий центр
openssl req -new -x509 -days 3650 -extensions v3_ca \
  -keyout ca.key -out ca.crt

# ключ и запрос для брокера
openssl genrsa -out broker.key 2048
openssl req -new -out broker.csr -key broker.key   # CN = имя, по которому подключаются!

# подпись
openssl x509 -req -in broker.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -out broker.crt -days 730
```

`CN` (или, правильнее, `subjectAltName`) должен совпадать с именем, по которому клиенты подключаются к брокеру. Несовпадение — самая частая причина «TLS не работает», и лечится оно **не** отключением проверки.

### Клиент

```bash
mosquitto_sub -h broker.example -p 8883 --cafile ca.crt \
  -u shadow-node-07 -P пароль -t 'shadow/shadow-node-07/cmd/#'
```

Клиент обязан знать `ca.crt`, чтобы проверить сертификат брокера. Ключ `--insecure` отключает проверку имени и превращает TLS в шифрование без аутентификации — то есть в защиту от пассивного слушателя, но не от подмены брокера.

### Взаимная аутентификация

```
require_certificate true
use_identity_as_username true
```

Тогда клиент предъявляет свой сертификат, и его `CN` становится именем пользователя — паролей не нужно вовсе. Для парка устройств это удобнее: сертификат кладётся в образ, отзывается через список отзыва (CRL), и `%u` в ACL продолжает работать.

Цена — инфраструктура: выпуск, распространение, отзыв и **срок действия**. Просроченный сертификат на узле, стоящем на крыше, — это выезд. Именно поэтому в реальных парках сроки делают длинными, а отзыв — работающим.

## 5. Мосты

```
connection to-central
address central.example:8883
topic shadow/# out 1 "" ""
bridge_cafile /etc/mosquitto/certs/ca.crt
remote_username edge-shenzhen
remote_password ...
cleansession false
```

Локальный брокер пересылает темы в центральный. Смысл — буферизация: при обрыве канала до центра узлы продолжают публиковать в локальный брокер, а он отдаст накопленное, когда связь вернётся.

Поля в `topic`: направление (`out`/`in`/`both`), QoS, локальный и удалённый префиксы. Префиксы позволяют не путать данные площадок: `shadow/#` с площадки Шэньчжэня приходит в центр как `sites/shenzhen/shadow/#`.

## 6. Что здесь общего с любой системой разграничения доступа

| Принцип | Здесь | Где ещё в курсе |
|---|---|---|
| default-deny | не разрешено — запрещено | AppArmor, [`s05e11`](../../season-05-security-pentesting/s05e11-hardening/) |
| права по потребности | узел пишет только свою тему | `sudoers`, [`s03e03`](../../season-03-system-administration/s03e03-sudo/) |
| идентификация до авторизации | `%u` работает только с учётными записями | ключи SSH, [`s02e08`](../../season-02-networking/s02e08-ssh-keys/) |
| нет пути в обход | нет незашифрованного слушателя | правила брандмауэра, [`s02e06`](../../season-02-networking/s02e06-firewall-ufw/) |
| проверять по смыслу | модель разрешений, а не текст | проверка достижимости, [`s04e07`](../../season-04-devops-automation/s04e07-ci-pipeline/) |

Разница между IoT и серверами тут не в принципах, а в масштабе и цене ошибки: устройств много, физический доступ к ним есть у посторонних, а обновление стоит выезда. Поэтому конфигурация брокера — не «настройка сервиса», а описание того, во что превращается взлом одного устройства.
