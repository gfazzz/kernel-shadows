# s07e11 — теория: модель, а не список правил

Дополнение к [`README.md`](README.md). Здесь — откуда берётся метка, чем SELinux отличается от AppArmor, переход домена, перемаркировка, и что из этого применимо в контейнерах.

---

## 1. Обязательный контроль доступа

```
запрос ──▶ обычные права (DAC) ──▶ SELinux (MAC) ──▶ разрешено
              владелец, rwx          политика
```

Две проверки подряд, и обе должны пройти. Отсюда первое следствие: **SELinux ничего не разрешает.** Он только запрещает — сверх того, что уже запретили обычные права. Файл с правами `600` не станет доступен из-за политики.

Второе следствие тоньше и объясняет, зачем всё это нужно. Обычные права **дискреционные**: владелец файла может их изменить, а процесс, работающий от root, может почти всё. Политика SELinux — **обязательная**: её не может изменить ни владелец файла, ни root-процесс. Взломанный `nginx` с правами root всё равно не прочитает `/etc/shadow`, если политика этого не разрешает.

Это и есть ответ на вопрос «зачем, если есть права»: **права защищают пользователей друг от друга, MAC защищает систему от процессов**, включая те, что работают от имени администратора.

## 2. Откуда берётся метка

| Объект | Откуда метка |
|---|---|
| файл при создании | наследует тип каталога-родителя |
| файл при `restorecon` | из базы `fcontext` по пути |
| файл при копировании `cp` | тип целевого каталога |
| файл при `mv` | **сохраняет старую метку** |
| процесс | переход домена при запуске |
| порт | из базы `port` |

Строка про `mv` — источник половины загадок. Файл, перемещённый в правильный каталог, сохраняет метку из старого места, и `ls -Z` показывает нужный путь с ненужным типом. Копирование помечает правильно, перемещение — нет.

```bash
cp --preserve=context  # сохранить метку осознанно
restorecon -Rv /srv/aurora   # привести к тому, что говорит политика
matchpathcon /srv/aurora/index.html  # что политика ожидает по этому пути
```

Последняя команда — самая недооценённая: она отвечает на вопрос «а какой тип тут должен быть» без всяких догадок.

## 3. Переход домена

```
init_t ──запускает /usr/sbin/nginx (httpd_exec_t)──▶ httpd_t
```

Процесс не выбирает себе домен. Он определяется тройкой «домен родителя, тип исполняемого файла, класс» — и правилом `type_transition` в политике. Отсюда неожиданное: **скопированный в другое место бинарник запустится в другом домене**, потому что у копии другой тип.

Классический случай: администратор кладёт свою сборку `nginx` в `/opt/nginx/sbin/nginx`, запускает — и всё работает, потому что домена `httpd_t` процесс не получил и оказался неограниченным. Выглядит как «SELinux не мешает», означает «защиты нет».

Посмотреть, что получилось:

```bash
ps -eZ | grep nginx
ls -Z /usr/sbin/nginx        # httpd_exec_t
```

## 4. Перемаркировка

Метка хранится в расширенном атрибуте файла (`security.selinux`), то есть в файловой системе. Отсюда:

- **файловая система без поддержки xattr** (старые сетевые, некоторые образы) не хранит меток, и весь том получает один тип при монтировании;
- **том, записанный при выключенном SELinux**, остаётся без меток;
- включение после `disabled` требует **полной перемаркировки** — файла `/.autorelabel` и перезагрузки, которая на большом диске занимает часы.

Именно поэтому «выключить на время» — плохая сделка: обратный путь дороже, чем кажется, и его придётся проходить в неудобный момент.

```bash
touch /.autorelabel && reboot     # полная перемаркировка
restorecon -R -v /srv             # выборочная, без перезагрузки
```

## 5. SELinux против AppArmor

В [`s05e11`](../../season-05-security-pentesting/s05e11-hardening/) укрепление делалось с AppArmor. Разница не в качестве, а в модели:

| | SELinux | AppArmor |
|---|---|---|
| к чему привязано | к метке объекта | к пути в файловой системе |
| где хранится | в xattr файла | в профиле |
| переживает `mv` | да (метка едет с файлом) | нет (путь изменился) |
| порог входа | высокий | ниже |
| гранулярность | выше | достаточная в большинстве случаев |
| где по умолчанию | RHEL, Fedora, CentOS | Debian, Ubuntu, SUSE |

Привязка к метке, а не к пути, — принципиальное отличие. Символическая ссылка, жёсткая ссылка, монтирование в другое место не обманывают SELinux: метка едет с самим объектом. Профиль AppArmor, написанный на путь, обмануть проще — и это единственное существенное преимущество более сложной модели.

Практический вывод для смешанного парка, как у Verne: **это не выбор, а обстоятельство.** Что стоит в дистрибутиве, тем и пользуются; переводить Ubuntu на SELinux ради единообразия — работа без пользы.

## 6. В контейнерах

```bash
ps -eZ | grep container
system_u:system_r:container_t:s0:c194,c528  ...
```

Среда выполнения контейнеров (`containerd`, `crio`, `podman`) запускает процессы в домене `container_t` и выдаёт каждому контейнеру **свою пару категорий MCS** (`c194,c528`). Категории и делают главное: процесс одного контейнера не может тронуть файлы другого, даже если у них одинаковый домен и одинаковые обычные права.

Что из этого следует для Kubernetes:

- монтирование каталога узла в под требует правильной метки, иначе отказ; отсюда `:z` и `:Z` у `podman`, а в Kubernetes — `securityContext.seLinuxOptions`;
- отказ виден в журнале **узла**, а не в логах пода: `kubectl logs` покажет «permission denied» и ничего больше;
- политика для контейнеров — общая на всех, а не своя у каждого образа.

Последнее объясняет, почему разбор такого отказа начинается на узле, а не в кластере: слой, который отказал, находится ниже того, где стоит наблюдатель.
