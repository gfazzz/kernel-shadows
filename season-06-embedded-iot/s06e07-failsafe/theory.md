# s06e07 — теория: отказы, приоритеты реакций и конфигурация со связями

Дополнение к [`README.md`](README.md). Здесь — полная карта отказов автопилота, что происходит при нескольких одновременно, как устроены параметры и почему конфигурации со связями требуют особого подхода к проверке.

---

## 1. Полная карта отказов

| Отказ | Параметр | Как обнаруживается |
|---|---|---|
| радиоуправление | `FS_THR_ENABLE`, `FS_THR_VALUE` | канал газа ниже порога или пропали кадры приёмника |
| наземная станция | `FS_GCS_ENABLE` | нет `HEARTBEAT` от станции дольше таймаута |
| батарея | `BATT_FS_*`, `BATT_LOW_*`, `BATT_CRT_*` | напряжение или израсходованная ёмкость |
| оценка положения | `FS_EKF_ACTION`, `FS_EKF_THRESH` | расхождение фильтра выше порога |
| GPS | `FS_EKF_*` (косвенно) | потеря решения ведёт к развалу EKF |
| выход за геозону | `FENCE_ACTION` | нарушение радиуса, потолка или многоугольника |
| отказ мотора | `FS_CRASH_CHECK` | несоответствие управления и реакции |
| «упал» | `FS_CRASH_CHECK` | резкое отклонение и отсутствие движения |
| «убежал» | `FS_EKF_THRESH`, `ANGLE_MAX` | превышение допустимых углов |

Значения `FS_*_ENABLE` — не «да/нет», а выбор реакции:

| Значение | Обычно означает |
|---|---|
| 0 | продолжать выполнение (никакой реакции) |
| 1 | вернуться домой (`RTL`) |
| 2 | продолжать миссию (если она есть) |
| 3 | сесть на месте |
| 4 | `SmartRTL`, если доступен |

Именно из-за нуля со смыслом «продолжать» проверка «параметр не равен нулю» осмысленна, а «параметр задан» — нет.

## 2. Когда отказов несколько

Реальные происшествия редко состоят из одного отказа. Приоритеты примерно такие:

```
критический заряд  >  развал оценки положения  >  геозона  >  потеря связи
```

Логика: садиться немедленно важнее, чем возвращаться; знать своё положение важнее, чем соблюдать границу; граница важнее, чем связь. Конкретный порядок зависит от прошивки, и держать его в голове не нужно — важно понимать, что **порядок существует**, и что реакции могут конфликтовать.

Классический конфликт: аппарат вышел за геозону (`FENCE_ACTION=RTL`) и одновременно потерял оценку положения (`FS_EKF_ACTION=Land`). Возвращаться некуда — положение неизвестно; садиться нельзя — он за границей. Разрешается это приоритетом, и результат надо знать заранее, а не выяснять в воздухе.

`SmartRTL` — отдельная полезная реакция: аппарат возвращается **по пройденному пути**, а не по прямой. Это спасает, когда между текущей точкой и домом стоит здание. Требует памяти о треке, поэтому недоступен сразу после включения.

## 3. Параметры как интерфейс

Автопилот — программа с сотнями параметров, которые задают её поведение без перекомпиляции. Это интересный образец конфигурации:

| Свойство | Следствие |
|---|---|
| плоское пространство имён | префиксы вместо секций: `FS_`, `BATT_`, `FENCE_` |
| строгая типизация значений | целые, дробные, битовые маски, перечисления |
| разные единицы у соседних параметров | сантиметры рядом с метрами |
| нет проверки связей | загрузится любая противоречивая комбинация |
| хранится в энергонезависимой памяти | переживает перепрошивку не всегда |

Работа с ними:

```bash
param download                  # вытащить всё с аппарата
param show FS_*                 # посмотреть группу
param set FS_GCS_ENABLE 1
param diff эталон.params        # сравнить с эталоном
```

`param diff` — важнейшая практика: набор параметров хранят в системе контроля версий и сравнивают с аппаратом перед вылетом. Это ровно та же идея, что проверка дрейфа конфигурации в [`s04e11`](../../season-04-devops-automation/s04e11-iac-audit/): состояние машины сверяется с описанным, а расхождение — находка.

### Опечатка в имени

```
LAND_SPED,50
```

Автопилот **молча проигнорирует** неизвестное имя. Ни ошибки, ни предупреждения: параметр просто не применится, и `LAND_SPEED` останется со значением по умолчанию. Отсюда проверка «нет неизвестных параметров» — она ловит то, о чём система не сообщает.

Тот же класс проблемы: опечатка в ключе YAML, неизвестная директива в конфигурации, которую парсер пропускает, переменная окружения с лишним подчёркиванием. **Молчаливое игнорирование неизвестного — самая недружелюбная стратегия обработки ошибок**, и встречается она повсеместно.

## 4. Единицы измерения

Разнобой в единицах — историческое наследие, но не только: сантиметры и см/с позволяют хранить величины целыми числами, что дешевле для микроконтроллера, чем плавающая точка.

| Суффикс/тип | Единицы |
|---|---|
| `_ALT`, `_ALT_FINAL` (RTL, WPNAV) | сантиметры |
| `FENCE_ALT_MAX`, `FENCE_RADIUS` | метры |
| `_SPEED` (LAND, WPNAV) | см/с |
| `_VOLT` | вольты |
| `_MAH` | миллиампер-часы |
| `FS_THR_VALUE` | единицы PWM (микросекунды импульса) |
| углы | градусы или сотые доли градуса — зависит от параметра |

Единственная надёжная стратегия — **смотреть в справочник каждый раз**. Ошибка в единицах не отличается от верного значения ничем, кроме порядка величины, и не ловится ни синтаксисом, ни диапазоном (60 и 6000 оба допустимы для `RTL_ALT`).

Практический приём: писать в комментарии рядом с параметром значение в человеческих единицах — `RTL_ALT,6000  # 60 м`. Комментарий не проверяется машиной, но именно он читается при следующей правке.

## 5. Конфигурации со связями

Обычный валидатор конфигурации проверяет поля по одному: тип, диапазон, обязательность. Ошибки, ради которых пишут валидатор, обычно живут не в полях, а в отношениях между ними.

Виды связей, встречающиеся почти в любой конфигурации:

| Вид | Пример здесь | Пример вне дронов |
|---|---|---|
| порядок порогов | `BATT_CRT < BATT_LOW` | `warning < critical` в мониторинге |
| вложенность интервалов | препятствие < `RTL_ALT` < потолок | порты в разрешённом диапазоне |
| согласие с внешними данными | радиус > маршрута | размер `tmpfs` ≤ памяти ([`s06e04`](../s06e04-readonly-root/)) |
| взаимная обязательность | ACL без аутентификации бессмысленны | TLS без сертификата |
| единицы | сантиметры против метров | таймаут в секундах против миллисекунд |

Отсюда практический вывод для любого, кто пишет проверку конфигурации: **список правил начинается там, где заканчивается схема.** Схема (типы и диапазоны) отсекает мусор; правила отсекают осмысленную, но неверную комбинацию, а именно она доходит до эксплуатации.

## 6. Как проверить, не рискуя аппаратом

```bash
sim_vehicle.py -v ArduCopter --console --map
# в консоли MAVProxy:
param load failsafe.params
param set SIM_RC_FAIL 1        # смоделировать потерю пульта
param set SIM_GPS_DISABLE 1    # смоделировать потерю GPS
```

Симулятор умеет вызывать отказы по команде: это единственный дешёвый способ увидеть, что реально произойдёт при заданных параметрах, включая конфликты нескольких реакций.

Разумный порядок, как и в [`s06e06`](../s06e06-mission-check/):

1. проверка набора параметров как текста — секунды;
2. `SITL` с моделируемыми отказами — минуты;
3. стенд без винтов — часы;
4. полёт.
