# Теория — s02e09

## 1. Конфигурация, которая выглядела правильной

> *Аудит перед сертификацией. Аудитор просит показать, что root-вход по SSH запрещён. Открываю `/etc/ssh/sshd_config`, ищу глазами, показываю строку:*
>
> ```
> #PermitRootLogin no
> ```
>
> — Вот, запрещён.
> — А почему решётка?
>
> *Я смотрю на решётку секунды три и понимаю, что видел эту строку десятки раз и каждый раз читал её как настройку. Потому что в ней написано то, что я ожидал прочитать.*
>
> *Проверяем на живом сервере:*
>
> ```console
> $ sudo sshd -T | grep -i permitrootlogin
> permitrootlogin yes
> ```
>
> *Root-вход был разрешён всё время. Просто в поставке дистрибутива закомментированная строка показывает значение по умолчанию, а умолчание в той версии было `yes`.*
>
> *Палыч потом сказал вещь, которую я цитирую до сих пор:*
>
> — Ты читал файл, а надо было спрашивать программу. Файл — это то, что ты хотел сказать. `sshd -T` — то, что она услышала. Между ними бывает решётка, опечатка, второй файл в `Include`, и переопределение в блоке `Match`.
>
> — А если сервер не мой и я не могу выполнить `sshd -T`?
> — Тогда читай файл честно: с якорем начала строки, с учётом отступов, отбрасывая комментарии. То есть делай руками ровно то, что сделала бы программа. Но если есть возможность спросить — спрашивай.

## 2. Директивы, которые действительно важны

| Директива | Безопасное значение | Что закрывает |
|---|---|---|
| `PermitRootLogin` | `no` | перебор самой ценной учётной записи; вход в обход именованных пользователей |
| `PasswordAuthentication` | `no` | перебор паролей целиком — метод просто не предлагается |
| `KbdInteractiveAuthentication` | `no` | обходной путь для паролей через PAM |
| `PermitEmptyPasswords` | `no` | учётные записи без пароля |
| `MaxAuthTries` | `3` | число попыток в одном соединении |
| `AllowUsers` / `AllowGroups` | явный список | доступ имеют только перечисленные |
| `X11Forwarding` | `no` | лишняя поверхность на сервере |
| `AllowTcpForwarding` | `no`, если не нужен | использование сервера как прокси |
| `ClientAliveInterval` / `CountMax` | `300` / `2` | зависшие сессии |
| `LogLevel` | `VERBOSE` | в журнал попадает отпечаток использованного ключа |

**`PermitRootLogin prohibit-password`** — промежуточное значение: root может войти по ключу, но не по паролю. Это лучше, чем `yes`, и хуже, чем `no`; часто именно оно стоит по умолчанию. Аудит, проверяющий «не равно `yes`», такую конфигурацию пропустит — и в отчёте появится галочка там, где договаривались о другом.

**`LogLevel VERBOSE`** недооценён: он добавляет в журнал отпечаток ключа, которым выполнен вход. Без этого при разборе инцидента известно только имя пользователя, а с ним — какой именно ключ использовался, что при нескольких ключах на пользователя решает вопрос «кто это был».

## 3. Как sshd на самом деле читает конфигурацию

Три правила, которые ломают наивный разбор файла:

**Побеждает первое вхождение.** В отличие от большинства конфигураций Unix, `sshd_config` берёт **первое** встреченное значение директивы, а не последнее. Строка, дописанная в конец файла, не переопределит ту, что выше.

**`Include` подтягивает другие файлы.** Современные дистрибутивы начинают конфигурацию с `Include /etc/ssh/sshd_config.d/*.conf`, и настройка может лежать вовсе не в основном файле. Поскольку `Include` стоит в начале, а побеждает первое вхождение, файлы из каталога обычно имеют приоритет над остальным содержимым.

**Блоки `Match` меняют правила для части подключений.**

```
PasswordAuthentication no

Match Address 10.50.0.0/24
    PasswordAuthentication yes
```

Глобально пароли выключены, для внутренней подсети — включены. Аудит, читающий файл построчно и не различающий блоки, увидит два противоречащих значения.

Отсюда и вывод из воспоминания: если есть доступ, спрашивать надо программу.

```bash
sudo sshd -T                          # эффективная конфигурация целиком
sudo sshd -T | grep -i permitrootlogin
sudo sshd -T -C user=max,host=x,addr=10.50.1.5   # с учётом блоков Match
sudo sshd -t                          # только проверка синтаксиса
```

## 4. Порядок применения без потери доступа

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
sudo nano /etc/ssh/sshd_config
sudo sshd -t                     # синтаксис
sudo systemctl reload ssh        # применить, не разрывая текущие сессии
# ...и НЕ закрывая текущую сессию, из другого терминала:
ssh -i ~/.ssh/id_ed25519 user@server
```

Ключевое: `reload` (или `restart`) не разрывает уже установленные соединения. Значит, открытая сессия остаётся спасательным тросом — через неё можно вернуть резервную копию, если новая конфигурация не пускает.

Дополнительная страховка на удалённой машине — тот же приём отложенного отката, что и с фаерволом:

```bash
echo 'cp /etc/ssh/sshd_config.bak /etc/ssh/sshd_config && systemctl reload ssh' | sudo at now + 10 minutes
```

Проверил вход — снял задание. Не проверил, потому что не смог войти, — конфигурация вернулась сама.

## 5. Туннели: что куда ведёт

```bash
ssh -L 8080:db.internal:5432 user@bastion
# твой localhost:8080 → (через bastion) → db.internal:5432
# Применение: доступ к внутреннему сервису, не открывая его наружу.

ssh -R 9000:localhost:3000 user@server
# server:9000 → (через твою машину) → твой localhost:3000
# Применение: показать коллеге локальную разработку. Внимание: GatewayPorts на сервере
# определяет, будет ли этот порт доступен снаружи или только с самого сервера.

ssh -D 1080 user@server
# SOCKS-прокси на localhost:1080; приложение, настроенное на него,
# выходит в сеть от имени server.
```

Мнемоника: **`-L` тянет к себе, `-R` отдаёт от себя, `-D` заворачивает всё**.

Современная альтернатива ручным туннелям до внутренних машин — `ProxyJump`:

```bash
ssh -J bastion db.internal
# или в ~/.ssh/config:  Host *.internal / ProxyJump bastion
```

Он не пробрасывает порты, а строит соединение через промежуточный хост, и в отличие от `ssh -A` не даёт бастиону доступа к твоему агенту ключей.

Стоит помнить, что проброс портов на сервере регулируется директивами `AllowTcpForwarding` и `GatewayPorts`: если сервер не должен работать прокси-узлом, это выключают.

## 6. VPN: когда туннеля мало

Туннель шифрует один канал и требует, чтобы приложение о нём знало. VPN поднимает сетевой интерфейс, и через него идёт весь трафик — прозрачно для приложений.

**WireGuard** устроен предельно просто: у каждой стороны пара ключей (как в SSH), в конфигурации перечислены публичные ключи собеседников и разрешённые для них адреса. Шифрование — ChaCha20-Poly1305, обмен ключами — Noise; настроек шифров нет вовсе, что убирает целый класс ошибок конфигурации.

Что даёт против наблюдателя: содержимое трафика недоступно, набор запрашиваемых имён и адресов внутри туннеля не виден. Что не скрывает: сам факт соединения с VPN-узлом, объём и тайминги трафика. Полной невидимости не бывает — есть смещение того, что именно видно.

## 7. Метанавык: конфигурация — не то, что написано, а то, что действует

Ошибка с решёткой — частный случай общего правила: **написанное намерение и действующее поведение — разные объекты**, и проверять надо второе.

То же самое встречается везде: правила фаервола в файле против `iptables -L`; юниты systemd против `systemctl show`; переменные в `.env` против окружения процесса; `docker-compose.yml` против `docker inspect`; желаемое состояние в Ansible против фактического.

Практический приём один и тот же: у почти каждой системы есть команда «покажи, что ты в итоге поняла». `sshd -T`, `nginx -T`, `systemctl show`, `docker inspect`, `terraform show`. Она отвечает на настоящий вопрос, тогда как файл отвечает на вопрос «что я собирался сделать».
