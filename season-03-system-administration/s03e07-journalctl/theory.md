# Теория — s03e07

## 1. Журнал, которого не было

> *У нас упал сервис. Не «выдавал ошибки» — просто в какой-то момент перестал отвечать, и мы перезагрузили машину, потому что надо было работать. Через двадцать минут всё поднялось, все выдохнули.*
>
> *На следующий день Палыч спросил, что произошло. Я открыл `journalctl -b -1` — предыдущую загрузку. Вывод: `Specifying boot ID or boot offset has no effect, no persistent journal was found`.*
>
> — Понял? — спросил он.
> — Журнала за прошлую загрузку нет.
> — Не «нет». Никогда и не было. Он всё это время лежал в `/run`, то есть в оперативной памяти, и стёрся ровно тогда, когда стал нужен.
>
> *Он показал одну строку:*
>
> ```bash
> ls -d /var/log/journal || sudo mkdir -p /var/log/journal && sudo systemctl restart systemd-journald
> ```
>
> — По умолчанию `Storage=auto`: если каталога нет, журнал не сохраняется. Каталог создают при установке не все дистрибутивы и не все образы. Это первое, что проверяют на новой машине, и последнее, о чём вспоминают.
>
> *Я спросил, почему это не сделано по умолчанию везде. Он пожал плечами:*
>
> — Потому что на встраиваемых системах писать на флеш-память постоянно — плохая идея. Разумное умолчание для одного случая становится ловушкой для другого. Так почти всегда: важно не то, что настройка неправильная, а то, что ты не знал, какая она.

## 2. Как устроен journald

Каждая запись — это набор **полей**, а не строка текста:

```bash
journalctl -o verbose -n 1
```

```
MESSAGE=Accepted publickey for dmitry from 185.220.101.47
PRIORITY=6
SYSLOG_IDENTIFIER=sshd
_PID=2203
_UID=0
_COMM=sshd
_EXE=/usr/sbin/sshd
_SYSTEMD_UNIT=ssh.service
_BOOT_ID=3f2a...
_HOSTNAME=shadow-server-01
```

Поля с подчёркиванием — **доверенные**: их заполняет journald по данным ядра, и процесс не может их подделать. Всё остальное сообщает о себе сам процесс, включая `SYSLOG_IDENTIFIER` и текст.

Отсюда практическое следствие: искать по `-u имя.service` (то есть по `_SYSTEMD_UNIT`) надёжнее, чем по тегу в тексте.

## 3. Отбор записей

```bash
journalctl -u nginx -u sshd            # несколько юнитов сразу
journalctl _SYSTEMD_UNIT=ssh.service   # то же явно
journalctl _PID=6623 _UID=0            # поля через пробел = И
journalctl -u sshd + _UID=1004         # «+» = ИЛИ
journalctl --since '2025-10-14 21:00' --until '2025-10-15 00:35'
journalctl --since '-2h'               # относительное время
journalctl -p warning..err             # диапазон приоритетов
journalctl -g 'Failed password'        # поиск по регулярному выражению
journalctl -k --since today            # ядро
journalctl -b            # текущая загрузка
journalctl -b -1         # предыдущая
journalctl --list-boots  # какие вообще есть
journalctl -n 50 -f      # хвост и слежение
```

`--since` понимает `today`, `yesterday`, `-1h`, `09:00`, полную дату. `-g` (grep) работает по полю `MESSAGE` и понимает регулярные выражения — это быстрее, чем `journalctl | grep`, потому что фильтрация идёт до форматирования.

## 4. Приоритеты и что они на самом деле означают

| № | Уровень | Что туда пишут |
|---|---|---|
| 0 | emerg | система неработоспособна |
| 1 | alert | требуется немедленное вмешательство |
| 2 | crit | критический сбой компонента |
| 3 | err | ошибка |
| 4 | warning | предупреждение |
| 5 | notice | нормальное, но заметное событие |
| 6 | info | обычная работа |
| 7 | debug | отладка |

Уровень выбирает **автор программы**, а не система. Отсюда две вещи, которые стоит знать заранее:

- Успешный вход, `sudo`, создание пользователя — это `info` и `notice`. **Разбор инцидента через `-p err` не покажет ничего.**
- Уровни у разных программ несопоставимы: то, что один демон считает `err`, другой пишет как `warning`. Сравнивать счётчики ошибок между службами бессмысленно.

## 5. Хранение и подчистка

```ini
# /etc/systemd/journald.conf
Storage=persistent          # всегда на диск, независимо от наличия каталога
SystemMaxUse=2G             # предел на весь журнал
SystemMaxFileSize=128M
MaxRetentionSec=1month
ForwardToSyslog=no
Seal=yes                    # криптографическая печать (нужен ключ, см. ниже)
```

```bash
journalctl --disk-usage
journalctl --vacuum-time=30d
journalctl --vacuum-size=500M
journalctl --verify              # проверить целостность
systemctl restart systemd-journald
```

**Журнал как улика.** Локальный журнал ничем не защищён от того, у кого есть root: `journalctl --vacuum-time=1s` стирает всё, а `rm -rf /var/log/journal/*` — тем более. Есть два ответа, и оба про то, чтобы записи оказались не только здесь:

- `Seal=yes` + `journalctl --setup-keys` — «запечатывание» с ключом, который хранят отдельно. Подчистку это не запрещает, но делает обнаружимой: `--verify` покажет разрыв.
- Пересылка на отдельный сервер (`systemd-journal-remote`, rsyslog, любой сборщик логов). Единственный способ, который реально работает: на чужой машине злоумышленник не root.

Правило разбора инцидента отсюда простое: **журнал скомпрометированной машины — свидетельство, а не доказательство.** Он верен ровно до момента, когда атакующий получил root; всё после этой отметки требует подтверждения из независимого источника.

## 6. Свои записи в журнале

```bash
logger -t ops-check -p daemon.notice "state collected: 4 hosts up"
echo "готово" | systemd-cat -t backup -p info
```

Для службы под systemd ничего этого не нужно: `StandardOutput=journal` (умолчание) означает, что достаточно печатать в stdout. Строку можно пометить уровнем, поставив в начало `<3>` — числовой приоритет в угловых скобках:

```bash
echo "<3>не удалось подключиться к базе"   # попадёт как err
```

Это самый дешёвый способ сделать вывод скрипта пригодным для `-p err`.

## 7. rsyslog никуда не делся

На большинстве серверов работают оба: journald принимает записи, а `ForwardToSyslog=yes` отдаёт их rsyslog, который раскладывает по файлам в `/var/log`. Отсюда дублирование, о котором стоит помнить при разборе места на диске: одно и то же лежит дважды.

Текстовые файлы при этом обслуживает `logrotate` (`/etc/logrotate.d/`), а журнал — сам journald своими лимитами. Две разные системы ротации на одной машине — обычное дело и обычный источник сюрприза «места нет, хотя я всё почистил».

## 8. Метанавык: хронология вместо поиска

Поиск отвечает на вопрос «есть ли здесь то, что я подозреваю». Он даёт ответ только на уже придуманную гипотезу и по определению не покажет того, о чём ты не подумал.

Хронология работает иначе: берётся окно времени, из него выписывается **всё** необычное подряд, и только потом ищется связь. Это медленнее и почти всегда результативнее — потому что инцидент состоит из обычных событий, каждое из которых по отдельности не подозрительно.

Практический приём, который стоит запомнить: сначала найти **одну достоверную отметку времени** (создан файл, появился юнит, изменился конфиг), а потом раскрыть журнал на полчаса вокруг неё. Почти всё остальное находится там же, в пределах десяти минут.
