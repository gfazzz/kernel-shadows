# s06e12 — теория: символьные устройства и граница с пользователем

Дополнение к [`README.md`](README.md). Здесь — полный набор операций файла, обмен данными через границу, альтернативы символьному устройству, блокирующее чтение и то, чем всё это связано с остальным курсом.

---

## 1. Устройства в Linux

| Вид | Пример | Как работает |
|---|---|---|
| символьное | `/dev/ttyS0`, `/dev/random`, `/dev/shadow0` | поток байт, без адресации блоками |
| блочное | `/dev/sda`, `/dev/mmcblk0` | блоки фиксированного размера, кеш страниц |
| сетевое | `eth0` | не файл вовсе: свой интерфейс `net_device` |

Символьное — самое простое и потому самое частое для собственных драйверов. Номера:

```
crw-rw---- 1 root root 511, 0 ноя 20 12:00 /dev/shadow0
                       └─┬─┘ └┬┘
                      major minor
```

`major` говорит, какой драйвер обслуживает устройство, `minor` — какое именно из его устройств. `alloc_chrdev_region` просит ядро выделить свободный `major` динамически; статические номера остались в наследство и в новых драйверах не используются.

## 2. Полный набор операций

```c
struct file_operations {
        struct module *owner;
        loff_t  (*llseek)   (struct file *, loff_t, int);
        ssize_t (*read)     (struct file *, char __user *, size_t, loff_t *);
        ssize_t (*write)    (struct file *, const char __user *, size_t, loff_t *);
        __poll_t (*poll)    (struct file *, struct poll_table_struct *);
        long    (*unlocked_ioctl)(struct file *, unsigned int, unsigned long);
        int     (*mmap)     (struct file *, struct vm_area_struct *);
        int     (*open)     (struct inode *, struct file *);
        int     (*release)  (struct inode *, struct file *);
        int     (*fsync)    (struct file *, loff_t, loff_t, int);
        …
};
```

| Операция | Когда нужна |
|---|---|
| `read`/`write` | поток данных |
| `llseek` | перемещение по позиции; `default_llseek` подходит для устройства с фиксированным содержимым |
| `poll` | чтобы устройство работало с `select`/`poll`/`epoll` |
| `unlocked_ioctl` | команды, не укладывающиеся в чтение и запись |
| `mmap` | прямое отображение буфера в память процесса — без копирования |
| `open`/`release` | счётчики, выделение состояния на открытие |

Неперечисленные операции ядро отклоняет само (`-EINVAL` или `-ENOTTY`), так что таблица — это одновременно и объявление возможностей.

### `open` даёт состояние на каждого читателя

```c
static int shadow_open(struct inode *inode, struct file *file)
{
        struct shadow_session *s = kzalloc(sizeof(*s), GFP_KERNEL);
        if (!s) return -ENOMEM;
        file->private_data = s;
        return 0;
}
```

`file->private_data` — штатное место для состояния конкретного открытия. Так делают, когда двум читателям нужны независимые позиции или независимые снимки. В этой серии состояние общее, поэтому и нужна блокировка.

## 3. Граница с пользовательским пространством

| Функция | Направление |
|---|---|
| `copy_to_user(dst_user, src_kernel, n)` | наружу |
| `copy_from_user(dst_kernel, src_user, n)` | внутрь |
| `get_user(x, ptr)` / `put_user(x, ptr)` | одно значение |
| `strncpy_from_user()` | строка с ограничением |
| `access_ok()` | проверка адреса (обычно уже внутри copy_*) |

Все возвращают число **не**скопированных байт (или код ошибки для `get_user`/`put_user`). Ноль — успех; проверять обязательно.

Типичные уязвимости на этой границе:

| Ошибка | Что даёт |
|---|---|
| `memcpy` вместо `copy_to_user` | запись по произвольному адресу ядра |
| не проверен возврат | молчаливая потеря данных |
| размер взят из пользовательского поля без проверки | переполнение |
| структура с «дырами» выравнивания | утечка неинициализированной памяти ядра |

Последняя тонкая и реальная: если отдавать наружу `struct`, невыровненные байты между полями содержат мусор из памяти ядра. Поэтому такие структуры перед отправкой обнуляют целиком (`memset` или `kzalloc`).

## 4. Когда данных ещё нет

Три поведения, между которыми выбирают осознанно:

```c
/* 1. конец данных — окончательно */
return 0;

/* 2. подождать появления */
if (wait_event_interruptible(shadow_wq, have_data()))
        return -ERESTARTSYS;

/* 3. не ждать, если просили не ждать */
if (file->f_flags & O_NONBLOCK)
        return -EAGAIN;
```

Хорошо ведущий себя драйвер поддерживает все три: блокируется по умолчанию, отвечает `-EAGAIN` при `O_NONBLOCK` и возвращает `0`, когда данных больше не будет никогда.

`poll` дополняет картину: он позволяет программе ждать сразу несколько источников через `select`/`epoll`, не блокируясь ни на одном.

## 5. Альтернативы символьному устройству

| Способ | Когда уместен | Цена |
|---|---|---|
| символьное устройство | поток данных, свой протокол | `major`/`minor`, `udev`, права |
| `misc_device` | одно устройство, `major` не важен | проще: `misc_register`, и всё |
| `sysfs` | одно значение — один файл | не для потоков; строгие правила формата |
| `debugfs` | отладка | не для эксплуатации: может быть не смонтирован |
| `procfs` | наследие | не рекомендуется для нового кода |
| `netlink` | двусторонний обмен, события | сложнее |

`misc_register` — то, с чего стоит начинать реальный драйвер: он избавляет от четырёх из пяти шагов регистрации. В этой серии выбран длинный путь намеренно: именно на нём видно, что такое «взял ресурс — верни» и зачем нужна лестница отката.

Правило выбора: **если данные — это одно значение, им место в `sysfs`; если поток — в символьном устройстве.** Смешение (файл в `sysfs`, отдающий многострочный отчёт) — распространённая, но осуждаемая практика: формат `sysfs` по договорённости «одно значение на файл».

## 6. Одновременность

```c
static DEFINE_MUTEX(shadow_lock);

if (mutex_lock_interruptible(&shadow_lock))
        return -ERESTARTSYS;
…
mutex_unlock(&shadow_lock);
```

| Средство | Можно ли спать | Когда |
|---|---|---|
| `mutex` | да | длинные секции в контексте процесса |
| `spinlock` | нет | короткие секции, доступ из прерывания |
| `atomic_t` | — | счётчики |
| `rcu` | — | много читателей, редкие изменения |

`mutex_lock_interruptible` возвращает `-EINTR`, если пришёл сигнал; драйвер превращает это в `-ERESTARTSYS`, и ядро само перезапустит системный вызов или отдаст ошибку. Без этого процесс, ждущий устройство, нельзя убить.

Главное правило — **симметрия на всех путях**: сколько взятий, столько и снятий, включая пути ошибок. Это тот же принцип «взял — отдай», что для памяти и номеров устройства, только цена ошибки другая: не утечка, а зависшая навсегда очередь читателей.

## 7. Отладка

```bash
sudo insmod shadow.ko depth=8
ls -l /dev/shadow0
cat /dev/shadow0
head -c 8 /dev/shadow0            # частичное чтение
dd if=/dev/shadow0 bs=4 count=3   # чтение кусками заданного размера
strace -e trace=read cat /dev/shadow0
dmesg -w
sudo rmmod shadow
```

`strace` показывает главное: последовательность вызовов `read()` с их `count` и возвратами. Именно там видно, отдаёт ли драйвер ноль в конце и продвигается ли позиция.

`udevadm monitor` покажет, как `device_create` привёл к появлению узла в `/dev` — узел создаёт не ядро, а `udev` по событию.

## 8. Чем это связано с остальным курсом

| Приём | Здесь | Где ещё |
|---|---|---|
| «всё есть файл» | устройство читается `cat` | GPIO через sysfs, [`s06e02`](../s06e02-gpio-sysfs/) |
| граница доверия | `copy_to_user` | проверка показаний, [`s06e10`](../s06e10-sensor-client/) |
| ноль как «конец», а не «ошибка» | возврат `read()` | `None` вместо нуля, [`s06e10`](../s06e10-sensor-client/) |
| взял — отдай | пять пар ресурсов | `export`/`unexport`, [`s06e02`](../s06e02-gpio-sysfs/) |
| проверяемое ядро логики | `shadow_view.c` | `shadow_ring.c`, [`s06e11`](../s06e11-kernel-module/) |
| накопление, а не переписывание | `shadow_ring.c` перенесён как есть | весь сезон |

Последняя строка — про сезон в целом. `shadow_mesh` собран из слоёв: плата опознана и настроена, дрон проверен, сеть закрыта, клиент написан, ядро расширено. Ни один слой не переписывал предыдущий — каждый опирался на проверенное.
