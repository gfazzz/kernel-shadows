## II. Теория: развилка и конвейер

### `if` смотрит на код возврата

Ты уже видел коды возврата в прошлой серии. `if` работает ровно с ними — не с текстом, не с «истиной»:

```bash
if ping -c 1 -W 2 "$host" >/dev/null 2>&1; then
    status="UP"
else
    status="DOWN"
fi
```

Никаких скобок вокруг команды не нужно: `if` запускает её и смотрит на доклад. Ноль — первая ветка, иначе — вторая.

Когда сравнивают значения, берут команду проверки `[ ... ]`:

```bash
[ "$count" -gt 10 ]        # числа: -eq -ne -gt -lt -ge -le
[ "$name" = "max" ]        # строки: = != -z (пусто) -n (не пусто)
[ -f "$file" ]             # файлы: -f файл, -d каталог, -r читается, -x исполняется
```

`[` — это **команда**, а не синтаксис языка (буквально файл `/usr/bin/[`). Отсюда обязательные пробелы внутри скобок: `[$a = $b]` bash прочитает как несуществующую команду `[$a`.

### `while read` — правильный способ читать файл

```bash
while IFS= read -r line; do
    echo "$line"
done < servers.txt
```

Три детали, каждая из которых не украшение:

- `IFS=` — не срезать ведущие и хвостовые пробелы в строке;
- `-r` — не считать обратный слэш экранированием (иначе `C:\new` превратится в перевод строки);
- `done < файл` — перенаправление на вход цикла, читается по одной строке.

Так же важно, чего здесь **нет**: `for line in $(cat file)`. Эта конструкция разбивает файл не по строкам, а по пробелам — строка `shadow-server-07 185.192.45.124` станет двумя элементами. Про это и про подводные камни подоболочки — в [`theory.md`](theory.md).

Из строки нужно вытащить первое поле — имя хоста:

```bash
host="${line%% *}"      # отрезать всё, начиная с первого пробела
```

Это параметрическое расширение bash: `%%` убирает самый длинный суффикс по шаблону. `awk` сделал бы то же самое, но он появится в курсе позже (s01e11), а лишний процесс на каждую строку — не бесплатен.

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Почему `for line in $(cat servers.txt)` — плохая идея для файла со строками вида „имя IP"?»*

<details>
<summary>Подумай 30 секунд</summary>

`$(cat file)` подставляет содержимое файла как одну большую строку, и bash разбивает её по пробелам и переводам строк одинаково. Строка `shadow-server-07 185.192.45.124` даст **два** элемента цикла вместо одного.

Плюс весь файл читается в память, а шаблоны вроде `*` в содержимом раскрываются как имена файлов. `while IFS= read -r line` читает ровно по строке и ничего не портит.
</details>

**LILITH:** *«В файле пустая строка и строка-комментарий. Что сделает твой цикл?»*

<details>
<summary>Ответ</summary>

Попытается пропинговать пустое имя и строку `# список серверов` — получит ошибки и посчитает их как `DOWN`, испортив статистику.

Поэтому в начале тела цикла ставят два фильтра:

```bash
[ -z "$line" ] && continue
case "$line" in \#*) continue ;; esac
```

`continue` переходит к следующей итерации. Реальные списки почти всегда содержат комментарии — привыкать пропускать их стоит сразу.
</details>

### Три ошибки, которые здесь делают

**Потерять счётчики.** Если цикл запускается через конвейер (`cat file | while read ...`), тело выполняется в **подоболочке**, и после цикла `up` снова равен нулю. Классика, которая выглядит как «скрипт считает неправильно». Лечится перенаправлением `done < файл` — так цикл остаётся в текущей оболочке.

**Не пропустить комментарии.** Реальный список без `#` не живёт: там пометки, даты, отключённые узлы. Скрипт, который пингует комментарий, портит статистику и выглядит глупо в отчёте.

**Проверять существование файла после цикла.** Если списка нет, цикл просто ничего не сделает, и скрипт бодро отчитается `UP=0 DOWN=0`. Ноль проверенных машин — это не «всё хорошо», это отказ проверки, и он должен быть виден: сообщение в stderr и ненулевой код.
