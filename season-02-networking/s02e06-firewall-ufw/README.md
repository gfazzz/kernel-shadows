## Теория: firewall и `ufw` (один концепт: правила стены)

**`ufw`** — дружелюбная обёртка над iptables (Type B — используем готовое):

```bash
sudo ufw default deny incoming    # запретить всё входящее...
sudo ufw allow 22/tcp             # ...и точечно разрешить нужное (SSH, web)
sudo ufw status numbered          # посмотреть правила
```

Главный принцип — **default-deny**: запретить всё, затем открыть только нужное (обратное всегда дырявое). Под капотом — цепочки iptables (`INPUT`/`OUTPUT`/`FORWARD`), правила сверху вниз. Детали, rate-limit и recovery — в [`theory.md`](theory.md).

> **LILITH:** *«Сначала `ufw allow 22`, ПОТОМ `ufw enable`. Перепутаешь — заблокируешь свой же SSH, и спасать сервер придётся из серверной. Firewall не прощает спешки.»*

Опасное в правилах: чувствительные сервисы (`3306` MySQL, `6379` Redis…), открытые на `Anywhere` — их место на `127.0.0.1` или за firewall.

## Проверка «в мире сюжета»

**Алекс:** *«Почему „разрешить всё, блокировать плохое" — плохая стратегия firewall?»*

<details>
<summary>Подумай 30 секунд</summary>

Плохого бесконечно много — все IP ботнета, все новые эксплойты не перечислить. Default-deny переворачивает задачу: запрещаем всё, разрешаем конечный список нужного (22, 80, 443). Что не разрешено явно — запрещено. Так дыр не остаётся по построению.
</details>

**Дмитрий:** *«`ufw status` показал `3306 ALLOW Anywhere`. Чем это грозит при DDoS и не только?»*

<details>
<summary>Ответ</summary>

MySQL (3306) торчит в интернет — любой может долбить его коннектами (усиливая нагрузку при DDoS) и пытаться брутфорсить/эксплуатировать БД напрямую. База должна слушать `127.0.0.1` или быть доступна только внутренней сети. Открытый наружу порт БД — приглашение.
</details>
