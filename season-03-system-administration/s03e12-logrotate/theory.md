# Теория — s03e12

## 1. Диск, который заполнился дважды

> *Логи забили `/var`. Я почистил, поставил `logrotate`, отчитался. Через месяц `/var` забился снова, и я обнаружил, что мой конфиг не отработал ни разу.*
>
> *Разбирались недолго. Палыч посмотрел на файл и спросил:*
>
> — Как он называется?
> — `app.conf`.
> — А где лежит?
> — В `/etc/logrotate.d/`.
>
> *Он открыл `/etc/logrotate.conf` и показал последнюю строку:*
>
> ```
> include /etc/logrotate.d
> ```
>
> — А теперь читай `man logrotate`, раздел про `include`. Файлы с точкой в имени и с расширениями `.rpmsave`, `.dpkg-old` и подобными игнорируются. Твой `app.conf` не читался никогда.
>
> *Я спросил, почему logrotate об этом не сказал.*
>
> — Ему нечего сказать. Он не знает, что ты положил туда файл, — он видит каталог с файлами, которые надо пропустить. Отсутствие файла и отсутствие сообщения выглядят одинаково.
>
> *С тех пор у меня привычка: после правки любой конфигурации из каталога `*.d/` — команда, которая показывает, что программа реально прочитала. Для logrotate это `logrotate -d`, для sudo — `sudo -l`, для systemd — `systemctl cat`, для sshd — `sshd -T`.*
>
> — Правило простое, — сказал он тогда. — Если ты положил файл, но не проверил, что его прочитали, — ты положил файл. Не более того.

## 2. Директивы

| Директива | Что делает |
|---|---|
| `daily`, `weekly`, `monthly`, `yearly`, `hourly` | периодичность |
| `size 100M` | поворачивать по размеру, не по времени |
| `maxsize 100M` | по времени, но раньше, если вырос |
| `minsize 1M` | по времени, но не раньше, чем вырастет |
| `rotate N` | сколько поколений хранить |
| `maxage N` | удалять старше N дней независимо от `rotate` |
| `missingok` | отсутствие файла — не ошибка |
| `notifempty` | пустой не поворачивать |
| `compress` | сжимать (по умолчанию gzip) |
| `compresscmd`, `compressext` | чем и с каким расширением |
| `delaycompress` | не сжимать самый свежий повёрнутый |
| `dateext`, `dateformat -%Y-%m-%d` | суффикс датой вместо номера |
| `create РЕЖИМ ВЛАД ГРУППА` | создать новый файл с этими правами |
| `copytruncate` | копировать и обнулить оригинал |
| `olddir /var/log/archive` | складывать повёрнутые отдельно |
| `su syslog adm` | от чьего имени работать с этим каталогом |
| `sharedscripts` | скрипты один раз на блок, а не на файл |
| `prerotate`/`postrotate` | до и после поворота |
| `firstaction`/`lastaction` | один раз до всего и после всего |

`nocompress`, `nomissingok` и прочие «no»-варианты отменяют то, что задано глобально в `/etc/logrotate.conf`.

## 3. Почему служба «пишет в пустоту»

Процесс работает с **дескриптором**, а не с именем. Последовательность при повороте:

```
1. logrotate:  mv app.log app.log.1     ← дескриптор процесса теперь указывает на app.log.1
2. logrotate:  create app.log           ← новый файл, никем не открытый
3. процесс:    write(fd, …)             ← пишет в app.log.1
```

Через `rotate N` циклов `app.log.1` становится `app.log.N` и удаляется. Имя исчезает, дескриптор остаётся — и получается то, что нашлось в [`s03e08`](../s03e08-disks-fs/): файл без имени, занимающий место, невидимый для `du`.

Два выхода:

- **`postrotate` + сигнал.** Процессу говорят закрыть и открыть файлы заново. Стандарт для служб, которые это умеют.
- **`copytruncate`.** Файл копируется, оригинал обнуляется через `truncate()` — дескриптор остаётся действительным и указывает на тот же (теперь пустой) файл. Строки, записанные между копированием и обнулением, теряются.

Третий вариант — вообще не поворачивать файлы, а писать в journald, у которого своя ротация по размеру (`SystemMaxUse=`). Это то, что делают современные службы под systemd.

## 4. Сигналы, которые понимают службы

| Служба | Команда в `postrotate` |
|---|---|
| rsyslog | `/usr/lib/rsyslog/rsyslog-rotate` |
| syslog-ng | `/usr/bin/pkill -HUP syslog-ng` |
| nginx | `[ -f /run/nginx.pid ] && kill -USR1 "$(cat /run/nginx.pid)"` |
| Apache | `apachectl graceful` или `systemctl reload apache2` |
| PostgreSQL | `systemctl reload postgresql` |
| произвольная под systemd | `systemctl reload имя.service` |

Проверка `[ -f /run/nginx.pid ]` перед `kill` не формальность: без неё `postrotate` падает на остановленной службе, и `logrotate` сообщает об ошибке при каждом запуске.

## 5. Как это запускается

```bash
systemctl status logrotate.timer     # современные системы
systemctl cat logrotate.service
ls /etc/cron.daily/logrotate         # старые системы
cat /var/lib/logrotate/status        # когда что поворачивалось
```

Файл состояния — единственный источник правды о том, что происходило. `logrotate` не поворачивает файл, если по его данным сегодня уже поворачивал; отсюда неожиданности при ручном запуске (`-f` заставляет).

**Проверка без последствий:**

```bash
logrotate -d /etc/logrotate.d/ops    # разбор и план, ничего не делается
logrotate -dv /etc/logrotate.conf    # всё, включая include
logrotate -f /etc/logrotate.d/ops    # принудительно, по-настоящему
```

`-d` подразумевает `-v` и показывает, какие файлы попали под шаблон, что с ними будет и какие скрипты выполнятся. Это тот самый способ убедиться, что файл вообще прочитан.

**Имена файлов в `/etc/logrotate.d/`** — без точек и без расширений вроде `.conf`, если в `logrotate.conf` не указано иное: правила `include` пропускают файлы, подходящие под `tabooext`. Проверить свой набор: `logrotate -d /etc/logrotate.conf 2>&1 | grep reading`.

## 6. journald — другая система

```ini
# /etc/systemd/journald.conf
SystemMaxUse=2G
SystemMaxFileSize=128M
MaxRetentionSec=1month
```

```bash
journalctl --disk-usage
journalctl --vacuum-time=30d
```

У journald нет `logrotate`: он сам режет журнал на файлы и удаляет старые по лимитам. Если `ForwardToSyslog=yes`, те же записи попадают ещё и в rsyslog, а оттуда в текстовые файлы — и обслуживаются уже `logrotate`.

Отсюда обычный сюрприз: «я почистил `/var/log`, а место не вернулось» — потому что вторая копия лежит в `/var/log/journal` и `logrotate` её не касается.

## 7. Сколько хранить

Глубина хранения — не вопрос места, а вопрос **времени обнаружения**. Инцидент замечают через дни; если журнал живёт три дня, к моменту разбора его уже нет.

Практические ориентиры:

| Что | Сколько |
|---|---|
| журналы приложений | 2–4 недели |
| журналы доступа (auth, sudo, sshd) | 3–12 месяцев |
| журналы аудита при требованиях регулятора | по требованиям, обычно год |
| отладочные | дни |

Всё, что нужно хранить дольше нескольких недель, отправляют на отдельный сервер: локальный журнал стирается тем, кто получил root, а глубина хранения без этого — иллюзия (см. [`s03e07`](../s03e07-journalctl/)).

## 8. Метанавык: настройка без обратной связи

`logrotate` относится к тому же неудобному классу, что `fstab` из [`s03e10`](../s03e10-fstab/): он срабатывает не тогда, когда его настраивают, а ночью, без свидетелей, и ошибка не даёт симптома.

Отличие в том, что здесь симптом появляется — но с задержкой в недели и в другом месте: кончилось место, журнал пустой, при разборе инцидента нет данных. Связать это с конфигурацией, написанной полгода назад, никто уже не пытается.

Единственная защита — проверка сразу после правки и проверка эффекта потом: `logrotate -d` в день изменения, а через неделю — взгляд на каталог с журналами: появились ли повёрнутые файлы, растёт ли новый, не пуст ли он. Две минуты, которые отделяют «настроил» от «работает».
