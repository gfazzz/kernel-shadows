# Теория — s01e16

## 1. «Я же под sudo»

> *Первую неделю на настоящем сервере я делал всё через `sudo`. Не из наглости — просто так не приходилось думать: команда не сработала, добавил `sudo`, сработала. Логика казалась безупречной.*
>
> *Палыч заметил это, когда я мимоходом сказал «ну я же под sudo».*
>
> — Покажи историю.
>
> *Он пролистал и остановился на строке `sudo cat ~/notes.txt`.*
>
> — Это твой файл. Зачем тут `sudo`?
> — По привычке.
> — А теперь смотри, что эта привычка сделала.
>
> *Он показал `ls -l` этого файла: владелец root. Я когда-то отредактировал его через `sudo`, редактор пересоздал файл, и владельцем стал root. С тех пор мне нужен был `sudo`, чтобы открыть свой собственный файл, — и я, конечно, добавлял `sudo`, и всё «работало».*
>
> — Понимаешь, в чём беда? Не в том, что ты испортил файл. В том, что система три дня подряд говорила тебе «что-то не так», а ты каждый раз затыкал её вместо того, чтобы услышать.
>
> *Он сформулировал правило, которым я пользуюсь до сих пор:*
>
> — `sudo` — это не «сделай, пожалуйста». Это «я утверждаю, что для этого действительно нужны права root». Каждый раз, когда набираешь его, ответь себе на вопрос: почему без него нельзя? Если ответа нет — команда лишняя, а проблема в другом месте.

## 2. Пользователи и группы

```bash
whoami                # имя
id                    # номер, основная группа, все группы
groups                # только группы
id anna               # то же про другого
getent passwd max     # строка из /etc/passwd
```

```
uid=1000(max) gid=1000(max) groups=1000(max),4(adm),1101(ops-logs)
```

- **uid** — номер пользователя. Система работает с ним; имя подставляется при выводе.
- **gid** — **основная** группа: её получают все создаваемые тобой файлы.
- **groups** — все группы, включая основную. Дополнительные дают доступ, но не влияют на то, какую группу получит новый файл.

Отсюда две вещи, которые полезно знать сразу:

- `uid=0` — это root, независимо от имени. Имя `root` — просто подпись к нулю.
- Если `ls -l` показывает вместо владельца число, значит такого пользователя на этой машине нет: файл пришёл с другой системы.

**Изменения в группах применяются при следующем входе.** Классическая загадка «меня добавили в группу, а доступа нет» решается выходом и повторным входом (или `newgrp имя`) — текущая сессия помнит список групп с момента её начала.

## 3. Как проверяется доступ

Когда ты открываешь файл, ядро проверяет **одно** из трёх, в порядке:

1. ты владелец → действуют права владельца, остальное не смотрится;
2. ты в группе файла → действуют права группы;
3. иначе → действуют права «остальных».

Именно **одно**, а не сумма. Отсюда неинтуитивное следствие: файл с правами `---rwxrwx`, принадлежащий тебе, ты прочитать **не** сможешь — проверка остановится на первом правиле и увидит, что владельцу не разрешено ничего.

И вторая часть: доступ проверяется по всему пути. Чтобы открыть `/srv/ops/logs/day.txt`, нужен `x` на каждом каталоге по дороге.

## 4. Что делает `sudo`

```bash
sudo команда           # выполнить от имени root
sudo -u anna команда   # от имени anna
sudo -l                # что мне разрешено
sudo -k                # забыть пароль немедленно
sudo -i                # интерактивная оболочка root (если разрешено)
```

Порядок действий:

1. **Аутентификация.** Спрашивается **твой** пароль. Проверяется не знание секрета root, а то, что за терминалом ты. Результат помнится минут пять, чтобы не спрашивать на каждой команде.
2. **Авторизация.** `sudo` читает список правил и ищет, разрешена ли тебе именно эта команда на этом хосте от имени этого пользователя.
3. **Запуск.** Разрешённое выполняется от имени указанного пользователя.
4. **Журнал.** Записывается кто, когда, откуда и что. Отказ записывается тоже — строкой `user NOT in sudoers`.

Ключевое: **`sudo` не «обходит права»**. Он запускает разрешённую команду от имени того, у кого прав больше. Если команды нет в списке, прав не прибавится.

## 5. Где живёт список

```bash
sudo -l                          # что разрешено мне
sudo cat /etc/sudoers            # основной файл (если разрешено)
ls /etc/sudoers.d/               # по файлу на роль или команду
sudo visudo                      # правка с проверкой синтаксиса
```

Строка правила читается так:

```
max  ALL=(root)  /usr/bin/apt update
 │    │    │            └ какая именно команда, с аргументами
 │    │    └ от чьего имени разрешено
 │    └ на каких хостах
 └ кому
```

`ALL` вместо команды означает «что угодно» — то, что стоит в строке `%sudo ALL=(ALL:ALL) ALL` из стандартной установки и даёт полный доступ всем членам группы `sudo`.

**Правку `sudoers` делают только через `visudo`**: он проверяет синтаксис до сохранения. Ошибка в этом файле ломает `sudo` целиком, включая возможность его починить.

## 6. `sudo` и `su`

| | `su -` | `sudo команда` |
|---|---|---|
| Чей пароль | root'а | свой |
| Объём | всё сразу | только перечисленное |
| Журнал | факт входа | каждая команда |
| Отзыв доступа | смена пароля у всех | правка одной строки |
| След в истории | ничего | полная запись |

В Ubuntu и Debian у root **нет пароля**: учётная запись заблокирована для входа (`!` в поле пароля). Это не недоделка, а решение — единственный путь к правам root проходит через `sudo`, а значит через список и журнал.

`sudo -i` даёт интерактивную оболочку root и, по сути, возвращает к модели `su`: дальше в журнале не будет ничего. Пользоваться им стоит редко и осознанно.

## 7. Привычки, которые стоит завести сразу

- **Перед `sudo` спросить себя, почему без него нельзя.** Половина случаев — файл твой, и нужен `chmod`, а не root.
- **Не редактировать свои файлы через `sudo`.** Редактор часто пересоздаёт файл, и владельцем становится root — дальше он «требует sudo» навсегда.
- **Читать сообщение об отказе целиком.** `Permission denied` и `user NOT in sudoers` — разные вещи: первое про права на файл, второе про список `sudo`.
- **Смотреть `sudo -l` на новой машине.** Занимает секунду и сразу показывает, что тебе вообще позволено.
- **Помнить про журнал.** Всё, что делается через `sudo`, записано с твоим именем. Это не слежка, а то, что позволяет потом отличить твою ошибку от чужой.

## 8. Метанавык: доступ как чужое решение

Права и `sudo` устроены так, что почти всё в них — **решение другого человека**, принятое заранее: кто-то создал твою учётную запись, включил тебя в группы, написал строки в `sudoers`. Ты этого не выбирал и обычно не видели.

Отсюда полезный сдвиг во взгляде. Отказ в доступе — не препятствие, которое надо преодолеть, а **сообщение о чьём-то решении**. И правильная реакция на него — не искать обход, а выяснить, было ли это решение осознанным.

Ровно это и произошло в задании: `plan.txt` не читается не потому, что что-то настроено неправильно, а потому, что Виктор так и хотел. Попытка обойти это через `sudo` попала в журнал — и, что важнее, была бы попыткой отменить чужое решение молча.

Через два сезона ты окажешься по другую сторону: будешь писать этот список сами и решать, кто что может. Опыт «мне не дали и это оказалось правильно» пригодится там больше, чем знание синтаксиса.
