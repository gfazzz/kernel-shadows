# Теория — s02e03

## 1. Сервер, который «упал», потому что не отвечал на ping

> *Ночное дежурство, звонок: «биллинг недоступен». Захожу, пингую — тишина. Пингую соседний сервер — отвечает. Делаю вывод: биллинг лёг, поднимаю тревогу, будим дежурного разработчика, начинаем готовить переключение на резерв.*
>
> *Через двадцать минут разработчик, зевая, говорит: «А я по SSH зашёл, он работает».*
>
> *Работал он всё это время. Днём накатили новую политику безопасности, и в ней ICMP был запрещён на всех машинах биллинга. Сервер жил, слушал, отвечал на запросы — просто молчал на `ping`.*
>
> *Палыч потом разбирал со мной эту ночь по шагам.*
>
> — Что тебе сказал `ping`?
> — Что хост недоступен.
> — Нет. Он сказал, что **не получил ответа**. Это не одно и то же, и разница — целая политика фаервола между вами.
> — Но обычно-то отвечают.
> — Обычно. А ты строил вывод так, будто всегда. `ping` — хорошее «да» и очень плохое «нет». Есть эхо — хост точно жив. Нет эха — ты не знаешь ничего.
>
> *Он тогда написал мне порядок, которым я до сих пор проверяю доступность:*
>
> ```
> ping        → жив? (если да — точно да)
> nc -vz порт → отвечает ли конкретный сервис
> curl -sS    → отвечает ли приложение осмысленно
> ```
>
> — И заведи привычку: прежде чем будить людей, потрать тридцать секунд на второй способ проверки. Ночью цена ошибки не в сервере, а в том, что через неделю на твои тревоги перестанут реагировать.

## 2. ICMP: не совсем «протокол ping»

ICMP — служебный протокол сетевого слоя, и `ping` использует лишь два его сообщения из многих:

| Тип | Сообщение | Кто шлёт |
|---|---|---|
| 8 / 0 | Echo Request / Echo Reply | `ping` |
| 11 | Time Exceeded — истёк TTL | маршрутизатор; на этом работает `traceroute` |
| 3 | Destination Unreachable (сеть/хост/порт/запрет) | маршрутизатор или хост |
| 3 код 4 | Fragmentation Needed | ключевое сообщение для определения MTU |

Отсюда неочевидное следствие: **полная блокировка ICMP ломает сеть**, а не защищает её. Без сообщения «нужна фрагментация» отправитель не узнает, что пакет велик для какого-то участка пути, и соединение будет висеть: рукопожатие проходит, а данные не идут. Это классический «чёрный дыр»-эффект PMTU, и лечится он разрешением хотя бы типа 3.

Разумная политика — не «запретить ICMP», а ограничить частоту Echo Request и разрешить служебные типы.

## 3. Как читать `ping`

```bash
ping -c 4 host             # четыре пакета и статистика
ping -c 1 -W 2 host        # для скриптов: один пакет, короткий таймаут
ping -i 0.2 host           # интервал 0,2 с (меньше 0,2 — только root)
ping -s 1400 host          # размер пакета: диагностика MTU
ping -M do -s 1472 host    # запретить фрагментацию: найти реальный MTU
ping -f host               # flood: только root, только на своей сети
```

| Поле | Смысл |
|---|---|
| `icmp_seq` | номер пакета; пропуски в нумерации = потери |
| `ttl` | остаток TTL; типичные старты — 64 (Linux), 128 (Windows), 255 (сетевое оборудование) |
| `time` | RTT в миллисекундах |
| `packet loss` | доля потерь за сессию |

По остатку TTL можно оценить число пройденных маршрутизаторов: ответ с `ttl=57` от Linux-хоста (старт 64) означает семь переходов.

**Портируемость.** Флаг `-W` в Linux задаётся в секундах, в macOS/BSD — в миллисекундах, а `-c` есть везде. Скрипт, который должен работать на обеих системах, либо определяет платформу, либо задаёт таймаут внешним `timeout 3 ping …`.

**RTT и джиттер.** Одиночное измерение почти бесполезно: важны медиана и разброс. Строка `rtt min/avg/max/mdev = 11.9/12.4/13.1/0.4 ms` информативнее любого отдельного `time=`. Резкий рост `mdev` (джиттера) при неизменном среднем — признак перегруженного или нестабильного участка.

## 4. `traceroute` и его иллюзии

```bash
traceroute -n 10.50.1.100     # -n: не резолвить имена, быстрее и честнее
traceroute -T -p 443 host     # TCP-режим: проходит там, где UDP/ICMP режут
tracepath host                # без root
mtr -rwc 100 host             # 100 замеров, отчёт с потерями по хопам
```

Три вещи, которые регулярно понимают неправильно:

**Звёздочки в середине — обычно не проблема.** Многие маршрутизаторы не отвечают на истёкший TTL или отвечают с низким приоритетом. Значение имеет, доходит ли трассировка до цели, а не наличие пропусков по пути.

**Потери на промежуточном хопе — не потери трафика.** Ответ на TTL-истечение генерирует управляющий процессор маршрутизатора, у которого низкий приоритет. Он может отбрасывать эти запросы, продолжая безупречно передавать транзитные пакеты. Смотреть надо на потери **на последнем** хопе.

**Путь туда не равен пути обратно.** Маршрутизация асимметрична: `traceroute` показывает только направление «отсюда — туда». Проблема может быть на обратном пути, которого ты не видишь; поэтому при разборе с провайдером просят трассировку с обеих сторон.

## 5. Порядок диагностики

Проверять снизу вверх, каждый шаг — отдельный вопрос:

```bash
ip link                       # есть ли линк на интерфейсе
ip addr                       # есть ли адрес
ip route get 10.50.1.100      # каким маршрутом пойдёт пакет
ping -c1 -W2 10.50.1.100      # доходит ли до хоста
nc -vz 10.50.1.100 443        # отвечает ли порт
curl -sS -o /dev/null -w '%{http_code}\n' https://host/   # отвечает ли приложение
dig +short host               # резолвится ли имя (следующая серия)
```

Порядок не даёт перескочить к красивой гипотезе. Опыт показывает, что первая догадка почти всегда «наверное, DNS», а причина чаще оказывается на два слоя ниже — и найти её заняло бы тридцать секунд, если бы её проверили первой.

**`tcpdump` — когда всё вышеперечисленное противоречит друг другу:**

```bash
sudo tcpdump -ni any icmp                 # видеть эхо-запросы вживую
sudo tcpdump -ni any 'tcp port 443'       # рукопожатия и сбросы
```

Он показывает, что реально уходит с интерфейса и что приходит, — и обычно разрешает спор «мы отправили» / «мы не получали» за одну минуту. Подробно — в Season 5.

## 6. Baseline: почему замер важнее порога

Порог «RTT больше 200 мс — тревога» кажется разумным, пока не выяснится, что до одного из узлов нормальный RTT равен 210, а до другого — 4. Один порог на всех даёт постоянные ложные срабатывания в первом случае и полную слепоту во втором.

Baseline решает это иначе: измеряем нормальное состояние каждого узла и сравниваем с ним. Тревога не «больше двухсот», а «в три раза выше собственной нормы». Именно так устроены современные системы мониторинга, и именно поэтому первое, что делают при внедрении, — собирают данные, ничего не сигналя.

Побочная польза от регулярного замера: он документирует сеть. Список хостов, которые действительно отвечают, всегда точнее вики-страницы, обновлённой в июле.

## 7. Метанавык: отрицательный результат слабее положительного

`ping` без ответа не доказывает, что хост мёртв. Пустой вывод `grep` не доказывает, что события не было, — может быть, лог ротировался. Отсутствие ошибок в логе не доказывает, что всё хорошо, — может быть, логирование сломано.

Это общее свойство: **положительное наблюдение сильнее отрицательного**. Увидел ответ — знаешь. Не увидел — знаешь только, что не увидел, и должен спросить себя, что ещё могло дать такой же результат.

Практический вывод простой: прежде чем объявить отсутствие чего-то фактом, найди второй, независимый способ проверить. Тридцать секунд, которые несколько раз за карьеру сэкономят ночь.
