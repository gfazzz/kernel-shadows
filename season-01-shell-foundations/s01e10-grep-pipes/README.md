## II. Теория: фильтр и конвейер

### `grep` — оставить только нужные строки

`grep` читает поток строк и печатает те, что подходят под шаблон:

```bash
grep "ERROR" app.log          # строки, содержащие ERROR
grep -i "error" app.log       # без учёта регистра
grep -v " 200 " access.log    # ИНВЕРСИЯ: строки БЕЗ " 200 "
grep -c " 404 " access.log    # только количество
grep -n "ERROR" app.log       # с номерами строк
```

Флаг `-v` здесь ключевой. Вопрос «что было ненормальным» переворачивается в «всё, кроме нормального»: нормальный ответ веб-сервера — `200`, значит, интересны строки, где статуса `200` нет.

Шаблон — не просто подстрока, а регулярное выражение:

```bash
grep '^185\.'          access.log   # строки, НАЧИНАЮЩИЕСЯ с 185.
grep -E ' (401|403|404|5[0-9]{2}) ' access.log   # перечисление статусов
```

`^` — начало строки, `$` — конец, `[0-9]` — цифра, `.` — любой символ (поэтому в IP точку экранируют: `\.`). Вертикальная черта «или» и `+`/`{}` требуют флага `-E`. Подробнее — в [`theory.md`](theory.md).

### `|` — конвейер

Труба соединяет выход одной команды со входом следующей:

```bash
grep -v " 200 " access.log | wc -l      # отфильтровать → посчитать
grep " 404 " access.log | head -5       # найти → взять первые пять
```

Это и есть способ, которым Unix решает большие задачи: не одна программа, которая умеет всё, а десяток мелких, каждая из которых умеет ровно одно, и труба между ними.

> **Ольга:** *«Не ищи команду „проанализируй лог". Её нет и не будет. Есть „отфильтруй", „вырежи поле", „отсортируй", „посчитай одинаковые". Анализ — это то, как ты их составишь.»*

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Нужны строки, где статус НЕ 200. Какой флаг?»*

<details>
<summary>Подумай 20 секунд</summary>

`grep -v " 200 "` — `-v` инвертирует условие и печатает строки, которые шаблону **не** соответствуют.

Пробелы вокруг числа не для красоты: без них шаблон совпадёт с `1200` в размере ответа, с адресом `10.0.200.5`, с датой. Фильтр по подстроке всегда ловит больше, чем задумано, — сузить его можно только контекстом вокруг.
</details>

**LILITH:** *«`grep -c` и `grep … | wc -l` дают одно число. Зачем труба?»*

<details>
<summary>Ответ</summary>

Затем, что `-c` умеет только считать свои же совпадения — это тупик. Труба соединяет что угодно с чем угодно:

```bash
grep -v " 200 " access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
```

Здесь фильтр, извлечение поля, сортировка и подсчёт — четыре разные программы, ни одна из которых не знает про остальные. Так из лога получается рейтинг атакующих. `-c` — частный случай; конвейер — принцип.
</details>

Проверяется и то, что атакующие попали в вывод, и то, что нормальные **не** попали, — фильтр, пропускающий всё, тестов не проходит.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
grep -vE ' 200 ' "$log"
count=$(grep -vE ' 200 ' "$log" | wc -l)
echo "Подозрительных запросов: ${count}"
```

`$(...)` подставляет вывод команды в переменную — ты это делал в s01e07. Эталон — в `solution/`, открывай после попытки.
</details>

### Три ошибки, которые здесь делают

**Слишком широкий шаблон.** `grep -v 200` без пробелов выбросит строки, где `200` встретилось где угодно: в размере ответа, в адресе, в номере порта. Отчёт получится честным по форме и неверным по сути — и заметить это можно только глазами, по конкретным строкам.

**Забыть про пустой результат.** Если атакующих не нашлось, `grep` вернёт код `1` — это не ошибка, а «совпадений нет». Скрипт, запущенный с `set -e`, на этом молча умрёт, не напечатав итог. Ноль подозрительных — тоже результат, и его надо показать.

**Считать `wc -l` там, где строк нет.** `grep … | wc -l` на пустом выводе честно даст `0`, а вот `grep -c` вернёт `0` и ненулевой код возврата. Мелочь, которая ломает конвейеры в cron.

## V. Четыреста двадцать строк

Скрипт отрабатывает меньше чем за секунду. Из тысяч строк остаётся несколько сотен, и они больше не выглядят океаном — это список.

`403` на `/admin`. `401` на `/login`, много раз подряд, с шагом в доли секунды. `404` на путях вида `/../../etc/passwd`. Кто-то методично проверял двери.

Ты отправляешь результат Анне. Ответ приходит в 04:31 — она тоже не спит.

```
Вижу. Это не DDoS ради нагрузки, это разведка под прикрытием шума.
Кто-то искал вход, пока все смотрели на график трафика.

Мне нужны АДРЕСА и частота. Не строки — цифры.
Кто стучался чаще всех.

— А.К.
```

Ты смотришь на свой вывод и понимаешь, в чём проблема. Строки есть. Адреса в них есть — первым полем. Но чтобы получить «кто чаще всех», надо вырезать это поле из каждой строки и посчитать повторы. `grep` так не умеет: он работает со строкой целиком, для него строка — неделимая.

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   Фильтровать научился. Из тысяч строк — сотни нужных.       │
│                                                              │
│   Но Анне нужны не строки, а АДРЕСА и ЧАСТОТА.               │
│   Строку надо разложить на поля и посчитать одинаковые.      │
│                                                              │
│   Для grep строка — единое целое. Нужен инструмент,          │
│   который видит в ней колонки.                               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

04:35. За окном ещё темно, и спать уже бессмысленно.
