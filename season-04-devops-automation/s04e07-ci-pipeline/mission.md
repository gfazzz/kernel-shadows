## Обстановка

Конвейер, написанный Дмитрием, зелёный на каждом коммите. При этом проверка
репозитория в нём находит секрет и не мешает слиянию, чужое действие
подтягивается с ветки `main` чужого репозитория, пароль реестра лежит
в самом файле, а выкат в бой стартует одновременно с проверками.

Задача — переписать файл так, чтобы зелёная галочка означала то, что от неё
ожидают.

## Приказ

Переписать `artifacts/ci.yml` (в репозитории — `.github/workflows/ci.yml`).

```bash
cp starter/ci.yml artifacts/ci.yml
bash tests/test.sh
```

## Требования

| Что | Почему |
|---|---|
| триггер `pull_request`, без `pull_request_target` | проверка обязана приходить до слияния, но без секретов для чужих веток |
| ни одного `\|\| true` и `continue-on-error: true` | проверка, которая не может провалиться, — не проверка |
| все `uses:` закреплены хешем или версией до patch | иначе завтра на вашей машине выполнится другой код |
| `permissions:` на верхнем уровне, без права записи | токен прогона по умолчанию умеет писать в репозиторий |
| пароль только из `secrets.*`, только через `env:` шага | `${{ }}` в `run:` вклеивает значение в текст команды |
| `github.event.*` не подставлять в `run:` | этот текст пишет автор чужого коммита |
| цепочка `needs` от проверок до любого выката | job без `needs` стартует параллельно, а не после |
| тег образа — хеш коммита, не `latest` | у предыдущей версии должно быть имя, иначе откат невозможен |
| job с `environment: production` и `if:` на `main` | ручное одобрение и одна разрешённая ветка |
| `runs-on` с версией, `timeout-minutes` у всех job | `ubuntu-latest` — тот же движущийся тег; зависший job держит очередь |
| выкат заканчивается проверкой готовности | «команда выполнена» не значит «служба отвечает» |

## Чем добывать

| Что нужно | Как |
|---|---|
| хеш версии действия | `git ls-remote https://github.com/actions/checkout v4.1.1` |
| секрет в шаг | блок `env:` у шага + `${{ secrets.ИМЯ }}` |
| пароль в команду без командной строки | `printf '%s' "${TOKEN}" \| docker login --password-stdin` |
| цепочка job | `needs: имя` или `needs: [a, b]` |
| ограничение по ветке | `if: github.ref == 'refs/heads/main'` |
| проверка готовности | `curl -fsS --retry 10 --retry-delay 3 https://…/healthz` |
| увидеть свой файл глазами платформы | `actionlint` на своей машине (не требуется для теста) |

## Критерии приёмки

- [ ] `artifacts/ci.yml` создан на основе `starter/`.
- [ ] Есть триггер `pull_request`; `pull_request_target` не используется.
- [ ] Все действия закреплены хешем или версией вида `vX.Y.Z`.
- [ ] Задан `permissions:`, право записи токену не выдано.
- [ ] Паролей открытым текстом нет; есть обращение к `secrets.*`.
- [ ] Ни одного `${{ secrets.… }}` и `${{ github.event.… }}` внутри `run:`.
- [ ] Ни одного `continue-on-error: true` и ни одного `|| true`.
- [ ] Проверки репозитория запускаются (`scripts/prepush_check.sh`).
- [ ] Каждый job, выходящий наружу, зависит от проверок по цепочке `needs`.
- [ ] Образ помечен хешем коммита; тега `latest` в выкате нет.
- [ ] Есть job с `environment: production` и `if:` на `refs/heads/main`.
- [ ] У всех job задан `runs-on` (не `*-latest`) и `timeout-minutes`.
- [ ] Каждый выкат заканчивается проверкой готовности.
- [ ] `bash tests/test.sh` → 24 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + sed + coreutils |
| Сеть | не нужна |
| github / docker | **не нужны** — файл проверяется как текст |
| Внешние пакеты | нет |
| Изоляция теста | разбор по отступам: верхний уровень — колонка 0, job — 2 пробела, их ключи — 4 |

Отдельно выделяются строки, входящие в значение `run:`: почти все интересные
ошибки — это то, что попало (или не попало) именно в команду. Зависимости
между job собираются в граф, и правило «в бой нельзя попасть в обход
проверок» проверяется обходом этого графа — без единого зашитого имени job.

Тест дополнительно проверяет, что в стартере остались все четыре исходные
ловушки: плавающая версия действия, проглоченный код возврата, пароль
открытым текстом и выкат тегом `latest`.

## Выполнение

```bash
cd season-04-devops-automation/s04e07-ci-pipeline
cp starter/ci.yml artifacts/ci.yml
$EDITOR artifacts/ci.yml
bash tests/test.sh
```

Если у вас есть свой репозиторий на GitHub, стоит проверить главное свойство
руками: сломать что-нибудь заведомо, отправить в ветку и убедиться, что
прогон покраснел. Проверка, которую ни разу не видели красной, ничем не
отличается от отсутствующей.

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «нет триггера pull_request» | только `on: push` | добавить `pull_request` |
| «версия действия не закреплена» | `@main` или `@v4` | хеш или `vX.Y.Z` |
| «нет блока permissions» | не задан | `permissions: contents: read` наверху |
| «секрет прямо в конвейере» | пароль в `env:` файла | `${{ secrets.… }}` |
| «секрет подставляется прямо в команду» | `${{ secrets.X }}` внутри `run:` | вынести в `env:` шага |
| «подстановка github.event.* в run» | текст события вклеен в команду | через `env:` и в кавычках |
| «код возврата проглочен» | `\|\| true` | убрать |
| «в обход проверок» | у job нет `needs` | выстроить цепочку |
| «выкат тегом latest» | нет неизменяемого тега | `${GITHUB_SHA}` |
| «выкат не ограничен веткой main» | нет `if:` у боевого job | `if: github.ref == 'refs/heads/main'` |

## После выполнения

Зелёный тест означает, что галочка конвейера теперь связана с состоянием
репозитория: она краснеет, когда проверка находит проблему, и не появляется
до слияния.

Стоит запомнить формулировку, которая переносится на весь остальной курс:
про любую автоматическую проверку спрашивают не «что она проверяет», а
**«как именно она может провалиться»**. Если короткого ответа нет — проверки
нет, а есть ощущение проверенности, и оно хуже, чем ничего: закрытое место
перестают осматривать.

## Кумулятивность

Проверка, которую запускает конвейер, написана в
[`s04e02`](../s04e02-branches-prepush/) — там она была привычкой одного
человека, здесь становится правилом для всех. Закрепление версий действий —
та же мысль, что точная версия образа в [`s04e05`](../s04e05-dockerfile/) и
[`s04e06`](../s04e06-compose/), но ставка выше: у чужого действия есть доступ
к секретам прогона. Расписание `schedule:` — тот же `cron`, что в
[`s03e06`](../../season-03-system-administration/s03e06-systemd-timers/), а
`needs:` — то же разделение порядка и зависимости, что `After=` и `Requires=`
в [`s03e05`](../../season-03-system-administration/s03e05-systemd-service/).
Права токена продолжают
[`s01e16`](../../season-01-shell-foundations/s01e16-sudo-basics/): выдают не
то, что удобно, а то, что нужно.
