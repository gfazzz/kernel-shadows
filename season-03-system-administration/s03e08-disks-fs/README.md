## «Удалите что-нибудь» — не решение

Таллин встречает дождём и стеклянным зданием, из окон которого видно средневековую башню. Кристьян Тамм не тратит время на знакомство.

> — Виктор сказал: `/var/log` девяносто пять процентов, через час встанет база. Что вы сделаете первым?

> — Посмотрю, что занимает место. `du`.

> — Хорошо. Не «удалю старые логи» — уже неплохо. — Он разворачивает экран. — Смотрите.

```
/dev/mapper/ops--vg-log   20G   18G  980M  95% /var/log
```

```
7.9G	/var/log
```

Ты смотришь на два числа и не понимаешь, какое из них врёт.

> — Ни одно, — говорит Кристьян. — Обе команды правы, просто они считают разное. И пока вы не поймёте, что именно, вы будете удалять файлы и смотреть, как свободное место не меняется. Это, кстати, самый частый способ провести вечер пятницы.

> **LILITH:** *«`du` спрашивает у каталогов, что в них лежит. `df` спрашивает у файловой системы, сколько блоков занято. Файл без имени не попадает в первый ответ и остаётся во втором.»*

## Чему ты научишься

- Почему `df` и `du` считают разное — и когда расхождение между ними и есть ответ.
- Тому, что место кончается двумя способами: байты и inode, и лечатся они по-разному.
- Находить удалённый файл, который держит процесс, — и не путать `(deleted)` с частью имени.
- Метанавыку: **сначала измерение, потом действие**. Вечер, потраченный на удаление нужного, начинался с догадки.

Подробнее, с историей и подводными камнями, — в [`theory.md`](theory.md).

## Теория: два вопроса о месте

### `df` и `du` считают разное

| | `df` | `du` |
|---|---|---|
| Источник | суперблок файловой системы | обход дерева каталогов |
| Что считает | занятые блоки | размеры файлов, до которых дошёл |
| Видит удалённые файлы | **да** | нет |
| Видит то, что под точкой монтирования | нет | да (без `-x`) |
| Скорость | мгновенно | тем дольше, чем больше файлов |

Отсюда два классических расхождения:

- **`df` больше `du`** — файл удалён, но открыт процессом. Имени нет, блоки заняты, и так будет, пока процесс не закроет дескриптор или не завершится.
- **`du` больше `df`** — под смонтированным каталогом остались файлы, записанные до монтирования. Их не видно, а место они занимают. Проверяется временным монтированием корня в другую точку.

### Файл живёт, пока на него есть ссылка

`rm` не удаляет файл. Он удаляет **имя**: уменьшает счётчик ссылок в inode. Данные освобождаются, когда счётчик ссылок стал нулём **и** ни один процесс не держит файл открытым.

```bash
lsof +L1          # файлы с нулём ссылок, открытые процессами
ls -l /proc/709/fd | grep deleted
```

Отсюда правильное лечение: не `rm` (уже сделано), а перечитать дескрипторы — `systemctl reload rsyslog` или `kill -HUP`. Крайний случай — усечь файл через `/proc`:

```bash
: > /proc/709/fd/7        # обнулить, не трогая дескриптор
```

### Место кончается двумя способами

```bash
df -h     # блоки
df -i     # inode
```

Каждый файл занимает **один inode**, независимо от размера. Их количество фиксируется при создании файловой системы и на ext4 не меняется. Каталог с миллионом писем по 200 байт исчерпает inode задолго до блоков — и тогда `No space left on device` появляется при совершенно пустом `df -h`.

### Резерв для root

ext4 по умолчанию резервирует **5 %** блоков для процессов root. Это не расточительство: резерв не даёт заполнить файловую систему полностью, чтобы служба под root могла дописать журнал, а администратор — войти. На разделе с данными его уменьшают:

```bash
tune2fs -m 1 /dev/mapper/ops--vg-log
```

Про `lsblk`, UUID, `blkid`, типы файловых систем, `fsck`, `tune2fs` и `fstrim` — в [`theory.md`](theory.md).

## Проверка: LILITH задаёт вопросы

**LILITH:** *«`df -h` показывает 40 % занятости, а запись падает с `No space left on device`. Как такое возможно?»*

<details>
<summary>Подумай 30 секунд</summary>

Кончились inode: `df -i` покажет `IUse% 100`. Блоки свободны, а записать некуда — новому файлу негде взять inode.

Типичные источники: каталог почтовой очереди, кеш сессий PHP, миллионы мелких файлов от сборки. Лечится удалением файлов (именно количеством, а не объёмом) — либо пересозданием ФС с другим `-i`, потому что на ext4 число inode задаётся при `mkfs` и потом неизменно.

Второй, более редкий вариант — исчерпан резерв: обычный пользователь упёрся в 5 %, оставленные для root.
</details>

**LILITH:** *«Удалили 10 ГБ логов, а `df` показывает то же самое. Перезагружать?»*

<details>
<summary>Ответ</summary>

Не обязательно, и лучше сначала посмотреть.

`lsof +L1` покажет процесс, который держит удалённый файл открытым. Почти всегда это демон, чей лог повернул `logrotate`, не сказав ему перечитать дескрипторы.

Правильный порядок: `systemctl reload` этой службы (или `kill -HUP`). Место освободится немедленно. Перезагрузка сработает тоже — она просто гораздо дороже и скрывает причину, которая повторится через неделю.
</details>

## Разбор типичных ошибок

**Сортировать размеры `du` обычным `sort -n`.** Первым окажется `120M`, потому что 120 больше 4.2, а буквы `sort -n` не смотрит. Нужен `sort -h` — он понимает суффиксы.

**Считать самой проблемной ту ФС, где больше процент.** `/var/log` заполнен на 95 % — и это лечится. `/var/spool` занят на 7 %, и на нём **нельзя создать ни одного файла**: `df -i` показывает `100%`. Второе хуже и заметно только специально.

**Записать `(deleted)` в путь к файлу.** Это пометка `lsof`, а не часть имени: файла с таким именем в системе больше нет вовсе, есть только inode и открытый дескриптор.

## Debriefing

**Двадцать гигабайт, которых не было**

Ты сдаёшь отчёт. Кристьян читает и впервые за разговор коротко кивает.

> — Хорошо. Теперь посчитайте вслух. Двадцать гигабайт том, восемнадцать занято. Из них `du` видит восемь. Десять держит `rsyslogd` — файл, удалённый `logrotate` шесть дней назад.

> — Шесть дней назад — это четырнадцатое.

> — Четырнадцатое. — Он не выглядит удивлённым. — Кто-то в тот вечер повернул журналы вручную и не перезапустил службу. Возможно, чтобы старые записи исчезли из `/var/log/ops`. Что и произошло — из каталога. Из файловой системы они никуда не делись, и `rsyslogd` всё это время исправно дописывал в файл, которого нет.

Он открывает `lsof` ещё раз.

> — Один `reload` — и десять гигабайт вернутся. А вместе с ними мы потеряем возможность вытащить содержимое через `/proc/709/fd/7`. Поэтому порядок такой: сначала копия, потом `reload`.

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   Десять гигабайт возвращены, файл скопирован для Анны.      │
│                                                              │
│   Но том всё равно двадцать гигабайт, а журналов будет       │
│   больше: операция идёт третью неделю.                       │
│                                                              │
│   Виктор прислал ещё один диск. Осталось понять, как         │
│   добавить его к /var/log, не останавливая сервер.           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
