# Теория — s03e05

## 1. Служба, которая работала до первой перезагрузки

> *Я поднял на сервере небольшой сервис на Python. Запустил через `systemctl start`, проверил, отчитался. Через две недели плановая перезагрузка — и сервиса нет. Запускаю руками — работает. Перезагружаю — нет.*
>
> *Я потратил полдня, разглядывая юнит. Синтаксис верный, `systemctl status` показывает `inactive (dead)` без единой ошибки. Пошёл к Палычу с формулировкой «systemd глючит».*
>
> — Покажи вывод `systemctl is-enabled`.
>
> ```
> $ systemctl is-enabled myapp
> static
> ```
>
> — Вот и всё. `static` означает, что включить его нельзя: у юнита нет секции `[Install]`, а значит, нет и ответа на вопрос, куда его вешать при загрузке. Ты запускал службу, которая никогда не была в автозагрузке.
>
> *Я спросил, почему `systemctl enable` не сказал об этом. Он показал: сказал. Одной строкой, которую я пролистал.*
>
> ```
> The unit files have no installation config
> ```
>
> — Systemd вообще довольно разговорчив, — сказал Палыч. — Проблема в том, что его сообщения читают по диагонали: важное и рутинное выглядят одинаково. Поэтому есть три команды, которые отвечают на вопрос быстрее, чем чтение файла: `is-enabled`, `is-active`, `show`.

## 2. Юниты и где они лежат

| Каталог | Что там | Приоритет |
|---|---|---|
| `/usr/lib/systemd/system/` | юниты из пакетов | низший |
| `/etc/systemd/system/` | юниты и переопределения администратора | **высший** |
| `/run/systemd/system/` | временные, до перезагрузки | средний |
| `~/.config/systemd/user/` | пользовательские (`systemctl --user`) | — |

Одноимённый файл в `/etc` полностью перекрывает пакетный. Поэтому первое, что делают при разборе, — `systemctl cat имя.service`: команда показывает, какой файл действует **и** какие drop-in-фрагменты к нему применились.

**Drop-in вместо правки чужого файла:**

```bash
sudo systemctl edit nginx.service     # создаст /etc/systemd/system/nginx.service.d/override.conf
```

Так меняют одну директиву, не трогая пакетный юнит: обновление пакета переопределение не сотрёт.

## 3. Типы юнитов

```
.service   служба (процесс)
.socket    сокет; активация службы при первом подключении
.timer     расписание (см. следующую серию)
.mount     точка монтирования; генерируется из /etc/fstab
.path      слежение за файлом или каталогом
.target    группа юнитов — «состояние системы» (аналог runlevel)
.slice     группа cgroup для распределения ресурсов
```

Цели вместо уровней запуска: `multi-user.target` — обычная работа без графики (бывший runlevel 3), `graphical.target` — с графикой, `rescue.target` — однопользовательский режим.

## 4. Зависимости

| Директива | Смысл |
|---|---|
| `Wants=` | «желательно запустить» — если не выйдет, продолжаем |
| `Requires=` | «обязательно» — если та служба упала, падаем и мы |
| `BindsTo=` | как `Requires`, но следим и за исчезновением устройства |
| `Before=` / `After=` | **только порядок**, ничего не запускает |
| `Conflicts=` | взаимоисключение: запуск одного останавливает другое |
| `PartOf=` | перезапуск/остановка родителя касается и нас |

Порядок и наличие — независимые вещи, и это главный источник ошибок. `Requires=` без `After=` означает «запусти обоих одновременно», что почти всегда не то, чего хотели.

`Requires=` стоит использовать реже, чем кажется: он превращает падение соседней службы в падение своей. Обычно правильный выбор — `Wants=` плюс `After=`.

## 5. Ограничение прав

```ini
NoNewPrivileges=yes           # потомки не получат новых привилегий (в т.ч. через SUID)
ProtectSystem=strict          # весь корень только на чтение
ProtectHome=yes               # /home, /root, /run/user не видны
PrivateTmp=yes                # свой /tmp, исчезает вместе со службой
PrivateDevices=yes            # только базовые устройства, без доступа к дискам
ProtectKernelTunables=yes     # /proc/sys и /sys только на чтение
ProtectKernelModules=yes      # запрет загрузки модулей
ProtectControlGroups=yes      # /sys/fs/cgroup только на чтение
RestrictSUIDSGID=yes          # запрет создавать SUID-файлы
RestrictAddressFamilies=AF_INET AF_INET6
SystemCallFilter=@system-service
CapabilityBoundingSet=        # пустой набор возможностей
ReadWritePaths=/var/lib/ops-monitor
StateDirectory=ops-monitor    # создаст каталог с нужным владельцем
```

`ProtectSystem=` имеет три уровня: `true` (только `/usr` и `/boot`), `full` (плюс `/etc`), `strict` (весь корень, кроме `/dev`, `/proc`, `/sys`). При `strict` запись возможна только там, где разрешено явно.

`StateDirectory=` удобнее, чем создавать каталог руками: systemd создаст `/var/lib/ops-monitor`, выставит владельца из `User=` и не потеряет его при обновлении.

**Проверить результат, а не файл:**

```bash
systemd-analyze security ops-monitor.service   # оценка экспозиции 0–10
systemctl show ops-monitor -p ProtectSystem    # эффективное значение
```

## 6. Ресурсы (cgroup v2)

```ini
MemoryMax=256M       # жёсткий предел; при превышении — OOM только этой службы
MemoryHigh=200M      # мягкий: нажим на выделение, без убийства
CPUQuota=20%         # доля процессорного времени
CPUWeight=100        # относительный вес при конкуренции
TasksMax=32          # число процессов и потоков
IOWeight=100         # приоритет дискового ввода-вывода
```

Ценность `MemoryMax` не в экономии памяти, а в локализации: без него служба с утечкой доводит систему до общего OOM, и ядро убивает не её, а самый крупный процесс — обычно базу данных.

`TasksMax` — защита от форк-бомбы, включая случайную (рекурсивный вызов скрипта самим собой).

## 7. Инструменты

```bash
systemctl status ops-monitor           # состояние, PID, последние строки журнала
systemctl cat ops-monitor              # действующий файл + drop-in-фрагменты
systemctl show ops-monitor             # ВСЕ эффективные параметры (сотни строк)
systemctl list-units --type=service    # что работает сейчас
systemctl list-unit-files --state=enabled   # что вернётся после перезагрузки
systemctl list-dependencies ops-monitor
systemctl daemon-reload                # перечитать файлы юнитов (после правки — обязательно)
systemd-analyze verify ./ops-monitor.service   # синтаксис и ссылки, без установки
systemd-analyze blame                  # что дольше всего стартовало
journalctl -u ops-monitor -f           # журнал именно этой службы
```

`daemon-reload` забывают чаще всего: файл исправлен, а systemd работает по старой, уже загруженной версии. Симптом — «я же поменял, а ничего не изменилось».

Разница между `list-units` и `list-unit-files` — это разница между «что работает» и «что вернётся»; при разборе инцидента нужны обе.

## 8. Метанавык: описывать намерение, а не действия

Init-скрипт отвечал на вопрос «какие команды выполнить, чтобы запустить службу». Unit-файл отвечает на другой: «в каком состоянии система должна находиться». Отсюда всё остальное — зависимости вместо порядка вызова, перезапуск вместо самописного сторожа, ограничения вместо обёрток, журнал вместо перенаправления в файл.

Практическое следствие: почти всё, что раньше писали скриптом вокруг службы, сегодня есть директивой. Если в юните появляется `ExecStart=/bin/sh -c 'while true; do …'`, это обычно значит, что нужная директива существует и просто не найдена.

Обратная сторона — юнит становится документом о правах: по нему видно, что служба может, и что она может, ограничено явно. Файл, из которого это не читается, ничем не лучше init-скрипта — он просто короче.
