## 2. Что на самом деле делает оболочка

Перенаправление — не часть команды. Команда о нём вообще не знает.

```bash
echo "строка" > file
```

Порядок такой: bash разбирает строку, **до запуска** `echo` открывает `file` (создавая или обрезая), подставляет его как дескриптор 1 — и только потом запускает `echo`, который просто пишет в свой stdout, не подозревая, куда тот ведёт.

Отсюда три следствия, которые обычно узнают на практике:

**Файл обрезается, даже если команда упала.** `неверная_команда > важное.txt` уничтожит `важное.txt`, хотя ничего не выполнится. Защита — `set -o noclobber`: тогда `>` откажется писать в существующий файл, а для явной перезаписи нужен `>|`.

**`команда > file` и `> file команда` — одно и то же.** Перенаправление можно ставить где угодно в строке, оно не позиционно.

**`>>` открывает в режиме append.** Каждая запись уходит в конец, даже если файл вырос между открытием и записью. Для журнала, куда пишут несколько процессов, это ещё и вопрос корректности: режим `O_APPEND` гарантирует, что писатели не затрут друг друга.

## 3. Дескрипторы: 0, 1, 2

| Дескриптор | Имя | По умолчанию |
|---|---|---|
| 0 | stdin | клавиатура |
| 1 | stdout | экран |
| 2 | stderr | экран |

```bash
cmd  > out.log            # только stdout
cmd 2> err.log            # только stderr
cmd  > out.log 2> err.log # раздельно
cmd  > all.log 2>&1       # оба в один файл
cmd &> all.log            # то же, короче (bash, не POSIX)
cmd  > /dev/null 2>&1     # выбросить всё
```

**Порядок в `> file 2>&1` имеет значение.** `2>&1` означает «сделай дескриптор 2 копией того, куда сейчас указывает 1». Если написать наоборот — `2>&1 > file` — то в момент копирования 1 ещё указывает на экран, туда stderr и уйдёт, а в файл попадёт только stdout. Классическая ошибка в cron-задачах: «ошибок в логе нет», потому что они всё это время сыпались на почту root.

Зачем разделение вообще: оно позволяет пустить результат в конвейер, не смешивая его с жалобами. `find / -name x 2>/dev/null | wc -l` считает найденное, а не строки «Permission denied».

## 4. `tee` — развилка потока

```bash
cmd | tee    file        # на экран И в файл (перезапись)
cmd | tee -a file        # на экран И в файл (append)
cmd 2>&1 | tee -a file   # включая ошибки
cmd | tee -a file >&2    # копия в файл, поток дальше — в stderr
```

`tee` читает stdin, пишет его в файлы и одновременно отдаёт в свой stdout. Название — от тройника в трубе, буквально «T».

Компромисс: код возврата конвейера — это код **последней** команды, то есть `tee`, а не твоей. Если код важен, берут `${PIPESTATUS[0]}` (bash) или включают `set -o pipefail`.

## 5. Время: формат — это интерфейс

```bash
date '+%Y-%m-%d %H:%M:%S'     # 2025-10-04 16:47:03
date -Iseconds                # 2025-10-04T16:47:03+07:00
date -u '+%Y-%m-%dT%H:%M:%SZ' # 2025-10-04T09:47:03Z
date '+%s'                    # секунды с эпохи
```

| Код | Значение | Код | Значение |
|---|---|---|---|
| `%Y` | год (4 цифры) | `%H` | час (00–23) |
| `%m` | месяц (01–12) | `%M` | минута |
| `%d` | день (01–31) | `%S` | секунда |
| `%F` | то же, что `%Y-%m-%d` | `%T` | то же, что `%H:%M:%S` |

Три причины, по которым берут именно порядок «от крупного к мелкому»:

1. **Сортируется как текст.** `sort` по журналу сразу даёт хронологию; `04.10.2025` — не даёт.
2. **Однозначен.** `04/10/2025` — это 4 октября в Европе и 10 апреля в США. Спор, который стоил не одного часа разбора.
3. **Машиночитаем.** Любой парсер логов (`journalctl`, Loki, Elasticsearch) понимает его без настройки.

**Про часовые пояса.** Пока сервер один, локальное время удобно. Как только серверов несколько и они в разных зонах, сопоставить события можно, только приведя всё к одной шкале — поэтому в распределённых системах пишут UTC (`date -u`), а красивое местное время показывают уже при просмотре. Отдельная радость — переход на летнее время: в час, который повторяется дважды, локальные метки перестают быть уникальными и монотонными.

**Метку берут в момент записи.** `TS=$(date ...)` перед циклом — это одно время на все строки; функция `ts()`, вызываемая внутри, даёт настоящую хронологию.

## 6. Ловушки журналов, которые ждут дальше

**`tail -f` замирает после ротации.** `-f` держит **inode**, а не имя. Когда `logrotate` переименовал файл и создал новый, ты продолжаешь смотреть в старый — тот самый, куда больше никто не пишет. Лечится `tail -F`: следить за именем и переоткрывать.

**Удалённый файл не освобождает диск.** Если процесс держит открытым дескриптор, `rm` уберёт имя, но место останется занятым до перезапуска процесса. Диагностика — `lsof | grep deleted`.

**Лог без ротации однажды съест раздел.** Это не гипотетика, а самая частая причина «сервер внезапно перестал писать что угодно». Ротацию (`logrotate`) и запуск по расписанию (`cron`, `systemd timer`) разбираем в Season 3 — там же станет ясно, почему `while true; sleep 300` не заменяет таймер: он не переживёт перезагрузку, не логируется отдельно и накапливает дрейф.

**`logger`** отдаёт строку системному журналу, и тогда за ротацию, метки и фильтрацию отвечает `journald`, а не ты:

```bash
logger -t monitor "server-31 DOWN"
journalctl -t monitor --since "1 hour ago"
```

Для своего скрипта достаточно `>>` и `date`; знать про `logger` полезно, чтобы не изобретать журнал там, где он уже есть.

## 7. Метанавык: наблюдаемость начинается с записи

Проверка отвечает на вопрос «как сейчас». Журнал отвечает на «когда началось», «сколько длилось», «повторяется ли». Разбор любого инцидента — это работа со вторым вопросом, и данные для него нужно было собрать **до** аварии. После — поздно, история не восстанавливается.

Дальше эта мысль только растёт: метрики (числа во времени), трассировки (путь запроса через сервисы), алерты (журнал, который сам зовёт человека). Всё это надстройки над одной привычкой — записывать со временем и не затирать записанное.
