## 1. Что такое GPIO

**General-Purpose Input/Output** — ножка микросхемы, чьё поведение задаёт программа. У неё два режима:

- **выход (`out`)** — напряжение на ножке задаёт плата: `0` = близко к нулю, `1` = напряжение питания логики (на Raspberry Pi — 3.3 В);
- **вход (`in`)** — напряжение задаёт внешний мир, плата его читает.

Ток, который ножка способна отдать, мал: на Pi это порядка 16 мА на ножку и около 50 мА суммарно на всю гребёнку. Отсюда практическое следствие: светодиод — через резистор, а мотор, реле или лента — только через транзистор или готовый драйвер. Ножка управляет ключом, а не нагрузкой.

### Нумерация: три разные системы

| Система | Пример | Где встречается |
|---|---|---|
| номер контакта на гребёнке | «контакт 11» | схемы, распиновки, инструкции к платам |
| номер GPIO у SoC (BCM) | `GPIO17` | sysfs, дерево устройств, документация чипа |
| номер в старых библиотеках (WiringPi) | `0` | старые примеры кода |

Один и тот же физический контакт называется 11, 17 и 0. Ошибка перевода между системами — самая частая причина «подключил куда сказано, не работает». В sysfs используется **номер SoC**, и только он.

## 2. sysfs-интерфейс подробно

### Полный набор файлов

```
/sys/class/gpio/
├── export        (w) записать номер -> появится gpioN/
├── unexport      (w) записать номер -> исчезнет gpioN/
├── gpiochip0/    информация о контроллере: base, ngpio, label
└── gpio17/
    ├── direction (rw) in | out | low | high
    ├── value     (rw) 0 | 1
    ├── edge      (rw) none | rising | falling | both
    └── active_low(rw) 0 | 1 — инвертировать логику
```

### `direction`: не только in и out

```bash
echo high > gpio17/direction   # сделать выходом И сразу установить 1
echo low  > gpio17/direction   # сделать выходом И сразу установить 0
```

Это не украшение, а защита от короткого «мигания». Последовательность `out` → `value=1` оставляет ножку в состоянии по умолчанию (обычно `0`) на несколько миллисекунд. Если ножка управляет реле или затвором, этот миг может быть заметен физически. `high` устанавливает направление и уровень одной операцией.

### `edge` и прерывания

```bash
echo in      > gpio17/direction
echo rising  > gpio17/edge
# теперь value можно ждать через poll(2)/select(2) вместо опроса в цикле
```

Без `edge` единственный способ узнать об изменении — читать `value` в цикле, тратя процессор и пропуская короткие импульсы. С `edge` ядро само разбудит ожидающий процесс. Из shell это неудобно (нужен `poll` на POSIX-уровне), из Python и C — обычная практика.

### `active_low`

```bash
echo 1 > gpio17/active_low     # теперь value=1 означает низкий уровень
```

Полезно, когда схема управляет «наоборот» (частый случай: светодиод подключён к питанию, и зажигается нулём). Позволяет писать логику в терминах «включено/выключено», а не «высокий/низкий».

### Права без root

Штатно `/sys/class/gpio` принадлежит root. На платах с `udev` правило вида

```
SUBSYSTEM=="gpio", KERNEL=="gpiochip*", GROUP="gpio", MODE="0660"
```

отдаёт доступ группе `gpio`, куда добавляют рабочего пользователя. Тогда служба не требует root — то самое сокращение прав, что в [`s05e11`](../../season-05-security-pentesting/s05e11-hardening/): демон, управляющий светодиодом, не должен иметь прав на всю машину.

Тонкость: после `export` каталог `gpioN/` создаётся ядром, а права на файлы внутри выставляет `udev` — то есть не мгновенно. Скрипт, который сразу после `export` пишет в `direction`, иногда получает `Permission denied` на ровном месте. Лечится ожиданием (`udevadm settle` или короткий цикл проверки доступности файла).

## 3. Почему sysfs объявлен устаревшим

Интерфейс `/sys/class/gpio` помечен как deprecated начиная с ядра 4.8. Причины:

| Проблема | В чём выражается |
|---|---|
| нет владельца | ножка, экспортированная процессом, остаётся занятой после его смерти |
| гонки | между `export` и появлением прав в `udev` |
| глобальная нумерация | номера ножек «плавают» между ядрами и платами |
| нет атомарности | нельзя выставить несколько ножек одновременно |
| накладные расходы | каждая операция — открытие и запись файла |

Замена — **`libgpiod`** и символьные устройства `/dev/gpiochipN`:

```bash
gpiodetect                       # какие контроллеры есть
gpioinfo gpiochip0               # какие линии и кем заняты
gpioget  gpiochip0 17            # прочитать
gpioset  gpiochip0 17=1          # выставить
gpiomon  gpiochip0 17            # следить за изменениями
```

Ключевое отличие — **линия принадлежит процессу**, который её запросил. Процесс умер — линия освободилась, и никакой уборки за собой не требуется. `gpioinfo` при этом показывает, кто именно держит линию:

```
line  17:  unnamed  "shadow-sensor"  output  active-high [used]
```

Почему в серии всё-таки sysfs: он остаётся на огромном количестве работающих плат со старыми ядрами, он не требует установки библиотек, и — главное для курса — он показывает механику без посредника. Поняв sysfs, переход на `libgpiod` занимает полчаса; наоборот — нет.

## 4. Электрическая сторона

### Подтяжки (pull-up / pull-down)

Вход, к которому ничего не подключено, электрически «висит»: его значение случайно и меняется от наводок. Чтобы у него было определённое состояние покоя, включают внутренний резистор — к питанию (`pull-up`, покой = 1) или к земле (`pull-down`, покой = 0).

Через sysfs подтяжками управлять нельзя — это делается в `config.txt` (см. `s06e03`) или через `libgpiod`/`pinctrl`. Симптом отсутствия подтяжки узнаваем: кнопка «нажимается сама», значение скачет между 0 и 1 без причины.

### Дребезг контактов

Механическая кнопка при нажатии замыкается не один раз, а десятки — за первые миллисекунды. Программа, читающая `value` в цикле, увидит серию нажатий вместо одного. Лечится программно (игнорировать изменения чаще, чем раз в ~20 мс) или схемно (конденсатор).

### Чего нельзя делать

| Действие | Что произойдёт |
|---|---|
| подать 5 В на ножку Pi | ножка рассчитана на 3.3 В — необратимое повреждение |
| соединить два выхода | столкновение источников, ток через кристалл |
| подключить мотор напрямую | превышение тока; плюс выбросы напряжения при остановке |
| писать в ножку, занятую периферией | ломается то, что на ней работало (консоль, шина) |

Отсюда правило серии: **список занятых ножек — не бюрократия, а предохранитель.**

## 5. Идемпотентность в управлении железом

Скрипт управления железом почти всегда вызывается повторно: из `systemd` при перезапуске службы, из монитора при восстановлении, руками в консоли. Полезно различать три вида операций:

| Вид | Пример | Повторный вызов |
|---|---|---|
| установка состояния | `direction out`, `value 1` | безопасен: результат тот же |
| захват ресурса | `export` | требует проверки: занято ≠ ошибка |
| действие во времени | «мигнуть 3 раза» | не идемпотентно по природе |

Первые два вида — то, из чего строят надёжные скрипты; третий выносят в отдельные команды и не вызывают из автозапуска. Ту же классификацию использует Ansible ([`s04e12`](../../season-04-devops-automation/s04e12-ansible-playbook/)): модули описывают состояние, а `command` — действие, и именно `command` ломает повторный прогон.

## 6. Как это тестируют без платы

Приём из этой серии переносится на любую работу с sysfs и procfs:

1. Все пути строятся от переменной корня (`--root`), а не от `/sys`.
2. В тесте корень — временный каталог с теми же файлами.
3. Реакцию ядра (создание `gpioN/` в ответ на запись в `export`) имитирует функция теста.
4. Скрипт при этом работает с настоящими файлами настоящим `printf`/`cat` — он не знает, что перед ним не ядро.

Это тот же mock-first, что с подменой `ssh`, `curl` и `docker` в [`s04e08`](../../season-04-devops-automation/s04e08-deploy-rollback/), только подменяется не команда в `PATH`, а корень файловой иерархии. Побочная польза: скрипт, у которого корень вынесен в параметр, автоматически становится пригодным для запуска в контейнере и для отладки на копии.
