## I. Бесконечный `cat`

Ли Вэй показывает вчерашнюю попытку стажёра.

```
$ cat /dev/shadow0
seq=1 t=22.000
seq=2 t=22.137
seq=1 t=22.000
seq=2 t=22.137
seq=1 t=22.000
^C
```

> — Что произошло?

Макс смотрит на код `read()`.

> — Он каждый раз отдаёт всё с начала.

> — Именно. И `cat` честно читает, пока ему что-то дают. А дают всегда. Он будет читать, пока не кончится место на диске, если вывод перенаправить.

Он подчёркивает две строки в прототипе:

```c
ssize_t shadow_read(struct file *f, char __user *ubuf, size_t count, loff_t *ppos);
```

> — Здесь два ответа на два разных вопроса, и оба надо дать правильно. `count` — сколько байт **просят**. `*ppos` — с какого места. А возврат — сколько **отдали**, и ноль в нём означает не «ошибка» и не «пусто сейчас», а **конец файла**. Это единственный способ сказать читателю «всё, больше нечего».

Он листает дальше.

> — И вторая половина. Вот `ubuf`. Что это?

> — Указатель на буфер программы.

> — Указатель на буфер программы **в её адресном пространстве**. Ты в ядре. Эта страница может быть выгружена, может быть не отображена, может вообще указывать в чужую память — программа передала это число, а не ты его вычислил. Написать по нему напрямую — либо паника, либо дыра, через которую пользователь пишет в ядро.

Он пишет одно слово: `copy_to_user`.

> — Вот граница. Всё, что через неё идёт, идёт только так.

> **LILITH:** *«Символьное устройство — это договор: ядро обещает вести себя как файл, а программа обещает разговаривать с ним как с файлом. Обе стороны договора держатся на трёх вещах: сколько просят, откуда, и что ноль значит конец. Сломай любую — и `cat` либо зациклится, либо потеряет данные.»*

## II. Теория: как ядро притворяется файлом

### Таблица операций

```c
static const struct file_operations shadow_fops = {
        .owner   = THIS_MODULE,
        .open    = shadow_open,
        .read    = shadow_read,
        .release = shadow_release,
        .llseek  = default_llseek,
};
```

Каждое поле — что делать, когда пользовательская программа вызывает соответствующий системный вызов. Не перечисленные операции ядро отклонит само.

`.owner = THIS_MODULE` — счётчик ссылок: пока файл открыт, модуль нельзя выгрузить. Без него `rmmod` во время чтения оставит ядро с указателями на выгруженный код.

### `read()` — три числа

```c
ssize_t shadow_read(struct file *f, char __user *ubuf, size_t count, loff_t *ppos)
```

| Что | Смысл |
|---|---|
| `count` | сколько байт просят — **максимум**, не обязательство |
| `*ppos` | с какой позиции читать; драйвер сам её продвигает |
| возврат > 0 | сколько байт отдали |
| возврат 0 | **конец файла** |
| возврат < 0 | код ошибки |

Отдать меньше, чем просят, — нормально и обычно. Отдать больше — выход за буфер программы. Не продвинуть `*ppos` — бесконечный цикл у читателя.

Именно поэтому подсчёт «сколько отдать» вынесен в проверяемую функцию:

```c
n = shadow_copy_slice(text, len, *ppos, chunk, count);
```

Три случая, которые она обязана различать: данных больше, чем просят; данных меньше, чем просят; данных нет — позиция уже за концом.

### `copy_to_user` — граница миров

```c
if (copy_to_user(ubuf, chunk, n))
        return -EFAULT;
```

Возвращает число **не**скопированных байт: ноль — успех. Функция умеет обрабатывать отсутствующую страницу, проверяет, что адрес принадлежит вызывающему процессу, и не даёт разыменовать чужой указатель.

`memcpy` вместо неё — классическая уязвимость: программа передаёт адрес внутри ядра, и драйвер послушно туда пишет.

Аннотация `__user` в прототипе — не комментарий: статический анализатор `sparse` проверяет, что такие указатели не разыменовываются напрямую.

### Регистрация: пять шагов и лестница отката

```
kzalloc              →  память под буфер
alloc_chrdev_region  →  номера (major, minor)
cdev_add             →  ядро знает про устройство
class_create         →  класс в /sys/class
device_create        →  узел /dev/shadow0 создаёт udev
```

Каждый шаг может не удаться, и каждый следующий обязан откатить все предыдущие:

```c
err_class:
        class_destroy(shadow_class);
err_cdev:
        cdev_del(&shadow_cdev);
err_region:
        unregister_chrdev_region(shadow_devt, 1);
err_text:
        kfree(text);
err_ring:
        kfree(ring);
        return err;
```

Метки идут в порядке, обратном захвату, и каждая освобождает ровно то, что было взято **до** неё. Пропущенная строка здесь не даст ни ошибки сборки, ни падения — она оставит занятый номер устройства до перезагрузки.

### Несколько читателей

`read()` могут вызвать одновременно два процесса. Общий буфер `text` при этом переписывается — значит, нужна блокировка:

```c
if (mutex_lock_interruptible(&shadow_lock))
        return -ERESTARTSYS;
...
mutex_unlock(&shadow_lock);
```

Тонкость: блокировку надо снять на **каждом** пути выхода, включая ошибочные. Забытое `mutex_unlock` перед `return -EFAULT` подвешивает всех последующих читателей навсегда.

`mutex_lock_interruptible` вместо `mutex_lock` позволяет прервать ожидание сигналом: процесс, застрявший на чтении устройства, должен убиваться по Ctrl+C.

Про `write`, `ioctl`, `poll`, `mmap`, `misc_device`, `debugfs` и `sysfs` как альтернативы — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«Почему нельзя просто `memcpy(ubuf, data, n)`? Указатель же дали.»*

<details>
<summary>Подумай 30 секунд</summary>

Потому что дали его **не вы**, а пользовательская программа, и он ничем не подтверждён. Три отдельные беды в одной строке:

Страница может быть не отображена — например, выгружена или ещё не выделена. `memcpy` в ядре не обработает страничную ошибку так, как это делает пользовательский код: получится паника.

Адрес может указывать не в пользовательское пространство, а в ядро. Тогда драйвер по просьбе программы запишет данные в память ядра — это готовая уязвимость повышения привилегий, и обнаруживается она в отчётах о безопасности, а не в тестах.

Адрес может принадлежать другому процессу — при некоторых схемах отображения.

`copy_to_user` проверяет принадлежность адреса, обрабатывает страничные ошибки и возвращает число нескопированных байт. Отсюда общий принцип, который в ядре формулируют жёстко: **данные, пришедшие из-за границы доверия, проходят её только через специально предназначенные для этого функции.** То же верно для `copy_from_user`, `get_user`, `put_user` и `strncpy_from_user`.
</details>

**LILITH:** *«Возврат 0 из `read()` — почему это не «сейчас нечего читать»?»*

<details>
<summary>Ответ</summary>

Потому что «сейчас нечего» и «больше не будет» — принципиально разные ответы, и для них есть разные способы их дать.

Ноль означает **конец файла**. Получив его, `cat` завершается, `read()` в цикле останавливается, буферизованный ввод считает данные исчерпанными. Это финальный ответ.

Если данные могут появиться позже, драйвер должен либо **заблокировать** вызывающего до их появления (`wait_event_interruptible`), либо, при открытии с `O_NONBLOCK`, вернуть `-EAGAIN` — «попробуй ещё раз». Оба варианта говорят «пока пусто», не закрывая тему.

Ошибка стоит дорого в обе стороны. Вернуть ноль вместо ожидания — читатель уйдёт, не дождавшись данных. Не вернуть ноль в конце — читатель не уйдёт никогда, и получится вчерашний бесконечный `cat`.

Отсюда правило чтения любого потока, не только в ядре: **у «пусто» должно быть два разных ответа**, и выбор между ними — это решение о семантике вашего устройства, а не деталь реализации.
</details>

## IV. Задание: `shadow_view.c` + `shadow_dev.c`

Артефакты — `artifacts/shadow_view.c` (логика) и `artifacts/shadow_dev.c` (драйвер).
`shadow_ring.c` перенесён из [`s06e11`](../s06e11-kernel-module/) без изменений: его не переписывают, им пользуются.

```bash
cp starter/* artifacts/
bash tests/test.sh
```

| Файл | Требование |
|---|---|
| `shadow_view.c` | `shadow_format_line`: «`seq=12 t=23.062`», дробная часть всегда три цифры, знак при нулевой целой |
| | `shadow_render`: от старого к свежему, `-1` если не влезло |
| | `shadow_copy_slice`: `min(count, len-pos)`; `pos >= len` → **0**, а не ошибка |
| `shadow_dev.c` | `file_operations` с `.owner`, `.open`, `.read`, `.release` |
| | `copy_to_user` + `-EFAULT`; `memcpy` в `ubuf` запрещён |
| | `*ppos` продвигается на число отданных байт |
| | пять пар «взял — отдал» и лестница меток `err_*` |
| | блокировка снимается на каждом выходе из `read` |
| | подсчёт «сколько отдать» не продублирован в драйвере |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Дробная часть — ровно три цифры с ведущими нулями: 62 тысячных это `.062`.

`shadow_render` идёт с конца: `peek(len-1)` — самое старое, `peek(0)` — самое свежее.

В `shadow_copy_slice` сначала отсеките `pos >= len` (это EOF), потом считайте `min`.

В драйвере: взять блокировку → собрать снимок → спросить `shadow_copy_slice` → `copy_to_user` → продвинуть `*ppos` → снять блокировку. И то же самое на каждом пути ошибки.

Парные вызовы перечислены в `data/pairs.txt` — тест читает тот же файл.

Эталон — в `solution/`, там у каждой строки написано, что она предотвращает.
</details>

### Три ошибки, которые здесь делают

**Не вернуть ноль в конце.** Читатель зацикливается — вчерашний `cat`.

**`memcpy` вместо `copy_to_user`.** Работает при удачном стечении обстоятельств и является уязвимостью при любом другом.

**Забыть `mutex_unlock` на пути ошибки.** Всё работает, пока ошибки не случится; после неё устройство мертво до перезагрузки.
