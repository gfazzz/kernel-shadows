## II. Теория: шесть полей

```
UUID=1b6e5c40-…   /var/log   ext4   defaults,noatime,nodev,nosuid,noexec   0   2
      │              │        │                  │                        │   │
      │              │        │                  │                        │   └ pass: порядок fsck
      │              │        │                  │                        └ dump: всегда 0
      │              │        │                  └ опции монтирования
      │              │        └ тип файловой системы
      │              └ точка монтирования
      └ что монтировать
```

### Почему UUID, а не `/dev/vdb`

`/dev/vdb` — это **порядок, в котором ядро нашло устройства при этой загрузке**. Добавили диск, поменяли порт, мигрировали на другой гипервизор — порядок другой. Тот же самый `fstab` смонтирует в `/var/log` совершенно другой том.

UUID генерируется при создании файловой системы и не меняется никогда:

```bash
blkid                     # UUID и типы всех устройств
lsblk -f                  # то же деревом
findmnt --verify --verbose  # проверить fstab, ничего не монтируя
```

Имена вида `/dev/mapper/ops--vg-log` устойчивы — их создаёт LVM, а не порядок обнаружения. UUID работает одинаково и там, и там, поэтому проще писать его везде.

### Опции монтирования

| Опция | Что делает |
|---|---|
| `defaults` | `rw,suid,dev,exec,auto,nouser,async` |
| `noatime` | не обновлять время доступа — чтение перестаёт порождать запись |
| `nodev` | не обрабатывать файлы устройств |
| `nosuid` | игнорировать биты SUID/SGID |
| `noexec` | не запускать программы |
| `ro` | только чтение |
| `nofail` | не останавливать загрузку, если устройства нет |

`nodev,nosuid,noexec` на разделах с данными — прямое продолжение [`s03e02`](../s03e02-permissions/): SUID-копия оболочки, лежащая в каталоге, смонтированном с `nosuid`, не даёт никаких прав. Это не защита от root — это сужение возможностей для того, кто root ещё не получил.

`noexec` при этом ломает часть пакетов, если поставить его на `/var`: некоторые службы распаковывают туда исполняемые файлы. На `/var/log` и `/var/spool` он безопасен.

### `dump` и `pass`

**`dump`** — реликт одноимённой утилиты, которой давно никто не пользуется. Всегда `0`.

**`pass`** — порядок проверки `fsck` при загрузке: `1` у корня (проверяется первым и отдельно), `2` у остальных файловых систем (проверяются параллельно), `0` у того, что проверять не нужно, — swap, tmpfs, сетевые ФС.

### Проверять до перезагрузки

```bash
findmnt --verify --verbose    # разбор fstab без монтирования
mount -a                      # смонтировать всё, что ещё не смонтировано
mount --fake -a               # только разбор, без действий
systemctl daemon-reload       # systemd генерирует .mount-юниты из fstab
```

`mount -a` — минимальная проверка, которую делают всегда: если после правки `fstab` она отработала молча, перезагрузка почти наверняка пройдёт.

Про `nofail`, `x-systemd.*`, сетевые ФС, `tmpfs`, bind-монтирование и генератор `.mount`-юнитов — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«В `fstab` есть строка для внешнего диска, который сейчас отключён. Машина перезагружается. Что произойдёт?»*

<details>
<summary>Подумай 30 секунд</summary>

Загрузка остановится в аварийном режиме с запросом пароля root: systemd не смог выполнить зависимость `local-fs.target`.

Лечится опцией `nofail` — с ней отсутствующее устройство перестаёт быть фатальным. Для съёмных и сетевых носителей её ставят всегда, часто вместе с `x-systemd.device-timeout=10` (иначе systemd будет ждать устройство полторы минуты).

Отсюда практика: на удалённом сервере после каждой правки `fstab` — `findmnt --verify` и `mount -a`, до перезагрузки, пока есть доступ.
</details>

**LILITH:** *«Перенесли систему на другой гипервизор. Загрузка остановилась, хотя `fstab` не трогали. Почему?»*

<details>
<summary>Ответ</summary>

Скорее всего, в `fstab` записаны имена устройств: `/dev/vda1`, `/dev/sdb`. Порядок обнаружения на новой платформе другой — тот же файл теперь указывает на другие носители.

Симптом узнаваем: до миграции работало годами, после переноса «сломалось само». Ничего не сломалось — адрес всё это время был случайным и совпадал.

Лечится из аварийного режима: `blkid`, заменить имена на `UUID=`, `mount -a`, перезагрузка.
</details>

## IV. Задание: переписать таблицу

Кристьян снял `blkid` после расширения тома. Артефакт — `artifacts/fstab`:

```bash
cp starter/fstab artifacts/fstab
bash tests/test.sh
```

Стартер — действующая таблица сервера. В ней смонтировано не то, не оттуда, не всё и без ограничений; одна запись указывает на устройство, которого нет с марта.

Требуется: все тома из снимка, устойчивая адресация, ограничивающие опции на журналах и очередях, верный порядок проверки, ни одной записи-призрака.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
D=../data
grep -v '^#' $D/blkid_shadow-01.txt                       # UUID и типы
awk '$0=="=== df -h ===" {f=1; next} /^=== /{f=0} f' $D/disk_shadow-01.txt
```

Список точек монтирования берётся из `df -h`, UUID — из `blkid`. Том, смонтированный в `/var/log`, — это логический том `ops--vg-log`, а не диск `/dev/vdb`.

Эталон — в `solution/`, там же комментарий к каждому решению.
</details>

### Три ошибки, которые здесь делают

**Оставить `/dev/vda1` для `/boot`.** Раздел на физическом диске — как раз тот случай, где имя меняется от загрузки к загрузке. Записи LVM устойчивы, записи разделов — нет, и в одном файле обычно исправляют только вторые.

**Не убрать строку `/backup`.** Устройства нет, `nofail` нет — и это одна строка между работающим сервером и аварийным режимом. Проверяется командой `findmnt --verify` за секунду.

**Смонтировать `/var/log` с `/dev/vdb`.** Это физический том LVM: файловой системы на нём нет. `blkid` показывает `TYPE="LVM2_member"`, и `mount` откажется — но узнается это при загрузке.

Ты думаешь.

> — Ничего. Всё записано на диск.
