## «Учётку закроют, а я останусь»

Андрей наливает вторую порцию чая. За окном светлеет — впрочем, оно и не темнело.

> — Хорошо. Вы нашли, кто может войти. Теперь второй вопрос, и он интереснее: что этот кто-то может делать.

Он разворачивает к тебе ноутбук.

> — Допустим, я злоумышленник. Вы нашли мою учётную запись и закрыли её. Что я сделаю заранее, чтобы это не имело значения?

Ты думаешь. Ответ приходит не сразу.

> — Оставите способ войти под другим именем?
> — Слишком шумно. Проще: оставлю программу, которая выполняется с правами root независимо от того, кто её запустил. Учётку закроют, файл останется, а права у файла будут не мои — они будут root.

Он пишет на доске три строки:

```
-rwxr-xr-x  обычная программа: выполняется с правами того, кто запустил
-rwsr-xr-x  SUID: выполняется с правами ВЛАДЕЛЬЦА файла
```

> — Вот эта буква `s` вместо `x` — самая опасная в системе. Она нужна: без неё `passwd` не смог бы менять пароли, а `sudo` — вообще ничего. И она же — любимый способ закрепиться.

> **LILITH:** *«Права в Unix — три буквы и три группы, всего девять бит. Выучить можно за десять минут. Спотыкаются не на них, а на трёх дополнительных битах, которые меняют не доступ, а то, от чьего имени идёт выполнение.»*

## Чему ты научишься

- Переводить `ls -l` в восьмеричную запись, не забывая специальный бит там, где он есть.
- Трём специальным битам — SUID, SGID, sticky — и тому, зачем `/tmp` нужен последний.
- Искать в правах то, что ищут при разборе инцидента: доступное всем на запись, ключ шире `600`.
- Метанавыку: **минимальные права — рабочая гипотеза**, а не идеал. `chmod 777` делает хуже, а не быстрее.

Подробнее, с историей и подводными камнями, — в [`theory.md`](theory.md).

## Теория: девять бит и ещё три

### Как читается строка `ls -l`

```
-rwxr-x---  1  max  ops-logs  4096  Oct 17 03:20  /home/max/report.sh
│└─┬─┘└┬┘└┬┘     │      │
│  │   │  └ остальные (other)
│  │   └ группа
│  └ владелец
└ тип: «-» файл, «d» каталог, «l» символическая ссылка
```

Каждая тройка — три бита: `r` (4), `w` (2), `x` (1). Их сумма и есть привычная восьмеричная запись:

| Символьно | Восьмерично | Смысл |
|---|---|---|
| `rwx------` | `700` | владелец делает всё, остальные ничего |
| `rw-r--r--` | `644` | обычный файл: владелец пишет, остальные читают |
| `rw-r-----` | `640` | читает владелец и группа — так лежит `/etc/shadow` |
| `rwxrwxrwx` | `777` | пишут все — почти всегда ошибка |

### Для каталогов буквы означают другое

Это источник половины путаницы:

- **`r`** — можно получить список имён (`ls`);
- **`w`** — можно создавать и **удалять** файлы внутри;
- **`x`** — можно войти внутрь и обратиться к файлу по имени.

Отсюда неочевидное: право удалить файл даёт не файл, а **каталог**. Если у каталога `w` для всех, любой пользователь удалит чужой файл, даже не имея на него никаких прав.

### Три специальных бита

```
-rwsr-xr-x   SUID  выполняется с правами владельца файла
-rwxr-sr-x   SGID  выполняется с правами группы файла
                   на каталоге — новые файлы наследуют группу каталога
drwxrwxrwt   sticky  в каталоге удалять файл может только его владелец
```

`sticky` на `/tmp` — причина, по которой общая папка вообще работоспособна: писать могут все, а удалять — только своё. Каталог с правами `777` **без** `t` отличается от `/tmp` одним символом и всем остальным.

SUID — механизм, без которого система не обошлась бы: `passwd` должен писать в `/etc/shadow`, `sudo` — переключать пользователя. Цена в том, что любая SUID-программа с ошибкой становится способом получить права её владельца.

Про `umask`, `chmod` с символьной записью, `chown`, ACL и то, почему `chmod 777` не «чинит», а прячет проблему, — в [`theory.md`](theory.md).

## Проверка: LILITH задаёт вопросы

**LILITH:** *«У файла права `r--r--r--`, у каталога, где он лежит, — `rwxrwxrwx`. Может ли посторонний его удалить?»*

<details>
<summary>Подумай 30 секунд</summary>

Да. Удаление файла — это изменение **каталога**, а не файла: из каталога убирается имя. Права самого файла при этом не проверяются вообще.

Именно поэтому `/tmp` имеет sticky bit: без него любой пользователь мог бы удалять чужие временные файлы, включая сокеты работающих служб.
</details>

**LILITH:** *«В домашнем каталоге пользователя лежит копия `/bin/bash` с владельцем root и битом SUID. Что это значит?»*

<details>
<summary>Ответ</summary>

Что любой, кто её запустит, получит оболочку с правами root — без пароля, без `sudo`, без записи в журнале `sudo`.

И что это не могло получиться само: чтобы файл принадлежал root и имел SUID, кто-то уже был root в момент его создания. Такой файл — не способ проникнуть, а способ **вернуться** после того, как исходную дыру закроют.

Проверка занимает одну команду и входит в любой разбор инцидента:
`find / -xdev -perm -4000 -type f -ls`.
</details>

Вопросы и критерии — в [`mission.md`](mission.md). SUID-файлов вне `/usr` в снимке **два**, и только один из них — работа злоумышленника.

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

```bash
D=../data
rows() { grep -E '^[-dl]' "$1"; }             # только строки прав

rows $D/perm_audit_shadow-01.txt | awk '$1 ~ /^d.{7}w/ {print $1, $NF}'   # каталоги 777

```

</details>

## Разбор типичных ошибок

**Считать `777` и `1777` одним и тем же.** Права каталога `/tmp` — `1777`, у `/srv/shared` — `777`. Единица впереди и есть sticky bit; без него общий каталог превращается в место, где любой удаляет чужое.

**Искать SUID по букве `s` где угодно в строке.** Символ `s` в позиции группы — это SGID, совсем другой механизм. Позиция важнее буквы: четвёртый символ — владелец, седьмой — группа, десятый — sticky.

**Считать всякий SUID вне `/usr` атакой.** В снимке их два. Один лежит в домашнем каталоге подсаженной учётки и принадлежит root — это закладка. Второй в `/opt/tools` с осмысленным именем и старой датой — скорее всего, кто-то из команды выдал утилите лишние права «чтобы работало». Дыра та же, разговор другой.

**Файл, который переживёт учётку**

Ты выписываешь находки, и они складываются в последовательность.

`/home/devops/.cache/bash` — копия оболочки, владелец root, бит SUID, дата создания на две минуты позже самой учётки `devops`. Закладка была поставлена сразу, до того как ей вообще воспользовались.

Приватный ключ Дмитрия с правами `644`. Ключ читается всеми, кто есть на машине.

Андрей смотрит список и впервые за ночь выглядит не по-академически.

> — Заметьте, что здесь нет ничего сложного. Ни одной уязвимости, ни одного эксплойта.
