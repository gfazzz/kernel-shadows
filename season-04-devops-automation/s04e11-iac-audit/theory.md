# Теория — s04e11

## 1. Двести сорок проверок

> *Мы купили сканер конфигураций. Дорогой, с отчётами. Первый прогон дал восемьсот находок.*
>
> *Через неделю их было восемьсот двенадцать. Через месяц — восемьсот сорок. Никто не открывал отчёт: там всё равно восемьсот.*
>
> — Сколько из них настоящих? — спросил Палыч.
> — Не знаю. Разбирать неделю.
> — Разбери. Только не все, а первые двадцать.
>
> *Из первых двадцати настоящими были три. Остальные — правила, не подходящие нашей системе. Мы их отключили, и осталось двести сорок. Разобрали ещё двадцать — настоящих одиннадцать.*
>
> — Теперь понял, чем отличается инструмент от отчёта? — спросил он потом.
> — Отчёт читают.
> — Отчёт читают, пока в нём нет мусора. Одно ложное срабатывание стоит дороже одного пропуска: пропуск ты не увидишь, а мусор научит тебя не смотреть.

## 2. Что именно проверять

Аудит описания смотрит не на диск, а на то, что отслеживает git: предмет — не рабочий каталог, а то, что получит любой, кто склонирует репозиторий.

```bash
git ls-files                     # состав репозитория
git ls-files --others            # то, что не отслеживается (черновики)
git ls-files --others --ignored --exclude-standard   # что скрыто правилами
```

Третья команда полезна отдельно: она показывает, что именно `.gitignore` прячет прямо сейчас. Иногда там обнаруживается каталог, который прятать не собирались.

## 3. История как отдельный предмет

```bash
git log --all --pretty=format: --name-only | sort -u        # все пути, когда-либо бывшие в репозитории
git log --all -S 'Sh4dow-Pr0d' --oneline                    # коммиты, где значение появлялось или исчезало
git log --all -p -- .env                                    # содержимое по этому пути во всех коммитах
```

`-S` («pickaxe») ищет по изменению **числа вхождений строки** — то есть находит и коммит, где секрет добавили, и коммит, где убрали. Это самый короткий способ ответить на вопрос «сколько времени значение пролежало в репозитории».

Порядок действий при находке в истории всегда один:

1. **сменить секрет** — единственный обязательный шаг;
2. отозвать доступы, выданные по нему;
3. посмотреть журналы: пользовались ли им;
4. и только потом — переписывать историю (`git filter-repo`), помня, что у всех клонов она останется прежней.

Пункт 4 без пункта 1 — уборка вместо реакции.

## 4. Восемь разделов

| Раздел | Признак | Что за ним стоит |
|---|---|---|
| `secrets` | `ИМЯ=значение` длиннее шести символов, `BEGIN … PRIVATE KEY`, `ghp_…`, `AKIA…` | значение действует прямо сейчас |
| `history` | `.env`, `*.pem`, `id_rsa`, `vault_pass.txt` в любом коммите | утечка, не отменяемая удалением |
| `gitignore` | не закрывает секреты; закрывает `*.example` | будущее и удобство коллег |
| `docker` | нет `USER`, база без версии, `COPY` ключа | контейнер от root, невоспроизводимая сборка |
| `compose` | `privileged`, `docker.sock`, `N:N` в портах | изоляция и то, что смотрит наружу |
| `ci` | `@ветка`, `\|\| true`, `continue-on-error`, нет `permissions` | чужой код и проверка, которая не может провалиться |
| `ansible` | пароль в инвентаре, `root`, `StrictHostKeyChecking=no` | вход в полсотни машин |
| `perms` | ключ с правами шире `600` | s01e15, самая старая привычка курса |

Восемь — не потому, что столько бывает, а потому, что ровно эти восемь были сломаны на глазах у студента. Правило, которого не видел сломанным, в отчёте выглядит как шум.

## 5. Ложные срабатывания

| Приём | Цена |
|---|---|
| пропускать `*.example`, `*.sample` | договорённость, которую надо соблюдать |
| исключать по значению (`CHANGEME`, `<...>`) | пропустит настоящий секрет вида `changeme123` |
| исключать по каталогу (`tests/`, `fixtures/`) | туда начнут класть настоящее |
| подавлять по строке комментарием | самый честный: решение видно в diff |

Общее правило: **исключение должно быть видно**. Скрипт, который печатает «пропущено файлов-образцов: 3», отличается от скрипта, который молча их не смотрит, ровно тем, что первое решение можно оспорить.

Разбор комментариев — частный случай той же мысли: строка `privileged: true` в пояснении к правильному файлу находкой не является, но убирать её надо так, чтобы номера строк в отчёте остались настоящими (очищать содержимое строки, а не удалять строку).

## 6. Коды возврата и место в конвейере

```
0 — находок нет, и было что проверять
1 — есть находки
2 — проверять оказалось нечего / ошибка вызова
```

Такой скрипт встаёт в конвейер из [`s04e07`](../s04e07-ci-pipeline/) как обычный шаг — без `|| true`, без `continue-on-error`. Начинают обычно с мягкого режима (сообщать, но не валить) на неделю, чтобы разобрать накопившееся, и переводят в жёсткий по календарю, а не «когда почистим»: второе не наступает.

Промышленные аналоги стоит знать по именам: `gitleaks` и `trufflehog` — секреты, `trivy config` и `checkov` — инфраструктура, `hadolint` — Dockerfile, `ansible-lint` — playbook, `actionlint` — конвейер. Свой скрипт не заменяет их; он объясняет, что они делают, и остаётся понятным в тот момент, когда чужой инструмент выдаёт находку без объяснения.

## 7. Что аудит описания не находит никогда

| Не найдёт | Почему |
|---|---|
| секрет, никогда не попадавший в git | его нет в предмете проверки |
| правильный по форме, но неверный по смыслу конфиг | синтаксис ≠ намерение |
| дрейф на машинах | это [`s04e10`](../s04e10-ansible-check/) |
| логику приложения | это другой предмет |
| то, для чего нет правила | список правил конечен и написан тобой |

Последняя строка — главная. Аудит описания измеряет не безопасность, а **соответствие твоему же списку**. Полезность списка определяется тем, как часто он пополняется после инцидентов.

## 8. Метанавык: у проверки две цифры

Отчёт «расхождений не найдено» и отчёт «сверено 26 файлов, расхождений не найдено» отличаются тем, что второй можно опровергнуть, глядя на число.

| Формулировка | Что с ней не так |
|---|---|
| «всё чисто» | неизвестен объём |
| «ошибок нет» | неизвестно, какие искали |
| «тесты прошли» | неизвестно, сколько их |
| «проверено 26 файлов, 8 правил, 4 находки» | проверяемо целиком |

Приём переносится на всё, что отчитывается: покрытие тестами, сверку копий, инвентаризацию, мониторинг. **Рядом с числом находок всегда должно стоять число просмотренного** — и отдельным случаем выделено «просмотрено ноль», потому что снаружи оно неотличимо от благополучия.

Это же и последний ответ на вопрос всего сезона. Зелёная галочка, `Up (healthy)`, `changed=0`, «находок нет» — четыре разных способа сказать «я не нашёл проблем». Ни один из них не означает «проблем нет», и разница каждый раз в том, что именно было в области видимости.
