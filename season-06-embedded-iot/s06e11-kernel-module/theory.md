# s06e11 — теория: ядро, модули и цена ошибки

Дополнение к [`README.md`](README.md). Здесь — сборка, журнал ядра, символы, память, блокировки, отладка и то, чем работа в ядре отличается от всего предыдущего в курсе.

---

## 1. Пространство ядра и пространство пользователя

| | пользователь | ядро |
|---|---|---|
| адресное пространство | своё у каждого процесса | одно на всех |
| ошибка | `SIGSEGV`, умирает процесс | порча чужой памяти, паника |
| библиотека C | вся | её нет |
| плавающая точка | есть | нельзя |
| стек | мегабайты, растёт | 8–16 КБ, фиксирован |
| прерывание работы | планировщик вытеснит | можно заблокировать всю машину |
| отладка | `gdb`, `printf`, перезапуск | `printk`, `dmesg`, перезагрузка |

Маленький фиксированный стек — отдельная причина стиля ядра: большие структуры на стеке не объявляют, рекурсию не используют, а всё сколько-нибудь объёмное выделяют через `kmalloc`.

## 2. Сборка модуля

### kbuild

```makefile
obj-m += shadow.o
shadow-objs := shadow_mod.o shadow_ring.o

KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules
```

Модуль собирается **не вашим Makefile**, а системой сборки ядра: `make -C $(KDIR) M=$(PWD)` заходит в дерево ядра и просит собрать внешний модуль из указанного каталога. Так гарантируется, что флаги компиляции, версия компилятора и конфигурация совпадут с ядром, для которого модуль предназначен.

Когда объектных файлов несколько, имя модуля обязано отличаться от имён объектов — отсюда `shadow.o` из `shadow_mod.o` и `shadow_ring.o`.

### Кросс-сборка под плату

```bash
make -C ~/rpi-linux ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- M=$PWD modules
```

Те же `ARCH` и `CROSS_COMPILE`, что в [`s06e01`](../s06e01-board-recon/), только применённые к дереву ядра. Заголовки должны быть от **того самого** ядра, что стоит на плате: несовпадение версии или конфигурации даёт отказ загрузки, а не ошибку сборки.

### Что проверяет ядро при загрузке

| Проверка | Что ломается при несовпадении |
|---|---|
| `vermagic` | версия ядра, компилятор, ключевые опции конфигурации |
| контрольные суммы символов (`modversions`) | ABI изменился — символ не совпал |
| подпись модуля | при включённом `CONFIG_MODULE_SIG_FORCE` |

Сообщения вида `invalid module format` и `disagrees about version of symbol` — это про них, и лечатся они пересборкой под нужное ядро, а не флагом `--force`.

## 3. Журнал ядра

```c
pr_emerg()  pr_alert()  pr_crit()  pr_err()
pr_warn()   pr_notice() pr_info()  pr_debug()
```

Это обёртки над `printk` с уровнем: `pr_info("…")` разворачивается в `printk(KERN_INFO "…")`. Уровни — те же восемь, что у syslog, и снова **меньше значит серьёзнее** (см. [`s06e05`](../s06e05-mavlink-telemetry/)).

```c
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt   /* до включений */
```

Такое определение автоматически добавляет имя модуля ко всем сообщениям — стандартная практика, избавляющая от ручных префиксов.

```bash
dmesg -w                       # следить за журналом
dmesg -l err,warn              # только важное
dmesg -T                       # с человеческими метками времени
cat /proc/sys/kernel/printk    # какие уровни попадают на консоль
```

`pr_debug` по умолчанию не печатается; включается через `CONFIG_DYNAMIC_DEBUG` и `/sys/kernel/debug/dynamic_debug/control` — то есть отладочные сообщения можно включать выборочно на работающей машине, не пересобирая модуль.

## 4. Память

```c
p = kmalloc(size, GFP_KERNEL);   /* может уснуть — нельзя в обработчике прерывания */
p = kzalloc(size, GFP_KERNEL);   /* то же, но обнулено */
p = kmalloc(size, GFP_ATOMIC);   /* не уснёт — для контекста прерывания */
v = vmalloc(size);               /* большой кусок, непрерывный только виртуально */
kfree(p); vfree(v);
```

| Флаг | Когда |
|---|---|
| `GFP_KERNEL` | обычный контекст процесса; вызывающий может подождать |
| `GFP_ATOMIC` | прерывание, спин-блокировка — ждать нельзя |
| `GFP_NOIO`, `GFP_NOFS` | внутри подсистем ввода-вывода, чтобы не зациклиться |

Выбор флага — не мелочь: `GFP_KERNEL` в обработчике прерывания может усыпить контекст, в котором спать запрещено, и это заканчивается зависанием.

Утечка в ядре не лечится завершением процесса: память не вернётся до перезагрузки. Отсюда правило симметрии — на каждый `kzalloc` в `init` есть `kfree` в `exit`, и путь ошибки освобождает ровно то, что успел взять.

## 5. Одновременность

Модуль может выполняться сразу в нескольких контекстах: два процесса читают устройство, приходит прерывание, работает таймер. Общие данные нужно защищать.

| Средство | Когда |
|---|---|
| `spinlock_t` | короткая секция, нельзя спать (в том числе в прерывании) |
| `struct mutex` | длинная секция, спать можно |
| `atomic_t` | счётчики |
| `rcu` | много читателей, редкие записи |
| `struct completion` | «подожди, пока другой закончит» |

В этой серии буфер защищать не требуется: он создаётся при загрузке и не используется параллельно. В `s06e12`, где появится `read()` из пользовательского пространства, вопрос встанет всерьёз — два процесса могут читать одновременно.

Практическое замечание: **блокировки — худшее место для «потом разберусь».** Ошибку в них не видно ни в тестах, ни в обычной работе; она проявляется под нагрузкой, редко и невоспроизводимо.

## 6. Параметры модуля

```c
module_param(depth, int, 0444);
module_param_named(buffer_depth, depth, int, 0644);
module_param_array(pins, int, &pins_count, 0444);
MODULE_PARM_DESC(depth, "…");
```

| Права | Что означает |
|---|---|
| `0` | файла в sysfs нет вовсе |
| `0444` | читать всем, менять нельзя |
| `0644` | root может менять **на работающем модуле** |

`0644` требует, чтобы код был готов к изменению значения в любой момент, — то есть чтобы параметр читался под блокировкой и не использовался как размер уже выделенного буфера. Проще и честнее оставить `0444`, если менять на ходу не предполагается.

Задать параметр можно и постоянно:

```
# /etc/modprobe.d/shadow.conf
options shadow depth=32 node_id=shadow-node-07
```

Именно поэтому параметр — внешний ввод: строка в этом файле переживёт всех, кто помнит, зачем её написали.

## 7. Отладка

| Инструмент | Что даёт |
|---|---|
| `pr_debug` + dynamic debug | выборочные сообщения без пересборки |
| `KASAN` | детектор выходов за границы и use-after-free |
| `lockdep` | детектор потенциальных взаимоблокировок |
| `kmemleak` | поиск утечек |
| `ftrace`, `perf` | трассировка вызовов и профилирование |
| `kgdb` | отладчик по последовательному порту |
| QEMU + виртуальная машина | падение стоит перезапуск ВМ, а не машины |

Разумный порядок работы: **юнит-тесты логики → сборка → загрузка в виртуальной машине с KASAN → плата.** Каждый шаг дороже предыдущего примерно на порядок — та же пирамида, что в [`s04e07`](../../season-04-devops-automation/s04e07-ci-pipeline/) и [`s06e06`](../s06e06-mission-check/).

## 8. Когда миллисекунды имеют значение

Обычное ядро Linux не даёт гарантий по времени реакции: поток может быть
вытеснен, обработчик прерывания отложен, а сборка страниц занять
непредсказуемо долго. Для сбора телеметрии это неважно; для управления
приводом или считывания датчика на двести герц — важно.

| Подход | Что даёт |
|---|---|
| `PREEMPT_RT` | почти всё ядро становится вытесняемым; задержки в десятки микросекунд |
| изоляция ядер (`isolcpus`, `nohz_full`) | процессор, на котором не крутится ничего лишнего |
| политика `SCHED_FIFO`/`SCHED_RR` | приоритет реального времени для потока |
| `mlockall()` | память процесса не уйдёт в подкачку |
| обработка в верхней половине прерывания | минимум задержки, но нельзя спать |

Измеряют это `cyclictest` из пакета `rt-tests`: он показывает
распределение задержек пробуждения, и именно его числа, а не ощущения,
служат основанием говорить «система реального времени».

Важное уточнение: **реальное время — это про предсказуемость, а не про
скорость.** Система с гарантированной задержкой в 200 мкс «реальнее»
системы, которая обычно отвечает за 20 мкс, но раз в час задумывается на
50 мс. Для встраиваемого устройства второе поведение часто хуже, чем
стабильно медленное.

Наш модуль к реальному времени отношения не имеет и не претендует: буфер
наполняется при загрузке. Но само разделение «логика отдельно, обвязка
отдельно» здесь помогает и там — код, который надо укладывать в жёсткие
сроки, стоит держать коротким и без неожиданных блокировок, а всё
остальное выносить.

## 9. Что здесь общего с остальным курсом

| Приём | Здесь | Где ещё |
|---|---|---|
| проверять внешний ввод на границе | `depth` от загрузчика | пределы полёта, [`s06e06`](../s06e06-mission-check/) |
| ограниченный буфер | кольцо на 64 значения | очередь клиента, [`s06e10`](../s06e10-sensor-client/) |
| освобождать то, что взял | `kzalloc`/`kfree` | `unexport` в [`s06e02`](../s06e02-gpio-sysfs/) |
| выносить логику из дорогой среды | `shadow_ring.c` | зависимости параметрами, [`s06e10`](../s06e10-sensor-client/) |
| целочисленная арифметика вместо дробей | тысячные доли | разбор `t=` в [`s06e10`](../s06e10-sensor-client/) |

Ядро не требует новых принципов — оно делает старые обязательными. То, что в пользовательской программе было хорошим тоном, здесь становится условием работоспособности машины.
