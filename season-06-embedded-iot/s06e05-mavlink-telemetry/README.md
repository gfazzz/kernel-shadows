> **LILITH:** *«Разрыв в нумерации значит „потеря" ровно до тех пор, пока ты не спросил, сколько цифр в этом счётчике и кто его ведёт. Однобайтовый счётчик двух систем даёт три разных неверных ответа на вопрос „сколько потеряно" — и все три выглядят правдоподобно.»*

## II. Теория: кадр и поток

### Кадр MAVLink 2

```
FD 1E 00 00 2A 01 01 18 00 00 │ …30 байт нагрузки… │ 7B 4C
│  │  │  │  │  │  │  └──┬───┘                        └──┬─┘
│  │  │  │  │  │  │     │                               контрольная сумма
│  │  │  │  │  │  │     номер сообщения, 3 байта, младший первым
│  │  │  │  │  │  компонент-отправитель
│  │  │  │  │  система-отправитель
│  │  │  │  номер кадра (seq), однобайтовый
│  │  │  флаги совместимости
│  │  флаги несовместимости
│  длина нагрузки
магический байт: FD = версия 2, FE = версия 1
```

Полная длина кадра = 10 (заголовок) + нагрузка + 2 (сумма). Магический байт — не украшение: по нему приёмник находит начало кадра в непрерывном потоке байтов и он же объявляет версию протокола. У MAVLink 1 заголовок короче (6 байт), поэтому спутать версии — значит читать все поля со сдвигом.

### Кто на линии

| sysid | Кто | Что шлёт |
|---|---|---|
| 1 | аппарат | `HEARTBEAT`, `ATTITUDE`, `GPS_RAW_INT`, `BATTERY_STATUS`… |
| 255 | наземная станция | `HEARTBEAT`, `COMMAND_LONG` |

Линия общая: кадры обеих систем идут вперемешку. **У каждой системы свой счётчик `seq`.** Считать потери по объединённому потоку — всё равно что считать пропуски в номерах документов, сложив две канцелярии.

### Три способа посчитать потери, из которых верен один

```
seq: … 253  254  255  0  1  2 …
```

| Способ | Что даёт на этих данных |
|---|---|
| `seq2 − seq1 − 1` по всем парам | −698: переходы через 255 уводят сумму в минус |
| то же, но убывания пропускаем | 66: теряются потери, случившиеся **на** переходе |
| без разделения по `sysid` | 14601: чужие счётчики принимаются за пропуски |
| **`(seq2 − seq1 − 1) mod 256`, отдельно по каждой системе** | **70 — верно** |

Приём общий для любых кольцевых счётчиков — номеров TCP-сегментов, счётчиков пакетов на интерфейсе, идентификаторов кадров CAN: **разность считается в арифметике той разрядности, в которой ведётся счётчик.**

### Читать поток, а не отдельные сообщения

Одно сообщение почти ничего не значит. Значение появляется из соседства:

```
26500  STATUSTEXT  severity=4  GPS_Glitch        ← предупреждение
28000  GPS_RAW_INT fix_type=1  satellites=3      ← решение потеряно
28100  STATUSTEXT  severity=2  EKF_variance      ← оценка положения развалилась
29000  STATUSTEXT  severity=2  Failsafe_GPS_RTL  ← аппарат принял решение сам
29000  HEARTBEAT   custom_mode=6                 ← режим сменился на RTL
```

Никто ничего не нажимал: аппарат потерял навигационное решение и по заранее заданному правилу пошёл домой. `HEARTBEAT` при этом шёл ровно и бодро всё время — он говорит «я жив», а не «у меня всё хорошо».

### `severity`: меньше — хуже

MAVLink использует шкалу syslog: `0` — EMERGENCY, `7` — DEBUG. «Самая высокая серьёзность» — это **наименьшее** число. Перепутать направление шкалы легко, а последствие простое: критические сообщения отфильтровываются как незначительные.

Про контрольную сумму с `CRC_EXTRA`, подпись кадров MAVLink 2, режимы `SITL` и почему `HEARTBEAT` — это ещё и таймер отказа связи, — в [`theory.md`](theory.md).

## III. Проверка: LILITH задаёт вопросы

**LILITH:** *«`HEARTBEAT` приходил каждую секунду весь полёт. Значит, со связью и аппаратом всё было в порядке?»*

<details>
<summary>Подумай 30 секунд</summary>

Нет. `HEARTBEAT` отвечает ровно на один вопрос: «работает ли программа, которая его шлёт». Он не знает ни про GPS, ни про батарею, ни про то, что аппарат уже развернулся и летит домой.

В этой записи `HEARTBEAT` шёл ровно — и одновременно с ним `GPS_RAW_INT` показывал потерю решения, `STATUSTEXT` сообщал о развале оценки положения, а `custom_mode` в самом же `HEARTBEAT` менялся на `RTL`. Полезная информация была **в полях**, а не в факте прихода сообщения.

Отсюда правило, общее для любого мониторинга: **сигнал «жив» и сигнал «здоров» — разные сигналы.** Проверка живости отвечает «процесс запущен», проверка готовности — «он способен делать свою работу». Система, где следят только за первым, узнаёт о проблеме от пользователей.
</details>

**LILITH:** *«Как отличить потерю четырёх кадров от переполнения счётчика?»*

<details>
<summary>Ответ</summary>

По разрядности счётчика. `seq` в MAVLink однобайтовый: после 255 идёт 0, и переход `253 → 2` означает «прошло 4 шага, из них 3 кадра не дошло» — если считать по модулю 256. Именно `(seq2 − seq1 − 1) mod 256`, а не разность целых.

Отличить «переполнение» от «потери» как отдельные события невозможно и не нужно: **переполнение — это не событие, а свойство арифметики.** Правильно поставленный вопрос звучит не «был ли переход через границу», а «сколько шагов счётчика прошло между двумя кадрами», и модуль отвечает на него сразу.

Ошибка становится опасной при больших разрывах: если потеряно больше 256 кадров подряд, счётчик успевает обернуться полностью, и различить «потеряно 3» и «потеряно 259» по одному `seq` нельзя в принципе. Тогда нужен второй источник — время. В этой записи четырёхсекундная дыра в `t_ms` подтверждает: связи не было вовсе, и потери реальны.
</details>

Артефакт — `artifacts/telemetry_report.txt`, 23 значения.

```bash

```

| Блок | Что узнать |
|---|---|
| кадр | магический байт, версия, длины, `seq`/`sysid`/`compid`/`msgid`, имя сообщения |
| линия | сколько систем, кто аппарат, кто станция, сколько кадров дошло |
| потери | число потерянных и доля, с учётом однобайтового счётчика и разделения систем |
| полёт | разрыв связи, потеря GPS, минимум спутников и батареи, худшая серьёзность, финальный режим |

<details>
<summary>Подсказка (если застрял на 5+ минут)</summary>

Байты кадра: `grep -v '^#' data/frame_sample.hex | tr -cs '0-9A-Fa-f' ' '` — дальше по смещениям.

`msgid` из трёх байт: `b7 + b8*256 + b9*65536`.

Потери: `awk '$2==1 {s=$4; if(p!=""){d=(s-p-1)%256; if(d<0)d+=256; t+=d} p=s} END{print t}'`.

Наибольший разрыв по времени — по соседним `t_ms` кадров аппарата.

Имена сообщений и режимов — соединением со справочниками в `data/`.

Эталон — в `solution/`, там над каждым значением стоит способ.
</details>

### Три ошибки, которые здесь делают

**Считать `seq` по всему потоку.** На линии две системы; их счётчики независимы, и вместе дают бессмысленное число.

**Игнорировать убывания `seq`.** Потери, случившиеся ровно на переходе через 255, исчезают из отчёта — а это как раз те, что труднее всего заметить.

**Прочитать `severity` как «больше — хуже».** Шкала обратная; при таком чтении критические сообщения попадают в мусор.
