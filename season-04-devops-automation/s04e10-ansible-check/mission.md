## Обстановка

Playbook готов, но перед тем как применить его к тридцати шести боевым
машинам, Клаус потребовал ответить на вопрос «что именно изменится».
Снимок прогона с `--check --diff` лежит в `data/ansible_check_prod.txt`:
ничего не менялось, ansible только рассказал, что бы он сделал.

Тридцать одна машина изменится примерно одинаково. Одна — заметно иначе.

## Приказ

Заполнить `artifacts/plan_report.txt` — четырнадцать значений из снимка.

```bash
cp starter/plan_report.txt artifacts/
bash tests/test.sh
```

Формат — `ключ=значение`, без пробелов вокруг знака равенства. Каждое
значение добывается командой, а не глазами: снимок длиной шестьсот строк.

## Требования

| Блок | Ключи | Что выяснить |
|---|---|---|
| масштаб | `hosts_in_recap`, `unreachable_hosts`, `changed_hosts`, `unchanged_hosts`, `tasks_total` | сколько машин участвовало и сколько изменится |
| слепые зоны | `tasks_skipped_all`, `blind_module` | какие задачи режим проверки не выполняет и почему |
| фон | `top_task`, `top_task_changed` | что меняется у всех — и почему это не находка |
| выброс | `drift_host`, `drift_tasks` | на какой машине изменится больше всего |
| находки | `unknown_key_comment`, `sshd_directive`, `ssl_mode_current` | что именно на ней не так |

## Чем добывать

| Что нужно | Как |
|---|---|
| только строки итога | `awk '/^PLAY RECAP \*/ {r=1; next} r' "$D" \| grep 'changed='` |
| недоступные | `grep -c 'unreachable=[1-9]'` |
| изменяющиеся | `grep -vc 'changed=0'` (не `grep -c changed`) |
| задачи | `grep -c '^TASK \['` |
| изменения по задачам | `awk '/^TASK \[/{t=$0} /^changed: \[/{c[t]++} END{for (k in c) print c[k], k}'` |
| пропущенные задачи | то же с `/^skipping: \[/` |
| модуль пропущенных | фрагмент playbook в конце снимка |
| разбор diff | `grep -B4 -A4` вокруг имени файла |

## Критерии приёмки

- [ ] `artifacts/plan_report.txt` создан на основе `starter/`, все 14 ключей заполнены.
- [ ] Число хостов взято из `PLAY RECAP`, а не из строк задач.
- [ ] Недоступные машины посчитаны отдельно.
- [ ] `changed_hosts` посчитан по строкам, а не по вхождениям слова.
- [ ] Названы пропущенные задачи и модуль, из-за которого они пропущены.
- [ ] Задача с максимумом изменений и хост с максимумом изменений различены.
- [ ] Из `--diff` выписаны три находки по машине-выбросу.
- [ ] `bash tests/test.sh` → 22 passed, 0 failed.

## Требования среды

| Требование | Значение |
|---|---|
| root / sudo | не нужен |
| ОС | любая с bash + awk + grep |
| Сеть | не нужна |
| `ansible` | **не нужен** — исследуется снимок в `data/` |
| Внешние пакеты | нет |
| Изоляция теста | все ожидаемые значения пересчитываются из снимка на месте |

В тесте не зашито ни одного ответа: он вычисляет их из
`data/ansible_check_prod.txt` при каждом запуске. Подмените снимок —
изменятся и эталонные значения. Сам снимок собирается заново из
`data/build_check_snapshot.sh` байт в байт.

Отдельно тест проверяет, что задача не выродилась: в снимке остаются
недоступные хосты, остаются пропущенные задачи, а «задача, меняющаяся
чаще всего» и «хост с наибольшим числом изменений» по-прежнему дают
разные ответы.

## Выполнение

```bash
cd season-04-devops-automation/s04e10-ansible-check
cp starter/plan_report.txt artifacts/
D=data/ansible_check_prod.txt
$EDITOR artifacts/plan_report.txt
bash tests/test.sh
```

Полезно начать с двух команд и посмотреть на форму данных:

```bash
awk '/^PLAY RECAP \*/ {r=1; next} r' "$D" | sort -t= -k3 -rn | head
awk '/^TASK \[/{t=$0} /^changed: \[/{c[t]++} END{for (k in c) print c[k], k}' "$D" | sort -rn
```

## Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `hosts_in_recap` = 34 | считали по строкам задач | недоступные машины в задачах не участвуют |
| `changed_hosts` = 77 | `grep -c changed` | считать строки: `grep -vc 'changed=0'` |
| `changed_hosts` = 34 | посчитаны все доступные | у троих `changed=0` |
| `tasks_skipped_all` = 0 | искали `skipped` вместо `skipping:` | в задачах строка `skipping: [хост]` |
| `blind_module` = `debsums` | взята программа, а не модуль | модуль — то, что после `ansible.builtin.` |
| `top_task` = `ssh-keys` | взята находка, а не максимум | максимум — по числу строк `changed:` |
| `drift_host` = имя из задачи | смотрели не туда | сортировать `PLAY RECAP` по `changed=` |
| `sshd_directive` = значение | выписано `yes` вместо имени | нужна директива, а не её значение |

## После выполнения

Зелёный тест означает, что вывод режима проверки прочитан как данные:
отдельно масштаб, отдельно фон, отдельно выброс — и отдельно то, о чём этот
режим не говорит вовсе.

Стоит запомнить две вещи. Первая: **чистый прогон проверки не означает, что
на машинах всё в порядке** — он означает, что в порядке всё описанное и
предсказуемое, а задачи на `command` и `shell` пропускаются целиком. Вторая:
**расхождение — это данные, а не помеха**. Массовое расхождение говорит, что
вперёд ушло описание; единичное — что в сторону ушла машина. Устранение
стирает разницу между этими случаями навсегда, поэтому сначала смотрят на
форму, а потом применяют.

## Кумулятивность

Переменная `ntp_servers`, из-за которой меняется тридцать одна машина, —
та самая, что появилась в инвентаре
[`s04e09`](../s04e09-ansible-inventory/): описание ушло вперёд, и это видно.
Находки на машине-выбросе читаются знакомо: чужой ключ в `authorized_keys` —
[`s02e08`](../../season-02-networking/s02e08-ssh-keys/), `PermitRootLogin` —
[`s02e09`](../../season-02-networking/s02e09-ssh-hardening/), права `0755` на
каталоге с закрытыми ключами —
[`s01e15`](../../season-01-shell-foundations/s01e15-permissions-basics/).
Разбор вывода по строкам, где наивный `grep -c` даёт число вчетверо больше
верного, — тот же приём, что в
[`s03e07`](../../season-03-system-administration/s03e07-journalctl/) и
[`s02e12`](../../season-02-networking/s02e12-firewall-log/). А сама мысль
«команда сообщает о том, что она умеет проверить, а не о том, что есть» —
прямое продолжение [`s04e07`](../s04e07-ci-pipeline/): проверка, которая не
может провалиться, ничего не проверяет.
