# s06e03 — теория: что происходит до первого слова ядра

Дополнение к [`README.md`](README.md). Здесь — полная цепочка загрузки, устройство overlay, режимы загрузки платы и то, как восстанавливаться после неверного `config.txt`.

---

## 1. Цепочка загрузки

### На Raspberry Pi

```
1. ROM в чипе          ищет загрузчик на SD (или USB, или в сети)
2. bootcode.bin/EEPROM инициализирует память, читает config.txt
3. start*.elf          прошивка GPU: применяет config.txt, собирает дерево
4. kernel8.img         ядро Linux; получает дерево и строку cmdline.txt
5. initramfs (если есть)
6. корневая ФС         из root= в cmdline.txt
7. systemd → службы
```

Особенность Pi: первым стартует не процессор ARM, а GPU — он и читает `config.txt`. Поэтому параметры там называются «параметрами прошивки», а не ядра, и синтаксис у них свой.

### На большинстве других плат — U-Boot

```
1. ROM              загружает SPL (первичный загрузчик) из flash/SD
2. SPL              поднимает DRAM, загружает U-Boot
3. U-Boot           читает свои переменные окружения и boot.scr
4. загружает        ядро (uImage/zImage) + .dtb + initramfs
5. передаёт         bootargs (аналог cmdline.txt)
```

U-Boot — полноценная среда с командной строкой:

```
=> printenv bootargs
=> setenv bootargs "console=ttyS0,115200 root=/dev/mmcblk0p2 rootwait"
=> saveenv
=> boot
```

Различается синтаксис, не суть: **где-то до ядра лежит место, где задаются дерево устройств и строка параметров.** На Pi это два текстовых файла, в U-Boot — переменные окружения, во встроенных системах — поля в структуре прошивки.

## 2. `config.txt` подробнее

### Часто используемые параметры

| Параметр | Что делает |
|---|---|
| `enable_uart=1` | включить последовательную консоль |
| `gpu_mem=16` | сколько памяти отдать видеоядру (минимум для безголовой платы) |
| `arm_freq=`, `over_voltage=` | частота и напряжение (разгон или, наоборот, ограничение) |
| `dtparam=audio=off` | отключить неиспользуемое |
| `disable_splash=1`, `boot_delay=0` | быстрее и тише стартовать |
| `dtoverlay=disable-bt` | вернуть консоли полноценный UART |
| `initramfs файл followkernel` | подключить initramfs |
| `dtdebug=1` | печатать разбор дерева в консоль — для отладки overlay |

### Условные фильтры

```
[all]              снова все платы (сброс фильтра)
[pi4]              только Raspberry Pi 4
[pi3]              только Pi 3
[cm4]              только Compute Module 4
[board-type=…]     по коду ревизии платы
[HDMI:0]           параметры конкретного видеовыхода
[EDID=…]           по подключённому монитору
[none]             ничего (удобно, чтобы «закомментировать» блок)
```

Фильтр действует до следующего фильтра. Практическое правило: **платозависимые параметры — в свою секцию, и сразу после неё `[all]`.** Одна лишняя строка `[all]` не стоит ничего; её отсутствие стоит вечера отладки.

### Порядок и дубли

Общее правило Raspberry Pi: при повторе одного параметра действует последнее присвоение. Полагаться на это не стоит — у части параметров и overlay поведение отличается, а читатель файла не обязан помнить исключения. Надёжнее не дублировать: **если параметр задан дважды, это ошибка редактирования, а не приём.**

Проверить, что прошивка реально применила:

```bash
vcgencmd get_config int      # целочисленные параметры
vcgencmd get_config str      # строковые
vcgencmd get_mem gpu         # сколько памяти ушло видеоядру
```

## 3. Overlay дерева устройств

### Что это

Overlay — фрагмент дерева, который накладывается на основное перед передачей ядру: включает узел, меняет свойства, добавляет устройство.

```dts
/dts-v1/;
/plugin/;
/ {
    compatible = "brcm,bcm2711";
    fragment@0 {
        target = <&spi0>;              /* к какому узлу */
        __overlay__ {
            status = "okay";           /* что в нём поменять */
        };
    };
};
```

Собирается тем же `dtc`, что и основное дерево, и кладётся в `/boot/overlays/`.

### Как узнать, что доступно

```bash
ls /boot/overlays/                     # список overlay на плате
cat /boot/overlays/README              # описание каждого и его параметров
dtoverlay -h w1-gpio                   # справка по конкретному
dtoverlay -l                           # что применено сейчас
```

`/boot/overlays/README` — самый недооценённый файл на плате: там документированы все параметры всех overlay, включая номера ножек и режимы.

### Применить на живой системе

```bash
sudo dtoverlay w1-gpio gpiopin=4       # до перезагрузки
sudo dtparam spi=on                    # тоже до перезагрузки
```

Удобно для проверки гипотезы: применили, посмотрели, появилось ли устройство. Но это **не замена** `config.txt` — после питания всё вернётся. Порядок работы: проверить на живой системе, зафиксировать в `config.txt`.

## 4. `cmdline.txt` и параметры ядра

### Полезные параметры

| Параметр | Смысл |
|---|---|
| `console=serial0,115200` | консоль ядра в последовательный порт |
| `console=tty1` | вторая консоль: сообщения дублируются на экран |
| `root=PARTUUID=…` | корневой раздел по идентификатору раздела |
| `root=UUID=…` | по идентификатору файловой системы |
| `rootwait` / `rootdelay=N` | дождаться носителя / подождать N секунд |
| `ro` / `rw` | смонтировать корень только для чтения / на запись |
| `fsck.repair=yes` | чинить ФС без вопросов |
| `quiet`, `loglevel=3` | меньше сообщений при старте |
| `init=/bin/sh` | аварийный вход вместо systemd |
| `systemd.unit=rescue.target` | загрузиться в ремонтный режим |

### Почему `PARTUUID`, а не `/dev/mmcblk0p2`

Имена устройств зависят от порядка обнаружения. Добавили USB-накопитель — и то, что было `sda`, стало `sdb`; загрузились с eMMC вместо SD — сменилась вся ветка имён. `PARTUUID` записан в таблицу разделов и не зависит ни от чего:

```bash
lsblk -o NAME,PARTUUID,UUID,FSTYPE     # посмотреть идентификаторы
blkid                                  # то же, подробнее
```

Тот же принцип, что имена интерфейсов вместо `eth0` и монтирование по UUID в `fstab`: **идентификатор должен принадлежать объекту, а не порядку его обнаружения.**

### Аварийный вход

Если система не грузится, а консоль работает, в `cmdline.txt` временно дописывают:

```
init=/bin/sh
```

Получается корневая оболочка без служб. Корень при этом смонтирован только для чтения — перемонтировать:

```sh
mount -o remount,rw /
```

Это стандартный способ починить сломанный `fstab`, пароль root или неверный юнит.

## 5. Режимы загрузки

У Pi 4 порядок источников хранится в EEPROM:

```bash
rpi-eeprom-config                  # посмотреть
sudo rpi-eeprom-config --edit      # поменять BOOT_ORDER
```

```
BOOT_ORDER=0xf41    # читается справа налево: 1=SD, 4=USB, f=повторить цикл
```

Варианты источников: SD-карта, USB-накопитель, сеть (TFTP/NFS), NVMe (на CM4). Для сети плата запрашивает адрес по DHCP и тянет ядро с TFTP-сервера — так разворачивают десятки одинаковых узлов без единой карты памяти.

### Когда плата не грузится

Диагностика по светодиоду и консоли:

| Симптом | Вероятная причина |
|---|---|
| нет активности вообще | питание, карта не читается, повреждён образ |
| мигает по схеме N раз | код ошибки прошивки (см. документацию Pi) |
| консоль молчит | нет `enable_uart=1`, не та скорость, консоль на mini-UART |
| ядро стартует, корня нет | неверный `root=`, нет `rootwait`, повреждённая ФС |
| мусор в консоли | не совпала скорость или mini-UART при меняющейся частоте |

Восстановление после неверного `config.txt` не требует ничего особенного: **раздел загрузки — обычный FAT**, читаемый с любого компьютера. Вынуть карту, поправить файл, вставить обратно. Именно поэтому этот раздел оставляют в FAT, а не в чём-то более современном.

## 6. Что из этого переносится на серверы

Слоёв меньше, но идея та же:

| Плата | Сервер |
|---|---|
| `config.txt` | настройки UEFI/BIOS |
| `cmdline.txt` | строка ядра в GRUB (`GRUB_CMDLINE_LINUX`) |
| overlay дерева | модули ядра и их параметры |
| `rootwait` | `rootdelay`, `x-systemd.device-timeout` в `fstab` |

Общий принцип: **чем раньше слой, тем меньше от него обратной связи.** Ошибку в юните видно в `systemctl status`, ошибку в строке ядра — только по тому, что система не поднялась, а ошибку в прошивке — по тому, что не зажёгся светодиод. Поэтому вниз по стеку растёт цена проверки перед изменением и ценность возможности откатиться физически (вынуть карту, переключить перемычку, зайти по консоли).
