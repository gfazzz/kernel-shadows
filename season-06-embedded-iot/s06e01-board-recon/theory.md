# s06e01 — теория: как незнакомая плата рассказывает о себе

Дополнение к [`README.md`](README.md). Здесь — то, что не поместилось в серию: чем embedded-машина устроена иначе, как устроено дерево устройств и как собирают под чужую архитектуру.

---

## 1. Чем embedded-машина отличается от сервера

| | сервер | плата |
|---|---|---|
| архитектура | x86_64, известна заранее | ARM (armv7l, aarch64), RISC-V, MIPS |
| обнаружение железа | PCI/ACPI опрашиваются сами | описание даётся заранее (device tree) |
| где собирают код | там же, где запускают | на другой машине (кросс-компиляция) |
| консоль при сбое | монитор, IPMI, KVM | UART: три провода и терминал |
| диск | SSD, RAID | SD-карта или eMMC, с ограниченным ресурсом записи |
| перезагрузка «вслепую» | редкость | обычное дело: выдернуть питание |

Практический вывод: **все привычки, основанные на «система сама разберётся», здесь не работают.** Сервер умеет обнаружить новый диск; плата не обнаружит ничего, чего нет в её описании.

## 2. `/proc/cpuinfo` подробнее

### Поля ARM

| Поле | Смысл |
|---|---|
| `processor` | логическое ядро; строк столько, сколько ядер |
| `BogoMIPS` | грубая калибровка задержки; **не мера производительности** |
| `Features` | расширения набора команд: `fp`, `asimd` (NEON), `crc32`, `aes` |
| `CPU implementer` | производитель ядра: `0x41` ARM, `0x51` Qualcomm, `0x4e` NVIDIA |
| `CPU architecture` | версия архитектуры (8 = ARMv8) |
| `CPU variant`/`part`/`revision` | модель и ревизия ядра — числами |
| `Hardware` | SoC (только на ARM; на x86 такого поля нет) |
| `Revision` | код ревизии платы у Raspberry Pi — упакованное поле, декодируется по таблице производителя |
| `Serial` | серийный номер платы |

`Features` — не украшение: наличие `aes` означает аппаратное шифрование (важно для TLS на слабой плате), наличие `asimd` — векторные операции. Проверять их стоит до того, как выбирать библиотеку.

### Почему имя ядра приходится искать

Ядро Linux хранит соответствие «implementer + part → имя» в `arch/arm64/include/asm/cputype.h`; `lscpu` из util-linux держит свою копию. В `/proc/cpuinfo` печатаются сырые номера, потому что список имён — вопрос версии таблицы, а номер неизменен. Отсюда правило: **номер — факт, имя — интерпретация по справочнику.**

```bash
lscpu | grep -i 'model name\|architecture'   # если lscpu есть на плате
```

На урезанном образе `lscpu` может отсутствовать — тогда остаются `cpuinfo` и таблица.

## 3. Дерево устройств

### Зачем оно

На x86 есть PCI и ACPI: устройства отвечают на опрос, ядро строит карту само. На ARM SoC периферия сидит на внутренних шинах, которые не опрашиваются, — прочитать «что тут есть» физически неоткуда. Решение: описание составляется заранее, компилируется в двоичный blob (`.dtb`) и передаётся ядру загрузчиком.

```
исходник .dts  ──dtc──▶  .dtb  ──загрузчик──▶  ядро  ──▶  /proc/device-tree
```

### Устройство узла

```dts
spi@7e204000 {
    compatible = "brcm,bcm2835-spi";
    reg = <0x7e204000 0x200>;      /* адрес и размер окна регистров */
    interrupts = <2 22>;           /* номер прерывания */
    clocks = <&clk_core>;          /* от какого тактового источника */
    status = "disabled";           /* включено или нет */
};
```

| Свойство | Что задаёт |
|---|---|
| `compatible` | по чему подбирается драйвер |
| `reg` | где в адресном пространстве лежат регистры устройства |
| `interrupts` | какое прерывание оно поднимает |
| `clocks`, `pinctrl-*` | тактирование и назначение ножек |
| `status` | `okay` — узел живой, `disabled` — драйвер не подойдёт |

### Overlay: изменить дерево, не пересобирая его

Полное дерево пересобирать ради одного датчика неудобно, поэтому существуют **overlay** — накладки, включающие узел или добавляющие устройство:

```
dtoverlay=spi0-1cs       # включить SPI с одним chip-select
dtparam=i2c_arm=on       # включить I2C
```

Строки пишутся в `config.txt` (см. `s06e03`) и применяются загрузчиком до старта ядра. Именно так на практике включают выключенную шину — не паяльником и не `modprobe`.

### Проверить дерево вручную

```bash
ls /proc/device-tree/                       # корневые свойства и узлы
cat /proc/device-tree/model; echo           # строки завершены NUL — echo для переноса
tr '\0' '\n' < /proc/device-tree/compatible # список compatible по строкам
dtc -I fs -O dts /proc/device-tree | less   # обратно в читаемый .dts
```

Свойства в `/proc/device-tree` — файлы, где строки разделены нулевым байтом, а числа лежат в big-endian. Отсюда `tr '\0' '\n'` при чтении списков.

## 4. Порядок `compatible` и семь семантик курса

Драйвер объявляет, какие строки он поддерживает; ядро идёт по списку узла слева направо и берёт первое совпадение. Поэтому список пишут **от частного к общему**: новая плата на знакомом SoC заработает по общей строке, а когда появится специализированный драйвер — перехватит по частной.

Курс к этому моменту требовал разной семантики от семи форматов:

| Формат | Кто побеждает |
|---|---|
| `sshd_config` | первое вхождение параметра |
| `ssh_config` | первое полученное значение |
| `sudoers` | последнее подходящее правило |
| `.gitignore` | последний подошедший шаблон |
| journal / release-файл | последнее присвоение |
| Ansible inventory | потомок бьёт предка; среди несравнимых — алфавит |
| device tree `compatible` | самое частное совпадение |

Общего правила нет и не будет. Единственная надёжная привычка — **прочитать в документации, как этот конкретный формат разрешает конфликт**, а не переносить логику из соседнего.

## 5. Кросс-компиляция

### Три архитектуры в одной фразе

- **build** — где компилятор собирался;
- **host** — где компилятор работает (ноутбук, x86_64);
- **target** — для чего он выпускает код (плата, aarch64).

Кросс-компилятор — тот, у которого host ≠ target.

```bash
sudo apt install gcc-aarch64-linux-gnu           # Debian/Ubuntu
aarch64-linux-gnu-gcc -o collector collector.c
file collector      # ELF 64-bit LSB executable, ARM aarch64
```

Для сборочных систем префикс передают через переменные:

```bash
make CROSS_COMPILE=aarch64-linux-gnu- ARCH=arm64      # ядро и модули
./configure --host=aarch64-linux-gnu                  # autotools
CC=aarch64-linux-gnu-gcc cargo build --target aarch64-unknown-linux-gnu
```

### Sysroot: чужие библиотеки

Если программа линкуется с библиотеками, компилятору нужны заголовки и `.so` **целевой** системы, а не хостовой:

```bash
aarch64-linux-gnu-gcc --sysroot=/opt/rpi-sysroot -o collector collector.c
```

Иначе сборка либо не найдёт заголовков, либо соберётся с хостовыми и упадёт на плате. Частая причина «на моей машине собралось, на плате не запускается» — не архитектура, а версия `glibc` в sysroot новее, чем на плате.

### Запустить чужой бинарник на своей машине

```bash
sudo apt install qemu-user-static
qemu-aarch64-static ./collector          # эмуляция набора команд
```

Полезно для быстрой проверки, но не заменяет платы: эмулируется процессор, а не GPIO, не датчики и не тайминги.

### Как читать ошибки запуска

| Сообщение | Причина |
|---|---|
| `Exec format error` | архитектура файла не совпала с процессором |
| `No such file or directory` на существующем файле | нет интерпретатора/компоновщика из заголовка ELF |
| `version GLIBC_2.34 not found` | собрано с более новой libc, чем на плате |
| `Permission denied` | вот это как раз про права |

Первые три — про сборку, и различить их можно за две команды: `file` на бинарнике, `uname -m` на плате.

## 6. Консоль, когда нет монитора

Строка `console=ttyS0,115200` в `bootargs` говорит, что ядро печатает сообщения в последовательный порт со скоростью 115200 бод. С тремя проводами (GND, TX, RX) и USB-UART переходником это единственный способ увидеть, почему плата не загрузилась:

```bash
screen /dev/ttyUSB0 115200        # или: picocom -b 115200 /dev/ttyUSB0
```

Отсюда правило раннего этапа: **сначала поднимают консоль, потом всё остальное.** Плата без консоли, которая не загружается, диагностике не поддаётся — она просто молчит.
